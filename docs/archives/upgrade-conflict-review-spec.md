# `vs upgrade` の競合 diff を、見たものと承認したものが一致するようにする

> 作成日: 2026-08-12
> ステータス: **実装済み**（2026-08-12）
> 対象: 競合ファイルの diff が途中で切れ、**見ていない変更まで `y` で適用されてしまう**問題
> 関連: `lib/vivlio_starter/cli/upgrade.rb`（`unified_diff` / `render_hunks` / `print_diff` / `classify_managed`）
> 派生: `upgrade-three-way-merge-spec.md`（そもそも聞かずに済ませる話。規模が一段違うので分離した）
> 出自: 移行済みプロジェクトで `vs upgrade` を実地に通した観察（2026-08-12）。凡例の追加（`049f9a71`）は同じ観察から出た応急処置で、本仕様書はその先を扱う

## 0. なぜこの仕様書があるか

実地の観察で、著者が**承認していない変更を承認してしまった**。

雛形側で 25 行目（絵文字）、著者側で 93 行目（色）と、**別の場所**を変えた状態で `vs upgrade` を実行した。画面に出たのは 25 行目の変更だけで、末尾は `… 残り 56 行（[d] で全文表示）` と切れていた。著者は「絵文字の変更なら良い」と判断して `y` を押し、**93 行目の自分の変更が消えた**。

> 「本のマークの変更なら OK」というつもりで `y` を選んだら、他の場所は見せてもらっていないのに承認扱いになってしまう

バックアップは残るが、**失われたことに気づけない**のが問題である。

**本仕様書の目標は一つ——「画面で見たもの」と「`y` が及ぶ範囲」を一致させること。**

## 1. 真因：diff が「ハンク」になっていない

```ruby
prefix = 共通の先頭行数
suffix = 共通の末尾行数
old_mid = old_lines[prefix...(old_lines.size - suffix)]
ops = lcs_diff(old_mid, new_mid)
```

**最初の変更から最後の変更までを、間の無変更行ごと 1 つの塊にしている。** 本物の unified diff なら、離れた変更は別々のハンクになり、間の無変更行は出ない。

上の実例で切り捨てられた 56 行は、**ほとんどが無変更行**だった（`body { font-family: … }` など）。情報量がほぼ無いものが、肝心の削除行を画面外へ押し出していた。ハンクに分けていれば全体で 12 行程度に収まり、**プレビューに全部入っていた**。

つまり「プレビューが短すぎる」のではなく、**diff が無駄に長い**。

## 2. 規模：競合は数件しか出ない

想定する場面は、**`1.0.0` を使っていた著者が `1.1.0` の登場に伴い `gem update` → `vs upgrade` する**という通常の経路である。

競合の条件は「雛形も著者も同じファイルを変えた」。著者が触るのは `custom.css` など数ファイル、マイナー更新で変わる雛形も数〜十数ファイル。**交差は 0〜3 件**にとどまる。

雛形は 7,748 ファイルあるが、うち 7,560 は画像でバイナリ（`（バイナリファイルのため diff を表示できません）`）。レビューの実質的な対象は CSS・原稿・設定の 200 弱で、そのうち実際に競合するのはごく一部である。

> **旧リポジトリを複製して原稿を書いた場合**は話が別で、実測では 26 ファイル全部が競合した。手で持ってきたファイルは lock と食い違うためである。ただしこれは正規の移行手順ではないため、**想定から外す**と決めた（2026-08-12）。一括操作キー（`a`/`s`/`q`）を用意しない判断はここから来ている。

**件数が少ないので、必要なのは「捌く手段」ではなく「1 件を正しく見せること」である。**

## 3. 設計

### (a) 同じ内容に行き着いたものは競合ではない

```ruby
if lock_digest.nil?             then current == scaffold ? :latest : :conflict
elsif scaffold == lock          then :latest
elsif current == lock           then :update
else                                 :conflict     # ← ここへ落ちる
end
```

判定はすべて lock との比較で、**「双方が同じ内容に到達した」ことを見ていない**。

```ruby
elsif current == scaffold then :latest   # 別経路で同じ内容に到達した
```

を `:conflict` の手前へ足す。1 行。**中身が同じものについて `y/n` を尋ねるのは、それ自体が誤り**である——どちらを選んでも結果は変わらないのに、著者に判断を求めてしまう。

### (b) ハンク分割

無変更行が `CONTEXT_LINES × 2` を超えたらハンクを区切る。標準の unified diff と同じ規則。

```
   @@ 25 行目付近 @@
     :root {
   -   --preface-h3-marker: "📗 ";
   +   --preface-h3-marker: "📚 ";
     }
   @@ 93 行目付近 @@
   -   color: #336699;
   +   color: var(--color-preface-accent);
```

各ハンクの行番号は、`prefix` を起点に「無変更行と削除行で 1 進む・追加行では進まない」と数えて求める（旧ファイル基準）。

これだけで、冒頭の実例は 60 行超から 12 行程度になり、**プレビューに収まる**。

### (c) 収まらないときは「全部に効く」と言う

ハンク分割で大半は収まるが、それでも切れる場合がある。**そのときに何を出すかが、事故を止める最後の砦になる。**

```
   … 残り 12 行・未表示 1 箇所（[d] で全文表示）
   ⚠️ [y] は表示していない箇所にも適用されます
```

現行の `… 残り 56 行（[d] で全文表示）` には、**`y` の及ぶ範囲についての情報が無い**。「残り 56 行」は「読まなくてよい続き」と読めてしまう。事故はここで起きた。

あわせて、prompt の前に要約を出す。

```
   競合 stylesheets/preface.css: 変更 2 箇所（+3 / -2 行）
```

**`-` 行はすべて著者の現在の内容**なので、この数字はそのまま「失われる行数」でもある。凡例（`- いまのあなたのファイル`）と併せて読めるようにする。

### (d) 色を付ける

`-` と `+` は記号だけで区別されていて、**流し読みで取り違えやすい**。本物の diff と同じく色を付ける。

| 対象 | 色 |
| --- | --- |
| `-` 行 | 赤 |
| `+` 行 | 緑 |
| `@@` ハンク見出し | シアン |
| 凡例・`…` の続き | 灰（dim） |

#### 判断すべき点が 3 つある

**① 既存の作法が無い。** 本コードベースには ANSI エスケープの利用が一箇所も無い（絵文字と `log_*` の語彙で色分けの役割を担ってきた）。**upgrade の diff 表示に閉じたローカルな仕組みとして入れる**——他所で使いたくなってから切り出す。

**② テストを壊さないこと。** `$stdout.tty?` だけで判定すると、端末から `rake test` を回したときに色が付き、diff 本文を検査しているテストが落ちる。

> **色は「生成」ではなく「出力」の関心事**として分離する。`unified_diff` / `render_hunks` は**素のテキストを返し続ける**。色を乗せるのは `print_diff` の中だけ。こうすると diff の中身を検査するテストは色の有無に一切影響されない。

**③ 無効化の道を用意する。** `NO_COLOR`（no-color.org の事実上の標準）が設定されていれば付けない。`TERM=dumb` も同様。パイプ・リダイレクト時（`tty?` が偽）も付けない。

## 4. 実装順序

1. **(a) 同一内容の誤検知** — 1 行。他と独立
2. **(b) ハンク分割** — 事故の直接の原因
3. **(c) 収まらないときの警告 ＋ 要約** — (b) で漏れた場合の砦
4. **(d) 色付け** — 見た目の改善。上の 3 つとは独立に入れられる

**1〜3 で事故は止まる。** 4 は独立しているので、順序を入れ替えても構わない。

3-way マージ（そもそも競合にしない）は `upgrade-three-way-merge-spec.md` へ分離した。**あれが無くても本仕様書だけで実害は消える。**

## 5. テスト

`notation-implementation-guide.md` §7 の流儀に従う。いずれも実ビルドを伴わない（`upgrade_commands_test.rb` は一時ディレクトリと DI で完結している）。

1. **分類**: 現物と雛形が同一で lock だけ古い → `:latest`（競合にしない）
2. **ハンク**: 離れた 2 箇所の変更が 2 ハンクに分かれ、間の無変更行が出ない
3. **ハンクの結合**: 近い 2 箇所（間隔 `CONTEXT_LINES × 2` 以下）は 1 ハンクにまとまる
4. **行番号**: 2 つめのハンク見出しが実際の行番号を指す
5. **要約**: ハンク数と増減行数が prompt より前に出る
6. **切り詰め**: プレビューが切れるとき「表示していない箇所にも適用される」と出る
7. **収まるとき**: 切り詰めが起きなければ、その警告は出ない
8. **色**: `print_diff` は色を付けるが、`unified_diff` の戻り値は素のまま
9. **無効化**: `NO_COLOR` あり／非 tty では色が付かない

## 6. 実装記録（2026-08-12）

(a)〜(d) をすべて実装した。`lib/vivlio_starter/cli/upgrade.rb` に +116 / -13 行、テスト 10 件追加（17 → 27 件）。

**実測**: 事故と同じ条件（100 行のうち雛形が 25 行目・著者が 93 行目を変更）で、diff が **60 行超から 16 行**になり、両方の変更がプレビュー（20 行）に収まった。切り詰めが起きないので警告も出ない。修正前のコードで新テストを回すと 5 failures + 3 errors で、赤→緑の両方向を確認している。

### 落とし穴 1: 色の判定に `lstrip` を使ってはならない

最初は「先頭の空白を除いた 1 文字目」で `-` / `+` を見分けようとしたが、**CSS のカスタムプロパティを含む文脈行が削除行に化ける**。

```
    --preface-h3-marker: "📚 ";     ← 文脈行（4 空白 + 内容）
   -  --preface-h3-marker: "📚 ";   ← 削除行（3 空白 + "-" + 内容）
```

`lstrip` すると両方とも `--preface-h3-marker: …` になり、区別できない。**この CSS こそが事故の現場のファイルだった**——直そうとしている当のものが、直し方を壊しにくる形になっていた。

表示行は `render_hunks` が自分で組み立てているので、**位置（添字 3）で判定する**。回帰テストあり。

同じ理由で凡例の行頭を `- ` から `凡例 ` へ変えた。`   - いまのあなたのファイル…` は添字 3 が `-` で、削除行として赤く塗られてしまう。

### 落とし穴 2: 色を「生成」に混ぜてはならない

`unified_diff` の戻り値に色を入れると、diff の中身を検査するテストが端末の有無で結果を変える（`$stdout.tty?` は端末から `rake test` を回すと真になる）。

**色は出力の関心事**として `print_diff` にだけ置いた。生成側は素のテキストを返し続ける。判定する `diff_color_enabled?(io = $stdout, env = ENV)` は引数で受けるので、テストが global state を差し替えずに済む。

### 落とし穴 3: 切り詰め警告は、隠れているものを見てから出す

実演環境を組んだところ、21 行の diff がプレビュー上限 20 行を **1 行だけ**超え、その 1 行が文脈行という場面を踏んだ。変更はすべて画面に出ているのに `⚠️ [y] は表示していない箇所にも適用されます` が出る。

**狼少年になる。** この警告は「本当に変更が隠れている」ときだけ意味を持つもので、空振りを許すと、肝心の場面（9 ハンク中 2 ハンクしか見えていない等）でも同じ重さで読み流される。隠れた行に `-` / `+` が 1 つも無ければ警告しない。

### ハンクの文脈は、中間部だけを見ていると取れない

`render_hunks` は `ops`（共通プレフィックス／サフィックスを除いた中間部）しか受け取らない。最初の変更がファイル先頭近くにあると、その手前の文脈が `ops` の外にある。`restore_full_ops` で前後の共通部分を `' '` の op として戻してから分割している。

## 7. 備考：応急処置との関係

2026-08-12 に凡例（`- いまのあなたのファイル / + 新しい雛形`）を追加した（`049f9a71`）。あれは「どちらが自分か分からない」という別の観察への対処で、本仕様書の (b)(c) とは独立している。**凡例があっても、見えていない変更は承認されてしまう**——観察の順序がそのまま、問題の層の深さの順序になっていた。
