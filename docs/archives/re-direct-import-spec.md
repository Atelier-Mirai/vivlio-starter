# Re:VIEW 直変換インポート 仕様書

> 作成日: 2026-09-12
> ステータス: **実装完了（2026-09-12）** — 実装で判明したことは §10
> 対象: `vs import` の変換経路を、**Re:VIEW Starter 同梱 Ruby による 2 段階変換**（`rake markdown` → Markdown 追従変換 → `.re` を読み直して構造復元）から、**`.re` を直接読んで Vivlio の Markdown を書き出す 1 段階変換**へ置き換える
> 決定事項:
> - **実装の可否は頻度ではなく対応先の有無で決める。** Re:VIEW / Starter が定義する 154 種を 3 分類し、**Vivlio に対応記法がある 114 種は出現 0 でも実装**、指定が落ちる 29 種は 🟡 付きで変換、対応概念のない 11 種だけを 🔴 で著者へ回す（§1.5・§3）。頻度分布（§1.2・§1.3）は「取りこぼしたときに壊れる箇所の多さ」を測るために使う
> - **知らない記法は黙って通さない。** 未対応・未知の記法は原文を残したうえで `file:line` 付きの 🔴 を出し、末尾に「何件を何に変換し、何件を残したか」の要約を出す（§4）。移行ツールに要るのは 100% の忠実さではなく、(1) よくある記法を正しく変換する (2) 決して黙って壊さない (3) 直すべき箇所を著者へ正確に伝える、の 3 つ
> - **`restorer` 3 本（508 行）と `markdown_converter.rb`（327 行）は廃止**。構造は原文から読むので「復元」という工程自体が消える。`yaml_processor.rb` / `image_processor.rb` は変換経路と無関係なのでそのまま使う（§5.3）
> - **catalog.yml に載っている章だけを変換する。** `contents/*.re` の全走査はしない——Re:VIEW では catalog に載せていない `.re` は原稿ではない（book_c に実例: 26 ファイル中 7 つだけが catalog にある）
> - **ラベル ID は全書で一意化する。** Re:VIEW は章内一意でよいが Vivlio は全書一意（`24-cross-reference.md`）。実測では 10 冊中 7 冊が重複を持つ（§3.6）
> 関連: `lib/vivlio_starter/cli/import/`, `at-directive-tier1-spec.md`（`@` 記法）, `90-notation-cheatsheet.md`・`22-extentions.md`（変換先の記法）

## 0. 背景

### 0.1 なぜ直変換にするか（＝寿命）

現在の `vs import` は、Re:VIEW Starter に同梱された Ruby（`lib/ruby/review-markdownmaker.rb` ほか）を **Starter プロジェクトのディレクトリで `rake markdown` として起動**し、生成された Markdown を追従変換している。この Ruby は `gem install review --version 2.5` にバージョンを固定しており、Re:VIEW 本体はその後もメジャーバージョンを重ねている。Re:VIEW Starter の開発は停止しているため、Ruby が進んで 2.5 が動かなくなっても直す人がいない。**`rake markdown` が動かなくなった時点で現在の `vs import` は丸ごと死ぬ。**

直変換なら、著者の `.re` さえ手元にあれば何年後でも取り込める。設計の美しさではなく、移行ツールとしての存続の問題である。

### 0.2 2 段階方式が実際に生んでいる害

「他人の出力した Markdown を後から直す」という構造は、次の 2 つの形で破綻している。

**(a) 構造が失われ、復元が当て推量になる。** Re:VIEW の `markdownbuilder` は

- `//sideimage` を `<img>` ＋空行＋本文へ平坦化し、**囲みの終わりを示す印を残さない**
- `//list` も `//output` も同じ ```` ```lang ```` フェンスへ落とし、**ブロックの種別を残さない**
- `//clearpage` を**空行 2 つ**に落とし、印を何も残さない

ため、`.re` を読み直して「原稿の何番目の囲みが、Markdown の何行目にあたるか」を位置対応で当てる復元コードが 3 本（508 行）必要になった。位置対応は数が合わなければ諦めるしかなく、実際 `verbatim_restorer.rb` は「数が合わない章は丸ごと見送る」と書いてある。直変換ならこの 508 行と、その当て推量そのものが消える。

**(b) 他人の出力を正規表現で後追いするため、壊し方が派手になる。** 閉じフェンスを開きと誤認して 68 箇所を総入れ替えにした事故（`CHANGELOG.md` 参照。1 章では 105 個の開きに対し裸の閉じが 1 個だけになっていた）は、原文を持たない側から Markdown を推測したことが原因である。

### 0.3 なぜ「マーカー注入」を採らないか

先方の builder を `prepend` で包んで構造マーカーを吐かせれば復元コードは消せる。しかし **Re:VIEW Starter にはライセンス表記が一切ない**（配布物にも `lib/ruby/*.rb` のヘッダにも公式ページにも記載がない。2026-08-10 確認）。作者は活動を停止しており確認もできない。`prepend` は改変にも複製にもあたらないと理解しているが、疑義ゼロの領域（**著者自身の原稿を読む**）から不明な領域へ踏み込む理由がない。

### 0.4 今より良くなる点

`//list[][yume.c][file=source/star2/yume.c,1]` は Re:VIEW がコードを**インライン展開**してしまうが、直変換なら Vivlio の ```` ```include:star2/yume.c ```` へ落とせる。`source/` は既に `codes/` へコピーしているので、**コードの単一の置き場所**が保たれ、著者がコードを直せば紙面に反映される。実測で 299 箇所がこの形である（§1.2）。

### 1.5 何を実装するか — 頻度ではなく実装容易性で決める

Re:VIEW と Starter が定義する命令は **154 種**（ブロック 70・インライン 84）。実原稿に現れるのは 42 種だが、**出現数の多寡で実装の可否を決めない**。頻度は §1.2 のとおり著者の書き癖を映したもので、記法の重要度ではないからである。決め手は「Vivlio に対応先があるか」——**あるなら実装する**。対応表に 1 行足す手間しかかからず、将来ほかの Re:VIEW プロジェクトを取り込むときの取りこぼしが減る。

| 区分 | 定義 | 種数 | 扱い |
|:---:|:---|---:|:---|
| **A** | Vivlio に対応記法があり、引数の受け渡しか単純な変換で済む | **114** | 変換する |
| **B** | 変換はできるが対応概念がなく、装飾・指定の一部が落ちる | **29** | 変換して 🟡 |
| **C** | 対応概念がなく、変換すると原稿の意味が変わる | **11** | 原文を残して 🔴 |

C はわずか 11 種——`//embed` `//raw` `//graph` `//hr`、`@<embed>` `@<raw>` `@<balloon>`、文字を大きくする `@<big>` `@<large>` `@<xlarge>` `@<xxlarge>` だけである（§3.5）。

B の 29 種には、`//image` の `border=on` のように**命令そのものは変換できるがオプションの一部が落ちる**ものを含む。落ちた指定は 1 件ずつ 🟡 で報告する（§4）。

内訳は §3 の対応表に置いた。§3.2・§3.3 が主要な 97 種の詳細、§3.4 が残り 57 種の一覧である。

## 2. 入力仕様 — `.re` の文法

本節は Re:VIEW Starter 同梱の `lib/ruby/review-compiler.rb`（`parse_document` / `parse_list` / `read_block`）と、同梱マニュアル `contents/03-syntax.re` §「インライン命令とブロック命令」から起こした。**Re:VIEW 本体の仕様ではなく Starter 拡張後の仕様**であることに注意する（本体と挙動が違う箇所は明記した）。

### 2.1 行頭の分岐

パーサは行の先頭だけを見て、上から順に次の分岐に入る。この**順序がそのまま優先順位**である。

| 判定 | 正規表現 | 行の意味 |
|:---|:---|:---|
| 1 | `\A#@` | コメント行（`#@#` は行コメント。`#@…` の他の形は処理指示） |
| 2 | `\A=+[\[\s{]` | 見出し |
| 3 | `\A( +)(\*+\|\-+) +` | 箇条書き（`*`）／**番号つきリスト（`-`）** |
| 4 | `\A\s+\d+\.` | 番号つきリスト（Re:VIEW 本体式） |
| 5 | `\A\s*:\s` | 定義リスト |
| 6 | `\A//\}\s*$` | ブロック終端 |
| 7 | `\A//\w+` | ブロック命令 |
| 8 | 空行 | 段落の区切り |
| 9 | 上記以外 | 段落（**行頭の空白は意味を持たない**） |

**この分岐はブロックの外でのみ働く。** `//list{ … //}` の中身は逐語なので、`- if items.any?` や ` : name` のような行が来ても箇条書き・定義リストとして読んではならない（実原稿のコード内に実例が多数ある）。パーサはブロックに入ったら終端 `//}` まで行を溜めるだけにする。

9 が重要で、実測 76,226 行のうち約 9,800 行が「空白で始まるが箇条書きでも定義リストでもない行」だった。著者が地の文をインデントして書いているだけで、Re:VIEW はこれを段落として扱い、連続する行を 1 段落へ連結する。**変換先で意味を持たせてはならない**（Markdown では 4 スペース字下げがコードブロックになる）。

### 2.2 落とし穴 — `-` は番号つきリスト

Starter の `LIST_ITEM_REXP` は `/\A( +)(\*+|\-+) +/` で、**`*` が unordered list、`-` が ordered list** と定義されている（`review-compiler.rb`）。Markdown の `-`（＝ 箇条書き）とは意味が逆である。

```
 - (A) 番号つき箇条書き（英数字が使える）
 - (B) 番号つき箇条書き（任意の文字列が使える）
 -- (B-1) 入れ子にできる
 *** 番号なし箇条書きを含めることもできる
```

マーカー直後の最初のトークンが**番号そのもの**として扱われる（`parse_item` の `num, text = text.split(/\s+/, 2)`）。上記なら `(A)` `(B)` `(B-1)` が番号、残りが本文。

実測 390 件（10 冊すべて）。内訳は **338 件（87%）が ` - 1. ` 形式**（数字＋ピリオド）で、残りは ` - 1) ` 4 件・` - (1) ` 3 件・全角空白つきの ` - 　　(1) ` 9 件ほか。

**出力は Markdown 標準へ落とす。** Re:VIEW 側で `-` が番号つきを意味することは入力の事情であって、変換後の原稿に持ち込むものではない。

| 原文 | 変換先 | 件数 |
|:---|:---|---:|
| ` - 1. 項目` | `1. 項目`（標準の番号リスト） | 338 |
| ` - (A) 項目` `- 1) 項目` | `(A) 項目` `1) 項目`（Vivlio の fancy list ＝ Pandoc の `fancy_lists` 互換） | 11 |
| ` * 項目` | `- 項目`（標準の箇条書き） | 1,494 |

87% が標準の番号リストへそのまま落ちるので、fancy list になるのは 11 件だけである。fancy list には「項目内でルビ・脚注参照・リンクの脚注化が使えない・短い列挙向け」という制約があるため（`21-markdown-tutorial.md`）、**fancy list へ落とす項目が長文だったり、それらの記法を含むときは 🟡 を出す**。

### 2.3 見出し

```
= 章タイトル
== 節タイトル
=={sec-id} ラベル付きの節
===[column] コラムのタイトル
===[/column]
==[notoc] 番号も目次項目も付けない節
```

- `=` の数がレベル（1〜6）
- 直後の `{…}` がラベル ID、`[…]` がタグ（`column` / `nonum` / `nodisp` / `notoc`）
- `===[column]習得したい…` のように**タグとタイトルの間に空白が無い書き方も実在する**（実測）
- コラムは `===[/column]` で明示的に閉じる。閉じずに次の見出しが来ても閉じたものとして扱われる

### 2.4 ブロック命令

```
//list[ラベル][キャプション][オプション]{
本文
//}
```

- **必ず行頭から始まる。** 前に空白があるとブロック命令として認識されない
- 引数は `[…]` の並び。**引数の中に `]` を書くときは `\]` とエスケープする**。実測に `//footnote[id][…@<code>{//tsize[|latex|][…]}…]` のような入れ子つきの引数があり、`\[[^\]]*\]` の素朴な正規表現では壊れる
- `//blankline` `//clearpage` `//noindent` のように本文を持たない命令（`defsingle`）は `{` を伴わない
- **ブロックは入れ子にできる**（Starter 拡張）。`//note{ … //list{ … //} … //}` は正当
- ただし `//list` `//emlist` `//listnum` `//emlistnum` `//source` `//program` `//terminal` `//cmd` `//output` `//embed` `//table` `//raw` は**逐語ブロック**で、中に他のブロックを置けない（`RAW_BLOCK_COMMANDS`）

**逐語ブロック内のインライン命令の扱いは Starter の実装が二枚舌になっている。** `read_block_for` のコメントは「`//embed` と `//table` ではインライン命令を解釈しない」と書いているのに、`_ignore_inline?` が引く `RAW_BLOCK_COMMANDS` には `list` や `terminal` も入っている。いっぽう実原稿には

```
//terminal[][Git のバージョン確認]{
  $ @<userinput>{git version}        @<balloon>{この行を入力します}
  git version 2.33.0   @<balloon>{このように表示されます}
//}
```

のように **`//terminal` の中で `@<userinput>` `@<balloon>` を使った原稿が現に存在し、本として出版されている**（`book_ssg_middleman` 45 件）。実装時は「逐語ブロック内でも `@<…>` は解釈する」を既定とし、完成した PDF と突き合わせて確定する（§9 の未決事項 3）。

### 2.5 インライン命令

```
@<code>{text}          基本形
@<code>|text|          フェンス記法（区切り文字は | $ など任意の記号）
@<href>{url, text}     複数引数はカンマ区切り
@<b>{var x = {a: 1\};} } は \} でエスケープ
```

- **入れ子にできる**（Starter 拡張）。`@<code>{func(@<b>{@<i>{arg}})}` は正当
- **複数行にまたがれない**
- フェンス記法（`@<b>|…|`）では**バックスラッシュによるエスケープが効かない**
- `@<B>` と `@<b>` は別物（`@<B>` は `@<strong>` のショートカット、`@<b>` は太字）

したがって引数のパースは、`{` 開始なら「`\}` を除く `}` の対応」、フェンス記法なら「同じ区切り文字の次の出現まで」を追う必要がある。**正規表現 1 本では書けない**（入れ子があるため）ので、文字送りのスキャナで書く（§5.1）。

#### 3.1.1 段落内の改行

**Re:VIEW は段落内の行を連結して 1 段落に組む。** `compile_paragraph` は各行を `.strip` して配列で builder へ渡し、builder がそれを続けて出力する（LaTeX では和文同士の改行は消える）。いっぽう Vivlio は `hardLineBreaks: true` で運用しており、**原稿の改行がそのまま紙面の改行になる**（`line-break-typesetting-notes.md`）。そのまま移すと改行が増える。

どれだけ増えるかを実測した。

- 段落 5,548 個のうち **79.5%（4,410 個）は 1 行**で書かれており、そもそも差が出ない
- 2 行以上の段落に含まれる改行は **1,540 箇所**。そのうち **86.1%（1,326 箇所）は文の切れ目**（前の行が `。` `？` `」` などで終わる）で、**13.9%（214 箇所）が文の途中**

```
…して「プログラミング」など。 ⏎ iPadでお絵描きや読書、i…      ← 文の切れ目（1,326 箇所）
…「配列」として文字列を扱うことから、 ⏎ C言語は文字列操作が… ← 文の途中（214 箇所）
```

著者は Re:VIEW 時代から一文一行寄りで書いており（vivlio-starter 自身の原稿では **95.6% が 1 行段落**）、文の切れ目での改行はそのまま残すほうが**いま書いている形に近い**。不自然になるのは文の途中で折り返した 214 箇所だけである。

**仕様**——前の行の末尾を見て分ける。

| 前の行の末尾 | 扱い | 実測 |
|:---|:---|---:|
| `。` `．` `！` `？` `」` `』` `）` などの文末字 | 改行を保つ | 1,326 |
| それ以外（文の途中で折り返している） | 次の行と連結する | 214 |

連結するときは**空白を入れない**（Re:VIEW も `.strip` して連ねるので空白は入らない）。ただし境界の両側が英数字のときだけ半角空白を 1 つ挟む——`Hello` ⏎ `world` が `Helloworld` になるのを防ぐ。

「1 バイトも違わない」ことは目指さない。原稿 7,165 行のうち紙面に差が出うるのは多くて 214 行で、その全部が「連結して Re:VIEW の見た目に戻る」側である。

#### 3.3.1 文字サイズ命令の扱い（実測にもとづく）

**`@<small>` 系は文中に混ざるほうが多数派。** 実測 111 件・110 行のうち、**行まるごと 1 命令なのは 20 行だけで、90 行は文の途中**に現れる。

```
通勤通学に電車やバスを利用する方も多いでしょう。例えば「さくら高校 @<small>{行}」と…
@<code>{JavaScript}で書かれたプログラムは、@<small>{(単体で実行されることもありますが)} …
```

用途は一貫していて、**丸括弧でくくった補足を本文より小さく組む**——「(お好みで)」「(正解はこの本を最後まで読んでね。)」「(顔写真は同社ウェブサイトより)」のような添え書きである（`@<xsmall>` 6 件も同じ用法）。

`:::{.small}` はブロック（段落全体）を包む記法なので、文中の数文字には当てられない。**行まるごとの 20 行は段落末 `{.small}` で表せるが、残り 90 行は表せない。** そこで次のように分ける。

| 原文の形 | 変換先 |
|:---|:---|
| 行が `@<small>{…}` 1 つだけ | 段落末へ `{.small}`（既存記法） |
| 文中に混ざる | `<span class="small">…</span>` |

**この変換には CSS の小さな直しが前提になる。** `chapter-common.css:702` の `.small` は `margin-block: 1lh; margin-inline: 2em;` を持っており、インライン要素に当たると**文中に 2em の隙間が空く**。余白の指定を `div.small` / `p.small` に限定し、`.small` 共通には `font-size` だけを残す（`.small p` の `text-indent: 0` はそのまま）。これは import とは独立に、`.small` が span へ当たったときの潜在的な不整合を解消する変更でもある。

**`@<large>` 系は実装しない。** 実測は 2 件で、うち 1 件は `#@#` でコメントアウトされており出力に出ない。**実質 1 件**である。

```
@<B>{@<large>{　　　　　扇 に て 酒 く む か げ や ち る 櫻}}   ← 俳句を大きく太字で 1 行
#@# @<br>{}@<large>{元旦からの日数を数える}                    ← コメントアウト済み
```

唯一の実例は「引用句・題字を 1 行だけ大きく見せる」用途で、Vivlio では見出し・`:::{.align-center}`・`stylesheets/custom.css` で表現できる。`.large` を新設すると、**文字サイズを段階（small / large / xlarge …）で持つ記法体系**を本体に抱えることになり、`config-key-criteria-guidelines.md` の「選ぶ理由のない選択肢を増やさない」に反する。**新設しないことを決定**（§9）。🔴 を出して著者に判断してもらう（§4）。

### 3.5 対応しない 11 種

次は Vivlio に対応概念が無く、無理に変換すると原稿の意味が変わる。**黙って落とさず、原文を残して 🔴 を出す。**

| 命令 | 理由 |
|:---|:---|
| `//embed` `//raw` `@<embed>` `@<raw>` | 出力形式ごとの生データ（LaTeX / HTML）。移行先では意味を持たない |
| `//graph` | 外部ツール（gnuplot ほか）を呼んで図を生成する。Vivlio では `mermaid` フェンスか生成済み画像を使う |
| `//hr` | 水平線。Vivlio の `---` は**改ページ**なので当てられない（下記） |
| `@<balloon>` | コード内の吹き出し |
| `@<big>` `@<large>` `@<xlarge>` `@<xxlarge>` | 文字を大きくする（§3.3.1） |

**`//hr` は Re:VIEW でもほとんど使われていない。** 実測 3 件は 3 冊に同じ章が複製されたもので、**3 冊とも catalog.yml に載っていない**（`environment.re`——書きかけ・没の章）。刊行された本には 1 件も出ていない。Starter の記法解説ガイド 4,626 行にも `//hr` の説明は無く、Starter の builder にも実装が見当たらない。用途は唯一の実例のとおり「話題の区切りに水平線を引く」だが、Vivlio では見出し・`{.aki2}`・`:::{.align-center}` に記号を置くなどで代えられる。**🔴 のままとする。**

加えて、**定義に存在しない命令**も 🔴 にする。実測で `@<if>{…}` が 1 件見つかった（Re:VIEW にも Starter にも `if` という命令は無く、原稿の誤記）。2 段階方式ではこうした誤記が Re:VIEW 側のエラーに紛れて著者へ届かなかった。

### 3.6 ラベル ID の一意化

Re:VIEW のラベルは**章内で一意**であればよいが、Vivlio のラベルは**本全体で一意**でなければならない（`24-cross-reference.md`）。実測すると 10 冊中 7 冊が重複を持っていた。

| 書名 | ラベル数 | 重複 | 例 |
|:---|---:|---:|:---|
| book_sakura_fubuki | 147 | 2 | `dom10` `dom11` |
| book_study_js | 115 | 1 | `glightbox3` |
| book_cs | 70 | 7 | `cssgridlayout` `container_mikan` ほか |
| book_yutakana_website | 46 | 1 | `contact` |
| book_c / book_java / book_ruby | 1〜3 | 各 1 | `tbl1`（3 章で同じ ID） |

**対策**: 全章を読み終えた時点で ID の出現表を作り、2 回以上現れた ID だけ `章basename-元ID`（例: `01-intro-tbl1`）へ改名する。参照側（`@<list>{id}` など）は同じ章の定義を指すので、**章ごとの対応表を持って書き換える**。重複しなかった ID は原文のまま残す（著者が覚えている名前を無駄に変えない）。改名したものは 🟡 で一覧を出す。

脚注 ID（`//footnote` / `@<fn>`）は章ごとのファイルに閉じるため一意化は不要。

## 4. 安全の規律 — 知らない記法は黙って通さない

移行ツールに要るのは 100% の忠実さではなく、**(1) よくある記法を正しく変換する (2) 決して黙って壊さない (3) 直すべき箇所を著者に正確に伝える**の 3 つである。この規律があれば 34 種から始めて必要に応じて足せる。

### 4.1 3 段階の通知

| 記号 | 使う場面 | 原文の扱い |
|:---:|:---|:---|
| 🔴 | Vivlio に対応概念が無い／未知の命令。**著者が手で直す必要がある** | そのまま残す |
| 🟡 | 変換はしたが**情報が落ちた**（`border=on`・文字サイズ・`//needvspace` など） | 変換後の形 |
| 🔵 | 変換の都合で**見た目が変わりうる**が、著者の作業は不要（`//emlist` に行番号が付く・`//tsize` を落とした など） | 変換後の形 |

### 4.2 メッセージの型

著者向けの警告は、**出現箇所（`file:line`）と具体的な直し方（before → after）を必ず添える**。

```
🔴 01-intro.re:142: //hr は Vivlio に対応する記法がありません。
   原文をそのまま残しました。
   対処: 水平線が要るなら stylesheets/custom.css に .hr を定義して
         :::{.hr} ::: で囲んでください。Vivlio の --- は改ページです（22 章）。

🟡 03-syntax.re:88: //image の border=on は落としました（罫線の指定は移せません）。
   before: //image[fig1][図1][width=60%,border=on]
   after : ![](fig1.webp){width=60%}
   対処: 罫線が要るなら :::{.bordered} で囲み custom.css で描いてください。
```

### 4.3 変換サマリ

章ごとの処理が終わったら、最後に**何をどれだけ変換したか**を出す。「静かに終わった＝全部うまくいった」と誤解させないために、**0 件でない限り未対応の件数を必ず表示する**。

```
📊 変換サマリ（12 章 / 3,217 行）
   ブロック命令  1,842 件を変換 ・ 3 件を未対応として残した（//hr 3）
   インライン命令 6,481 件を変換 ・ 45 件を未対応として残した（@<balloon> 45）
   ラベル ID     3 件を一意化のため改名した（tbl1 → 01-intro-tbl1 ほか）
   🔴 48 件 / 🟡 12 件 — 詳細は上のログを参照してください
```

## 6. catalog・ファイル名・章の種別

### 6.1 catalog に載っている章だけを変換する

Re:VIEW では `contents/*.re` のうち catalog.yml に載っているものだけが原稿である。book_c は 26 個の `.re` を持つが catalog に載るのは 7 個で、残りは書きかけ・没・コメントアウト済みの章だった。**全走査すると没原稿が本に混じる。**

`catalog.yml` のコメント行（`# - lectures.re`）は「まだ有効にしていない章」の予定表なので、現行どおり**行単位の置換で並び・部・コメントを原文のまま残す**（`yaml_processor.rb` の設計をそのまま使う）。

### 6.2 章番号と種別の突き合わせ

Vivlio は**ファイル名の番号帯**で種別を決める（00 = 前書き / 01–89 = 本文 / 90–98 = 付録 / 99 = 後書き）。Re:VIEW は catalog の**セクション**（`PREDEF` / `CHAPS` / `APPENDIX` / `POSTDEF`）で決める。この 2 つは食い違いうる。

実測した 12 プロジェクトはすべて規約どおりだった（著者が一貫した命名をしているため）が、一般の Re:VIEW プロジェクトでは `intro.re` のように番号を持たないファイル名も普通にある。

**方針**: 食い違い・番号なしを検出したら 🔴 を出し、**あるべき名前を提示する**（`APPENDIX の intro.re → 90-intro.md にしてください`）。自動リネームはしない——章 basename は索引・クロスリファレンス・`chapter-rename-followers-guidelines.md` の追随設定に波及するため、著者の合意なく変えるべきではない。

## 10. 実装記録（2026-09-12 実装完了）

実装して初めて分かったこと。同じ場所をもう一度触る人向けに残す。

### 10.1 Re:VIEW の文法で、マニュアルに書かれていなかったこと

**インライン引数の入れ子は `@<name>{` でだけ数える。** Starter のスキャナ（`scan_inline_command`）は `/(\@<\w+>[{$|])|(\\[\\}])|([}$|])/` で走査しており、**裸の `{` は数えない**。だから `@<b>{var x = {a: 1\};}` のように「開いていない `}`」をエスケープする書き方が成立する。素直に `{` と `}` を対で数える実装にすると、この行が読めない。

**ブロック引数のエスケープは `\]` と `\\` だけ。** `parse_args` は `gsub(/\\(.)/) { ch == ']' || ch == '\\' ? ch : '\\' + ch }` で、それ以外の `\x` は**バックスラッシュを残したまま通す**（`\[` は `\[` のまま）。

**表のヘッダ区切りは `-` か `=` を 12 文字以上。** マニュアル（§「表の書き方」）にだけ書かれている。実原稿には `============`（12 文字）と `-----------------`（17 文字）の両方があり、`-` しか見ない実装では `=` の表が丸ごと崩れる。取りこぼさないよう実装は 3 文字以上を受ける。**セルの区切りは「1 文字以上のタブ」**なので `split(/\t+/)` で割る（`split("\t")` だと連続タブが空セルになる）。

**`//talk` の引数は `[アイコン][名前][発話]`。** アイコンを使うときは名前を省き（`//talk[avatar-b]{ … //}`）、使わないときは第 2 引数に名前を書く（`//talk[][クラリス]{ … //}`）。発話は第 3 引数（コンパクト形式）かブロック本体のどちらか。第 1 引数を話者名だと思って実装すると、アイコンを使わない原稿で話者が空になる。

### 10.2 変換で決めたこと

**脚注の定義は章末へまとめる。** `//footnote[id][本文]` は原稿の途中に置かれるが、Markdown の脚注定義はどこに書いてもよい。章末に集めるほうが、変換後の原稿を読むときに本文が途切れない。

**`//sampleoutputbegin` … `//sampleoutputend` は `::::`（コロン 4 つ）で囲む。** 中に `:::{.talk}` のような囲みが入りうるため。入れ子は外側のコロンを増やして表す。

**CSV gem は使わない。** Ruby 4.0 で bundled gem へ移り、`Gemfile` に書かないと読めない。`csv=on` の表のためだけに依存を増やす価値はないので、クォート対応の 20 行を自前で持つ（実測 999 行のうちダブルクォートを含む行は 0 だった）。

### 10.3 `.bordered` を足す前に分かったこと

`stylesheets/chapter-common.css` の `figure :is(img, svg)` に**既定で `0.5mm` の枠が引かれていた**（`--color-figure-border: #ccc`）。つまりキャプション付きの画像（`//image`）は、`border=on` が無くても Vivlio では枠が付く。`.bordered` が実際に要るのは**キャプションのない画像**と **`:::{.sideimage-*}` の中の画像**で、こちらは figure にならないため既定の枠が効かない（`//sideimage` の `border=on` は実測 55 件）。

あわせて `cross_reference_processor.rb` の `build_figure_html` が `extract_classes` の結果を捨てていた（`{.bordered}` を解いてはいたが `<figure>` へ出していなかった）ので、`align_class` を `class_attr` に広げて配置クラスと同時に出すようにした。

### 10.5 スコープ外で見つかった本体の制約

**定義リストの中では VFM 固有の記法が組まれない。** 実ビルドで `{翳|かざ}` がルビにならず、文字のまま紙面に出た。原因は取り込みではなく本体側で、`markdown_transformer.rb:611` が「VFM は定義リストに未対応」として**検出したブロックを Kramdown でレンダリングして `<dl>` を作っている**ため。Kramdown は VFM 固有の記法（ルビ `{漢字|よみ}`・数式 `$…$`・キー表示 `〘…〙`・索引 `[語|読み]`）を知らないので、そのまま素通しする。強調やインラインコードは Kramdown が解釈するので効く。

`text-align-class-preprocessing`（`.text-*` を前処理で生 HTML 化すると中の Markdown が壊れる）と同型の問題である。実測では定義リスト 609 行のうち該当は 7 行（1.1%）と少ないため、取り込み側は 🟡 を出すにとどめた。**本体で直すなら別タスク**——Kramdown へ渡す前にルビ等を展開するか、`<dl>` 化を VFM の後段へ回すか。

**キャプションが空の図表はラベルを落とす。** `//image[kurashi][]` のようにキャプションを空にした画像を `** @kurashi **` と書き出すと、Vivlio はキャプションの定義ではなく**参照**として読み、「未定義のラベルID」になる（実ビルドで検出）。タイトルが空のときはキャプション行そのものを出さず、ラベルが失われることを 🟡 で伝える。
