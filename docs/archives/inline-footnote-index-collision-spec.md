# インライン脚注 `^[…]` と索引マークアップ `[…]` の綴り衝突

> 作成日: 2026-08-01
> ステータス: **実装完了**（2026-08-01）
> 対象: インライン脚注 `^[短い補足]` が脚注にならない不具合（2026-07-30 発見）
> 関連: `lib/vivlio_starter/cli/pre_process/markdown_preprocessor.rb`（犯人 A）, `lib/vivlio_starter/cli/index/index_match_scanner.rb`（犯人 B）, `lib/vivlio_starter/cli/index/unified_index_manager.rb`（犯人 C）, `contents/21-markdown-tutorial.md` §脚注, `contents/90-notation-cheatsheet.md`
> 前身: `inline-footnote-collision-notes.md`（症状の一次資料。本仕様書に全内容を取り込んだので削除した）

## 0. なぜこの仕様書があるか

前身のメモは「症状の確認のみ・原因未特定」で止まっており、次のアクションは「犯人を特定してから仕様書を起こす」だった。2026-08-01 に切り分けを実施し、**犯人を 3 箇所すべて特定した**ので仕様書に昇格させる。

メモの推測は**半分当たって半分外れていた**。「索引マークアップと綴りが衝突している」という筋読みは正しい。しかし名指ししていた `index_match_scanner.rb` は**この症状の犯人ではなく**、真犯人は前処理側の別実装だった。さらに、メモが警戒していた「同型の抜け」は**推測ではなく既に 3 箇所に実在していた**。

メモが自ら戒めていた「`skip_term?` に一行足せば直ると決めつけないこと」は正しく、しかも**そこを直しても原理的に直らない**（§4.1）。

## 1. 症状

原稿に

```markdown
…356 枚目にあたります^[この 49 ページというずれは本書での値です。…安全です。]。
```

と書くと、生成 HTML はこうなる。

```html
…356 枚目にあたります^この 49 ページというずれは本書での値です。…安全です。。
```

- `^` がそのまま本文に出る
- ブラケット `[` `]` が消える
- 脚注の本体が本文に流れ込み、脚注末尾の `。` と本文の `。` が重なる（`安全です。。`）
- `<a class="footnote-ref">` も `.page-footnote` も生成されない

参照形式 `[^label]` は正常に動く。

## 2. 前提の確認（VFM は無罪）

**VFM 自体はインライン脚注に完全対応している。** 2026-08-01 に再実測（`npx @vivliostyle/vfm fn.md`）:

```html
<p>本文です<a id="fnref1" href="#fn1" class="footnote-ref" role="doc-noteref"><sup>1</sup></a>。</p>
<p>参照形式です<a id="fnref2" href="#fn2" class="footnote-ref" role="doc-noteref"><sup>2</sup></a>。</p>
…
<li id="fn1" role="doc-endnote">短い補足<a href="#fnref1" class="footnote-back" role="doc-backlink">↩</a></li>
```

インライン脚注と参照脚注は**同一構造の HTML**（`a.footnote-ref[href^="#fn"]`）になる。後処理 `post_process/footnote_converter.rb` はこのセレクタだけを見ているので、**VFM に無傷で渡しさえすれば後段の変更は一切要らない**。壊しているのは VFM より手前の前処理である。

## 3. 真因

`[…]` を「索引マークアップ」と解釈する実装が**3 箇所に重複しており、どれも `^[` を除外していない**。インライン脚注の `^` はブラケットの**外側**にあるため、「中身が `^` で始まるか」という既存の除外条件（参照形式 `[^id]` 向け）に一切引っかからない。

| | 場所 | 現況 | 影響 |
| :--- | :--- | :--- | :--- |
| **A** | `MarkdownPreprocessor#strip_index_markup!`<br>`markdown_preprocessor.rb:527` | **稼働中・症状 §1 の犯人** | ブラケットを削り、脚注本体を本文へ流す |
| **B** | `IndexMatchScanner::INDEX_TERM_PATTERN` / `skip_term?`<br>`index_match_scanner.rb:68` / `:258` | 潜在（A が先に消すため現在は到達しない） | **A を直すと顕在化**し、脚注本体が `<dfn>` 化される |
| **C** | `UnifiedIndexManager#extract_manual_markup_terms`<br>`unified_index_manager.rb:570-580` | **稼働中**（`vs index:auto`） | 脚注本体を**辞書へ恒久登録**する |

### 3.1 犯人 A — 症状を出しているのはここ

```ruby
# markdown_preprocessor.rb:531
stripped = protected_text.gsub(/\[([^\[\]\n]+)\](?!\()/) do
  inner = ::Regexp.last_match(1)
  if inner.start_with?('^')        # ← [^id] しか除外していない
    ::Regexp.last_match(0)
  elsif inner.include?('|')
    inner.split('|', 2).first
  else
    inner                          # ← ^[本文] の [] がここで落ちる
  end
end
```

`^[この 49 ページ…]` は `inner = "この 49 ページ…"` となり `^` で始まらないので、最後の枝でブラケットだけが剥がされる。実測で症状 §1 と**文字単位で一致**した（`安全です。。` の重複まで再現）。

### 3.2 犯人 B — メモが名指ししていた箇所（この症状の犯人ではない）

`index_match_scanner.rb` は同型のパターンを持ち、`skip_term?` も `[^id]` しか除外しない。実測でも `^[…]` の中身に対して `skip?=false` を返す。

ただし**現在このコードには到達しない**。ビルドのステップ順が

```
preprocess sections（＝犯人 A が全ブラケットを剥がす）
  → index scan and build（＝犯人 B が読む）
```

であり、犯人 B が読むのはワークスペースの前処理済み `.md`（`scan_all_chapters!(read_only: false)` → `find_chapter_file(prefer_contents: false)`）だからである。**犯人 B が見る時点でブラケットは既に存在しない。**

これがメモ §3 の「`process_term` は必ずタグを返すのに、実際にはタグが無い」という矛盾の答えである。矛盾ではなく、**到達していなかった**。

> **副次的に判明した設計事実**: 手動索引マークアップ `[用語]` がビルドで索引に載るのは、犯人 B のビルド時ブラケット走査**ではない**。`vs index:auto` が `contents/` を読んで辞書 `config/index_glossary_terms.yml` に登録し（＝犯人 C）、ビルド時は辞書ベースの `apply_auto_indexing` がプレーンテキストを拾う、という**辞書経由の往復**で成立している。犯人 A がブラケットを剥がすのはその前提では正しい。実測: 辞書に無い `[手動索引語]` を前処理に通すと `手動索引語` になり、ブラケットは残らない。

### 3.3 犯人 C — いちばん質が悪い（辞書を汚す）

```ruby
# unified_index_manager.rb:580
content_without_code.scan(/\[([^\]|]+)\](?!\()/) do |match|
  term = match[0]
  next if term.match?(/^https?:/)
  next if term.match?(/^\^/)      # ← ここも [^id] だけ
  …
```

これは**原稿 `contents/` を直接読む**ので前処理の影響を受けない。`vs index:auto` を実行すると、インライン脚注の本文がまるごと索引語として `config/index_glossary_terms.yml` へ書き込まれる。実測:

```
登録される term="この 49 ページというずれは本書での値です"
```

一度登録されると `apply_auto_indexing` が**本文中の同じ文字列を全章で自動タグ付け**するため、被害は書き込み以降も残る。`^[A|B]` のように本文に `|` を含む場合は `[用語|読み]` 側のパターンに掛かり、`term="A" yomi="B"` として登録される。

**現時点で辞書は汚れていない**（実測: `config/index_glossary_terms.yml` 153 語に脚注本文由来の語は無い）。原稿中の `^[…]` が 21 章・90 章のフェンス内にしか無く、`CodeBlockStripper` が除外しているためである（§7）。つまり**被害は未発生で、修正は予防**である。

## 4. 修正方針

### 4.0 これは新しい層ではない — 既存の除外語彙が「不完全かつ 3 重化」しているだけ

新しいガード機構を足すのではないことを先に確認する。既存パターンを読み直す:

```ruby
/\[([^\[\]\n]+)\](?!\()/
#                 ^^^^^ 「] の後ろが ( なら、その [ はリンク記法のものだ」
```

**`(?!\()` は既にこの判定をしている。** 「その `[` は索引マークアップのものか、それとも別の記法が自分の構文として持っているブラケットか」という問いは、**このパターンに最初から実装されている**。リンク記法 `[text](url)` については正しく答えられている。

欠けているのは**インライン脚注 `^[…]` という項目 1 件**であり、判定の枠組みそのものではない。`(?<!\^)` を足すのは、`(?!\()` と同じ問いに同じ形式で答える**既存語彙の補完**である。

したがって本修正で**概念は 1 つも増えない**。増えるどころか、同じ責務のコードが 3 箇所（§3 の A・B・C）にコピーされている現状を 1 箇所に畳むので、**実装の数は 3 → 1 に減る**。

これは `notation-implementation-guide.md` §2 が末尾で明示している判断基準そのものである:

> これらと同じ責務のコードを transformer 内に書き始めたら、それは**基盤側に API を足すサイン**（mermaid が独自フェンス解析を持っていた反省から `replace_top_level_fences` が生まれた）。

mermaid が独自のフェンス解析を持っていたのを `Masking.replace_top_level_fences` へ引き上げた前例と、今回は**同型**である。索引マークアップの綴り判定が 3 箇所に散っているのは、まさにその「サイン」が出ている状態にあたる。

### 4.1 除外は「パターン」で行う。`skip_term?` では原理的に直らない

`skip_term?(term_text)` が受け取るのは**ブラケットの中身だけ**で、直前の `^` は見えない。`^[補足]` と `[補足]` は `skip_term?` から見て**完全に同一の入力**である。したがってここに条件を足しても両者を区別できない。

除外は「`[` の直前が `^` か」を見られる**正規表現の側**でしか表現できない。既存パターンに否定後読みを 1 つ足す:

```ruby
/(?<!\^)\[([^\[\]\n]+)\](?!\()/
#  ^^^^^^ 追加: 直前が ^ なら索引マークアップとみなさない
```

`(?!\()` がリンク記法 `[text](url)` を除外しているのと同じ構えを、前方にも置くだけである。

### 4.2 一箇所に集約する（＝ §2 の「再実装禁止リスト」に載せる）

メモ §6 の指摘どおり、個別に条件を足すと同型の抜けが再発する。**実際 3 箇所に増えていた**のが証拠なので、パターンと除外判定を 1 箇所へ引き出す。

`lib/vivlio_starter/cli/index_markup.rb`（新規・`cli/masking.rb` の兄弟）:

```ruby
module VivlioStarter
  module CLI
    # 索引マークアップ [用語] / [用語|読み] の綴りの唯一の定義元。
    #
    # 「その [ は索引マークアップのものか、別の記法が自分の構文として
    # 持つブラケットか」の判定をここに集約する。利用側（前処理・索引
    # スキャナ・辞書登録）が各自の正規表現を持たないための正典。
    module IndexMarkup
      # 索引マークアップの検出パターン。
      #
      # 除外している「[...] と綴る他の記法」（増やすときはここに 1 項目足す）:
      #   (?!\()  リンク・画像記法 [text](url) … ] の直後が (
      #   (?<!\^) インライン脚注 ^[本文]       … [ の直前が ^
      #
      # 参照脚注 [^id] はこのパターンに合致するため、中身側の除外
      # （skip_term?）で落とす。ブラケットの外と中で担当が分かれる。
      TERM_PATTERN = /(?<!\^)\[([^\[\]\n]+)\](?!\()/
      …
    end
  end
end
```

**`Masking` には入れない。** `NotationGuard` が冒頭で明文化している判断に従う:

> **なぜ Masking と別モジュールなのか**: `Masking.each_prose_line` は前処理・索引・メトリクスなど 10 箇所以上から「コード領域解釈の唯一の実装」として使われている。記法の知識をそこへ混ぜると lint と無関係な前処理まで意味が変わる。（`notation_guard.rb:19-24`）

`Masking` はコード領域の解釈に徹させ、記法の知識はその記法のモジュールが持つ——これが既に確立した型である。`IndexMarkup` は `NotationGuard` と**同じ形**であって、新しい設計様式ではない。

配置の理由: 依存の向きは既に `index/ → pre_process/` が存在する（`unified_page_builder.rb` → `pre_process/book_settings_css`）。逆向きに `pre_process/ → index/` を足すと相互依存になる。`cli/` 直下なら `masking.rb` と同じく両者から素直に `require_relative` できる。

> **命名の注意**: `cli/guards.rb` は無関係である（コマンド実行前の前提条件検証＝`GuardError` の層で、`precondition-guard-spec.md` が正典）。本モジュールを `IndexGuard` 等と名付けると別概念と混同されるので、記法の名前をそのまま採って `IndexMarkup` とする。

### 4.2.1 `notation-implementation-guide.md` §2 の表に追記する

集約しても、次に `[…]` を使う記法を作る人がその存在を知らなければ 4 箇所目が生まれる。§2 の再実装禁止リストへ 1 行足すところまでが本修正の範囲:

| 基盤 | 責務 | 正典 |
|---|---|---|
| `IndexMarkup::TERM_PATTERN` | **索引マークアップ `[用語]` の綴りの唯一の定義**。`[…]` と綴る記法を新設したら、衝突しないようここへ除外を 1 項目足す | `cli/index_markup.rb` |

§4.2 の「除外を増やすときはここに 1 項目足す」というコメントと対になって、`NotationGuard::MACHINE_DATA_CONTAINERS`（「記法を追加するときはここへ 1 語加えればガードが追従する」）と同じ運用になる。

### 4.3 適用箇所

| 箇所 | 変更 |
| :--- | :--- |
| `markdown_preprocessor.rb:531` | 自前の正規表現を `IndexMarkup::TERM_PATTERN` に差し替え |
| `index_match_scanner.rb:68` | `INDEX_TERM_PATTERN` を `IndexMarkup::TERM_PATTERN` の別名にするか撤去 |
| `unified_index_manager.rb:580` | `[用語]` 側を `IndexMarkup::TERM_ONLY_PATTERN` に差し替え（**下記の訂正を参照**） |
| `unified_index_manager.rb:570` | `[用語\|読み]` 側を `IndexMarkup::TERM_WITH_YOMI_PATTERN` に差し替え（`^[A\|B]` 対策） |

> **訂正（実装時に判明）**: 当初この表は `unified_index_manager.rb:580` を汎用の `TERM_PATTERN` へ差し替えると書いていたが、**それでは `[用語|読み]` が二重登録される**。辞書登録だけは「読み付き → 読みなし」の 2 パターンを順に当てる方式で、読みなし側の文字クラスが `[^\]|]+` と `|` を除外していることが二重登録を防いでいる。汎用パターンは `|` を許すため、同じ語が読み付きと読みなしの両方で拾われてしまう。
>
> よって `IndexMarkup` は 3 つのパターンを持つ——`TERM_PATTERN`（前処理・スキャナ用。`|` を許し、読みの分離は利用側）、`TERM_WITH_YOMI_PATTERN`、`TERM_ONLY_PATTERN`（辞書登録用の対）。**除外条件だけが 3 本で共有される**という形にした。回帰テスト `test_term_only_pattern_should_not_double_register_yomi_form` がこの性質を固定している。

`skip_term?` の `start_with?('^')` は**残す**。パターンが `^[…]` を弾いても、`[^id]` そのものはパターンに合致し続けるため、中身側の除外は依然必要である。

## 8. 決めたこと・残る論点

### 決めたこと

- **記法は取り下げず、直す。** VFM が対応済みで後処理も無改造で通る（§2）以上、取り下げる理由は無い。案内済みの記法を消すほうが著者への負担が大きい。
- **`vs preflight` の記法ガードで警告する案（メモ §6 の第 3 案）は採らない。** 直せるものを警告で回避するのは `warning-messages-actionable` の趣旨に反する（著者に修正案を出せない警告になる）。

### 残る論点

1. **`.sideimage` コンテナ内のインライン脚注は本修正後も動かない。** `expose_container_footnotes!`（`markdown_preprocessor.rb:495`）が走査するのは `\[\^(url\d+|\d+)\]` だけで、`^[…]` を拾わない。VFM がコンテナ内の脚注を認識しない問題への対処なので、インライン脚注も露出対象に含めるかは別途判断が要る。**本仕様書の対象外**（コンテナ外では直る）。
2. **犯人 B は修正後も実質デッドコードのまま**である（§3.2 のとおり、ビルド時にはブラケットが既に無い）。撤去するか、`find_chapter_file` の `contents/` フォールバック用に残すかは、索引まわりを触るときに改めて判断する。今回は**衝突の穴を塞ぐだけに留める**（デッドだからと放置すると、経路が変わった瞬間に再発する）。
3. **`[…]` と綴る記法は今後も増えうる。** §4.2 の集約は「増えたときに 1 箇所だけ直せばよい」ための土台であって、衝突そのものを禁じるものではない。除外が 4 件・5 件と増えて先読み／後読みの羅列が読めなくなったら、そのときに `NotationGuard::MACHINE_DATA_CONTAINERS` 型のデータ駆動（記法名＋前置／後置の表）へ移す。**2 件の時点で表を作るのは過剰**なので、名前付きコメント付きの正規表現 1 本に留める。

4. **同じファイルに「再実装禁止」違反がもう 1 件ある**（本修正の対象外・別途）。`IndexMatchScanner#process_line`（`index_match_scanner.rb:216-224`）は、コード保護を `Masking` / `MarkdownUtils.extract_code_spans` に委ねず**独自のトークン退避を手書きしている**:

   ```ruby
   protected_line = line.gsub(/`[^`]+`/) do |match|
     token = " VSCODE#{code_spans.size} "
   ```

   `notation-implementation-guide.md` §2 が正典と定める `MarkdownUtils.extract_code_spans` の再実装であり、しかも**弱い**——`Masking::INLINE_CODE_SPAN` が担保する「N 連バッククォート同士の対」（`` ``foo`bar`` ``）を扱えず、単一バッククォート対しか見ない。同じドメインの `CodeBlockStripper` は既に `Masking` への薄い委譲層に整理済みなので、ここだけが取り残されている。

   **今回は触らない**（索引のタグ付け挙動が広範囲に変わりうるため、脚注の修正と混ぜると切り分けができなくなる）。ただしこれこそが「アドホックな修正が増えていく」実例なので、記録して次に索引まわりを触るときの入口にする。
