## 0. 背景・問題

### 0.1 実測: PDF を吐く vivliostyle 起動は 1 回あたり約 22 秒の固定費

A5・515 ページ・`targets: pdf, epub, kindle` のフルビルドで、前付・奥付の生成に **71.10 秒**
かかっていた。

```
  - build front and back matter          71.10s
    (vivliostyle build)                 (37.50s)  ← _titlepage_legalpage.pdf（2 ページ）
    (vivliostyle build)                 (30.55s)  ← _colophon.pdf（1 ページ）
```

**たかだか 3 ページの組版に 68 秒**である。原因を切り分けるため、中身が空の 1 ページ HTML
（スタイルシート・フォント・画像を一切参照しない）を `vivliostyle build` に通した。

| 対象 | 所要 |
|---|---|
| 最小 HTML 1 ページ・CSS 無し | **21.7s** |
| `_colophon.html` 単体（フル CSS・フォント 8 種） | **22.3s** |

差は 0.6 秒。つまり **組版の実作業はほぼゼロで、ほぼ全部が vivliostyle CLI の起動費**
（Chromium の立ち上げと PDF 出力パイプラインの初期化）である。ページ数が少ないから
速い、という関係にはならない——**何を組んでも約 22 秒かかる**。

裏付けとして、同じビルド内で EPUB を吐く 2 回は 15.10s / 5.70s と安い。出力が EPUB で
Chromium の PDF レンダを通らないためで、**重いのは PDF を吐く起動だけ**である。

### 0.2 現状のレンダ回数

フルビルドで PDF を吐く vivliostyle 起動は **4 回**ある。

| # | ステップ | 対象 | 実測 |
|---|---|---|---|
| 1 | `build overall pdf` | 本文全体 → `_sections.pdf` | 147.55s |
| 2 | `backlink dedup` | 浄化後の本文全体を再レンダ | 152.50s |
| 3 | `build front and back matter` | 本扉＋権利ページ → `_titlepage_legalpage.pdf` | 37.50s |
| 4 | 〃 | 奥付 → `_colophon.pdf` | 30.55s |

1 と 2 は削れない。「どの †マークが重複か」はページ番号が分からないと判定できず、
ページ番号はレンダしないと存在しない——鶏と卵であり、`backlink-dedup-pdf-map-spec.md` §0 が
**「再レンダ 106.5s は本文が変わる以上不可避」**と明記している（同仕様が消したのは
Phase 1 の Playwright プレビューレンダ 73 秒のほうで、再レンダは意図して残された）。

削れるのは **3 と 4** である。

## 1. 方針

### 1.1 本文スパインの末尾に 3 ページを載せ、結合時に範囲指定で並べ替える

```
レンダ:  00-preface … _indexpage │ _titlepage │ _legalpage │ _colophon
         └────────── 本文 N ページ ─────────┘   N+1        N+2        N+3

結合:    qpdf --pages 表紙 1-z  本文 N+1-N+2  本文 1-N  [白紙]  本文 N+3  裏表紙 1-z
                                └ 前付 ┘    └ 本文 ┘         └ 奥付 ┘
```

**中間ファイルへ分割しない**のが要点。`_sections.pdf` から 3 本の PDF を切り出してから
結合する案（当初の第一候補）も成立するが、**切り出した各ファイルがフォントを丸ごと
抱え込む**ため最終 PDF が太る。実測は §3.1。

結合工程は「ファイルの列」から**「ファイル＋ページ範囲の列」**（`PdfMerger::Segment`）へ
一般化する。従来の「ファイル全体」は範囲が `1-z` の特別な場合にすぎないので、
個別レンダへ退避したときも同じ列で表現でき、下流は 2 経路を区別しなくてよい。

### 1.2 なぜ先頭ではなく末尾か

目次のページ番号は CSS の `target-counter(attr(href url), page)` で解決される
（`toc.css:108, 194, 268`）。本扉・権利ページを**スパインの先頭**に足すと本文の
ページ番号が 2 つずれ、目次・索引・相互参照・dedup のページマップが軒並み動く。

**末尾に足せば本文のページ番号は 1 つも動かない。**

## 2. 実装

### 2.1 特殊ページ HTML の生成を共通前段へ前倒しする

`PdfBuilder.generate_front_and_back_matter_html!` を新設し、パイプラインの
`generate part title pages` と `techbook post-process` の間に置く。理由は 2 つ。

1. 本文スパインへ相乗りさせるので、本文レンダの開始時点で HTML が要る
2. techbook 後処理（波ダッシュ置換・絵文字画像化・SVG→WebP 参照整合）が `html/` を
   一括で舐めるため、そこへ間に合わせれば**個別再適用のコードが消える**

前倒しの安全性は確認済み: `_titlepage.md` / `_legalpage.md` / `_colophon.md` の内容は
すべて `book.yml` 由来で、**総ページ数など「本文を組んだ結果」に依存する値を含まない**
（`.cache/vs/` の生成物を実見して確認）。

**この前倒しには副産物がある。** EPUB のスパインは末尾に `./_colophon.html` を含み
（`entries.epub.js` を実見）、`EpubBuilder.stage_consumer_htmls!` が `html/` から読んで写す。
一方その `_colophon.html` を `html/` へ**書く**のは、従来 PDF 側の Step 9 だった。
つまり **EPUB 生成は PDF 側の工程が書いたファイルを読んでいた**。逐次実行では
「先に書かれている」だけで済むが、`build-target-parallelization-spec.md` が両者を
並列に走らせると読み書きの競合になる。前倒しはその依存も断つ（同仕様 §3.3）。

### 2.2 本文 entries の末尾に 3 ページを足す

`PdfBuilder.sections_entry_htmls` の戻り値の末尾へ `special_page_htmls` を連結する。
**3 つ揃っているときだけ**足す——欠けたまま相乗りさせると結合時のページ範囲を決められない。

dedup の再レンダ（`backlink_dedup_orchestrator.rb`）は `vivliostyle.config.sections.js` を
再利用するので自動的に同じ 3 ページを含む。入稿用の従来レンダ（`_sections_print.pdf`）も
同じ entries を共用するため、同様に相乗りする。

### 2.3 位置は `/Dests` から実測する（目印の埋め込みが要る）

分割位置を「末尾 3 ページ」と決め打ちしてはいけない。権利ページが 2 ページに溢れることも、
改丁指定で白紙が挟まることもあり、数え間違えると**静かに隣のページを切り出す**という
壊れ方をする。

そこで `PdfPageMapExtractor#document_first_pages` を追加し、`/Dests` の名前に埋まっている
元 URL から「スパイン文書 → その文書が始まる通しページ番号」を引く。本扉の開始位置を T、
奥付の開始位置を C とすると、本文 `1..T-1` / 前付 `T..C-1` / 奥付 `C..末尾` に割れる。

**ただし `/Dests` はすべての id に対して出るわけではない。** §3.4 のとおり
**リンクの飛び先になっている id だけ**が書き出されるため、どこからもリンクされない
前付・奥付は素のままでは 1 件も dest を持たない。`PdfBuilder.inject_matter_anchors!` が
staged HTML（`pdf/` のコピーのみ）へ自己参照する空リンクを 1 つ埋め、目印にする。

```html
<a id="vs-matter-colophon" href="#vs-matter-colophon" style="position:absolute"></a>
```

`position: absolute` で流れから外すのは、本扉・権利ページの `body` が `display: grid` で
行を明示しており、素の子要素を 1 つ足すと**行の割り当てが 1 つずつずれてレイアウトが崩れる**
ため。インラインで書くのは、この目印が著者の意匠ではなくビルドの仕掛けだからである。
書き込むのは `pdf/` のコピーだけなので、`html/` の原本はクリーンなまま——EPUB / Kindle には
現れない（実測で確認）。

### 2.4 CSS: 柱の抑止とノド／小口の固定

3 ページは既に**名前付きページ**を使っている（`titlepage.css` / `legalpage.css` /
`colophon.css`）ので、スパイン中のどこに置かれてもノンブル抑止は効く。足りないのは次の 2 点。

**(a) 柱（`@top-right`）の抑止**

これらに柱が出ていなかったのは「自分のドキュメントの 1 ページ目」だからで、
`page-settings.css` の `@page :nth(1) { @top-right { content: none; } }` が効いていた。
本文スパインの末尾に置くと `:nth(1)` が外れ、`string(chapter-number, first)` が
**最後の章の値を保持したまま**柱に出る。名前付きページ側で明示的に消す。

**(b) ノド／小口の固定**

`@page :left` / `@page :right` が綴じ側（ノド）と外側（小口）をページの表裏で入れ替える。
3 ページは独立ドキュメントの何ページ目かで表裏が確定していたが、本文末尾に置くと
**本文のページ数次第で表裏が変わり、余白が左右反転する**。最終的な綴じ位置に合わせて
名前付きページで余白を固定する。

```css
@page titlepage { margin-left: var(--page-margin-inner); margin-right: var(--page-margin-outer); }
@page legalpage { margin-left: var(--page-margin-outer); margin-right: var(--page-margin-inner); }
@page colophon  { margin-left: var(--page-margin-outer); margin-right: var(--page-margin-inner); }
```

`break-before: recto` / `verso` で表裏を強制する手は**採らない**。レンダ中に白紙が挟まって
分割位置が動くうえ、`page.chapter_pagebreak: any` の本では改丁の思想と衝突する。
奥付を左ページに置くための白紙挿入は、従来どおり結合工程が担当する。

**(c) 生成 CSS の改丁指定を打ち消す**

`BookSettingsCss::CHAPTER_PAGEBREAK_SELECTORS` は**裸の `body`** を含み、生成 CSS は
`body, body.toc, … { break-before: … }` の形で出る。特殊ページ 3 枚はいずれも
`book-settings.css` を読んでいる（`<link>` を 3 つとも実見）ので、この裸の `body` は
特殊ページにも当たる。

| `chapter_pagebreak` | 生成される値 | 本扉の直前 |
|---|---|---|
| `recto`（既定） | 生成 CSS は空 | 改ページのみ・白紙なし |
| `any` | `break-before: page` | 改ページのみ・白紙なし |
| `verso` | `break-before: verso` | **白紙が 1 枚入り得る** |

`verso` のときだけ分割位置がずれるので、`body.titlepage` / `body.legalpage` /
`body.colophon`（クラス付きなので裸の `body` に勝つ）で `break-before: auto` を明示する。
スパイン文書は必ず改ページされるため `auto` で足りる。

### 2.5 個別レンダへの退避と、その安全装置

特殊ページ HTML が欠けている、または位置を特定できない場合は、従来どおり個別に
レンダして `_titlepage_legalpage.pdf` / `_colophon.pdf` を作る（`build_front_pages_and_tail!`）。

ただし **「本文に相乗り済みなのに位置が引けない」状態で個別レンダしてはならない**。
同じページが本文の中と結合列の両方に入って二重になる（実測 515 → 518 ページ・§7.3）。
`PdfBuilder.ensure_separate_render_is_safe!` がこの状態を検出し、原因と対処を示して
ビルドを止める。静かに壊れた PDF を出すよりよい。

### 2.6 下流への影響

| 箇所 | 影響 |
|---|---|
| `PdfMerger` | 「ファイルの列」→「区間（`Segment`）の列」へ。`merge_pdfs_with_qpdf!` / `insert_blank_page_before_colophon` / `compute_front_matter_offset` のシグネチャが変わる |
| `PrintPdfBuilder` | 同上に追随。導出経路・従来レンダ経路とも区間で受ける |
| `BacklinkDedupOrchestrator` | 変更なし（`_sections.pdf` の名前・役割は不変） |
| `OutlineExtractor` | 変更なし（アウトライン抽出の対象 HTML に特殊ページは入らない） |
| EPUB / Kindle | 変更なし（`html/` の原本から展開するため） |

`insert_blank_page_before_colophon` と `compute_front_matter_offset` は、**パスの綴りでなく
区間の `role`** を見るように変えた。相乗り経路では 3 区間すべてが同じ `_sections.pdf` を
指すため、ファイル名では区別できない。

## 3. 実装前に潰した検証項目

### 3.1 qpdf の切り出し・並べ替えで `/Dests` とリンク注釈が生き残るか【実測済み】

本文には索引・用語集のバックリンク、相互参照、脚注の往復リンクが大量にある。
A5・510 ページの実物（`/Dests` 3,978 件・注釈 10,040 件）で測った。

| 操作 | ページ | `/Dests` | 注釈 | 所要 |
|---|---|---|---|---|
| 元 `_sections.pdf` | 510 | 3,978 | 10,040 | — |
| `--pages . 1-507` | 507 | 3,978 | 8,473 | 0.52s |
| `--pages . 508-510` | 3 | 3,978 | 1,567 | 0.43s |
| `--pages . 508-509 . 1-507 . 510`（並べ替え） | 510 | 3,978 | 10,040 | 0.53s |

注釈は 8,473 + 1,567 = 10,040 で完全一致。さらに並べ替え後のアンカー着地位置を全件突合し、
**3,923 / 3,923 が期待どおりの位置**（本文は一律 +2、先頭へ回した 2 ページは −507）で、
欠落 0・ずれ 0 だった。`qpdf --check` も構文エラー無し。

**そのうえで、当初の第一候補（3 本に分割してから結合）は採らないことにした。**
切り出した各ファイルが**フォントを丸ごと抱え込む**ためである。

| | 出力サイズ | 元との差 |
|---|---|---|
| 元 `_sections.pdf` | 93.41 MB | — |
| 1 ページだけ切り出したファイル | **2.91 MB** | — |
| 案 A（3 分割 → 結合） | 95.28 MB | **+1.87 MB** |
| 案 B（分割せず範囲指定で並べ替え） | 93.22 MB | **−0.19 MB** |

93MB の本では +2% だが、**フォントの埋め込み量は本の厚さにあまり比例しない**ため、
薄い本ほど比率が悪化する。速度のために出力を太らせる取引は割に合わない。

### 3.2 名前付きページが `:left` / `:right` に勝つこと【実証済み】

CSS Paged Media Level 3 の詳細度は (A: ページ名の有無, B: `:first`/`:blank` の数,
C: `:left`/`:right` の数) の順で比較され、名前付きページ（A=1）が `@page :right`（C=1）に勝つ。

実装前の傍証: `_titlepage_legalpage.pdf` の 2 ページ目（＝左ページ）は
`@page :left { @bottom-left { content: var(--folio-left-content); } }` の対象だが、
`@page legalpage { @bottom-left { content: none; } }` が勝ってノンブルが出ていなかった。

実装後の決定的な確認は §7.4。

### 3.3 `chapter_pagebreak: verso` のとき本扉の前に白紙が入る

§2.4(c) のとおり。分割位置を `/Dests` から実測するのは、**この種の取りこぼしが起きても
静かに壊れない**ようにするためでもある。ページ番号を数えて切る実装は、白紙が 1 枚
入った瞬間に奥付の代わりに白紙を切り出し、しかもエラーにならない。

### 3.4 `/Dests` は「リンクの飛び先になっている id」にしか出ない【本仕様の最大の落とし穴】

`backlink-dedup-pdf-map-spec.md` §0 は「id を持つ全要素の named destination を書き出す」と
書いているが、**実際はそうではない**。実測（A5・513 ページ）で `/Dests` は 3,977 件あるのに
**最後のエントリが p.499**で、それ以降の `_indexpage`（p.500-510）と特殊ページ 3 枚
（p.511-513）は 1 件も持っていなかった。

| 文書 | id の有無 | 被リンク | dest |
|---|---|---|---|
| `99-postface.html#終わりに` | あり | 目次からリンク | **出る** |
| `_glossarypage.html#gls-cli` | あり | 本文からリンク | **出る** |
| `99-postface.html#fn1` | あり | 同一文書内の脚注リンク | **出る** |
| `_toc.html#目次` | あり | なし | **出ない** |
| `_part1.html#第一部はじめる` | あり | なし | **出ない** |
| `_indexpage.html` | id が 0 個 | — | 出ない |

スパイクで確かめた 3 通り（単独レンダ）:

| 仕込み | dest |
|---|---|
| `<body id="…">`（被リンクなし） | **出ない** |
| `<a id="m" href="#m"></a>`（自己参照） | **出る** |
| `<a href="#m"></a><span id="m"></span>` | **出る** |
| 上に `style="position:absolute"` を付けたもの | **出る**（レイアウトは 1 ページのまま） |

同一文書内のリンクでも dest が出る（脚注がその証拠）ので、自己参照する空リンクを
1 つ埋めれば足りる。これが §2.3 の目印の根拠である。

### 6.1 並列化との合成

`build-target-parallelization-spec.md`（PDF 枝 ∥ EPUB/Kindle 枝・−130.5s）と本仕様は
独立に効き、しかも本仕様は §2.1 のとおり並列化の障害を 1 つ先に取り除く。

| | 共通前段 | PDF 枝 | EPUB 枝 | 合計 |
|---|---|---|---|---|
| 本仕様の前 | 16.2s | 406.5s | 130.5s | **553.25s** |

## 7. 実装記録（2026-08-01）

### 7.1 実測

`build front and back matter` **73.17s → 0.71s**（同一マシン・同一設定）。前倒しした
HTML 生成 0.96s を足しても **−71.5 秒**。

成果物は**ページ数が一致し、サイズはむしろ小さくなった**。

| | ページ | サイズ |
|---|---|---|
| 変更前 | 515 | 96.54 MB |
| 変更後 | 515 | **96.44 MB** |

ビルド全体の秒数（635.60s → 577.54s）は、同じ設定でも本文レンダが 158.71s → 167.91s と
6% ぶれるため**比較に使わない**。判断はステップ単位で行うこと。

### 7.2 `/Dests` の前提が違っていた（設計のやり直し 1 回）

§3.4 のとおり、`/Dests` は「id を持つ全要素」ではなく「リンクの飛び先になっている id」に
しか出ない。最初の実装は `_titlepage.html` / `_colophon.html` の見出し id が引けると想定して
おり、**実ビルドで検出に失敗してフォールバックへ落ちた**。

先行仕様（`backlink-dedup-pdf-map-spec.md` §0）の記述を鵜呑みにしたのが原因。あちらが
扱う `gls-src-*` / `idx-*` はすべて被リンクなので、記述の不正確さが露見しなかった。
**`/Dests` を新しい用途に使うときは、その id が誰かにリンクされているかを先に確かめること。**

### 7.3 フォールバックが二重混入を生んだ

検出に失敗したとき、従来どおり個別レンダへ退避した結果、特殊ページが
**本文 `_sections.pdf` の中と結合列の両方に入り 518 ページ**になった（正しくは 515）。
エラーも警告も出ない。

原因は、フォールバックが「本文には特殊ページが入っていない」という**変更前の前提**の
ままだったこと。§2.5 の安全装置（`ensure_separate_render_is_safe!`）を足して、
相乗り済みなのに位置が引けない状態ではビルドを止めるようにした。

**退避経路は、退避のきっかけになった変更を前提に組み直す必要がある。** 元の経路を
そのまま残せば安全、とは限らない。

### 7.4 ノド／小口の固定が効いていることの決定的な確認

奥付はレンダ上 **513 ページ目（奇数＝右ページ）** に組まれた。名前付きページの固定が
効いていなければ `@page :right` が勝ってノドが左（22mm）に来るはずだが、最終 PDF の
奥付の左端は **25.5mm** だった。

```
小口 18mm + padding 約 7.4mm = 約 25.4mm  ← 実測 25.5mm（名前付きページが勝った）
ノド 22mm + padding 約 7.4mm = 約 29.4mm  ← @page :right が勝った場合
```

権利ページ（左ページ）の左端 18.0mm も、本文の左ページ 18.0mm と一致した。
本扉・権利ページはレンダ上の表裏と最終位置の表裏がたまたま一致するため判別に使えない——
**奥付だけが両者を区別できる**位置に来る。

### 7.5 既存テストが `config/book.yml` に依存して空振りしていた

`ColophonPageParityTest` の 5 件は `chapter_pagebreak` の実装以降、`config/book.yml` の値で
通り方が変わる状態になっていた。`any` だと `insert_blank_page_before_colophon` が
早期 return するため、**4 件が判定を素通りしたまま緑になり、1 件が落ちていた**。
`chapter_pagebreak_any?` を明示的に固定して、設定に依存しないようにした。

グローバル設定を読むメソッドを途中に足すと、その下流のテストが黙って空振りになる。
