# 日本語の文へ当てる独自校正ルール（`vs lint`）

## 1. 目的

`vs lint` に、textlint のルールでは扱えない 2 種の指摘を加える。

| ルール ID | 指摘 | 自動修正 |
| :--- | :--- | :--- |
| `mazegaki` | 交ぜ書き（「だ円」「けん引」「ばん回」） | できる |
| `ambiguous-comparison` | 二通りに読める対比（「B は A と同じように X しない」） | できない |

「ら抜き言葉」は **すでに動いている**。`preset-japanese` に `no-dropping-the-ra` が
含まれており、`config/.textlintrc.yml` が同プリセットを有効にしているため、
「見れる」「集めれる」は現状でも `[no-dropping-the-ra]` として挙がる。本仕様は
これを再実装しない（原稿 `31-lint.md` に「効いている」と書くだけで足りる）。

## 2. なぜ prh 辞書ではなく Ruby 実装なのか

交ぜ書きは 1 対 1 の置換なので、一見 `config/textlint_rewrite.yml`（prh）へ
書けば済むように見える。それを採らない理由は 3 つある。

1. **既存プロジェクトへ届かない。** `config/` 以下は著者が編集するファイルで、
   `vs upgrade` が上書きできない。prh 辞書方式では `vs new` した新規プロジェクト
   にしか行き渡らず、既刊の原稿を抱えた著者ほど恩恵を受けられない。gem 本体に
   置けば gem の更新だけで届く。
2. **ルール単位で切れない。** prh の指摘はすべて `ruleId: prh` なので、
   `book.yml` の `lint.disabled_rules` に `prh` と書くと表記揺れ辞書ごと死ぬ。
   「表外漢字は開く（かなで書く）」方針の著者は交ぜ書きの指摘だけを切りたい。
3. **対句は prh では表現できない。** prh は `expected` への置換が必須で、
   `vs lint --fix` がその置換を機械的に当ててしまう。対比の書き換えは文脈依存
   （どちらが X するのかは著者しか知らない）なので、自動修正は害になる。
   どのみち独自実装が要る以上、2 つを 1 系統に収めるほうが安い。

## 3. 交ぜ書き（`mazegaki`）

### 3.1 何を交ぜ書きと呼ぶか

熟語の一部の漢字だけをかなで書いた表記を指す。二つの由来がある。

- **常用漢字表に入ったのに、かな書きが残っているもの** — 「完ぺき→完璧」
  「破たん→破綻」「隠ぺい→隠蔽」。2010 年の改定で「璧・綻・蔽・拉・捻」等が
  常用漢字になったので、いまは漢字で書ける。
- **いまも表外漢字で、新聞・放送がかな書きにしているもの** — 「だ円→楕円」
  「けん引→牽引」「ばん回→挽回」「ぜい弱→脆弱」。漢字にするかは文体の選択
  であり、本ルールは「漢字にする」側に立つ（`lint.disabled_rules` で切れる）。

### 3.2 語の採否基準

辞書は新聞用語集の丸写しにしない。次の 2 つを**ともに**満たす語だけを載せる。

1. **技術書・一般の文章に現れる。** 「き電（饋電）」のような業界語は載せない。
2. **他の語の一部として現れない綴り。** ひらがな 1〜2 字＋漢字という短い並びは、
   無関係な文にたまたま含まれる。「う回（迂回）」は「使う回数」に、
   「語い（語彙）」は「日本語いろは」に当たるため**載せない**
   （落とした語と理由の一覧は `mazegaki_dictionary.rb` の冒頭にある）。
   前後の制約で救えるものは正規表現で載せる——「ら致」は「〜から致します」を、
   「べき乗」は「予約すべき乗り換え」を、「き裂」は「引き裂く」を外している。

   **危険かどうかは頭の中でなく、実際の文字列で確かめる。** 「かく乱」を一度
   「書く乱れた字に当たる」として落としたが、これは誤りだった——「書く乱れ」の
   「書」は漢字なので「かく乱」の並びにならない。実際に当たるのは「とにかく乱暴」
   「せっかく乱れて」のひらがな副詞で、そちらは後方の制約で外せる（§実装記録 5）。

**「かな書きのほうが主流だから」は載せない理由にならない。** 常用漢字表が 2000 字余りに
収まらないために交ぜ書きが主流になった語（`改ざん`・`せん断`・`宝くじ`）も、漢字表記
そのものは正しく、きちんと書けることに価値がある。読み手を選ぶ漢字を避けたい著者は
`config/textlint_allowlist.yml` に語を書けば黙る（§5）。**辞書は「漢字表記があるものは
載せる」、選ぶのは著者**という切り分けにする。

この基準は 2 度動いた。当初は「世間の標準表記になっている語は載せない」として
`改ざん`・`宝くじ` を外し、次に「規格が表記を定める語（JIS の `せん断`）だけ外す」へ
狭め、2026-08-18 に除外そのものをやめた。**除外の線引きは書き手の方針であって、
辞書の側で決めるものではなかった**——JIS が「せん断」を採るのは常用漢字表に収める
ためであり、「剪断」が誤りだからではない。

### 3.3 交ぜ書きではないが同居させる語

`障害者 → 障碍者` は漢字から漢字への置き換えで、かなが混じっていない。それでも
同じ辞書（`MazegakiDictionary::KANJI_CHOICE`）に置く。`障がい → 障碍` を採る著者に
とって、`障害者` だけ素通りするのが中途半端だからである。**ルール ID も分けない**
——`disabled_rules: [mazegaki]` で切ったのに一部の指摘だけ残るほうが、著者にとって
意外な振る舞いになる。

対象は文字列「障害者」に限る。「障害」全般へ広げると「システム障害」「障害物競走」
まで書き換わり、用字の選択ではなく誤りになる。

### 3.4 自動修正

`vs lint --fix` で置換する。コード領域（フェンス・インラインコード）は
`Masking` で退避してから当てるため、「`ろ過` と書く」のような解説行は壊れない。

## 4. 二通りに読める対比（`ambiguous-comparison`）

### 4.1 何が曖昧なのか

> Ractor はスレッドと同じようにメモリを共有しない。

この一文は二通りに読める。

- スレッドも Ractor もメモリを共有しない（＝比較対象も否定側）
- スレッドとは違って Ractor は共有しない（＝比較対象は肯定側）

日本語では否定がどこまで係るかを語順で決められないため、文脈だけでは判別
できない。読者が誤って受け取っても気づけないのが厄介で、技術書では致命的に
なりうる（上の例は事実としては後者——スレッドはメモリを共有する）。

### 4.2 直し方

両者の性質を独立した文で明示する。

```
（before）Ractor はスレッドと同じようにメモリを共有しない。
（after） スレッドはメモリを共有するが、Ractor は共有しない。
```

### 4.3 検出

一文の中に「比較表現 → 否定」がこの順で現れたら指摘する。

- **比較表現** — 「と同じように」「と同様に」「と同じく」
- **否定** — 「〜ない」「〜ません」「〜ず」「〜ぬ」

**「のように」は比較表現に含めない。** 当初は含めていたが、本書へ当てたところ
10 件検出して**10 件すべてが誤検出**だった（実測は「実装記録」§1）。日本語の
「のように」は例示・限定・様態に広く使われ、比較の意味だけを正規表現で切り出す
手立てがない。残した 3 つは比較の格助詞「と」を伴うため、構文として比較である
ことが確定する。「スレッドのように共有しない」の形は見逃すが、10 件の誤検出を
出して無視される lint になるよりよい。

**「ない」で終わる形容詞は否定と取らない。** 「少ない」「危ない」「もったいない」
「〜に違いない」は、字面が「ない」でも否定ではない。

文の区切りは `。` と表のセル境界 `|`。段落単位で連結してから分けるので、
段落内改行で折り返した文も 1 文として読む。**段落の切れ目は空行だけではない**——
箇条書き・表・見出し・引用の開始行でも切る。隣り合うだけの項目を 1 文として
読むと、比較表現を持たない行が前の項目の否定と結びついて誤検出になる（§実装記録 3）。

自動修正はしない（§2-3）。

## 5. 出力への合流

- 表示は textlint 側と同じ体裁で、ラベル先頭に `[ルール ID]` を置く。著者が
  `lint.disabled_rules` へ書く名前をそのまま読み取れるようにするため。
- 件数はサマリーの「日本語校正」に合算する。著者から見れば textlint の指摘と
  区別する理由がない。
- `--textlint-only` では走る（日本語校正の一部）。`--spellcheck-only` では走らない。
- **抑止コメント（`<!-- vs-lint-disable -->` 系）に従う。** 校正について書いた章は
  自らの例文が指摘されるので、抑止の手段は実際に要る。textlint 側はコメントを
  textlint 記法へ変換して渡しているため、独自ルールが従わないと「同じコメントが
  片方にしか効かない」という不可解な振る舞いになる。
- **除外リスト（`config/textlint_allowlist.yml`）に従う（交ぜ書きのみ）。**
  辞書は gem 側にあって著者が削れないため、**語ごとに拒否する道が要る**。
  窓口は textlint と同じファイルに一本化する——`book.yml` の `lint.disabled_terms` は
  「指摘したくない語句は config/textlint_allowlist.yml に書きます」という理由で
  廃止済みで、独自ルールだけ別の場所を見ると著者が二度学ぶことになる。
  - **語全体が覆われたときだけ黙らせる**（textlint の allowlist と同じ判定）。
    部分一致にすると、除外リストにある「括弧」の 1 行（「括弧 => カッコ」を止めるためのもの）が
    「かぎ括弧 => 鉤括弧」まで消してしまう。
  - **黙らせた語は `--fix` の置換対象からも外す。** 指摘しないと決めた語を直すのは
    筋が通らないうえ、「黙っているのに原稿が書き換わる」のは最も分かりにくい壊れ方になる。
  - 効くのは交ぜ書きだけである。除外リストは「この語はこのままでよい」という語彙の
    宣言なので、構文の指摘（二通りに読める対比）には当てはまらない。

## 6. 検証

1. 交ぜ書きの各語が検出され、`--fix` で置換されること。
2. コードブロック・インラインコード内の交ぜ書きは検出も置換もされないこと。
3. 「次のように動作しない」が対句として検出**されない**こと。
4. 「A と同じように X しない」が検出されること。段落内改行を挟んでも検出されること。
5. `lint.disabled_rules` に `mazegaki` / `ambiguous-comparison` を書くと消えること。
6. **本書に当てて誤検出が無いこと。** 語の採否（§3.2）とパターンの絞りは
   机上では決められない。実測した件数を本仕様の「実装記録」へ残す。

### 2. 交ぜ書きは本書に 1 件も無かった（辞書 40 語の時点）

辞書 40 語を本書 27 ファイルへ当てて 0 件。技術同人誌の著者はもともと漢字で書く
ため、これは想定どおり。**検出力の確認は合成した原稿で行った**（テスト
`prose_checker_test.rb` PC-01）。誤検出しないことの確認が本書の役割である。
——この判断は §3 で覆る。0 件だったのは辞書が本書に出る語を持っていなかったため
でもあった。

### 3. 辞書を 40 → 140 語へ広げたら、段落の作り方の誤りが露見した

追加は 100 語（`しきい値 → 閾値`・`べき乗 → 冪乗`・`宝くじ → 宝籤` ほか）。
語が増えたぶん検出も増え、本書・`docs/`・`README.md` の **263 ファイル**へ当て直した
ところ、対比のほうで **14 件**挙がった（拡充前は本書 27 ファイルで 0 件）。
うち 5 件が段落の作り方に由来する誤検出だった。

- **箇条書きの項目どうしを 1 文へ連結していた。** 「複数章は `主要参照: …`（カンマ
  区切り）」という**比較表現を 1 つも含まない行**が挙がっていて気づいた。前の項目の
  「と同様の」と、この項目の「ありません」が 1 文として読まれていた。
- **表のセルどうしも同じだった。** 「Kindle と同じく PDF ページを切り出す」セルと
  「文字が選択できず、拡大で劣化する」セルが繋がっていた。

段落の切れ目にブロック開始行（`- ` `| ` `# ` `> ` `1. `）を加え、文の区切りに `|` を
足して **14 → 9 件**。残る 9 件は仕様書の例文（本仕様自身を含む）と、実際に二通りに
読める文で、誤検出ではない。**`vs lint` が見るのは `contents/` だけ**なので、
`docs/` の 9 件は実害ではなく精度の測定材料である。

拡充後の本書 `contents/` は **交ぜ書き 2 件・対比 0 件**。2 件はどちらも
「しきい値」（`32-metrics.md` / `41-book-yml.md`）で、辞書を広げたことで初めて
見つかった実際の交ぜ書きである。

**教訓は「比較表現を持たない行が挙がったら、段落の作り方を疑う」。** 検出そのもの
より、指摘が指す行が説明のつかない位置にあることが手掛かりになった。

### 4. 提供された辞書データは 97 語のうち 33 語しか使えなかった

分野別（一般・法律／IT・工学／医療／ビジネス）に整理された変換表を素材として
受け取った（連想配列の形で書かれた、取り込み用のデータ例）。
重複を除くと 97 語で、そのうち辞書に載ったのは 33 語（うち 16 語が新規、17 語は
既に持っていた）。落とした 64 語の内訳は次のとおりで、**そのまま取り込んでいたら
`--fix` が原稿を壊していた**。

- **全体がかな書きの語が 32 語**（「らち」「はたん」「そご」「かんがい」「へんこう」）。
  漢字とかなが混ざっていないので、そもそも交ぜ書きではない。加えて同音語と衝突する
  ——`らち → 拉致` は「**らち**が明かない（埒）」を、`へんこう → 偏光` は「変更」を、
  `かんがい → 灌漑` は「感慨」を書き換えてしまう。かな書きを漢字へ起こすのは
  文脈判断（形態素解析）の仕事で、辞書の単純置換では扱えない。
- **読みと熟語が対応しない誤りが 8 語**。`そう打 → 操舵`・`摩かん → 摩天`・
  `ち電 → 沈殿`・`ち遅 → 遅延`・`そう相 → 相殺`・`せん妄 → 閃妄`（正しくは譫妄）・
  `えしゃ → 壊死`・`なりすまし → 冒頭/仮装`。
- **他の語の一部として現れる綴り**（`き釈`＝「大き釈明」、`せん削`＝「動きません削除」）。
  このとき `かく乱` `き損` も落としたが、後日の再検討で制約を付けて救えた（§5）。
- **交ぜ書きにする理由のない語**（`しん透 → 浸透`・`とう析 → 透析`・`き釈 → 希釈`。
  どちらの字も常用漢字なので、かな書きになる動機がない）。

救えるものは制約を付けて採った——`こう着 → 膠着` は「あちらへ行こう着いたら」を、
`せん動 → 扇動` は「動きません動作が」を外している。

**辞書データは量ではなく、1 語ずつの検証が要る。** 変換先が誤った辞書は、検出が
外れるだけでなく `--fix` が原稿を書き換えてしまうため、綴りの安全性（誤検出）と
読みと熟語の対応（誤変換）の両方を語ごとに確かめた。

### 5. 落とした 3 語は、実際の文字列で確かめ直したら救えた

`かく乱`（攪乱）・`き損`（毀損）・`き裂`（亀裂）は、いずれも「他の語の一部として
現れる」として一度落としていた。指摘を受けて確かめ直したところ、**除外の判断自体が
甘かった**。

- **`かく乱` は理由が誤っていた。** 「書く乱れた字に当たる」と書いたが、
  「書く乱れ」の「書」は漢字なので、そもそも `かく乱` という並びにならない。
  実際に当たるのは「とにかく乱暴」「せっかく乱れて」といったひらがな副詞で、
  直前の「に・も・っ」を外せば済む。
- **`き損` `き裂` は危険が実在したが、後続で切れた。** 「引き損なう」「聞き損じる」・
  「引き裂く」「引き裂かれた」は本当に当たる。ただし危険な用法はどれも動詞の
  複合形なので、後続の「な・ね・じ」「く・け・か・こ・き」を外すだけで
  「整合性のき損」「疲労き裂」は残る。

**教訓は「危険は頭の中でなく実際の文字列で確かめる」。** 漢字を含む語を思い浮かべて
「当たりそう」と判断すると、`かく乱` のように当たらない語まで落とす。逆に
`き損` のように、落とすほどではない（後続で切れる）語も落としてしまう。
語ごとに実文をいくつか書いて突き合わせるほうが速く、確実だった。

### 6. 抑止コメントの尊重は後から足した

原稿 `31-lint.md` へ「交ぜ書きとは何か」を書いた瞬間、その例文が自分の
ルールに引っかかった。本文 §5 に追記したとおり、独自ルールも `vs-lint-disable` に
従う必要がある。**この検証は原稿を書くまで思いつかなかった**——ルールを追加する
ときは「その機能を解説する章」を必ず書いてみるとよい。

### 7. 副産物: `-next-line` が textlint に効かない

上の対応中に、`<!-- vs-lint-disable-next-line -->` が **textlint の指摘に対して
まったく効いていない**ことが分かった（`textlint-filter-rule-comments` v1.3.0 に
実装がない）。独自ルール側は自前で解釈するため効いており、**同じコメントが片方にしか
効かない**状態だった。

**同日中に直した。** `TextlintFormatter.aggregate_json` に `suppressed_lines:`
（`{ パス => 行番号の集合 }`）を渡し、出力段で行ごと落とす。**集約より前に当てる**のが
要点で、集約後は行番号が 1 行へ畳まれて選り分けられない。一時ファイルへ
`disable`／`enable` を挿し込む方式は採れない——行数が変わり、報告される行番号が
原稿とずれる。

この不具合は**独自ルールを足したから見つかった**。片方だけ実装して初めて
「効く側と効かない側」の差が出て、案内どおりに書いた原稿が指摘され続けた。
