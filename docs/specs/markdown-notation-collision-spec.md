# Markdown 標準記法との衝突と取り違え

## 0. 何が起きたか

2026-08-22、頒布用に組んだ PDF の索引に、**1 文字の `g`** がページ番号「147」を伴って
載っていた。原因は第 10 章の表セルにあった 1 箇所。

```markdown
| `index_library.yml` | 書籍間で持ち運ぶ用語集[g]・reject・読み（export/import） |
```

`[g]` は「用語集フラグの `[g]`」を説明するつもりの地の文だが、Vivlio Starter では
`[語]` が**手動の索引マークアップ**である。ビルドはこれを索引語として登録し、
**警告を 1 つも出さずに**巻末へ並べた。`g` は棄却リストに入っていたのに載った——
**手動マークアップは辞書を経由しない**からである。

原因を追う過程で、「Vivlio Starter は Markdown 標準記法をどこまで正しく扱えているか」を
**全数で確かめる**ことにした。本仕様書はその結果と、そこから決まる対応をまとめる。

---

## 1. 全数調査（2026-08-22 実測）

### 方法

CommonMark と GFM の記法を網羅した検証原稿を書き、2 経路の出力を突き合わせた。

1. **VFM 単体** … `vfm probe.md`（＝素の対応状況）
2. **実パイプライン** … `catalog.yml` へ一時登録して `vs build`（前処理 → 索引スキャン →
   VFM → 後処理をすべて通した結果）

差が出た箇所が Vivlio Starter の責任である。

### 結果

| 記法 | 判定 |
|---|---|
| ATX 見出し `#`〜`######` | ◯ |
| Setext 見出し（`===` / `---` の下線） | ◯ **ただし取り違えの元**（§7） |
| 太字・斜体・打ち消し線・コードスパン | ◯（斜体は下線で表示。意図的・21 章に明記） |

## 2. 責任の切り分け

壊れる 3 件は、**直す場所が同じではない。**

| 種別 | 内容 | 対応 |
|---|---|---|
| **T（ツールの不具合）** | 標準記法を壊している。著者は正しく書いている | **ツールを直す** |
| **L（記法の取り違え）** | 直すと副作用が大きい、または意図が機械に読めない | **`vs lint` が伝える** |

| | 記法 | 種別 |
|---|---|---|
| **T-1** | 参照リンク | ツールを直す |
| **T-2** | タスクリスト | ツールを直す |
| **L-1** | 短い ASCII の `[g]` | lint |
| **L-2** | 4 スペース字下げコードブロック | lint（非対応と伝える） |
| **L-3** | 段落直後の `---` / `===` | lint（取り違えを伝える） |

**T を lint の警告で済ませてはならない。** 標準記法を「書かないでください」と言うのは、
Markdown で書ける本を謳う製品として筋が通らない。とくに参照リンクは**本書が読者に
勧めている**（§11）。

## 3. T-1: 参照リンクを壊さない

### 現状（実測）

本番の `IndexMatchScanner#scan_and_tag_file!` に通した結果。

```
入力  参照リンク: [リンクテキスト][ref]
      [ref]: https://example.com

出力  参照リンク: <dfn …>リンクテキスト</dfn><dfn …>ref</dfn>
      <span …>ref</span>: https://example.com
```

**リンクもリンク定義も消える。** 索引を切っている本（`index_glossary.enabled: false`）でも
`MarkdownPreprocessor#strip_index_markup!` がブラケットだけ外すため逃げられない。

```
参照リンク: リンクテキストref
ref: https://example.com
```

### 判定の根拠は CommonMark そのもの

`[foo]` が参照リンクになるのは、**同じ文書に `[foo]: url` の定義があるときだけ**と
CommonMark が定めている。定義が無ければただの文字列である。この規則をそのまま使えば、
判定の根拠が「Vivlio Starter の都合」ではなく**Markdown の仕様**になる。

### 手順

1. **章の頭でリンク定義を集める。** 行頭（インデント 3 つまで）の `[ラベル]: 行き先` を拾い、
   ラベルを正規化して表に持つ（CommonMark はラベルを大文字小文字の区別なし・空白を畳んで
   比較する）。コード領域は `Masking` が除く。
2. **除外する 3 つの形**を索引マークアップから外す。
   - **リンク定義の行そのもの** … `[ref]: https://…`
   - **隣接した `][`** … `[本文][ref]` `[ref][]`。定義の有無を問わず常に外す
     ——**索引語を 2 つ区切りなしで並べる用途は存在しない**ので、定義表を引くまでもない
   - **定義済みラベルの単独形** … `[ref]` 単体。ここだけ 1 の表を引く
3. **索引マークアップとして残るもの**は従来どおり。定義の無い `[基本情報技術者]` は
   これまでどおり索引語になる。

同じラベルを索引語としても使いたい場合（`[CSS]` と `[CSS]: https://…` が同居）はリンクが勝つ。
CommonMark の解釈と一致するので驚きは最小である。

## 4. T-2: タスクリストを壊さない

### 現状（実測）

VFM は GFM のタスクリストに**正しく対応している**。

```html
<ul class="contains-task-list">
  <li class="task-list-item"><input type="checkbox" checked disabled> 済んだこと</li>
```

ところが**索引スキャン（Step 4）は VFM 変換（Step 5）より前に走る**ので、VFM はタスクリストを
見られない。

```
- <dfn …>x</dfn> 済んだこと
- <dfn …> </dfn> これからやること      ← 空白 1 文字が索引語。アンカーまで振られる
```

### 走査から外す

GFM のタスクリスト・マーカーは、**リスト項目の先頭**にある `[ ]` `[x]` `[X]` で、直後に空白が
続くものと定められている。`- ` `* ` `+ ` と番号付き（`1. `）のいずれのリスト記号にも付く。
この位置の `[…]` を索引マークアップから外す。行中の `[ ]` は対象にしない。

### 表示（PDF / EPUB / Kindle）

**字形の実測。** 同梱書体を `ttfunk` で全数確認した。

| 文字 | Zen 系（本文書体 7 種） | HackGen（コード書体） |
|---|:---:|:---:|
| ☐ (U+2610) ☑ (U+2611) ✓ ✔ | **×** | ◯ |
| □ (U+25A1) ■ (U+25A0) | ◯ | ◯ |

**☑ ☐ は本文書体に入っていない。** 本文で使うとコード書体へ落ちるか、最悪 OS 書体へ
フォールバックして **Type 3 混入の 6 番目の経路**（`type3-font-embedding-notes.md` §8）を踏む。

| ターゲット | 見せ方 |
|---|---|
| PDF / EPUB | `<input>` を隠し、`li.task-list-item::before` で**枠と鉤を CSS で描く**。字形に依存しないので Type 3 の危険がなく、文字サイズにも追従する |
| Kindle | `::before` も `var()` も効かない。`EpubBuilder` の localize で `<input>` を **`□` / `■` の文字へ置換**する。`body.vs-kindle` 側は `::before` を使わない |

あわせて `ul.contains-task-list` に `list-style: none` を当てる（行頭記号と枠が二重に出るため）。

## 5. L-1: 短い ASCII の `[語]`

### なぜ lint か

`[g]` は記法として妥当な形で、索引語のつもりかどうかは機械に判らない。ビルドを失敗させれば
正しい手動マークアップまで止まる。著者に判るのは書いた直後だけである。

### 何を見るか

読みなし・ASCII 可視文字 1〜2 字の `[…]`。例: `[g]` `[eV]` `[!]`。

**しきい値は 2 文字。`UnifiedIndexManager` の R9（`ASCII_SHORT_TERM_PATTERN`）と同じ値にする。**
3 文字へ広げると `[CSS]` `[PDF]` `[XML]`——**意図的な索引語としてごく自然な綴り**——を叩き始める。
知識は 1 つ、しきい値も 1 つ。

`a[i]` のような「直前が識別子」の型は入れない。地の文で配列を書くこと自体が稀で、書くなら
インラインコードにするのが本書の作法。誤検出の危険に対して実りが薄い。

### 読みは仮名で

`[eV|電子ボルト]` のように「意味」を `|` の右へ書きたくなるが、あの欄は**読み**である。
`determine_kana_row` の実測:

| 書き方 | 出る欄 |
|---|---|
| `[eV\|電子ボルト]` | **E** |
| `[eV\|いーぶい]` | **E** |
| `[電子ボルト\|でんしぼると]` | た |
| `[用語\|読み]` | その他 |

**語の 1 文字目が英字なら、読みを見る前に英字の欄が確定する。** 読みは並べ替えにしか使われず、
漢字を入れると漢字コード順でグループの末尾へ寄るだけ。意味を添える場所は**用語集の定義文**である。
**警告文では「仮名の読みを添える」と明示する。**

## 6. L-2: 4 スペース字下げコードブロックは非対応とする

### なぜ直さないか

CommonMark で字下げコードかどうかを決めるには、**リストの中にいるか**を追う必要がある。
`Masking` は行単位の走査なので、「4 スペース＝コード」という素朴な規則は誤りになる。

本書の地の文で 4 字下げがある行を数えると **2 件**で、**どちらもコードではなかった**。

```
21-markdown-tutorial.md:163      - 第 3 レベル          ← 入れ子リスト
22-extentions.md:956         複数行に続けたいときは…    ← 会話ブロックの継続行
```

素朴な規則を入れると、この 2 行がコード扱いになって索引タグが付かなくなる。正しく実装する
価値に対してコストが釣り合わない。**フェンスで書くのが現在の一般的な作法**でもあり、
21 章もフェンスとインラインコードの 2 つだけを教えている。

### ただし「黙って壊れる」ままにはしない

現状は非対応ではなく**破損**である。索引タグが `&lt;dfn …&gt;` として紙面に出る。

```html
<pre><code>4 スペースの&lt;dfn id="idx-…" class="index-term"&gt;字下げ&lt;/dfn&gt;コードブロック</code></pre>
```

VFM 自体は `<pre>` に組んでしまうので、放置すると壊れた出力がそのまま刷られる。
**lint が書いた時点で伝える**ことで非対応を実効化する。

指摘の対象は、**前後を空行で挟まれた 4 スペース以上の字下げ行**（リスト項目の継続行を
避けるため、直前の非空行がリスト記号で始まる場合は除く）。修正案は「フェンス（```）で
囲んでください」。

## 7. L-3: 段落直後の `---` / `===`

### 何が起きるか

21 章は「`---` `***` `___` は改ページ」と正しく書いている。しかし**直前に空行がないと
Setext 見出しになる**（CommonMark が Setext 見出しを優先する）。実測で確認した。

| 書いたもの | 起きること |
|---|---|
| 段落の直後の `---` | 改ページのつもりが **H2 見出し**になる |
| 段落の直後の `===` | **H1 見出し**になる。章タイトルと同じ階層なので、目次と PDF アウトラインに章として紛れ込む |

`===` のほうが被害が大きい。改ページの取り違えは紙面を見れば気づくが、目次の汚染は巻末まで
組んで初めて分かる。

本書の 27 章には **0 件**。まだ誰も踏んでいない。

### なぜ lint か

Setext 見出しは VFM（CommonMark）の挙動であり、こちらから禁止はできない。できるのは
**書いた時点で伝える**ことだけである。修正案は二択で明快:

- 改ページにしたい → **前に空行を入れる**
- 見出しにしたい → **`##` を使う**

## 8. 出力・窓口・`--fix`

### 出力

`warning-messages-actionable` の流儀に従い、**出現箇所と before → after を必ず添える**。
表示は既存の `ProseChecker` の集約形式に合わせる。

```
📄 contents/33-index-glossary.md  (校正)
    1件  [stray-index-markup] [g] は索引語として登録されます
         行: 299
         コードなら `[g]` と囲む／索引に載せるなら [g|よみ] と仮名の読みを添える
```

### ルール ID と窓口

| ルール ID | 対象 |
|---|---|
| `stray-index-markup` | L-1 |
| `indented-code-block` | L-2 |
| `setext-heading` | L-3 |

| したいこと | 書くところ |
|---|---|
| ルールごと切る | `book.yml` の `lint.disabled_rules: [setext-heading]` |
| 一部分だけ切る | `<!-- vs-lint-disable -->` …… `<!-- vs-lint-enable -->` |

**`config/textlint_allowlist.yml` は窓口にしない。** あれは「この語は正しい日本語だ」と
宣言する語彙辞書で、ここで指摘するのは語彙ではなく**形**である。

### `--fix` はしない

3 つとも正解が一意に決まらない。`[g]` は `` `[g]` `` か `[g|よみ]` の二択、字下げは
フェンスの言語名を機械が選べず、`---` は改ページか見出しかで意味が正反対になる。
`mazegaki` が `--fix` できるのは 1 対 1 の置換だからで、ここは 1 対 2 以上になる。

## 9. 実装の置き場所

- **索引マークアップの形の判定は `IndexMarkup` へ集約する**（T-1・T-2・L-1）。綴りを知って
  いるのはあのモジュールで、「その `[` は索引マークアップか」の判定を 2 箇所へ分けない
  （`notation-implementation-guide.md` §2）。リンク定義の表も、タスクリストの位置判定も、
  L-1 のしきい値もここに置く。`ProseChecker` と `IndexMatchScanner` は問い合わせるだけにする。
- **R9 のしきい値を `IndexMarkup` から引き直す。** 今は `UnifiedIndexManager` が持っている。
  同じ「2 文字」が 2 箇所に別々の定数として立つのを避ける。
- **lint の 3 ルールは `Lint::ProseChecker`**（`mazegaki` / `ambiguous-comparison` と同じ形）。
  `NotationGuard` ではない——あれは記法を**中和して黙らせる**側で、こちらは**報告する**側。
- **タスクリストの Kindle 置換は `EpubBuilder` の localize。** `ADMONITION_LABELS` と同じ層。

### 11-3 ビルド時に R9 が効かない件（2026-08-22・対応済み）

`vs index:auto` の R9 は辞書を守るが紙面は守らない。lint は著者が回さないことがあるので、
**紙面へ出る直前にも同じしきい値で見張る**ことにした。ただし**弾かない**——`[g]` が本当に
索引語のつもりかは機械に判らず、弾けば正しい手動マークアップまで巻き込む。**警告だけ**出し、
索引語としては従来どおり登録する。文面は R9 に揃えた（著者から見て同じ話なので）。

語ごとに 1 行へ畳む。同じ `[g]` が 30 箇所あっても 30 行並べない。

## 13. 回帰の器 — フィクスチャと `rake test:notation`

### 器はすでにある。動かす仕組みが無いだけ

`test/vivlio_starter/fixtures/notation/`（7 ファイル＋ README）が 2026-08-11 に作られている。
README は 3 つの軸（記法そのもの／入れ子の文脈／置き場所）と 5 つの不変条件を定め、
`rake test:notation` で回すと書いている。**しかしそのタスクは存在しない。** `rake -T` にも
`test:release` にも無く、どのテストからも参照されていない——**眠ったままの器**である。

しかも今回壊れていた記法が 1 つも入っていない。

| 記法 | `01-commonmark.md` |
|---|---|
| 参照リンク `[text][ref]` / `[ref]: url` | 無し |
| タスクリスト `- [ ]` `- [x]` | 無し |
| 4 スペース字下げコードブロック | 無し（唯一の 4 字下げ行は入れ子リスト） |
| Setext 見出し | 無し |

README 自身が「**本書に書かれていない記法は、どのテストも守れない**」と述べている。
今回起きたのは、その一段先——**フィクスチャに書かれていない記法も守れない**、である。

### 足す不変条件: VFM 単体との突き合わせ

既存の 5 条件は「壊れた痕跡を探す」形（`<pre>` の中に索引タグが無いか等）で、
**どう壊れるかを先に知っていないと書けない**。今回の 3 件はいずれも既存の 5 条件に
掛からなかった。

6 本目として、次を足す。

> **VFM 単体の出力と、実パイプラインの出力で、記法の生存が一致すること**

`vfm fixture.md` を基準に、パイプライン通過後の HTML と記法ごとに突き合わせる。
**壊れ方を先に知らなくてよい**のが要点で、VFM が組めたものが消えていれば、原因が
索引スキャンでも前処理でも後処理でも落ちる。今回の 3 件はこの 1 本で同時に捕まった。

### 2 つの器を分ける

| 器 | 何を見るか | 判定 |
|---|---|---|
| `rake test:notation` | 記法が生き残っているか（構造） | **機械**。`test:release` に載せる |
| 目視ページ（`math:check` 型） | チェックボックスの意匠・Kindle での劣化 | **目視**。`test:release` には載せない |

記法の生存は機械で判定できる。数式が「正しく見えるか」は目でしか判らない——だから
`math:check` は目視なのであって、記法の回帰まで目視に頼る理由はない。
タスクリストの枠の見た目（§4）だけは目視の側に置く。

### 実行の作り

**リポジトリの `contents/` を差し替えない。** 隔離した一時プロジェクトで回す。

1. 一時ディレクトリに `vs new <名前> --yes` で雛形を作る
2. `contents/` をフィクスチャで置き換え、`catalog.yml` を対応する内容に書く
3. リポジトリの `bin/vs`（`ruby -Ilib bin/vs`）でビルドする——`rake reinstall` を要らなくする
   ため。`PATH` 上の `vs` は導入済み gem を使い、変更が反映されないまま検証してしまう
4. 生成された HTML と、`vfm` 単体の出力を突き合わせる

### 未実装の記法をどう扱うか

T-1・T-2・L-2 を入れるまで、新しく足した検体は落ちる。**落ちたままにしない。**
既知の破れを明示した一覧を持ち、そこにあるものは 🟡 で報告して失敗にはしない。
**実装したら一覧から消す**——消し忘れると、直ったことに気づかないまま緑が続くため、
一覧の各行には対応する節（§3・§4・§6）を書き添える。

## 14. 実装記録

### T-1 参照リンク（2026-08-22）

判定は `IndexMarkup` へ集約し、消費側（`IndexMatchScanner` と
`MarkdownPreprocessor#strip_index_markup!`）は `other_notation?` 1 つだけを見る。

**前後 1 文字は `MatchData` から引いた**（`pre_match` / `post_match`）。走査対象の文字列を
受け取らずに済むので、退避（マスク）済みの行を扱う索引スキャナからも、素の本文を扱う
前処理からも同じ呼び方ができる。当初は行と位置を渡す設計にしていたが、`LineMask` が
内部文字列を公開しておらず行き詰まった。

**落とし穴: 脚注定義 `[^1]: …` をリンク定義として拾っていた。** 綴りが同じだけの別記法。
実害は無かった（`skip_term?` が先に落とす）が、本書 4 章と雛形 2 ファイルの脚注が
ラベル表に入り込んでいた。`LINK_DEFINITION` に `(?!\^)` を足して除外した。

**本書のリンク定義は 0 件**だったので、索引は 1 語も変わっていない。

### T-2 タスクリスト（2026-08-22）

走査から外す判定（`task_list_marker?`）と、表示の 2 本立て。

**表示は当初の案どおり CSS で描いた。** `<input>` を隠すのではなく `appearance: none` で
入力欄の見た目だけ消し、その要素自身へ枠を描いている——`::before` を `<input>` へ当てる
書き方は置換要素の扱いが処理系で割れるため避けた。`:has()` も使っていない（EPUB の
読み手が古い場合に効かない）。済み印は `:checked` の背景画像（インライン SVG の白い鉤）で、
画像が読めない環境でも `background-color` の塗りつぶしが残るので意味は伝わる。

Kindle は `EpubBuilder#textify_task_list_checkboxes!` が `<input>` を `■` / `□` の
`<span class="vs-task-mark">` へ差し替える。`decorate_list_markers_for_epub!` の中に置いた
——既に fancy list とアウトラインリストの実体注入をしている場所で、層が同じ。

**実ビルドで確認済み**（小さな本を組み、済み＝白い鉤つきの黒枠／未了＝白枠で出た）。
`pdffonts` で Type 3 は 0 件、埋め込み書体のみ。

**副作用が 1 つある。** `ul.contains-task-list` の `list-style: none` は、同じリストに
混ざった**印の無い項目からも行頭記号を奪う**。GFM の描画系も同じ振る舞いなので許容した。

### L-1〜L-3 lint ルール（2026-08-22）

`ProseChecker` の第 3〜5 のルールとして実装。`mazegaki` / `ambiguous-comparison` と
同じ形なので、`disabled_rules` も `<!-- vs-lint-disable -->` も既存の仕組みがそのまま効く。
