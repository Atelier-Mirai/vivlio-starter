# 索引マークアップ `[語]` が Markdown 標準記法を壊す問題

## 0. 何が起きたか

2026-08-22、頒布用に組んだ PDF の索引に、**1 文字の `g`** がページ番号「147」を伴って
載っていた。原因は第 10 章の表セルにあった 1 箇所。

```markdown
| `index_library.yml` | 書籍間で持ち運ぶ用語集[g]・reject・読み（export/import） |
```

`[g]` は「用語集フラグの `[g]`」を説明するつもりの地の文だが、Vivlio Starter では
`[語]` が**手動の索引マークアップ**である。ビルドはこれを索引語として登録し、
**警告を 1 つも出さずに**巻末へ並べた。`g` は棄却リストに入っていたのに載った——
**手動マークアップは辞書を経由しない**からである。

原因を追って現在の挙動を実測したところ、**問題は 1 文字の誤登録よりずっと広かった。**
`[…]` は Markdown 標準の記法とも綴りが衝突しており、Vivlio Starter はそれらを
黙って壊している。本仕様書はその全体を扱う。

---

## 1. 現在の挙動（実測・2026-08-22）

### 1-1 綴りの定義元

`IndexMarkup::TERM_PATTERN` が唯一の定義元。

```ruby
TERM_PATTERN = /(?<!\^)\[([^\[\]\n]+)\](?!\()/
```

除外しているのは 2 つだけ——`](` が続くもの（インラインリンク・画像）と、`[` の直前が
`^` のもの（インライン脚注）。加えて `skip_term?` が中身の先頭 `^`（参照脚注 `[^1]`）を落とす。
**それ以外のあらゆる `[…]` は索引マークアップとして扱われる。**

### 1-2 何がマークアップとみなされるか

12 の書き方へ当てた実測。

| 書いたもの | 索引語になるか |
|---|---|
| `フラグは [g] と書きます。` | **「g」** |
| `- [ ] やること` | **「 」**（空白 1 文字） |
| `- [x] 完了した` | **「x」** |
| `詳しくは[公式ドキュメント][docs]を参照。` | **「公式ドキュメント」「docs」** |
| `[docs]: https://example.com` | **「docs」** |
| `詳細は [表 1] を見てください。` | **「表 1」** |
| `配列は a[i] で参照します。` | **「i」** |
| `箇条書きの [!] は強調マーカーです。` | **「!」** |
| `[用語\|ようご] と書くと…` | 「用語\|ようご」（意図どおり） |
| `[^1]: 脚注の本体です。` | ならない |
| `本文^[インライン脚注]の続き。` | ならない |
| `![アインシュタイン](Einstein.webp)` | ならない |

### 1-3 参照リンクが壊れる（実測）

本番の `IndexMatchScanner#scan_and_tag_file!` に通した結果。

```
入力  参照リンク: [リンクテキスト][ref]
      [ref]: https://example.com

出力  参照リンク: <dfn …>リンクテキスト</dfn><dfn …>ref</dfn>
      <span …>ref</span>: https://example.com
```

**リンクもリンク定義も消える。** インラインリンク `[text](url)` と自動リンク `<url>` は無傷。

索引を切っている本（`index_glossary.enabled: false`）でも逃げられない。
`MarkdownPreprocessor#strip_index_markup!` がブラケットだけ外すため:

```
参照リンク: リンクテキストref
ref: https://example.com
```

### 1-4 タスクリストが壊れる（実測）

VFM は GFM のタスクリストに**正しく対応している**。

```html
<ul class="contains-task-list">
  <li class="task-list-item"><input type="checkbox" checked disabled> 済んだこと</li>
```

ところが**索引スキャン（Step 4）は VFM 変換（Step 5）より前に走る**ので、VFM は
タスクリストを見られない。

```
- <dfn …>x</dfn> 済んだこと
- <dfn …> </dfn> これからやること      ← 空白 1 文字が索引語。アンカーまで振られる
```

### 1-5 辞書登録とビルドで番人が食い違う

`vs index:auto`（辞書登録）には **R9** がある。

```ruby
# lib/vivlio_starter/cli/index/unified_index_manager.rb:49
ASCII_SHORT_TERM_PATTERN = /\A[\x21-\x7E]{1,2}\z/
```

2 文字以下の ASCII（`[eV]` `[Hz]` `[g]`）は辞書に載せず、章名を添えて警告する。
**警告の作りはよい。** ところが**ビルド時の `IndexMatchScanner` には同じ番人がいない。**
R9 が守るのは辞書だけで、紙面は守られていない。今回の `g` はここを通った。

### 1-6 読みは行の決定に関与しない

`[eV|電子ボルト]` のように「意味」を `|` の右へ書きたくなるが、あの欄は**読み**である。
`determine_kana_row` の実測:

| 書き方 | 出る欄 |
|---|---|
| `[eV\|電子ボルト]` | **E** |
| `[eV\|いーぶい]` | **E** |
| `[電子ボルト\|でんしぼると]` | た |
| `[用語\|読み]` | その他 |

**語の 1 文字目が英字なら、読みを見る前に英字の欄が確定する。** 読みは並べ替えにしか
使われないので、漢字を入れると漢字コード順でグループの末尾へ寄るだけになる。
意味を添える場所は**用語集の定義文**である。

## 2. 問題の切り分け

同じ「`[…]` の誤解釈」でも、**責任の所在が 2 つに分かれる。**

| 種別 | 内容 | 直す場所 |
|---|---|---|
| **T（ツールの不具合）** | Markdown 標準の記法を壊している。著者は正しく書いている | **`IndexMarkup` を直す** |
| **L（意図が読めない）** | 記法としては妥当で、索引語のつもりかどうか機械に判らない | **`vs lint` が指摘する** |

**T を lint の警告で済ませてはならない。** 標準記法を「書かないでください」と言うのは、
Markdown で書ける本を謳う製品として筋が通らない。本書は 21 章と早見表で**参照リンクを
読者に勧めており**（§6）、動かない記法を教えている状態でもある。

---

## 3. 修正 T-1: 参照リンクを壊さない

### 判定の根拠は CommonMark そのもの

`[foo]` が参照リンクになるのは、**同じ文書に `[foo]: url` の定義があるときだけ**と
CommonMark が定めている。定義が無ければただの文字列である。この規則をそのまま使えば、
「Vivlio Starter の都合」ではなく**Markdown の仕様**が判定の根拠になる。

### 手順

1. **章の頭でリンク定義を集める。** 行頭（インデント 3 つまで）の
   `[ラベル]: 行き先` を拾い、ラベルを正規化して表に持つ（CommonMark はラベルを
   大文字小文字の区別なし・空白を畳んで比較する）。コード領域は `Masking` が除く。
2. **除外する 3 つの形**を索引マークアップから外す。
   - **リンク定義の行そのもの** … `[ref]: https://…`
   - **隣接した `][`** … `[本文][ref]` `[ref][]`。定義の有無を問わず常に外す
     ——**索引語を 2 つ区切りなしで並べる用途は存在しない**ので、定義表を引くまでもない
   - **定義済みラベルの単独形** … `[ref]` 単体。ここだけ 1 の表を引く
3. **索引マークアップとして残るもの**は従来どおり。定義の無い `[基本情報技術者]` は
   これまでどおり索引語になる。

### 副作用の見積り

同じラベルを索引語としても使いたい場合（`[CSS]` と `[CSS]: https://…` が同居）、
リンクが勝つ。CommonMark の解釈と一致するので、驚きは最小である。

## 4. 修正 T-2: タスクリストを壊さない

### 走査から外す

GFM のタスクリスト・マーカーは、**リスト項目の先頭**にある `[ ]` `[x]` `[X]` で、
直後に空白が続くものと定められている。`- ` `* ` `+ ` と番号付き（`1. `）のいずれの
リスト記号にも付く。この位置の `[…]` を索引マークアップから外す。

行中の `[ ]` は対象にしない——タスクリストではないため、従来どおり扱う。

### 表示（PDF / EPUB / Kindle）

**字形の実測。** 同梱書体を `ttfunk` で全数確認した。

| 文字 | Zen 系（本文書体 7 種） | HackGen（コード書体） |
|---|:---:|:---:|
| ☐ (U+2610) ☑ (U+2611) ✓ ✔ | **×** | ◯ |
| □ (U+25A1) ■ (U+25A0) | ◯ | ◯ |

**☑ ☐ は本文書体に入っていない。** 本文で使うとコード書体へ落ちるか、最悪 OS 書体へ
フォールバックして **Type 3 混入の 6 番目の経路**（`type3-font-embedding-notes.md` §8）を踏む。

そこで**ターゲットごとに描き分ける**（`:::{.class}` ボックスで確立した Kindle 劣化の型と同じ）。

| ターゲット | 見せ方 |
|---|---|
| PDF / EPUB | `<input>` を隠し、`li.task-list-item::before` で**枠と鉤を CSS で描く**。字形に依存しないので Type 3 の危険がなく、文字サイズにも追従する |
| Kindle | `::before` も `var()` も効かない。`EpubBuilder` の localize で `<input>` を **`□` / `■` の文字へ置換**する。`body.vs-kindle` 側は `::before` を使わない |

あわせて `ul.contains-task-list` に `list-style: none` を当てる（行頭記号と枠が二重に出るため）。

## 5. lint に残すもの

T-1・T-2 を直すと、**lint が見るのは 1 つだけ**になる。

| 型 | 見つけ方 | 例 | 直し方 |
|---|---|---|---|
| **S1** 短い ASCII | 読みなし・ASCII 可視文字 1〜2 字 | `[g]` `[eV]` `[!]` | `` `[g]` `` と囲む／`[g\|よみ]` と**仮名の**読みを添える |

**しきい値は 2 文字。R9 と同じ値にする。** 3 文字へ広げると `[CSS]` `[PDF]` `[XML]`
——**意図的な索引語としてごく自然な綴り**——を叩き始める。知識は 1 つ、しきい値も 1 つ。

`a[i]` のような「直前が識別子」の型は入れない。地の文で配列を書くこと自体が稀で、
書くならインラインコードにするのが本書の作法。誤検出の危険に対して実りが薄い。

**指摘しないもの**: 読み付き `[語|よみ]`／日本語を含む語／3 文字以上の ASCII／
コード領域（`Masking` が退避）／脚注・インラインリンク・画像（`IndexMarkup` が既に除外）。

### 出力

`warning-messages-actionable` の流儀に従い、**出現箇所と before → after を必ず添える**。
表示は既存の `ProseChecker` の集約形式に合わせる。読みは**仮名で**と明示する（§1-6）。

```
📄 contents/33-index-glossary.md  (校正)
    1件  [stray-index-markup] [g] は索引語として登録されます
         行: 299
         コードなら `[g]` と囲む／索引に載せるなら [g|よみ] と仮名の読みを添える
```

### 設定の窓口

| したいこと | 書くところ |
|---|---|
| ルールごと切る | `book.yml` の `lint.disabled_rules: [stray-index-markup]` |
| 一部分だけ切る | `<!-- vs-lint-disable -->` …… `<!-- vs-lint-enable -->` |

**`config/textlint_allowlist.yml` は窓口にしない。** あれは「この語は正しい日本語だ」と
宣言する語彙辞書で、ここで指摘するのは語彙ではなく**形**である。`[eV]` を意図して索引へ
載せたいなら `[eV|いーぶい]` と書けば済む。

### `--fix` はしない

`[g]` の正解は `` `[g]` ``（コードだった）か `[g|よみ]`（索引語にしたかった）かの
**二択で、決められるのは著者だけ**。`mazegaki` が `--fix` できるのは 1 対 1 の置換だからで、
ここは 1 対 2 になる。機械が選ぶと、直したはずの原稿が別の壊れ方をする。

## 6. あわせて直すもの

### 6-1 参照リンクを教えている記述

T-1 で参照リンクが動くようになれば、以下はそのままで正しくなる。**T-1 を入れずに
lint だけ入れると、本書が自分の教えを警告する**ことになるので、順序を違えない。

| 場所 | 記述 |
|---|---|
| `contents/21-markdown-tutorial.md:440` | 「**参照リンク**: `[text][id]` と `[id]: url`」 |
| `contents/90-notation-cheatsheet.md:92` | 「同じ URL を何度も使う → `[テキスト][id]`、別行に `[id]: URL`」 |
| `templates/markdown_snippet.md:587` | 参照リンクの見本（コピー用） |

T-1・T-2 の後は、**タスクリストを本書の記法一覧へ載せる**ことも検討する（現在どこにも
書いていないが、VFM は最初から対応していた）。

### 6-2 ビルド時に R9 が効かない件

§1-5 の非対称。lint は著者が回さないことがある。紙面へ出る直前の番人として
`IndexMatchScanner` にも同じしきい値を置くかは別途判断する。ただし**ビルドを止めては
ならない**——正しい手動マークアップまで巻き込む。出すなら警告のみ。

## 7. 実装の置き場所

- **形の判定はすべて `IndexMarkup` へ集約する。** 綴りを知っているのはあのモジュールで、
  「その `[` は索引マークアップか」の判定を 2 箇所へ分けない
  （`notation-implementation-guide.md` §2）。リンク定義の表も、タスクリストの位置判定も、
  S1 のしきい値もここに置く。`ProseChecker` と `IndexMatchScanner` は問い合わせるだけにする。
- **R9 のしきい値を `IndexMarkup` から引き直す。** 今は `UnifiedIndexManager` が持っている。
  同じ「2 文字」が 2 箇所に別々の定数として立つのを避ける。
- **lint のルールは `Lint::ProseChecker` の第 3 のルール**（`mazegaki` /
  `ambiguous-comparison` と同じ形）。`Finding.new(rule: 'stray-index-markup')`。
  `NotationGuard` ではない——あれは記法を**中和して黙らせる**側で、こちらは**報告する**側。
- **タスクリストの Kindle 置換は `EpubBuilder` の localize。** `ADMONITION_LABELS` と同じ層。

1. **T-1**: `[本文][ref]` ＋ `[ref]: url` が索引語にならず、VFM 変換後にリンクとして出る

3. **T-1**: 索引を切った本（`strip_index_markup!` 経路）でも参照リンクが壊れない
4. **T-2**: `- [x]` / `- [ ]` / `1. [ ]` が索引語にならず、`task-list-item` として組まれる
5. **T-2**: 行中の `[ ]` は従来どおり扱う（タスクリストではない）
6. **T-2**: Kindle ビルドで `<input>` が `□` / `■` の文字に置き換わる（`epub_kindle_layout_test`）

8. **S1**: `[CSS]` `[PDF]`（3 文字 ASCII）は指摘しない
9. **S1**: コードフェンス・インラインコード・`<code>` の中は指摘しない
