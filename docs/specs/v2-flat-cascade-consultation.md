## 1. 問い

PDF は層のある CSS を読み、勝ち負けは層の順で決まる。EPUB と Kindle は層を外して層の順に並べた CSS を読む（KFX が `@layer` の中を捨てるため）。平らな CSS では、勝ち負けは詳細度で決まり、詳細度が同じときだけ並びの順で決まる。そのため、**下の層の詳細度の高い規則が、上の層の規則に勝つ**組が出る。

§2.1 の層の順の理由のうち、二つはこの「詳細度に関係なく層で勝つ」ことに頼っている。

- `theme` が `parts` の上にある理由:「層が上なら、詳細度が低い規則でも勝つ。テーマは詳細度を上げたり `!important` を使ったりせずに済む」
- `utilities` が `theme` の上にある理由: 著者が原稿に書いた `{.text-right}` などが、テーマの規則に負けないようにする

EPUB と Kindle では、この二つが成り立たない。§4.3 は、検査（`InversionCheck`）で組を挙げ、テーマを作る人が詳細度をそろえて直す、という扱いにしている。この扱いのままでよいか、それとも平らにするときに層の順を保つ仕組みを入れるか、を決めてほしい。

## 2. S3-1 で分かったこと

### 2.1 検査の判定の広さで、挙がる数が大きく変わる

§4.3 (c) の判定は「最後の複合選択子が同じクラスを含むか、どちらもクラスを持たず同じ要素名」である。同梱の CSS（`stylesheets/`・EPUB と Kindle の束・`book-settings.css` を除く）で数えた。

| 判定 | 静的に挙がる組 |
| :--- | ---: |
| §4.3 (c) のとおり | 8（3 種類） |
| 片方がクラスを持たない組も含める（`p.note` と `p`、`.part-title` と `body` など） | 842 |

(c) で挙がる 8 組は、どれも実際の本では起きないか、1.x の EPUB と同じ結果になるので、理由を書いた許可の表に載せた（`css_layer_test.rb` の `ALLOWED_INVERSIONS`）。広い判定の 842 組のほとんどは、著者の指定（`.aki`・`.aki2`・`.align-*`・`.text-*`。utilities 層）と、詳細度の高い部品の規則（`body.vs-header-simple h2`・`pre[class*="language-"]` など）の組である。

### 2.2 実際の HTML で起きる組は 4 組だけ

広い判定の組を、組み上がった HTML（本書の PDF 用 HTML・EPUB・Kindle 用 EPUB、B4 の EPUB）で絞った。両方の選択子に当たる要素がある組は 4 組で、**utilities 層の組は 0** だった（著者の指定のクラスが、部品の規則が選ぶ要素に付いていない）。4 組とも上の層は settings 層（`book.yml` から生成する `book-settings.css`）である。

| 層ありで勝つ規則（上の層） | 平らにすると勝つ規則（下の層） | 起きる場所 | 今の扱い |
| :--- | :--- | :--- | :--- |
| `body.vs-kindle strong { color: #15803d }`（settings） | `p:has(> strong:only-child):has(+ table) strong { color: var(--color-text) }`（parts） | Kindle の章 | KFX は `:has()` の規則を捨てるので、画面では settings の色になる |
| `body.vs-header-simple h2 { page-break-before: auto }`（settings） | `body.vs-header-simple.vs-kindle h2 { break-before: page }`（parts） | Kindle の付録 | Kindle は S2 の前から平らな CSS を読んでおり、付録の節の前で改ページしている。S3-2 で target 層へ移すと、層でも勝つ |
| `body { page-break-before: always }`（settings） | `.part-title { break-before: recto }`（pages） | 部扉（PDF・EPUB・Kindle） | **(c) では挙がらない**（片方がクラスを持つ）。層ありの PDF では S2-1 から settings が勝っている（1.x は詳細度で recto）。部扉は 1 枚ずつ組んで結合するので、本書の画素は変わっていない |
| `body { page-break-before: always }`（settings） | `body.toc { break-before: recto }`（pages） | 目次（PDF） | 同上 |

下の 2 組は、PDF と EPUB で勝つ側が違い、しかも §4.3 (c) の判定では見つからない。判定を広げても、HTML で絞れば数は手で読める大きさに収まる。

### 2.3 KFX は詳細度を上げた選択子を解しそう（画面では未確認）

平らにするときに上の層の詳細度を上げる案（下の §3 の B）が成り立つかを、`scripts/kfx_probe.rb` の 3 項目で測った（Kindle Previewer 4.0.4）。

| 項目 | CSS | 期待 | 中間生成物 |
| :--- | :--- | :--- | :--- |
| 対照 | `.t-ctl { 緑 } div p.t-ctl { 赤 }` | 赤（詳細度の高い後の規則） | 期待どおり |
| クラスの重ね | `.t-rep.t-rep.t-rep { 緑 } div p.t-rep { 赤 }` | 緑 | 期待どおり |
| 当たらないクラスの `:not()` の重ね | `p.t-not:not(.t-n1):not(.t-n2) { 緑 } div div p.t-not { 赤 }` | 緑 | 期待どおり |

変換の中間生成物は、変換器の前処理（Chromium）が解いた値であり、KFX の描画が捨てる規則を映さないことがある（`kindle-css-compatibility-notes.md` §2.1）。画面での確認は、必要なら Opus が行う。

## 3. 考えられる案

| 案 | 中身 | 得るもの | 失うもの |
| :--- | :--- | :--- | :--- |
| A. 今の仕様のまま | 平らな CSS は詳細度で決まると割り切る。検査で組を挙げ、vs の CSS は直すか許可の表に載せ、テーマを作る人には `vs theme:check` が 🟡 で知らせる | 生成が単純。出力の CSS が読める | テーマを作る人が、部品の詳細度に合わせて選択子を書く必要がある（§2.1 の理由が EPUB と Kindle では成り立たない） |
| B. 平らにするとき、上の層の詳細度を上げる | 各層の規則の選択子に、当たらないクラスの `:not()` を層の位置に応じた数だけ足し、詳細度の順が層の順と同じになるようにする（PostCSS の cascade-layers が `:not(#\#)` で行うことを、KFX が解する形で行う） | PDF と EPUB と Kindle で勝ち負けが同じになる。テーマを作る人は層だけ考えればよい | 選択子が長くなる（下の層の詳細度の最大値 × 層の数）。実測の最大は、parts 層がクラス 7（`[0,7,2]`・コードの行番号の規則）、pages 層が **id を含む** `#toc li.toc-section > .toc-title::after`（`[1,2,2]`）。クラスの `:not()` では id に勝てないので、id の `:not(#…)` を使うか（KFX での扱いは未測定）、`#toc` の規則を書き直す必要がある。`!important` と層の外（`custom.css`）の扱いも決める必要がある。KFX の描画での確認が要る |
| C. B を一部の層だけに | 「詳細度に関係なく勝つ」ことに頼る層（`theme`・`utilities`、必要なら `settings`・`target`）だけを上げる | B より出力が短い | 層ごとに扱いが違い、仕組みの説明が増える |

あわせて、§4.3 (c) の判定の広さも決めてほしい。2.2 のとおり、(c) は実際に起きる組を見落とす。広い判定にして、ビルドでは組み上がった HTML で絞る形にすれば、数は小さい。ただ、テストは HTML なしの静的な検査なので、広い判定では許可の表が 842 組になる。テストの側の扱いも含めて決めてほしい。

## 5. 答え（Fable・2026-11-15）

### 5.1 決めたこと

| # | 問い | 決定 |
| :--- | :--- | :--- |
| 1 | A・B・C のどれか | **A**。平らな CSS は詳細度で決まるものとし、層の順を詳細度に置き換える仕組みは入れない。B と C は見送り、再検討の条件を 5.3 に書く |
| 2 | 判定の広さ | 組の判定を広げるのではなく、**要素ごとに「勝つ宣言」を比べる**判定に変える（5.4）。静的な検査（HTML なし）は今の (c) のまま、早めの警報として残す |
| 3 | 部扉と目次の `break-before` | **直さない。逆転ではなく、組で比べる判定の誤検出である**（5.2） |
| 4 | 入れる段階 | 5.6 の表 |

### 5.2 部扉と目次の組は誤検出である

§2.2 の下の 2 組は、層ありでも平らでも同じ宣言が勝つ。本書は `page.chapter_pagebreak: any` で、settings 層の規則は選択子の並びに `.part-title` と `body.toc` を含む（`BookSettingsCss::CHAPTER_PAGEBREAK_SELECTORS`。元の選択子を写して、同じ詳細度で後から勝つ作りである）。

`Cascade` で、部扉と目次の入口の `break-before` を取り合う宣言を並べ、二つの強さで勝つ宣言を求めた。

| ページ | 層ありで勝つ宣言 | 平らで勝つ宣言 |
| :--- | :--- | :--- |
| 部扉 | settings の `.part-title { page-break-before: always }` | 同じ |
| 目次 | settings の `body.toc { page-break-before: always }` | 同じ |

- 組で比べると、settings の `body`（詳細度 `[0,0,1]`）と pages の `.part-title`（`[0,1,0]`）は入れ替わって見える。しかし、同じ settings の規則の `.part-title`（`[0,1,0]`・後に書かれている）が、どちらの形でも両方に勝つ。
- 設定が `any` のとき recto でなくなるのは、設定の意図どおりである。1.x も同じ選択子の写しで同じ結果だった。「S2-1 から settings が勝っている（1.x は詳細度で recto）」という §2.2 と `css-layer-restructure-spec.md` §10.5 の 1 の記述は誤りなので、決定を移すときに直す。
- 残る実際の組は Kindle だけの 2 組で、どちらも S3-2 で target 層へ移すと層でも同じ側が勝つ。**同梱の CSS で、層を外すと結果が変わる組は、S3-2 の後は 0 になる。**

### 5.3 A にする理由と、B・C を見直す条件

1. **直す対象が無い。** 実際に起きる組は 5.2 のとおり S3-2 で 0 になる。著者の指定（utilities 層）の組は、本書と B4 で 0 である。
2. **B は、確かめきれない書き方を上の層の全部の規則に付ける。** KFX は解せない選択子を持つ規則を丸ごと捨てる（`:is()` の例。`kindle-css-compatibility-notes.md` §2）。`:not()` の重ねを描画が解すかは中間生成物では分からず、実機も無い。解さない描画が一つでもあると、その端末では theme より上の規則が全部消える。Kindle は最も重視する出力先で、得るもの（1 のとおり今は 0 組）に対して失うものが大きい。
3. **B でも保てない取り合いが残る。** `@page` の規則には選択子の詳細度が無い。`style` 属性との勝ち負けも変わる。id を含む選択子には `:not(#…)` が要り、KFX での扱いは測っていない。
4. **テーマの主な入口は変数で、変数は平らでも層の順どおりに決まる。** `--book-*` の定義は `:root`・`body`・`body.<種類>` に書く決まりで（`theme-contract-spec.md` §3.5）、詳細度が同じなので、平らな CSS でも後の層の定義が勝つ。Kindle 用のリテラル化も同じ順で解く（`css-layer-restructure-spec.md` §4.4）。「テーマは詳細度を上げずに済む」は、変数で変える範囲ではどの出力先でも成り立つ。
5. **標準のテーマは 1.x の選択子のまま切り出す。** S6 で `standard` を切り出すとき、選択子を変えなければ、平らな CSS での勝ち負けは 1.x の EPUB と同じである。

見直す条件: S6・S7 で同梱のテーマか公式テーマを入れたとき、5.4 の判定で挙がる組が、テーマの選択子を部品にそろえる直し方では解けない場合。そのときは C（theme と utilities だけ）を検討し、先に `kfx_probe.rb` の 3 項目と `:not(#…)` を Kindle Previewer の画面で確かめる。今は画面の確認をしない。

### 5.4 判定を「要素ごとに勝つ宣言を比べる」に変える

組で比べる判定は、広げると誤検出が増え（5.2）、狭めると見落とす。HTML があるときは、推測をやめて勝つ宣言を直接比べる。

- **定義:** 組み上がった HTML のある要素の、あるロングハンドについて、その要素に当たる宣言の全部から、層ありの強さで勝つ宣言と、平らの強さで勝つ宣言を求める。二つが別の宣言で、値の意味が違うとき、逆転とする。報告は「層ありで勝つ宣言」と「平らで勝つ宣言」の組で行う。
- **求め方:** 候補は、今の判定からクラスの条件を外した広い組（`Selector.may_overlap?` だけ）で絞る。候補の組の両方に当たる要素について、同じロングハンドの宣言のうち、その要素に当たるものを集め、`Cascade.layered_precedence` と `Cascade.flat_precedence` の最大を比べる。当たるかどうかの判定は今の `present` と同じ（疑似要素と動的な疑似クラスは外す。Nokogiri が読めない選択子は当たるものとする）。
- **静的な検査（HTML なし）:** §4.3 (c) のまま残す。これは保証ではなく、vs の CSS を書き換えたときの早めの警報である。広い判定にはしない（許可の表が 842 組になり、読めない）。
- **保証:** HTML のある場面で行う。段階の確かめで、B1 と B4 を `--log=debug` で組み、挙がる組が 0 か、理由つきで記録されていること。

報告の場面:

| 場面 | 何を使うか | 出し方 |
| :--- | :--- | :--- |
| `rake test`（`css_layer_test.rb`） | 静的な (c) と許可の表 | 今のまま |
| 段階の確かめ（S3-2 以降） | 要素ごとの判定。B1・B4 の EPUB と Kindle 用 EPUB | `--log=debug` の出力が 0 組であることを記録する |
| `vs build`（著者） | 要素ごとの判定のうち、層ありで勝つ側が層の外（`custom.css`・frontmatter の CSS）の組。`targets` に `epub` か `kindle` があるときだけ | 知らせない。生成が解く（5.7）。解けなかった宣言だけ 🟡 |
| `vs build`（同梱でないテーマ） | 要素ごとの判定のうち、層ありで勝つ側が theme 層の組 | 🟡（§4.3 の今の決まりどおり） |
| `vs theme:check` | 静的な (c) | 🟡。「起きうる組」として示し、確定は `vs build` が行うと書く |

### 5.5 A に合わせて直す仕様の文

- `css-layer-restructure-spec.md` §2.1 の theme の理由: 「層が上なら、詳細度が低い規則でも勝つ」は PDF の話であると書く。EPUB と Kindle では、詳細度が同じなら層の順で勝ち、詳細度が低ければ負ける。部品の見た目を変えるテーマの規則は、**変数で変えるか、部品の規則と同じ選択子で書く**。
- 同 §7.1: `custom.css` は、PDF でも EPUB でも Kindle でも、詳細度に関係なく勝つ（EPUB と Kindle は 5.7 の生成による）。
- 同 §4.3: (2) を 5.4 に置き換える。許可の表の説明に、(c) が警報であることを書く。
- `theme-contract-spec.md` §3.5 の表に 1 行足す: 「部品の見た目を変える規則 — 変数で変える。規則で変えるときは、部品の規則と同じ選択子で書く（EPUB と Kindle では詳細度で勝ち負けが決まるため）」。
- 層の中の `!important` は禁止のまま（§2.4）。層の外（`custom.css`）は、平らな CSS で負ける宣言にだけ、生成が `!important` を付ける（5.7）。
- §2.2 の部扉と目次の記述と、§10.5 の「仕様と違えたこと」の 1 を、5.2 に合わせて直す。

### 5.7 層の外（`custom.css`）は、平らな CSS でも勝たせる（2026-11-15 ユーザーの指摘で変更）

はじめの答えは「`custom.css` が EPUB と Kindle で負ける規則を 🟡 で知らせ、vs の規則と同じ選択子（`body.vs-header-simple h2`）へ書き直してもらう」だった。これを取り下げる。著者は `## 見出し` が `h2` であることは知っているが、vs の内部の選択子は知らないし、知らせる必要も無い。直し方を vs が示せるなら、vs が生成の段で直す。

- **方法:** 5.4 の判定で、層ありで勝つ宣言が層の外にあり、平らでは層の中の宣言に負ける要素があるとき、その層の外の宣言に、平らな CSS の中でだけ `!important` を付ける。層の中に `!important` は無い（§2.4）ので、付けた宣言は詳細度に関係なく層の中の宣言に勝つ。選択子は変えないので、当たる要素は変わらない。
- **繰り返し:** 付けた結果、層の外の宣言どうしの勝ち負けが変わる要素があれば（詳細度の高い別の `custom.css` の宣言に勝ってしまう）、層ありで勝つ側にも付ける。層ありと平らで勝つ宣言が全部の要素でそろうまで繰り返す。付ける宣言は増える一方なので、必ず止まる。
- **解けない場合:** 次のときは付けずに 🟡 で知らせる。(1) 著者が自分で `!important` を付けた宣言と取り合う。(2) 付ける宣言が、`style` 属性で同じプロパティを指定している要素にも当たる（PDF では `style` 属性が勝つ）。知らせる文は「`custom.css` のこの指定は、EPUB と Kindle では効かない」と場所だけを示し、vs の選択子は見せない。
- **B と違う点:** `:not()` の重ねのような、KFX で確かめていない書き方を使わない。`!important` は 1.x が Kindle 用の規則で使っており（`kindle-css-compatibility-notes.md` の h4 の印）、届くことが分かっている。付けるのは実際に負ける宣言だけである。
- **確かめ（S3-3）:** `custom.css` に `h2 { margin-block-start: 2em; }` と `table { inline-size: 80%; }` を書いた写し（簡素な見出し・`.long-table` を含む）で、EPUB の Chromium の計算値と Kindle の中間生成物が PDF と同じ値になること。`custom.css` が空の本で、平らな CSS が変わらないこと。
