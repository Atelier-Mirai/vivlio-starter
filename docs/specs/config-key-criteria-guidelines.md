# そのキーは設定であるべきか — book.yml の取捨基準

対象: `config/book.yml` にキーを足す開発者・既存キーを見直す開発者
策定日: 2026-08-08（`book.yml` を 671 → 437 行へ減量した作業から抽出）

---

## 0. いつ読むか

- **新しい設定キーを足そうとしているとき。** 足す手順は `config-extension-guidelines.md`
  にあるが、その前に「そもそも足してよいか」を本書で問う
- **既存のキーが多すぎると感じたとき。** 減らす対象を選ぶ物差しとして

---

## 1. 大前提 — 載せると決めたキーは全部 `book.yml` に書く

著者が「どんな設定キーがあるか」を知る手段は、`book.yml` を開くことしかない。
ドキュメントを丹念に読む著者はほとんどいない。したがって `book.yml` は
設定ファイルであると同時に**設定の一覧カタログ**であり、コメントは削るべき贅肉ではなく機能である。

**減量は記法の圧縮で行ない、キーを隠すことでは行なわない。**

本書が問うのはその手前——**そのキーが存在してよいか**である。「載せるか隠すか」ではない。
存在してよいと決めたなら、必ず `book.yml` に書く。

---

## 2. 判断軸は 5 本

| 軸 | 問い | 該当したら |
| :--- | :--- | :--- |
| 手法パラメータか | その値を変えたとき、**比較先の基準も一緒に動くか** | 定数にする |
| 重複した入口か | 同じ目的を果たす**別の窓口**が既にあるか | 既存の窓口へ寄せる |
| CLI が一次インターフェースか | それは**その一回だけ**の指定か、本の性質か | コマンド引数にする |
| 選ぶ理由のない選択肢か | もう一方を選ぶ著者を**具体的に描けるか** | 固定する |
| 正しい警告を黙らせるだけか | 警告の**原因を直さずに**黙らせていないか | 原因側を直す |

以下、それぞれの実例と見分け方。

---

### 2.1 手法パラメータか

**問い: その値を変えたとき、比較先の基準も一緒に動くか。** 動かない（比較先が定数）なら、
それは設定ではなく計算方法そのものである。

**実例: `metrics.mattr_window`（削除）**

同一原稿（3 章・47,549 字）で窓幅だけ変えた実測。

| 窓幅 | MATTR | 評価 |
|---:|---:|---|
| 50 | 0.710 | 非常に豊富 |
| 100 | 0.589 | 標準的（既定・評価バンドはこの窓で較正） |

原稿を 1 文字も変えずに評価が 2 段階動く。比較先の 0.5 / 0.6 / 0.7 は
`formatter.rb` のハードコード定数で、窓幅と連動しない。**較正が黙って壊れる。**
しかも `book.yml` のコメントは「50〜100 が目安」と変更を勧めていた。

**対比: `metrics.readability.standard`（残した）**

これは 🤔 やや難解 の発火位置を決める。「うちの読者にはこれで適正」と線を動かすのは
著者が答えを持つ問いであり、動かしても他の指標の較正は壊れない。**編集判断は設定にする。**

**付随する注意:** 「著者が変更できない定数」の説明を `book.yml` のコメントに書かないこと。
設定ファイルに書いてあると変更できると誤解される。

---

### 2.2 重複した入口か

**問い: 同じ目的を果たす別の窓口が既にあるか。**

**実例: `spellcheck.extra_words` / `spellcheck.ignore_words` / `lint.disabled_terms`（削除）**

いずれも `config/spellcheck_allowlist.yml` `config/textlint_allowlist.yml` と同じ役目だった。
入口が 2 つあると、著者はどちらに書くべきか毎回迷う。

**入口の重複は本物のほうを壊す。** `extra_words` を削除して除外リストが唯一の経路になった際、
**そちらが実は壊れていた**ことが判明した——YAML の除外リストを辞書ファイルと同じ行単位で
読んでいたため、`- "High-Score"` が `-High-Score` として登録され、ハイフンを含む語の除外が
効いていなかった。入口が分散していたぶん一方の不具合が表に出にくかった。

窓口を 1 つに絞れば、そこが壊れればすぐ分かる。

---

### 2.3 CLI が一次インターフェースか

**問い: それは「その一回だけ」の指定か、それとも本の性質か。**

一回だけならコマンド引数である。本の性質なら設定である。

**実例: `index_glossary.library.path` / `.export_to` / `.import_from`（削除）**

索引ライブラリの書き出し先は「今回だけ別名で書き出す」類の指定で、本の性質ではない。
`vs index:export mybook.yml` と引数で言うほうが早いし、設定に書くと
「いま書き出したファイルはどこへ行ったのか」を `book.yml` に確認しに行くことになる。

**見分け方:** その値を書いた翌週にもう一度読み返すか。読み返さないなら引数である。

---

### 2.4 選ぶ理由のない選択肢か

**問い: もう一方を選ぶ著者を具体的に描けるか。** 描けないなら選択肢ではない。

**実例: `index_glossary.smart_context_cutting`（削除）**

文脈の切り出しで形態素境界を考慮するかどうか。`false` にすると語の途中で切れた文脈が出る。
**それを望む著者は存在しない。**

**実例: `vfm.hard_line_breaks`（削除）**

原稿中の改行を改行として組むか、スペース扱いにするか。日本語の技術書で後者を選ぶ場面が
描けず、必要なら章のフロントマターで上書きできる。

**選ばれない分岐は壊れていく。** `smart_context_cutting: false` の経路は実ビルドを一度も
通っておらず、削除するまで誰も気づかなかった。選択肢を用意するとは、その全分岐を
テストし続ける約束をすることである。

---

### 2.5 正しい警告を黙らせるだけか

**問い: その設定は、警告の原因を直さずに警告だけを消していないか。**

**実例: `preflight.allowed_classes`（削除）**

未知のコンテナクラス名を「既知」として登録するキーだった。だが `:::{.myawesome}` が
意味を持つのは `stylesheets/` に `.myawesome` の CSS を書いたからで、**CSS を書けば
チェックは自動的に既知と判定する**。CSS を書かずに使う独自クラスは、そもそも何も起きない。

つまりこのキーは「綴りを間違えていませんか」という**正しい警告を黙らせる**だけだった。
原因（CSS を書く）を直せば警告は消える。

**見分け方:** そのキーを使う著者は、警告が指摘した問題を解決したことになるか。
ならないなら、直すべきは原因側である。

---

## 3. 逆に、設定であるべきもの

5 軸はすべて「外す理由」である。**残す理由**は 2 つに集約される。

- **編集判断** — 著者が答えを持つ問い。対象読者・分量方針・判型・書体・出力形式
- **文体の選択** — 「サーバ」か「サーバー」か、強調にゴシックを使うか

どちらも**著者ごとに答えが違い、変えても他の基準を壊さない**。

---

## 4. 迷ったときの順序

1. **2.1 から 2.5 を順に当てる。** どれかに該当すれば設定にしない
2. **どれにも該当しなければ、残す理由（§3）を 1 文で書けるか試す。**
   書けないなら、まだ設定にする段階ではない
3. 残すと決めたら `config-extension-guidelines.md` の 3 ステップ
   （スキーマ登録 → 正規アクセス → 消費テスト）に従って足す

**「実装が N 箇所で参照している」は必要性の証拠にならない。** 件数ではなく中身を見て、
「著者が読む情報か」で判断する。

---

## 5. 外すと決めたら

`config-retirement-guidelines.md` の手順に従う。`RETIRED_CONFIG_KEYS` へ登録しないと、
旧 `book.yml` を持つ著者が「設定したのに効かない」という最悪の形に出会う。

参照側は `metrics_config[:x] || CONST` の形を残しておけば、既存プロジェクトの
`book.yml` に値が残っていても動く。
