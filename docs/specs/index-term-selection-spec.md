# 索引語の選別仕様書 — スコアの是正・閾値の規模非依存化・一般語の除外提案

> 作成日: 2026-08-02
> ステータス: **実装待ち**
> 対象: 「どの語を索引に載せるか」の決まり方。スコア式（`IndexCandidateExtractor`）、採否の閾値、登録済み語の見直し導線
> 前提: `index-code-protection-unification-spec.md` を先に実装すること（タグ付け結果が変わるため、混ぜると切り分けができない）
> 決定事項:
> - **スコアは出現由来の派生データである**。辞書には永続化せず、実行のたびに導出する（`index-glossary-consistency-spec.md` §0 の原則の延長。`backlink_sources` を辞書から外したのと同じ扱い）
> - 現行スコアは **TF を三重に計上**しており、「頻出＝高スコア＝自動承認」になっている。ボーナスを出現ごとの加算から**語ごと 1 回**へ改め、TF-IDF 本体も**対数 TF**にする
> - 目安語数は**刊行済み技術書 10 冊の実測**から決める（β=0.749・`index-size-calibration-data.md`）。**書籍タイプでは索引語数を予測できない**ことが実測で分かったので、設定キーは「本の種類」ではなく**索引の密度（編集方針）**にする
> - **`vs index:plan` は報告ではなく操作盤にする**。現況を並べるだけでは「260 語にしたいがどのキーをいくつにするか」に答えられない。設定候補・それぞれの目安・**約 N 字に 1 語**・書くべき YAML を示す（§6.2）
> - 採否は**本文の文字数から Heaps 則で導いた目安語数**で決める。ページ数は使わない——同じ原稿が A5 で 500 ページ、A4 で 350 ページになっても索引語の適正数は同じであるべきで、判型で 1.4 倍動くのは誤り（当初案のページ数推定は実測で 2.2 倍外れた）
> - **推奨候補は語数の過不足ではなく重要度で決める**。登録済みの語と未登録の候補を同じ土俵でスコア順に並べ、目安語数の枠内に食い込む未登録語を推奨とする。語数が目安に達していても、重要な語が未登録なら推奨に出る
> - **後方互換は取らない**。廃止キー（`auto_approve_threshold` / `review_threshold` / `high_candidates_ratio`）は読まず、書かれていたら 1 回だけ警告して移行を促す
> - 下見は `vs index:auto --dry-run` ではなく**独立したサブコマンド `vs index:plan`** にする。`auto` は「全自動でやる」と読めるコマンドで、オプション 1 つで「実は確認用」に変わるのは名前の意味をぶらす
> - 表示は**順位と語数**で言い、割合は出さない。「上位 60% まで」は語感から外れ、100 点満点に準えて逆の意味にも読める
> - 本の広い範囲に散らばる語（**一般語**）は、レビューファイルで `[-i]` を**あらかじめ付けた状態**で提示する。外すか残すかの判断は著者が行う（自動では外さない）
> - 「広さ」の判定は**章数の比率**で行う。絶対章数だと薄い本と厚い本で意味が変わる
> 較正データ: `index-size-calibration-data.md`（刊行済み技術書 10 冊の実測）
> 関連: `lib/vivlio_starter/cli/index/index_candidate_extractor.rb`, `scoring_engine.rb`, `unified_index_manager.rb`, `unified_terms_manager.rb`, `review_markdown_generator.rb`, `config/book.yml`, `index-main-reference-spec.md`（本仕様の `TermSpread` を使う）

## 0. 背景 — 索引の質は「載せる語」で決まる

索引の使い勝手は「参照の出し方」より前に「**どの語を載せるか**」でほぼ決まる。
「ファイル」「ページ」「コード」が索引にあれば、どれだけ体裁を整えても読者は引けない。

本書はその選別を扱う。参照の出し方（主要参照・太字・ページ範囲）は
`index-main-reference-spec.md` の担当で、**本仕様を先に入れる**——語が絞られてはじめて、
主要参照を指定すべき語の数が現実的になるためである。

## 1. 現状の実装事実（2026-08-02 実測・全 27 章 / 索引語 153 語）

### 1.1 レビュー帯が空である

| 帯 | 語数 |
|---|---|
| `score >= 300`（自動承認） | **127 語** |
| `150 <= score < 300`（レビュー対象） | **0 語** |
| `score < 150` | 26 語（すべて score 0 ＝ ライブラリ取込・手動マークアップ由来） |

スコアの中央値は 469、最大 7,728。`auto_approve_threshold: 300` は
**実質すべてを自動承認する値**になっており、著者が選別する機会が存在しない。

### 1.2 原因 — TF が三重に計上されている

スコアは 4 つの経路で加算されるが、**そのうち 3 つが出現ごとの加算**である。

| 経路 | コード | 加算 |
|---|---|---|
| 定義パターン | `index_candidate_extractor.rb:157` | `@term_scores[term] += 30` を **`scan` の各マッチで** |
| 専門用語パターン | 同 `:179` | `+= 15` を **各マッチで** |
| 名詞連続 | 同 `:231` | `+= 10` を **各出現で** |
| TF-IDF | 同 `:255` | `tfidf = tf * idf * 5` を**文書ごとに合算** ＝ `5 * idf * Σtf` |

4 経路すべてが出現数に線形なので、**スコアはほぼ出現数の写し**になる。
「専門用語パターン」はカタカナ 3 文字以上にも当たるため、「ファイル」は
371 回 × 15 = 5,565 点をここだけで得る。

結果、スコア上位は索引語として最悪の語で占められる:

```
PDF 7728 / ファイル 5269 / ビルド 3301 / コマンド 3153 / EPUB 3126 / ページ 2873 …
```

逆に索引語として優秀な「特殊相対性理論」「形態素解析」「ニュートン」は score 0 である
（自動抽出では拾われず、手で入れた語）。**索引語としての価値とスコアが逆相関している。**

### 1.3 語の広がり（実測）

| 出現章数 / 全章数 | 語数 | 性格 |
|---|---|---|
| **0.50 以上** | **20 語** | ファイル(23/27), Markdown(22), コマンド(21), ビルド(20), コード(20), PDF(20), プロジェクト(19), ページ(19), 技術書(17), インストール(17), データ(17), オプション(16), ディレクトリ(16), ブロック(16), コードブロック(15), スタイル(15), ツール(15), 章番号(14), Ruby(14), レイアウト(14) |
| 0.33 以上 0.50 未満 | 38 語 | 主要参照の指定が要る帯（`index-main-reference-spec.md` の担当） |
| 0.33 未満 | 95 語 | そのままで索引として機能する |

上の 20 語の大半は、**索引から外すべき語**である（「Markdown」「PDF」のように
本の主題そのもので残したい語も混ざるため、自動では外さない）。

## 2. 設計原則 — スコアは派生データ

`index-glossary-consistency-spec.md` §0 は、辞書を「**語彙の一次データ**」（語・読み・flags・
定義・承認状態）に限り、**出現情報は原稿から毎回導出する**と定めた。
`backlink_sources` を辞書から外したのはこの原則による。

`score` は出現回数と出現章数から算出される、まぎれもない**出現情報**である。
にもかかわらず辞書に永続化されており（`unified_terms_manager.rb:279`）、
原稿を推敲してもスコアは古いまま残る。`context` が stale 化したのと同じ構造である。

したがって本仕様では **`score` を辞書から外す**。副次的な利点として、
スコア式を変えても**移行問題が起きない**（旧スケールの値が残らない）。

## 3. 要件

### R1: ボーナスを「出現ごと」から「語ごと 1 回」へ

`extract_definition_patterns!` / `extract_technical_terms!` / `process_noun_sequence` の
加算を、その語について**一度だけ**にする。

```ruby
# 各抽出メソッドは「この語にこの性質がある」という事実だけを記録する
@term_flags[term] << :definition   # Set
@term_flags[term] << :technical
@term_flags[term] << :noun_sequence
```

集計時に一度だけ重みを掛ける:

```ruby
BONUS = { definition: 30, technical: 15, noun_sequence: 10 }.freeze
bonus = @term_flags[term].sum { BONUS[it] }
```

**context の記録は現状どおり出現ごとに続ける**（レビュー表示に使うため）。
変えるのはスコアへの加算だけである。

### R2: TF-IDF を対数 TF にする

```ruby
# 現行（index_candidate_extractor.rb:240-263）
#   @documents.each_value { tf = ...; @term_scores[term] += tf * idf * 5 }
#   ＝ 5 * idf * Σtf （TF に線形）
#
# 新
def calculate_tfidf_scores!
  return if @documents.empty?

  doc_count = @documents.size
  @term_scores.each_key do |term|
    tf = @documents.each_value.sum { it.scan(term).size }
    next if tf.zero?

    df  = @documents.each_value.count { it.include?(term) }
    idf = Math.log((doc_count + 1.0) / (df + 1.0)) + 1.0
    @term_scores[term] += (1 + Math.log(tf)) * idf * TFIDF_SCALE
  end
end
```

`TFIDF_SCALE` の既定は **30**。実データ（全 27 章 / 索引語 153 語）でのシミュレーション結果:

| | 新スコア | (tf, df) |
|---|---|---|
| アインシュタイン | **429** | (70, 4) |
| CommonMark | 405 | (15, 1) |
| 物理学 | 366 | (16, 2) |
| 用語集ページ | 353 | (14, 2) |
| … | | |
| コード | 232 | (151, 20) |
| コマンド | 231 | (182, 21) |
| プロジェクト | 228 | (108, 19) |
| Markdown | 208 | (122, 22) |

順位が正しく反転する（分布: min 109 / p25 249 / median 282 / p75 308 / max 429）。

**`TFIDF_SCALE` の値は採否に影響しない。** R3 で採否をスコアの絶対値ではなく順位で
決めるため、スケールは単調変換にすぎず順位を変えない。効くのはレビュー md の表示だけで、
閾値の再チューニングは要らない——これも絶対値の閾値を捨てたことの利点である。

**注意**: `ScoringEngine`（`scoring_engine.rb`）は同種の重み表を持つが、
`IndexCandidateExtractor` からは使われていない（`@term_scores` への直接加算のみ）。
本仕様では **`ScoringEngine` を正典化して `IndexCandidateExtractor` から使う**形に寄せ、
重み・スケール定数の定義箇所を 1 つにする。二重管理は `PLANNED.md`「既定値の二重管理」で
既に事故が報告されている形なので、ここで潰しておく。

### R3: 採否を「本文の分量から導いた目安語数」で決める

絶対値の閾値は、書籍の規模・語彙量・章数で意味が変わる。実際 §1.1 のとおり
既定値 300 は本書ではまったく機能していない。

**かといって「候補の上位 N%」も正しくない。** 候補の総数は抽出ヒューリスティクスが
何件拾ったかで決まる量で、**本の性質を何も表していない**。同じ原稿でも抽出器を
変えれば母数が動き、そのたびに採用語数が動く。著者が知りたいのは
「この本には索引語が何語あるべきか」であって「候補の上位何割か」ではない。

そこで採否は**目安語数（target terms）**で決める。目安は本文の分量から導き、
著者はその 1 つの数字だけを調整すればよい。

#### 3.1 目安語数の算出 — `IndexSizeEstimator`

**ページ数は使わない。文字数を使う。**

当初案はページ数から導いていたが、実測すると破綻していた。本書は
版面計算による推定 229 ページに対し、**実際にビルドすると A5 で約 500 ページ**である
（2.2 倍の乖離）。版面計算は地の文の密度しか見ておらず、コードブロック・図版・章扉・
改ページを勘定できない。

より本質的な理由がある。**同じ原稿が A5 で 500 ページ、A4 で 350 ページになっても、
索引語の適正数は同じであるべき**である。ページ数を基準にすると、判型を変えただけで
索引の目安が 1.4 倍動く。索引は本の中身の性質であって、紙の都合ではない。

#### 3.2 Heaps 則 — 索引語は分量に比例しない

索引語数は分量に**比例せず逓減する**。原稿が増えても既出語の再出現が多く、
新語の登場は鈍っていくためである（Heaps 則 `V = K × N^β`）。

```
目安語数 = 基準語数 × (本文文字数 / 50,000) ^ BETA
```

**`BETA = 0.749` は仮定ではなく実測値である。** 刊行済み技術書 10 冊の
本文文字数と索引語数を計測し、log-log 回帰で得た（→ `index-size-calibration-data.md`）。
3 倍の分量でも索引語は約 2.3 倍にしかならない。比例で計算すると厚い本ほど過大な目安が出る。

#### 3.2-1 基準語数は「書籍タイプ」ではなく「索引の密度」で決まる

**当初案は誤りだった。** `book_type: tutorial / standard / reference` という
3 段の設定で書籍タイプから目安を導こうとしたが、**実測はこれを支持しなかった**。

| 分類 | 5 万字換算の語数 | 中央値 | 範囲 |
|---|---|---|---|
| 入門書（5 冊） | 88, 118, 151, 226, 228 | 151 | 88〜228 |
| 一般的な技術書（5 冊） | 65, 151, 167, 171, 173 | 167 | 65〜173 |

**両群はほぼ完全に重なる。** 中央値の差は 10% で、群内のばらつき（2.6 倍）より
はるかに小さい。書籍タイプで目安を出す設定を置けば、
「入門書だから索引は薄くてよい」という**誤った因果を著者へ刷り込む**ことになる。

一方、実測値を値の順に並べると**明確な 3 群に分かれる**。

```
65, 88  ┊  118, 151, 151, 167, 171, 173  ┊  226, 228
       ↑ 30 の空き                        ↑ 53 の空き
```

そしてこの境目は書籍タイプと一致しない——各群に入門書と一般技術書が混在する。
実際に効いているのは**索引をどれだけ丁寧に拾うかという編集方針**である。

したがって目安は**索引の密度**（＝著者が自分で決められる編集方針）で選ぶ。
機械が本の種類から推測するものではない。設定キーは §3.4 のとおり `target_terms` 1 本にまとめる。

```ruby
BETA = 0.749
BASE_TERMS = {
  light:    (65..90),     # 控えめ: 主要な語だけを拾う（CPUの創りかた, github）
  standard: (120..175),   # 標準・既定（java-tutorial, whitehacker, 研鑽Ruby ほか 6 冊）
  thorough: (225..230)    # 丁寧: 初学者向けに広く拾う（java-tutorial-plus, 偉大な定理）
}.freeze

def target_range(chars, density)
  factor = (chars / 50_000.0)**BETA
  base = BASE_TERMS.fetch(density)
  ((base.begin * factor).round..(base.end * factor).round)
end
```

**目安は幅で出す。**単一の数字にすると「300 語ちょうどにする」という誤った目標になる。
帯の計算（§3.4）には**幅の上限**を使う——推奨候補を出し惜しみしないため。

#### 3.3 どの文字数を使うか — `total_char_count` 相当

**地の文の文字数**（コードブロックと Markdown 記法を除去し、空白を除いた長さ）を使う。
索引語は地の文からしか拾わない（`Masking` でコードを除外している）のに、
コード量が目安語数を押し上げるのは筋が通らないためである。

本書の実測（2026-08-02）:

| 数え方 | 文字数 | 目安語数（`standard`） |
|---|---|---|
| 生（改行除く。`vs metrics` が表示する数字） | 261,811 | 400〜583 語 |
| **地の文**（`total_char_count` 相当） | **128,839** | **240〜352 語** |

現在の登録は 153 語なので、**本書はどちらの基準でも索引語が大きく足りていない**（§3.5）。

なお **β の実測が地の文基準で 0.749、全文字基準で 0.816** となり、後者は Heaps 則の
想定域（0.6〜0.75）から外れる。コード量は索引語を増やさないので、コードを含めて数えると
「分量が増えても語が増えない」方向へ歪むためである。これも地の文を選ぶ根拠になる
（→ `index-size-calibration-data.md` §4）。

> **⚠ 前提に未決の論点がある。** `vs metrics` が著者に見せている「文字数」は
> 生のほう（261,811）で、地の文（128,839）はどこにも表示されていない。
> つまり著者は本仕様が使う数字を**見たことがない状態**になる。
> この食い違いは `metrics-char-count-basis-report.md` に切り出した。
> **索引の実装はその結論を待たない**（数字が 2 つあること自体は索引の問題ではない）。
> 結論が出たら本節の基準をそれに合わせること。

**計数は再実装しない。** `Metrics::Analyzer` の `extract_prose`
（`Masking.strip_code` ＋ `strip_markdown`）を公開 API へ引き上げて使う。
索引側で同じ除去処理を書き直すと、`vs metrics` の表示と黙ってずれる。

#### 3.4 設定キーは `target_terms` 1 本にする

**プリセット名と語数の 2 キーに分けない。** キーが 2 つあると「どちらを使うのか」で
迷う。1 本にして、**値の形で使い分ける**ほうが素直である。

```yaml
index:
  # 索引語数の目安。プリセット名か語数を直接書く
  target_terms: standard    # light / standard / thorough（刊行書 10 冊の実測）
  # target_terms: 260       # 語数を直接指定

  candidate_pool: 3.0       # 目安語数の何倍までを候補として提示するか
  auto_approve: false       # 推奨候補を自動承認するか（既定 false ＝ 著者が選ぶ）
```

`target_terms` の解釈:

| 値 | 意味 |
|---|---|
| `light` / `standard` / `thorough` | `BASE_TERMS` × Heaps 係数で**幅**を算出（既定は `standard`） |
| 整数（例 `260`） | その語数を目安とする（幅ではなく 1 点） |

**`auto_approve` の既定を false にする**のは、現状の 127 語自動承認がまさに
今回の問題を作ったからである。

**既存キー `high_candidates_ratio` は廃止する**。推奨／一般の分割は
目安語数が決めるので、比率で切り直す意味がなくなる。

#### 3.4-1 帯の決め方 — 語数の過不足ではなく「重要度」で決める

**「目安に達しているから推奨候補は 0 件」は誤りである。** 語数が足りていても、
スコアの高い語が未登録なら、それは索引に入るべき語である。逆に、
語数が足りなくても重要でない語を足す意味はない。

そこで**登録済みの語と未登録の候補を同じ土俵でスコア順に並べる**。

```
全語 = 登録済み索引語（M 語） ＋ 未登録候補（C 件）   … スコア降順に一列
```

| 帯 | 定義 | 意味 |
|---|---|---|
| **推奨候補** | 上位 N 位以内にいる**未登録**の語 | 目安の枠内に食い込むほど重要なのに、まだ索引に無い |
| **一般候補** | N 位〜N × `candidate_pool` 位の未登録語 | 選ぶ幅 |
| **見直し候補** | N 位より下にいる**登録済み**の語 | 枠外に押し出された語。§5 の一般語提示と合流させる |
| （提示しない） | それ以下 | 件数は必ず報告する |

`N` は目安語数（プリセット指定なら幅の**上限**、整数指定ならその値）。

この定義なら、**語数が目安に達していても推奨候補は出る**——登録済みの語より
スコアの高い未登録語があれば、それが上位 N に食い込むからである。
同時に「入れ替え」の視点が自然に得られる（推奨候補 5 語・見直し候補 5 語なら、
語数を変えずに索引の質だけを上げられる）。

**登録済み語にもスコアを付ける必要がある。** 抽出器の候補に現れない語
（手動マークアップ・ライブラリ取込）でも、同じ式（R1 + R2）で原稿から算出する。
算出できない語（原稿に出現しない＝死語）は最下位に置き、見直し候補へ回す。

#### 3.5 較正の根拠と限界

`BETA` と `BASE_TERMS` は**刊行済み技術書 10 冊の実測**による
（→ `index-size-calibration-data.md`。計測方法・精度の限界・生データはそちら）。

**限界を承知して使うこと**:

- **索引語数は ±10〜20% の誤差を含む**。PDF のテキスト抽出は 2 段組で語と
  ページ番号が別行になり、下位項目のインデントも失われる。実測値は
  「見出し語＋下位項目」に近い数で、やや過大の可能性がある
- **`thorough` の実測は 2 冊しかない**（226, 228）。幅が狭いのは冊数のせいで、
  その帯が本当に狭いことを意味しない
- **用語集を併設する本は索引が薄くなる**（`github` の実測 88 は、
  索引とは別に用語集を持つためと思われる）。`[i]` と `[g]` の配分を
  目安へどう反映するかは未検討

自著への当てはめ:

| | vivlio-starter | workbook |
|---|---|---|
| 地の文 | 128,839 字 | 341,590 字 |
| `light` | 130〜179 語 | 270〜371 語 |
| `standard` | **240〜352 語** | **498〜730 語** |
| `thorough` | 457〜463 語 | 949〜962 語 |

**本書の現在 153 語は基準 75 語相当で `light` 帯の下端**である。
分量の近い実測書（whitehacker 136,079 字 / 319 語、データ分析SQL 145,942 字 / 382 語）と
比べると、**標準的な密度の半分以下**しかない。

> ただし**語数を増やす前に中身を入れ替えるべき**である。現在の 153 語には
> 「ファイル」「ページ」「コマンド」のような一般語が 20 語含まれている（§1.3）。
> 数だけ合わせても索引の役には立たない。§3.4 の「推奨候補は重要度で決める」設計と
> §5 の一般語提示が噛み合って、はじめて語数の議論に意味が出る。

#### 3.6 旧キーは読まない。移行を促す

`auto_approve_threshold` / `review_threshold` / `high_candidates_ratio` が
`book.yml` に書かれていても**読まない**。書かれていたら 1 回だけ警告し、
新しい書き方を提示する（`warning-messages-actionable` の流儀）。

```
🟡 index.auto_approve_threshold は廃止されました（値: 300）
   索引語数はスコアの絶対値ではなく、本文の分量から導いた目安語数で決めます
   （Heaps 則。3 倍の分量でも索引語は約 2 倍にしかなりません）。
   config/book.yml の index: から次の 3 キーを削除してください:
     auto_approve_threshold / review_threshold / high_candidates_ratio
   代わりに指定するもの（いずれも省略可・既定で動きます）:
     target_terms: standard # light / standard / thorough、または語数（例 260）
     candidate_pool: 3.0    # 目安の何倍までを候補に出すか
```

**提示しなかった候補も黙らせない**（`no silent caps`）:

```
ℹ️ 550 位以下の 1,882 件は候補として提示していません
   増やすには config/book.yml の index.candidate_pool を上げてください（現在 3.0）
```

### R5: 一般語を `[-i]` 付きで提示する

#### 5.1 判定 — `TermSpread`

新設: `lib/vivlio_starter/cli/index/term_spread.rb`

```ruby
# 語が本のどれだけ広い範囲に散らばっているかを測る。
# 索引語としての価値は「広く出ること」ではなく「特定の箇所で説明されていること」なので、
# spread が大きい語ほど索引項目としては引きにくい。
#
# 判定は章数の比率で行う。絶対章数だと 5 章の薄い本と 50 章の本で意味が変わる。
TermSpread = Data.define(:term, :chapter_count, :total_chapters) do
  def ratio = total_chapters.zero? ? 0.0 : chapter_count.fdiv(total_chapters)
end
```

- 数え方は辞書の `pattern`（無ければ語の完全一致）を各章の本文へ当て、**1 章 1 回**と数える
- 本文は `CodeBlockStripper.strip` を通す（コード例の出現で膨らませない）
- **章数の下限**: 全章数が `MIN_CHAPTERS_FOR_SPREAD = 6` 未満の本では判定しない。
  5 章の本では 3 章に出るだけで比率 0.6 になり、誤検出しかしない
- **絶対下限**: `chapter_count < 3` の語は比率がいくつでも一般語としない

#### 5.2 提示 — レビュー md のサブセクション

`## 1. 登録済み用語の確認` の**内側**に置く。セクション番号を増やさないので、
`review_markdown_generator.rb` の既存パーサ（`## 4. 除外済みリスト` を境界に使う実装）に
影響しない。

```markdown
## 1. 登録済み用語の確認 (Terms: 153語)

### 一般語（索引から外すことを推奨・20語）

本の広い範囲に散らばっている語です。索引から引いても読者が「どこを読めばよいか」を
判断できないため、外すことを推奨します。
- 外す場合: [-i] のまま `vs index:apply`
- 残す場合: [i] に戻したうえで `主要参照:` を指定してください（未指定だとビルド時に警告されます）

- [-i] **ファイル** (ふぁいる) - 一般語: 23/27 章（85%）に出現
- [-i] **Markdown** (まーくだうん) - 一般語: 22/27 章（81%）に出現
…

### 登録語 (133語)

- [i] **アインシュタイン** (あいんしゅたいん) - スコア: 429.0
…
```

**行の書式は既存と同一**にする。追加情報は `- スコア: …` と同じ**行末の位置**へ置く
——`- [-i] ` と `**用語** (読み)` の間に何かを差し込むと、
`parse_index_rejected` ほか 6 つのパーサの正規表現
（`^- \[-i\](?: \`(?:NEW!|Today)\`)? \*\*(.+?)\*\* \(([^)]+)\)`）が**軒並みマッチしなくなる**。

`[-i]` は `parse_index_rejected` が拾い、`apply_markdown_review!` が
`remove_flag!(term, 'i')` ＋ `save_rejected_terms` を行う。**既存経路がそのまま使える**ので、
`apply` 側の変更は不要である。

#### 5.3 【保留】刊行書 10 冊由来のストップリストを足すか

`index-size-calibration-data.md` の 10 冊から、索引語の判定に使える語彙を 3 種抽出した（2026-08-02）。

| リスト | 語数 | 条件 |
|---|---|---|
| **Tier 1** 一般語 | 55 | 8 冊以上の本文に延べ 100 回以上出るが、**単独でも複合語でも索引に現れない**（利用・表示・内容・記述・説明 …） |
| **Tier 2** 単独不可語 | 36 | 単独では 1 冊も索引にしないが、**複合語としては 3 冊以上が採録**（コード・実行・処理・コマンド・条件 …） |
| 参考語彙 | 195 | 2 冊以上の索引に採録された語 |

**同梱するかは未決。** まず `TermSpread` だけで実装し、**リストの有無で抽出結果がどれだけ変わるかを実測してから決める**（差が小さければ同梱しない）。

- **参考語彙 195 語は同梱に向かない**。10 冊中 4 冊が Java/Ruby、2 冊が SQL/DB で、

  書籍固有語や、索引ページに載っていたメールアドレスの混入がある
- Tier 2 の `イン` `プロ` は **MeCab の分割誤り**。採用するなら要除去

#### 5.4 自動では外さない

「Markdown」「PDF」は本書の主題そのもので、著者が残したい語でありうる。
判断は著者に委ねる——`quantity-is-not-necessity` と同じ立場で、
機械は「広く散らばっている」という事実だけを示し、価値判断はしない。

### R6: `vs index:plan` — 索引の操作盤

#### 6.1 なぜ `index:auto --dry-run` ではないか

当初案は `vs index:auto --dry-run` だったが、これは**コマンド名の意味をぶらす**。
`auto` は「全自動でやってくれる」と読めるサブコマンドで、そこにオプションを 1 つ付けると
「実は語数確認用でした」に変わるのは筋が通らない。

**独立したサブコマンド `vs index:plan` を設ける。** 辞書もレビューファイルも書かない
読み取り専用コマンドである。

```
ワークフロー:
  0. vs index:plan   → 目安語数と現況を確認する（新設・任意）
  1. vs index:auto   → 候補抽出・_index_glossary_review.md 生成
  2. レビューファイルを編集
  3. vs index:apply  → 辞書を更新
  4. vs build        → 索引ページを含む PDF を生成
```

#### 6.2 【要点】報告ではなく操作盤にする

**`plan` は「いまこうなっています」を並べるだけでは意味がない。**
著者の問いは「**260 語にしたい。どのキーをいくつにすればよいか**」であり、
現況の羅列はその答えになっていない（Phase 1 実装後にユーザーから指摘・2026-08-02）。

したがって `plan` は次の 3 つを必ず示す。

1. **いまの設定と、そこから決まる目安**
2. **設定を変えたらどうなるか**（全プリセットの目安を並べる）
3. **書くべき YAML そのもの**

さらに **`約 N 字に 1 語` を併記する**。著者は「500 字に 1 語くらいで」という
**密度**で考えるのに対し、設定は語数で持つ。この列が両者をつなぐ橋になる。

```
$ vs index:plan

本文の分量: 27 章 / 129,006 字（コード・記法を除く地の文）
索引語の登録: 153 語

■ いまの目安（index.target_terms: standard）
    244〜356 語   ＝ 約 362〜528 字に 1 語
    現在 153 語は目安を 91 語下回っています（約 843 字に 1 語）

■ 設定を変えるとこうなります
    light       132〜183 語   約 704〜977 字に 1 語
    standard    244〜356 語   約 362〜528 字に 1 語   ← 現在
    thorough    458〜468 語   約 275〜281 字に 1 語

    語数を直接決める場合は config/book.yml に:
      index:
        target_terms: 260        # 約 496 字に 1 語

■ 候補
    4,255 件（登録済み 153 語と同じ土俵でスコア順）
      推奨候補   上位 356 位以内の未登録語     N 件
      一般候補   357〜1,068 位の未登録語      N 件
      見直し候補 356 位より下にいる登録済み語   N 件
      1,069 位以下の N 件は提示していません
        増やすには index.candidate_pool を上げてください（現在 3.0）

※ vs index:plan は下見です。辞書・レビューファイルは変更していません
```

**この表示が明かすこと**（実測・2026-08-02）: 「丁寧に拾いたい＝ 500 字に 1 語」は
実測では `thorough` ではなく **`standard` の下端**である。実測の `thorough`
（java-tutorial-plus・偉大な定理）は約 280 字に 1 語で、はるかに密だった。
**ラベルだけ見て `thorough` を選ぶと想定の倍近くになる**——この列があれば防げる。

#### 6.3 表示は `index:plan` と `index:auto` で同一にする

**`plan` だけの特別な画面は作らない。** 見え方が実行ごとに変わると、著者は
「下見で見た内容と本番が違うのでは」と疑うことになる。`index:auto` は
同じ内容を表示したうえで、辞書とレビューファイルを書く。違いは末尾の案内だけ。

#### 6.4 帯の呼び方 — 割合ではなく順位と語数で言う

当初案の「レビュー対象の帯（10%〜60%）」は 2 つの点で悪い。

- **上から何 % という言い方をしない**。「上位 60% まで」は日常の語感から外れており、
  さらに 100 点満点に準えて「60 点以上＝良いほう」と**逆の意味に読める**
- そもそも割合は §3 で捨てた。決まるのは語数と順位である

したがって表示は **順位（`357〜1,068 位`）と件数**で言い、割合は一切出さない。
帯の名前は**レビューファイルで既に使っている語をそのまま使う**——新語彙を導入しない
（`review_markdown_generator.rb` の `## 2. 推奨候補` / `## 3. 一般候補`）。

| 帯 | 表示名 | 由来 |
|---|---|---|
| 枠内に食い込む未登録語 | **推奨候補** | レビュー md §2 と同じ |
| 選ぶ幅 | **一般候補** | レビュー md §3 と同じ |
| 枠外へ出た登録済み語 | **見直し候補** | 新設（§5 の一般語提示と合流させる） |
| それ以下 | 名前を付けず「N 件は提示していません」 | 帯ではなく残余なので命名しない |

#### 6.5 実装

- `IndexPlanCommand`（`vs index:plan`）／ルーティング／ヘルプ **【実装済み・Phase 1】**
- 表示の組み立ては `IndexPlanReporter` に集約し、`plan` と `auto` の両方から呼ぶ。
  **2 箇所で別々に組み立てない** **【実装済み・Phase 1】**
- `plan` は `merge_terms!` / `record_scanned_chapters!` /
  `@markdown_generator.generate!` を一切呼ばない **【実装済み・Phase 1】**
- 目安・設定候補・字/語・候補の帯を表示へ足す **【Phase 2】**

3. **推奨候補が 0 件にならないこと**を確認する。現在 153 語で目安の下限を下回っているので、
   上位に食い込む未登録語が出るはずである（§3.4 の設計が効いている証拠）
4. `vs index:auto` → 一般語 20 語と見直し候補の提示を目視 → 残す語を `[i]` へ戻す
5. `vs index:apply` → 辞書が更新されること
6. `vs build` → 索引ページの `<dt>` 数が辞書の索引語数と一致すること
