# `vs upgrade` の競合レビューを、見える・選べる・終わるものにする

> 作成日: 2026-08-12
> ステータス: **実装待ち**
> 対象: 競合ファイルの diff が途中で切れ、**見ていない変更まで `y` で適用されてしまう**問題と、競合が多数になったときレビューが終わらない問題
> 関連: `lib/vivlio_starter/cli/upgrade.rb`（`unified_diff` / `render_hunks` / `confirm_conflict?` / `classify_managed`）
> 出自: 移行済みプロジェクトで `vs upgrade` を実地に通した観察（2026-08-12）。凡例の追加（`049f9a71`）は同じ観察から出た応急処置で、本仕様書はその先を扱う

## 0. なぜこの仕様書があるか

実地の観察で、著者が**承認していない変更を承認してしまった**。

雛形側で 25 行目（絵文字）、著者側で 93 行目（色）と、**別の場所**を変えた状態で `vs upgrade` を実行した。画面に出たのは 25 行目の変更だけで、末尾は `… 残り 56 行（[d] で全文表示）` と切れていた。著者は「絵文字の変更なら良い」と判断して `y` を押し、**93 行目の自分の変更が消えた**。

> 「本のマークの変更なら OK」というつもりで `y` を選んだら、他の場所は見せてもらっていないのに承認扱いになってしまう

バックアップは残るが、**失われたことに気づけない**のが問題である。

## 1. 真因：diff が「ハンク」になっていない

```ruby
prefix = 共通の先頭行数
suffix = 共通の末尾行数
old_mid = old_lines[prefix...(old_lines.size - suffix)]
ops = lcs_diff(old_mid, new_mid)
```

**最初の変更から最後の変更までを、間の無変更行ごと 1 つの塊にしている。** 本物の unified diff なら、離れた変更は別々のハンクになり、間の無変更行は出ない。

上の実例で切り捨てられた 56 行は、**ほとんどが無変更行**だった（`body { font-family: … }` など）。情報量がほぼ無いものが、肝心の削除行を画面外へ押し出していた。ハンクに分けていれば全体で 12 行程度に収まり、**プレビューに全部入っていた**。

つまり「プレビューが短すぎる」のではなく、**diff が無駄に長い**。

## 2. 規模の見積もり

| | 数 |
| --- | --- |
| 雛形が管理するファイル | 7,748 |
| lock が追跡するファイル | 7,737 |
| うち画像（Twemoji 等） | 7,560 |
| CSS | 27 ／ 原稿 27 |

**画像はバイナリで、diff が出ない（「バイナリファイルのため diff を表示できません」）。** レビューの実質的な対象は CSS・原稿・設定の 200 弱である。

とはいえ**移行してきたプロジェクトでは、そのほとんどが競合になり得る**。実測: 旧版（gem リポジトリのフォーク）を複製して `vs upgrade --dry-run` を実行したところ、**26 ファイルすべてが競合**と判定された。手で持ってきたファイルは lock と食い違うためである。

**逐一 y/n を求める設計は、この規模では破綻する。**

## 3. 設計：まず数を減らし、残ったものを見えるようにする

「一括適用」の選択肢を足すのは**諦めであって解決ではない**。順序を逆にする。

### 3.1 減らす（構造で）

#### (a) 同じ内容に行き着いたものは競合ではない

```ruby
if lock_digest.nil?             then current == scaffold ? :latest : :conflict
elsif scaffold == lock          then :latest
elsif current == lock           then :update
else                                 :conflict     # ← ここへ落ちる
end
```

判定はすべて lock との比較で、**「双方が同じ内容に到達した」ことを見ていない**。手でファイルを持ってきた移行者は必ずここを踏む。

```ruby
elsif current == scaffold then :latest   # 別経路で同じ内容に到達した
```

を `:conflict` の手前へ足す。**実測で 1 件、移行直後のプロジェクトでは大半がこれに当たる。**

#### (b) 重ならない変更は自動で合流させる

lock は `vs new` 当時の内容、つまり**共通祖先**である。3-way マージの材料はすでにそろっている。

冒頭の実例（雛形が 25 行目・著者が 93 行目）は**重なっていない**ので、自動で両立できる。著者に聞く必要はない。

聞くのは**本当に同じ箇所を双方が変えたとき**だけに絞る。

### 3.2 見えるようにする（残った競合について）

#### (c) ハンク分割

無変更行が `CONTEXT_LINES × 2` を超えたらハンクを区切る。標準の unified diff と同じ規則。

#### (d) 要約を先に出す

```
競合 stylesheets/preface.css: 変更 2 箇所（+3 / -2 行）
```

ハンク分割で大半は全文が収まるが、それでも切れる場合に「まだある」ことが分かる。**`y` は見たものだけでなく全部に効く**——この一致しない期待こそが事故の原因だった。

#### (e) 失われるものを名指しする

```
⚠️ 適用すると、あなたの変更 1 箇所が失われます（バックアップ: .cache/vs/upgrade-backup/…）
```

3-way マージ後に残った競合は、定義上「著者の変更が消える」場所である。それを明示する。

### 3.3 終わらせる（それでも多いとき）

残った競合に対してのみ、まとめて処理する手段を用意する。

| キー | 動作 |
| --- | --- |
| `y` / `n` | このファイルを適用 / スキップ（現行） |
| `d` | diff 全文（現行） |
| `a` | **以降すべて適用** |
| `s` | **以降すべてスキップ** |
| `q` | **中断**（ここまでの適用は保持） |

`a` / `s` は `git add -p` の慣習に合わせる。**3.1 で数を減らしたうえでの最後の逃げ道**であり、これ単体を最初に足してはならない——見ずに承認する道を広げるだけになる。

## 4. 実装順序

1. **(a) 同一内容の誤検知**（1 行）— 移行者の競合数が激減する。単独で価値があり、他と独立
2. **(c) ハンク分割 ＋ (d) 要約** — 事故の直接の原因。ここまでで「見えない承認」は消える
3. **(e) 失われるものの明示** — (b) の前でも意味がある
4. **(b) 3-way マージ** — 最大の効果だが最大の規模。1〜3 が入っていれば、これが無くても実害は小さい
5. **(f) 一括操作キー** — (b) の後で、残った件数を見てから必要性を判断する

**1〜2 を入れれば事故は防げる。** 3 以降は体験の改善であり、リリースとの兼ね合いで切ってよい。

## 5. テスト

`notation-implementation-guide.md` §7 の流儀に従う。

1. **分類**: 現物と雛形が同一で lock だけ古い → `:latest`（競合にしない）
2. **ハンク**: 離れた 2 箇所の変更が 2 ハンクに分かれ、間の無変更行が出ない
3. **要約**: ハンク数と増減行数が prompt より前に出る
4. **切り詰め**: プレビューが切れるときは「全部に効く」と分かる文言が出る
5. **失われる変更**: 著者の変更を含む競合で警告が出る
6. **3-way**: 重ならない変更が自動合流し、重なる変更だけ質問になる
7. **一括操作**: `a` で以降が適用され、`q` で中断してもそこまでの適用が残る

いずれも実ビルドを伴わない（`upgrade_commands_test.rb` は一時ディレクトリと DI で完結している）。

## 6. 備考：応急処置との関係

2026-08-12 に凡例（`- いまのあなたのファイル / + 新しい雛形`）を追加した（`049f9a71`）。あれは「どちらが自分か分からない」という別の観察への対処で、本仕様書の (c)〜(e) とは独立している。**凡例があっても、見えていない変更は承認されてしまう**——観察の順序がそのまま、問題の層の深さの順序になっていた。
