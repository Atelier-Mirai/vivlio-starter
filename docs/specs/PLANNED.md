# Planned（将来計画）

本システムの将来対応・改善アイデアを目的別に整理する。

- 見出しは目的別の `##`／`###` に統一し、各項目は `-` の箇条書きで記す。
- 優先度は行頭に `[High]` / `[Medium]` / `[Low]` で付す（未判定のものは付けない）。
- 既存仕様書がある項目は末尾にファイル名を添える（`docs/specs/` / `docs/archives/` は付けない。実装後に移動しても壊れないようにするため）。

## Version 2.0 構想（メジャーアップデート）

後方互換を破る大きな方向転換を伴うため、v2.0 でまとめて取り組む。

- [High] **小説（挿絵入り）への対応**: 現在は技術書専用。小説向けレイアウト（縦書き・挿絵配置・章扉など）に対応できるようテーマ／組版を拡張する。
- [High] **テーマシステムの実装**: vivliostyle 公式の `bunko.css` などの既存テーマ CSS を活用。`book.yml` からのテーマ選択、CSS の動的切り替え、小説用縦書き・技術書用横書きのプリセット提供。
- [Low] **CLI 終了コードの体系化**: 現状「正常 0 / 問題あり 1」の 2 値を、UNIX 慣例（例: grep の 0=見つかった / 1=見つからない / 2=エラー）に倣いエラー種別ごとに分ける。影響範囲が広く後方互換を破るため v2.0 で対応。

## ビルド / 出力

- [Low] **画像の width 属性自動補完**: `![](foo.png)` のように幅指定なしでも、実寸やクラス指定に応じて `width=100%` 等を自動補う（大判図をページ送りにせず収めるため）。
- [Medium] **「表1＋背＋表4 を 1 枚にくるみ表紙」の形**: 入稿先の慣習でくるみ表紙を求められる場合も有るが、結合処理を伴う別機能になるため、現状は非対応。

- [Low] **版面の分断を機械が見つける**: `page.section_pagebreak: false` を選ぶと、見出しやキャプションがページ末尾に取り残される事故が起こりうる。節が必ずページ先頭から始まっていた頃は**原理的に起きなかった**ので、防御が無かった。**判明していた 2 種は CSS で塞いだ**（2026-08-10）ので、残るのは「塞ぎ漏れを見つける」仕組みの話。
  - **見出しの孤立は PDF では起きない**。`break-after: avoid` を足したが、**PDF ではこの宣言の有無で結果が変わらない**——Vivliostyle が既に見出しを次の内容と一緒に送るためで、「見出しは収まるが続く 1 行が収まらない」高さを B5・spacer 176〜196mm の 1mm 刻みで探しても孤立する組み合わせが無かった。宣言は EPUB / Kindle 向けの保険として残してある。
  - **キャプションの孤立は起きた**。同じ条件でも `<p class="table-caption">` / `.code-caption` は後続の表・コードと一緒に送られない。A/B 実測で **規則なし 8/14・規則あり 0/14**、本書でも実在の分断が 2 件あった（リスト 6-1・6-2）。`break-after: avoid` で解消（`table.css`）。Re:VIEW Starter の `caption_needspace` 相当。
  - **検出は描画結果に対して行う**。`pdftotext` の抽出順は視覚順と一致せず**単独では使えない**——本書 449 ページを「ページ末尾の行が見出し／キャプションか」で走査すると、見出しで 2 件・キャプションで 3 件挙がったが、**見出しは 2 件とも、キャプションは 1 件が誤検出**だった（後ろに内容があるのに抽出順の都合で最後に来ていた）。Vivliostyle の組版結果か PDF のテキスト描画座標を併用する必要がある。
  - **原稿側の「取り残した改ページ」は 2026-08-16 に実装済み**（`Guards::StrayPageBreakCheck`・`vs preflight` の 🟡）。描画結果を見る必要がなく原稿だけで判定できるため、残る 2 種より先に片づいた。**判型を変えた直後こそ走らせたい**——版面が変わると「たまたま目立たなかった」箇所が浮かぶ（この項目自体、B5 → A4 の変更で 4 件が露見して立った）。
  - 出し方はビルド後の 🟡 か `vs preflight` の一部。指摘には**ページ番号と見出し／キャプション名**を添え、`@pagebreak` で個別に逃がす道を示す。
  - 関連: `page-break-control-spec.md`（`---`＋`##` の二重改ページ正規化）・`chapter-pagebreak-spec.md`

- [Medium] **素の表記を TeX 記法へ起こす**: 著者が `2^(1/3)`・`√(πr²)`・`π` のように素で書いた数式を、`$2^{1/3}$`・`$\sqrt{\pi r^2}$`・`$\pi$` の TeX 記法へ変換し、通常の数式経路（LaTeX → SVG）に乗せる。逆向き（TeX → 素の表記。Kindle でフォントサイズに追従させるため）は `MathTextRenderer` として実装済みで、その対になる → `kindle-inline-math-textify-spec.md`

## 記法・置換ルール

- **`@` ディレクティブの拡張**: Tier 2（`@nobr`・`@fill`・`@index`）と `@abbr` の代替案（用語集統合 or 標準 `*[…]:` `<abbr>`）はブレスト段階 → `at-directive-ideas.md`

- [Medium] **目次ラベルが `@` ディレクティブを解釈してしまう**: 見出しの中でインラインコードとして書いた記法（`` ### 改ページ `@pagebreak` ``）は、本文では `<code>` に守られて無傷だが、**目次ラベルはバッククォートの落ちた素のテキスト**（`data-heading` 由来）なので、そこへ置換ルールが当たる。実測: 本書の目次で `改ページ <div class="vs-break-page"></div>` が生まれていた（`<span>` の中に `<div>` が入る不正な入れ子でもある）。いまは実害が出ていない——改ページ記法の CSS を生成ページへ配っていないため（`pagebreak.css` のコメント参照）。ただし**記法を解説する本では踏みやすい形**なので、いずれ塞ぐ。
  - 直し方の候補: (1) 目次ラベルを `data-heading` の素テキストでなく見出しの内側 HTML（`<code>` を保った形）から作る、(2) 生成ページ（`_toc` ほか）を `@` ディレクティブ置換の対象から外す。(1) のほうが「記法は原稿にだけ効く」という筋に合うが、索引タグ（`.index-term`）など見出し内の他の装飾をどう落とすかの整理が要る。

- [Medium] **`vs furigana`（半自動ルビ付与）**: 小学生向けなど、対象読者の学年より上の漢字へ振り仮名 `{漢字|よみ}` を**半自動**で付けるコマンド。`vs metrics` の「漢字レベル（ルビ候補）」で**どの漢字が対象か**は把握できるので、その先の「本文へ実際にルビ記法を書き込む」変換を担う。
  - **対象の指定**: `book.yml` や引数で「基準レベル」を選ぶ（例: 小4向け＝小5以上／中学以上／常用外のみ、等。レベル定義は `furigana-level-spec.md` 参照＝`vs metrics` と共通の L0〜L4）。
  - **読みの生成と限界（最重要）**: 読みは MeCab から得るが、**まさにルビを振りたい稀な漢字（未知語）で最も外れる**（例「碍子」は `碍` が非常用で未知語となり誤分割・誤読になりやすい）。よって**全自動で正確なルビは不可能**という前提に立ち、(1) 読みが不確実・未知の語にはルビを付けずに**警告＋出現箇所を提示**して著者に委ねる、(2) 付けたルビも**要確認**として一覧化する、という半自動方式にする。将来的に漢字→音訓の補助辞書でカバー率を上げる。
  - **補助辞書の種はもう手元にある**（2026-08-18）: 交ぜ書き辞書（`mazegaki_dictionary.rb`）は「かな書き → 漢字表記」の対がそのまま**表外漢字の読み**になっている。`だ円 → 楕円` の「だ」は「楕」の読みであり、共通の接頭辞・接尾辞を削るだけで機械的に取り出せる。**実測: 140 語から 139 件・ユニーク 125 字**が得られ、同じ字に別の読みが付いた衝突は 1 字だけだった（`鬱` の「うつ」と「うっ」＝促音便で実質同じ）。
    - **上の「碍子」の例がそのまま解ける。** `がい子 → 碍子`・`障がい → 障碍`・`障がい者 → 障碍者` の 3 経路すべてが `碍 → がい` で一致する。`閏 → うるう` も 3 経路一致、`閾 → しきい`・`籤 → くじ`・`爬 → は`・`冪 → べき` も取れる。**MeCab が最も外す領域と、この辞書が覆う領域が重なっている**のが要点で、常用漢字の読みは MeCab が正しく返すため補う必要がない。
    - **限界**: (1) 熟語由来なので**音読みに偏る**（訓読み・送り仮名のある語は取れない）、(2) 連濁が混じる（`子ども → 子供` から `供 → ども` が出るが、字の読みは「とも」。**語単位の読みとしては正しい**ので、字へ分解せず語のまま使うほうが安全）、(3) 語数は辞書の規模なりで、ルビが要る語全体から見れば小さい。
    - 抽出ロジックは本体に置いていない（使う側が無いうちに作っても腐るため）。`vs furigana` に着手するときに `MazegakiDictionary.readings` として起こす。`KANJI_CHOICE`（`障害者 → 障碍者`）は漢字どうしの対応なので、かな側が読みでないことを見て自動で外れる。
  - **安全性・冪等性**: ファイルを改変するため、(1) 既に `{…|…}` でルビ済みの箇所を二重化しない、(2) コードブロック・URL・既存ルビ内は対象外、(3) `--dry-run` で差分プレビュー、(4) バックアップ or Git 前提。`vs metrics` は読み取り専用の統計に徹し、書き込み系はこの `vs furigana` に分離する。

- [Low] **交ぜ書き辞書を prh 形式で外部公開する（1.0 の後）**: `mazegaki_dictionary.rb` の 140 語は、調べた範囲で**既存のどこにも無いデータ**である（RubyGems に交ぜ書き検出の gem は無く、npm の `mazegaki` は 0 件、textlint の日本語ルールは `ja-hiragana-*` のように**すべて逆方向**、prh 公式辞書 3155 行にも表外漢字を `expected` にする規則は 1 つも無い。2026-08-18 実測）。公開すれば textlint 利用者がそのまま使える。
  - **形態は prh の YAML が最有力。** データだけで済み実装コストがゼロで、利用者は `rulePaths` に 1 行足すだけで使える。制約つきの語（`(?<!ん)だ円`）も prh は正規表現を受け、後読みは Node が対応している。**Ruby gem 化は優先度が低い**——Ruby には日本語校正のエコシステムがほぼ無く（あるのは textlint ラッパー 3 つだけ）、使う土壌の無いところへ配ることになる。textlint ルール（npm）としての実装も、prh 辞書で足りるぶん重複になる。
  - **二重管理を避ける形**: **正典は Ruby 側（`mazegaki_dictionary.rb`）に置き、prh YAML は生成物にする**。辞書を足すのは Ruby だけ、公開物は rake タスクで毎回吐き直す。生成は 30 行程度で書ける。逆向き（YAML を正典に Ruby が読む）にすると、gem 同梱物が増えるうえ採否の理由コメントが YAML へ移せない。
  - **振り仮名側は `vs furigana` の実装後**。いま公開できるのは「表外漢字 125 字の読み」という素材だけで、語単位か字単位か・連濁をどう扱うかは実装が決める。形が決まる前に配ると、後から互換を壊すことになる。
  - **1.0 より前に出さない理由**: 公開すると issue と PR の受け口が増え、辞書は「この語も入れて」が来やすい。採否の基準は実際に 2 度動いており（§`lint-japanese-prose-rules-spec.md` 実装記録）、`かく乱` は誤った理由で一度落として後から救っている。**この判断を外部から継続的に求められる状態**を 1.0 前に抱えるのは重い。

- [Low] **交ぜ書き語を原稿から集めて辞書を育てる**: 辞書は gem 側にあり著者が足せないため、**「この語も交ぜ書きだ」と気づいても行き先がない**。140 語は出発点にすぎず、語彙は実際の原稿からしか育たない。集め方には 3 つの向きがある。
  - **案 1: 候補を機械が挙げる（`vs lint --suggest` 等）。** 交ぜ書きは「かな 1〜3 字＋漢字」という**形**を持つので、MeCab で 1 形態素として認識される語のうち、かなと漢字が混在し辞書に無いものを候補にできる。MeCab は索引・メトリクス・見出し分割で既に使っている。**`vs index:auto` と同じ流儀**（候補抽出 → レビュー用ファイル → 著者が選ぶ）に載せられるのが利点で、新しい操作を覚えなくて済む。
    - **ノイズの絞り込みが肝。** 素朴にやると「お願い」「引き出し」「取り消し」のような**正当なかな漢字混在語**が大量に混じる。効きそうな条件は (1) 1 形態素であること、(2) かな部分が 3 字以下、(3) **漢字部分が常用漢字表外を含む**——(3) の判定は `furigana-level-spec.md` の L0〜L4（`vs metrics` と共通）が既に持っている。それでも「送り仮名を伴う動詞」は残るので、品詞が名詞のものに限るとよい。
    - **著者の手元で完結する**のがこの案の強みで、報告に依存しない。本体の辞書へ還るかは別問題だが、少なくともその著者の原稿は直る。
    - **候補の種には Mozc 用の交ぜ書き抑制辞書が使える**（`akirakubo/mazegaki`・5177 語・BSD-3-Clause / Copyright 2010-2016 Google Inc.）。MeCab で形から拾うより精度が高い。ただし**`--fix` する辞書へ直接入れてはならない**（この項目の末尾を参照）。取り込む場合は BSD の条件として**著作権表示とライセンス条文の保持が必須**で、`LICENSE` とは別に出所を明記したファイルが要る。
  - **案 2: 著者辞書（`config/mazegaki_extra.yml`）。** 分野固有の語を著者が足せる窓口で、`textlint_allowlist.yml`（黙らせる）の対になる。ただし**集約の仕組みではない**——足された語が本体へ届くかは著者の報告次第である。公開後なら PR の受け口として機能する。
  - **案 3: `allowlist` に足された語を見る（逆向き）。** 「この語はかなで通す」と登録された語は、**辞書が過剰だった証拠**である。集まれば採否基準の較正に使える（`ひな型`・`かぎ括弧` は本書で実際にその候補になった）。これも著者が知らせない限り届かない。
  - **順序**: 案 1 が単独で価値を持つので先。案 2・3 は公開して受け口ができてからで足りる。
  - **外部辞書をそのまま `--fix` に載せると原稿が壊れる**（2026-08-18 実測）。上記 Mozc 辞書の 4720 語（既存 140 語との重複を除いた分）を手元の日本語テキスト **450 ファイル・438 万字**へ当てたところ、**59 種・439 箇所**が当たり、上位はすべて誤検出だった。
    - `合し → 合祀` **98 箇所**（「結**合し**た」「統**合し**て」）／`が解 → 瓦解` **73 箇所**（「これ**が解**析」）／`側が → 側臥` **52 箇所**（「呼び出し**側が**」）／`も本 → 摸本` **35 箇所**／`目と → 目睹` **21 箇所**。`--fix` を掛ければ「結合した」が「結合祀た」になる。
    - **原因は用途の違いで、辞書の質ではない。** Mozc の抑制辞書は「**読みが一致する語対**」を機械抽出したもので、「ごうし」という読みの文脈でのみ候補を抑制する。こちらは文字列置換なので読みを見ず、「あわし」と読む箇所まで当たる。**リスクも非対称**——あちらは誤っても変換できないだけだが、こちらは原稿が書き換わる。作者自身が README に「語の意味は考慮されていません」「変な語が登録されている可能性があります」と明記している。
    - **こちらの辞書の裏付けにはなった。** 140 語のうち **79 語（56%）が Mozc 辞書にも存在**し、独立に作られた辞書と一致した。残り 61 語はこちらにしかない（`しきい値`・`べき乗`・`障がい`・`うるう年` など）。また誤検出した 59 種を除く **4661 語はコーパスで一度も誤爆しなかった**——安全性の証明にはならないが、良質な語が埋もれている可能性は高い。
    - **辞書へ直接取り込むなら 1 語ずつの検証が要る。** 4700 語を手で見るのは非現実的なので、自動選別の基準を先に決めること（かな部分が 2 字以上／`此の方`・`仕上り巾` のような現代表記でないものを除く／活用形・語幹 384 件を除く／正解が 2 つ以上ある 378 語は `--fix` で選べないので除く）。

## EPUB / Kindle

- [Low] **ポップアップ脚注（`epub:type="noteref"` / `"footnote"`）**: 参照番号をタップすると脚注が小窓で開く方式。Kindle(KFX)・Apple Books が対応しており、非対応リーダーは現状どおり本文に流し込まれるだけなので**加えるだけで壊れない**（追加であって置き換えではない）。2026-08-02 に脚注を「左罫つきの注記ブロック」として本文と切り分けたので**当面は不要**——参照の直後に読める形になっている。読者から「本文が脚注で分断される」という声が出たときに着手する。
  - **前提はすでに揃っている**（2026-08-02 に生成物で実測）。着手時に構造を作り直す必要はない。
    - `<html>` に `xmlns:epub="http://www.idpf.org/2007/ops"` が宣言済み（名前空間の追加作業は不要）
    - 参照リンク `<a id="fnref1" href="…#fn1">` の飛び先が `aside` の `id` と正確に対応している（`fn1`/`fn2`/`fn3`）
    - 段落内インライン span の `id` は `strip_inline_footnote_ids_for_epub!` が除去済みなので、`#fnN` の解決先が `aside` に一意（ポップアップの対象が曖昧にならない）
  - **作業は属性 2 つ**。`EpubBuilder#decorate_footnotes_for_epub!` が既に `aside.page-footnote-print[data-footnote-number]` を走査しているので、そこで `aside['epub:type'] = 'footnote'` を、対応する `a#fnrefN` に `epub:type="noteref"` を付ける。
  - **確認は実機で**。KFX のポップアップは epubcheck では検証できず、Kindle Previewer で開くしかない（`kindle-css-compatibility-notes.md` の実機確認の流儀に従う）。ポップアップ化すると `aside` は本文に出なくなるため、**CSS 側の注記ブロック体裁（`body.vs-epub aside.page-footnote`）を残すか外すか**も同時に判断する。

- **Kindle 実機での確認**（`image-format-per-target-spec.md` の残り）: 2026-08-17 に PDF・EPUB とも画像を大きく作り替えたので、KFX の表示を Kindle Previewer で確かめたい。素材そのものは 1 バイトも変わっていないため理屈上は影響しないが、Kindle 向けの画素数が版面基準の縮小で下がった（画面幅 1024px × 紙面で占めていた割合）。特に**版面の半分に置いた図が 493px 程度まで落ちる**ので、拡大表示したときの粗さを目視で見ておく。確認の流儀は `kindle-css-compatibility-notes.md` に従う。
- [Low] **Kindle 固定レイアウト（`kindle.layout: fixed`・PDF ラスタライズ流用）**: A5 PDF をページ画像化して固定レイアウト KPF にする案。劣化対応不要で組版忠実だが、主力端末 6〜7″ は文庫（A6）サイズで判型が合わず、フォント可変・検索・配信料（約 ¥50〜90/冊 増）を失うため**見送り**。数式・図版主体の本や文庫判型向けの第 3 ターゲットとして RC 後に再検討。調査結果・実装スケッチ → `kindle-fixed-layout-ideas.md`

## 開発者体験 / CLI UX

- [Medium] **`vs import` を `.re` 直変換にする（RC 後）**: いまは 2 段階——Re:VIEW Starter 同梱の Ruby で `.re` → Markdown へ変換させ、その Markdown を追従変換し、**さらに `.re` を読み直して失われた構造を復元**している。この形をやめ、`.re` から直接 Vivlio の Markdown を書き出す。

  **なぜやるか（＝寿命）**。`lib/tasks/starter.rake` は `gem install review --version 2.5` と**バージョンを固定**しており、Re:VIEW 本体はその後もメジャーバージョンを重ねている。Re:VIEW Starter の開発は停止しているため、Ruby が進んで 2.5 が動かなくなっても直す人がいない。**`rake markdown` が動かなくなった時点で現在の `vs import` は丸ごと死ぬ。**直変換なら著者の `.re` さえあれば何年後でも取り込める。設計の美しさではなく、移行ツールとしての存続の話。

  **なぜ「マーカー注入」を採らないか**。先方の builder を `prepend` で包んで構造マーカーを吐かせれば復元コードは消せるが、**Re:VIEW Starter にはライセンス表記が一切ない**（配布物にも `lib/ruby/*.rb` のヘッダにも公式ページにも記載なし。2026-08-10 確認）。作者は活動停止しており確認もできない。`prepend` は改変にも複製にもあたらないと理解しているが、疑義ゼロの領域（著者自身の原稿を読む）から不明な領域へ踏み込む理由がない。

- **A4 以外の判型での目次・索引・用語集**: この 3 ページは長らく `book-settings.css` を読んでおらず、`page-settings.css` の `@page { size: 210mm 297mm }` で **A4 固定**に組まれていた（`chapter-pagebreak-spec.md` §7.2 で link を追加して解消）。A5 / B5 でのビルド確認は未実施。
- **既定値の二重管理**: `page.section_pagebreak` などの既定が `common.rb` のスキーマと同梱 `book.yml` の両方にあり、黙ってずれる（実例: `section_page_break` 改名時にスキャフォールドが取り残された）。案 A = 既定値専用 YAML（`lib/vivlio_starter/config/defaults.yml`）を新設してスキーマをそこから読む／案 B = 同梱 `book.yml` とコード側既定の**キー名の対応**、および `theme.css` のフォールバック値とコード側定数の一致を、回帰テストで固定する。**スキャフォールドの `book.yml` を既定値の情報源にするのは不可**——あれは `copy_to_scaffold.rb` が root から作る「サンプル本の設定」で、`theme.color: red` のような本書固有の値と `{{MAIN_TITLE}}` のテンプレート記法が混ざっている。

  **資料: 既定値が実際にどこに置かれているか**（2026-08-01 実測）

  | キー | 既定値 | 既定の在り処 | 同梱 `book.yml` の値 |
  |---|---|---|---|
  | `theme.frontispiece.edge_inset` | 10mm | `theme.css:79` `--frontispiece-edge-inset` | 5mm |
  | `theme.frontispiece.heading_chars` | 8 | `book_settings_css.rb:184` `DEFAULT_HEADING_CHARS` ＋ `theme.css:87` の `103.7mm`（8 字ぶん） | 10 |
