# 素の表記を数式として組む仕様書

> 作成日: 2026-08-19
> ステータス: **実装待ち**
> 対象: `PLANNED.md` の [Medium]「素の表記を TeX 記法へ起こす」。**LaTeX を知らない著者が素で書いた数式**（`√n`・`a^(p-1) mod p`・`Σx²`・`x_(n+1) = x_n − f(x_n)/f'(x_n)`）を、著者に何も要求せずに綺麗な数式として組む。逆向き（TeX → 素の表記。Kindle でフォントサイズに追従させるため）は `MathTextRenderer` として実装済みで、その対になる
> 決定事項（`workbook` コーパス 166 ファイル＋`problems.yml` と MathJax の実測に基づく。根拠は §1〜§3）:
> - **原稿に LaTeX は一度も書かない。** これが最上位の不変条件。LaTeX はビルド中だけの中間表現で、著者が読み書きするのは常に素の表記（§4）
> - **ビルド時に自動判定する。** `vs lint --fix` のような一手間を著者へ要求しない。Kindle 劣化処理（`textify_simple_math_for_kindle!`）が既に逆向きの自動変換を本番で行っており、自動判定は新しい原則ではない
> - **バッククォートを `$` の代用と見なす。** 等幅で本文と区別したいという意図で書かれた原稿が大量に実在する（インライン＝コードスパン、ディスプレイ＝言語なしフェンス。§2）
> - **日本語を含む式も組む。** MathJax が日本語を `<text>` で出すため 2 つ手当てが要る——PDF はフォント埋め込み（Type 3 対策・実測済み）、EPUB/Kindle はラスター対（KFX の SVG 不確実性を踏まない）。ただし**判定器が推測で拾う経路では日本語を数式にしない**（§3）
> - **地の文（バッククォートの外）は対象外**（§11）
> - 実装は 2 部品に分ける: **変換器**（素 → TeX）と**判定器**（どれが数式か）。変換器から先に作れる（§8）
> 関連: `lib/vivlio_starter/cli/pre_process/math_transformer.rb`, `lib/vivlio_starter/cli/build/math_text_renderer.rb`（逆向き）, `kindle-inline-math-textify-spec.md`, `math-frontispiece-svg-spec.md`, `type3-font-embedding-notes.md`（§3 の根拠）, `epub-frontispiece-facsimile-spec.md` §4.2（`alt` のもう 1 人の消費者）, `notation-implementation-guide.md`

## 0. 背景

数式は `$…$` の中身を**そのまま LaTeX として** MathJax へ渡している（`MathTransformer`）。LaTeX を書ける著者にはこれで足りるが、書けない著者は素の表記で書く。そして素の表記は、**エラーにならないまま黙って壊れる**。

本仕様は「LaTeX を知らない著者でも綺麗な数式が出る」ことを目的とする。著者に新しい記法を覚えさせないこと、原稿を書き換えさせないことを、機能の質と同じ重みで扱う。

## 1. 実測 A — MathJax は素の表記を黙って壊す（2026-08-19）

`mathjax_to_svg.mjs` と同じ構成で `doc.convert()` し、出力 SVG のグリフと MathML ノード種別を確認した。**どれもエラーを出さない。**

### 1-1. 文字が消える

| 入力 | 実際に描かれた字 | 何が起きたか |
|---|---|---|
| `x²+y²` | `𝑥+𝑦` | 上付きが丸ごと落ちる |
| `10¹⁴` | `10` | 同上。原稿に実在する表記 |
| `H₂O` | `𝐻𝑂` | 下付きが落ちる |
| `a＋b` | `𝑎𝑏` | 全角演算子が落ちる |
| `ａ＋ｂ` | （何も描かれない） | 全角英数字は式ごと消える |

### 1-2. 別の式として組まれる

| 入力 | 実際に描かれた形 | 何が起きたか |
|---|---|---|
| `2^(1/3)` | `2` の右肩に `(`、後ろに `1/3)` | `^` の引数は直後の 1 文字。`(` だけが上付きになる |
| `√2` | `√` と `2` が並ぶだけ | `√` はただの記号グリフ。根号の横線が無い |
| `√x+1` | `√𝑥+1`（横線なし） | 同上 |
| `x<=y` | `𝑥<=𝑦` | `≤` にならない |

### 1-3. そのままで正しい（＝変換不要）

| 入力 | 結果 |
|---|---|
| `π` | `\pi` と**完全に同一**の SVG（859 バイト・同一グリフ） |
| `\sqrt{π r^{2}}` | `\sqrt{\pi r^2}` と**完全に同一** |
| `×` `÷` `±` `≒` `≦` `≠` `∞` `°` | 正しい演算子として描かれる |
| `1/2` | `1/2`（`\frac` へ起こす必要は無い） |

**1-3 が設計を小さくした。** ギリシャ文字表も記号表も要らない。変換器が持つべきは 1-1 と 1-2 の型だけである。

## 2. 実測 B — 著者はバッククォートを数式デリミタとして使っている

`workbook`（`answers/ruby/*/COMMENTARY_*.md` 166 ファイル ＋ `problems.yml`）を機械分類した。

| うち**数式** | **361 出現 / 280 種（11%）** |
| 言語なしフェンス 全体 | 546 |
| うち**ディスプレイ数式** | **70** |

`x^2 ≡ 1 (mod n)`  `v = √(GM/R)`  `cₙ = f⁽ⁿ⁾(0)/n!`  `√( p̂(1−p̂) / n )`
```
````
```
eˣ  = 1 + x + x²/2! + x³/3! + x⁴/4! + ...

```
````

**バッククォートは、数式記法が無かった著者が選んだ代用である。** 等幅になって本文と区別が付くから使われている。この実態を記法として受けるのが、著者に何も要求しない唯一の道になる。

**逆に、コードスパンの 89% は本物のコード**（`puts`・`Complex.polar`・`array[i]`）なので、全部を数式にすることはできない。判定が要る（§6）。

## 3. 実測 C — 日本語は `<text>` になる。だから 2 つ手当てが要る

`\text{符号}` の SVG 出力:

```xml
<text data-variant="normal" transform="scale(1,-1)" font-size="884px" font-family="serif">符</text>
<text data-variant="normal" transform="translate(1000,0) scale(1,-1)" font-size="884px" font-family="serif">号</text>
```

MathJax は `fontCache: 'none'` でグリフの輪郭を `<path>` として焼き込むが、**自分のフォントに無い字だけは `<text>` へ落ちる**。CJK は入っていないので、日本語を書いたときだけこの経路に入る。手当てなしでは 2 つ壊れる。

### 3.1 PDF — Type 3 フォントが混入する（実測 → 対策も実測）

`type3-font-embedding-notes.md` §4 と同じ仕組み。`<img>` 参照の SVG は独立文書なので `@font-face` が届かず、`font-family="serif"` が OS フォントへ落ちる。対照実験（2026-08-20・`fixtures/type3/verify.sh` と同じ手順）:

| PDF の中身 | Type 3 | 日本語の埋め込まれ方 |
|---|---|---|
| ASCII のみ（対照） | 1 | — |
| ＋ 日本語**なし**の数式 SVG | 1 | （`<text>` が無い） |
| ＋ 日本語**あり**の数式 SVG | **3** | `HiraMinProN-W3`（**Type 3**・OS の明朝） |
| ＋ **`SvgFontEmbedder` を当てた** SVG | **1**（対照と同じ） | `ZenKakuGothicNew-Bold`（**CID TrueType**） |

**対策は既存の仕組みでそのまま効く。** `SvgFontEmbedder` は showcase で「`font-family` が汎用名だと `@font-face` を当てられないので専用ファミリ名を与える」という同型の問題を既に解いている。数式でも `font-family="serif"` を専用名（`vs-math-cjk`）へ書き換えて注ぐだけで、2 文字・2KB で Type 3 が消えた。

### 3.2 EPUB・Kindle — SVG のまま送らない

Type 3 は PDF の話なので EPUB・Kindle には関係ない。ただし**別の理由で SVG のままは避ける**。

- フォントを data: URI で埋めた SVG は、**base64 を内包した SVG** になる。`kindle-inline-math-textify-spec.md` §1-4 は「KFX のインライン SVG 対応自体が不確実で、過去に『SVG 内 base64 画像非対応』で**出版ブロックの実績**がある」と記録している。同じ族のリスクを、検証できないまま踏みに行かない。
- showcase・mermaid が**まさにこの理由で**ラスターを対にしている（`data-vs-raster` → `EpubBuilder` が EPUB/Kindle で PNG へ差し替える）。埋め込みフォント入りの SVG は PDF にだけ届き、Kindle には焼き上がった PNG が行く。

よって**同じ形を採る**。ラスター化は `rsvg-convert`（doctor 管理の既存ツール・showcase と同じ主経路）で足りる。

### 3.3 適用は「`<text>` を含む SVG」だけ

判定は**入力の日本語ではなく、出力の `<text>` の有無**で行う。MathJax が字を持たないものは CJK に限らないので、出力を見るほうが漏れない。

- `<text>` を含まない SVG＝これまでどおり。**通常の数式は 1 バイトも変わらない**（拡大に強いベクタのまま EPUB へ行く）
- `<text>` を含む SVG＝フォント埋め込み（PDF）＋ラスター対（EPUB/Kindle）

該当量は `workbook` 実測でインライン 280 種中 18 種（6%）、ディスプレイ 70 件中 20 件（29%）。

### 3.4 明示は尊重し、推測は保守的にする

`$$下限 = p̂ − 1.96 × √( p̂(1−p̂) / n )$$` は**著者が明示的に数式だと宣言している**ので、上の手当てをして組む。

一方、第 2 段階の**判定器は日本語を含むコードスパン／フェンスを数式にしない**。`攻撃側の戦闘力 = (投入兵士数 × 訓練度) × 大名の武力 × 乱数` を数式画像にしても得るものは無く、本文フォントのまま組むほうが綺麗である——そして**それを機械が黙って決めてよい判断ではない**。明示された `$…$` は尊重し、推測で拾う経路は保守的にする。

### 3.5 字送りは壊れない（2026-08-20 に訂正）

当初「`translate(1000,0)` は欧文の固定送りなので日本語の字間が合わない」と書いたが、実測すると 1 文字あたり 2.262ex ≒ 1em で、**全角の送りとして正しい**（`\text{下}` 2.262ex / `\text{下限}` 4.525ex / 4 文字 9.05ex と線形）。この項は根拠にならない。

## 3-2. 経路の全表（ターゲット × 種別 × 内容）

場合分けを重ねると必ず抜けるので、**実測して次元を畳んでから**表にした。結論として、振る舞いを決めるのは 3 つだけである。

| 記号 | 意味 | 決まり方 |
|---|---|---|
| **A** | SVG に `<text>` が入るか | MathJax がグリフを持たない字があるか。実測では **CJK だけ**。**インライン/ディスプレイで変わらない** |
| **B** | `MathTextRenderer` が受理するか | **Kindle のインラインでのみ**効く |
| **C** | 素の表記の原文があるか | `data-vs-tex` の有無（＝著者が素で書いたか） |

「Unicode 記号を含むか」「ギリシャ文字を含むか」は **A に影響しない**（MathJax はどちらのグリフも持っている）。B にだけ効く。

### 3-2.1 PDF — 常に SVG。種別・B・C に依存しない

| A | 結果 |
|---|---|
| なし | ✅ そのまま |
| あり | **フォント埋め込み**（`SvgFontEmbedder`）で Type 3 = 0（§3.1 で実測） |

### 3-2.2 EPUB（クリーン） — 常に SVG。種別・B・C に依存しない

| A | 結果 |
|---|---|
| なし | ✅ そのまま（ベクタのまま送る。拡大に強い） |
| あり | フォント埋め込みで**自己完結**する SVG になる（リーダーの `serif` に委ねない） |

**クリーン EPUB はラスター化しない。** showcase・mermaid は「両フレーバで見た目を揃える」ためクリーン EPUB もラスターを使うが、数式 SVG はパスだけで安全であり、Kobo・Apple では拡大に強いベクタの利点が残る。

### 3-2.3 Kindle インライン — 3 段に落とす

| B | C | 結果 | A の影響 |
|---|---|---|---|
| 受理 | — | **HTML テキスト**（`<i>`/`<sup>`。変数が斜体になり最も綺麗） | **無し**（SVG を参照しない） |
| 拒否 | あり | **著者の原文テキスト**（素の表記はそのまま読める形で書かれている） | **無し**（同上） |
| 拒否 | なし | SVG（px 固定） | A あり なら ⚠ 残る（§3-2.5） |

**「拒否 → 原文テキスト」が効く。** 素の表記で書かれた式は変換なしで読めるので、コーパス実測で Kindle のフォントサイズ追従が **20% → 100%** になる。

### 3-2.4 Kindle ディスプレイ — 常にラスター

`Σ` や `∫` を含む大きな式を独立行に組むのがディスプレイ数式の意図なので、**テキスト化せず組版を保つ**。KFX の SVG 対応が不確実（`kindle-inline-math-textify-spec.md` §1-4）という事情もあり、PNG のほうが確実に運べる。ビルド時に焼くので A の影響も消える。

### 3-2.5 残る 1 マス

**「Kindle インライン ＋ `MathTextRenderer` が拒否 ＋ LaTeX で書かれた ＋ CJK を含む」**（例: 著者が `$\text{下限}\sqrt{2}$` と LaTeX で書く）だけが SVG のまま Kindle へ届き、`<text>` を抱える。素の表記の原文が無いので原文テキストへ落とせない。

ただし**その SVG には書体が埋め込まれている**（§3.1・段階⑤）ので、リーダーがフォントを解決できなくても字は出る。残るのは「KFX が base64 入り SVG をどう扱うか」だけで、これは実機でしか分からない。実際に出る量を見てから決める。

## 4. 大原則 — 原稿に LaTeX は書かない

```
【原稿】        約数は `a^(p-1) mod p` で判定します
                      ↓ ビルド時のみ（.md には書かれない）
【中間】        a^{p-1} \bmod p
                      ↓
【PDF/EPUB】    a^(p-1) mod p が数式として組まれる

  著者が a を b に直したいとき → 原稿の `a` を `b` にするだけ
```

`$\sqrt{n}$` のように LaTeX を原稿へ書き込む変換（`--fix` を含む）は**行わない**。LaTeX を知らない著者が自分の原稿を読めなくなり、機能の目的そのものを壊すため（§11）。

## 5. 変換サブセット（素の表記 → TeX）

### 5.1 起動条件（ゲート）

`$…$` の中身に**素の表記のしるし**が 1 つも無ければ、変換器は入力をそのまま返す。既に正しい TeX で書かれた式を 1 文字も変えないための保険である（`\sqrt{}` に `√` は無く、`^{2}` に `²` は無く、`f^{(n)}` は `^` の次が `{` であって `(` ではない）。

しるし: Unicode 上付き（`U+00B2 U+00B3 U+00B9`・`U+2070–U+207F`）／下付き（`U+2080–U+208E`）／`√`／`^(` `_(`／ASCII 関係演算子 `<=` `>=` `!=`／全角英数字・全角記号（`U+FF01–U+FF5E`・`U+3000`）／`Σ ∏ ∫ ・ ° ≒ ≡ ≈` ／ギリシャ文字／`mod`。

判定器（§6）経由で入ってきた式は既に数式と判定済みなので、ゲートは通過扱いにする。

### 5.2 変換規則

**実測で「壊れているもの」だけを変換する。** 2026-08-19 に MathJax の出力を 1 つずつ確認し、そのまま正しく描かれる記号は表から外した。表を短く保つこと自体が目的ではなく、**触らない記号は壊しようがない**のが理由である。

### 変換する（実測で壊れている）

| 分類 | 素の表記 | TeX | 変換しないと何が起きるか |
|---|---|---|---|
| 上付き | `x²` `10¹⁴` `10⁻³⁴` `eˣ` `f⁽ⁿ⁾` `(x+y)ⁿ` | `x^{2}` `10^{14}` `10^{-34}` `e^{x}` `f^{(n)}` `(x+y)^{n}` | 文字が消える |
| 下付き | `H₂O` `c₀` `Hₙ` | `H_{2}O` `c_{0}` `H_{n}` | 文字が消える |
| べき乗 | `2^s` `a^(p-1)` `10^((Rb − Ra)/400)` `2^-52` | `2^{s}` `a^{p-1}` `10^{(Rb - Ra)/400}` `2^{-52}` | 直後の 1 文字だけが上付きになる |
| 添字 | `X_k` `A_pub` `x_(n+1)` | `X_{k}` `A_{pub}` `x_{n+1}` | 同上 |
| 根号 | `√2` `√(GM/R)` `√( p̂(1−p̂) / n )` | `\sqrt{2}` `\sqrt{GM/R}` `\sqrt{\hat{p}(1-\hat{p})/n}` | 横線（vinculum）が無い |
| **中黒** | `I(n)・C(2n)` `2n・tanθ` | `I(n) \cdot C(2n)` `2n \cdot \tan\theta` | **`・`（U+30FB）が丸ごと消える** |
| **総和** | `Σx²` `Σ(k=0 to ∞)` | `\sum x^{2}` `\sum_{k=0}^{\infty}` | **`Σ`（U+03A3）は斜体の変数 `𝛴` になる**（`∑` U+2211 なら正しい） |
| 積分 | `∫[0, π/2]` | `\int_{0}^{π/2}` | 上下限が付かない |
| 極限 | `lim(n→∞)` | `\lim_{n \to ∞}` | `𝑙𝑖𝑚` と斜体で並ぶ |
| 関数 | `sin(x)` `arctan(1/5)` `tanθ` `log₂(n)` | `\sin(x)` `\arctan(1/5)` `\tan\theta` `\log_{2}(n)` | `𝑡𝑎𝑛𝜃` と 1 文字ずつ斜体になる |
| 剰余 | `a mod n` `x ≡ 1 (mod n)` | `a \bmod n` `x ≡ 1 \pmod{n}` | `𝑚𝑜𝑑` と斜体になる |
| ASCII 関係 | `<=` `>=` `!=` | `\leq` `\geq` `\neq` | `<=` のまま 2 文字で出る |
| 全角 | `ａ＋ｂ` `（` `　` | 対応する半角へ | 式ごと消える |
| 装飾 | `p̂`（p ＋ U+0302） | `\hat{p}` | アクセントが乗らず横に並ぶ |

### 変換しない（実測でそのまま正しい）

| そのまま通す | 実測 |
|---|---|
| ギリシャ文字 `π λ φ χ θ ρ μ α`… | `π` は `\pi` と**完全に同一**の SVG（§1-3） |
| `≡ ≈ ≒ ≠ ≦ ≧ ∈ →` | すべて `mo`（演算子）として正しく描かれる |
| `× ÷ ± ∓ ∞ ° ...` | 同上 |
| `·`（U+00B7 中点） | `mo` になる。消えるのは `・`（U+30FB）のほう |
| `∑`（U+2211）`∏`（U+220F）`∫` | すでに総和・総乗・積分の演算子 |
| `−`（U+2212）`!` `f'(x)` `1/2` `10,000` | そのまま正しい |
| `\command` `{…}`（中は再帰） | 既存 TeX を壊さない |

**`Π`（U+03A0 ギリシャ大文字パイ）は変換しない。** `Σ` と対称に見えるが、総乗記号としての用例がコーパスに無く、円周率まわりの変数として使われうるため。実例が出てから足す。

**`√` の結合規則は「次の 1 トークンだけ」。** `√x+1` は `\sqrt{x}+1`（`\sqrt{x+1}` にはならない）。全体に掛けたければ `√(x+1)` と括弧で括る。原稿（§10）で明記する。

**上付き・下付きの直前に基底が無いとき**（`²x`）は変換せず原文のまま残す。基底の無い `msup` になるため。

### 5.3 全体拒否はしない

`MathTextRenderer`（逆向き）は 1 トークンでも解釈できなければ式全体を拒否する。こちらは逆に**部分変換**とし、解釈できない字は原文のまま次へ送る。素の表記と TeX が混在しうる（`\frac{1}{2}√2`）ためで、全体拒否は「直せるものを直さない」だけになり安全側にも倒れない。安全性は判定器（§6）とゲート（§5.1）が担う。

## 6. 判定 — どれを数式と見なすか

### 6.1 対象

| 記法 | 扱い | 根拠 |
|---|---|---|
| `$…$` `\(…\)` | インライン数式 | 既存。中身を §5 で起こす |
| `$$…$$` `\[…\]` | ディスプレイ数式 | 既存。同上 |
| **`` `…` ``（インラインコードスパン）** | 数式と判定したらインライン数式 | §2 |
| **言語なしフェンス** | 数式と判定したらディスプレイ数式 | §2 |
| 言語付きフェンス（```` ```ruby ````） | **常にコード** | 著者が言語を明示している |
| 地の文 | **対象外** | §11 |

### 6.2 判定規則

**コードのしるしを 1 つでも含めばコード（拒否が優先）。** そのうえで数式のしるしがあれば数式とする。

- **コードのしるし**: `.メソッド`（小数点は除く）／`::` `=>` `||` `&&` `#{` `@変数`／`**`（Ruby のべき乗・Markdown の太字と衝突）／`配列[添字]`／Ruby の予約語・頻出メソッド名（`puts` `def` `end` `nil` `each` `map` …）／ブロック `{ |`／文末の `;` `{` `}`
- **数式のしるし**: §5.1 のしるし一式（ギリシャ・上下付き・`√`・`^`・関係演算子・`Σ ∏ ∫ ・ °`）／両側に被演算子のある `mod`／関数名の直後に `(` か `θ`
- **日本語を含む綴りは、強いしるしがあるときだけ数式にする**。`平文^e mod n` は変数名が日本語なだけの式なので組む（`^`・上下付き・`√`・`Σ`・関係演算子・関数名・`mod` が強いしるし）。`行計 × 列計 ÷ 総計` は `×` しか手がかりが無く、式か地の文か機械には決められないので触らない（§3.4）
- ディスプレイ（言語なしフェンス）は追加で: 空でない全行が関係演算子（`= ≡ ≈ ≒ < >`）を含み、行数が 8 行以下、かつコードのしるしが無いこと
- ディスプレイはさらに**実行結果の貼り付けを弾く**: `【…】` の見出し行を含む／`→` を含む／行頭が `ラベル:` で右辺に単位付きの数値が並ぶ（`反復1: π近似=3.14…`・`341: base=2だけで判定 → 合成数と判定`・`別々の2列（各λ=0.8）: W=4.97 分`）。
  **ただし `：` を一律に弾いてはならない**——`外接： C(n) = 2n・tanθ` は日本語ラベル付きの本物の数式で、同じ字を使う。弾く根拠は「右辺が式でなく値の羅列であること」に置く

### 6.3 判定の実測（`workbook`）

| | 検出 | 誤判定 |
|---|---|---|
| インライン | 361 出現 / 280 種 | 約 5 件（`mod` 単体・`(a / gcd(a, b)) * b`） |
| ディスプレイ | 70 件 | 4〜5 件（実行結果の貼り付け。`反復1: π近似=3.14…`・`【…】` 見出し付き） |
| 取りこぼし | — | 2 件（`Math.log(n)`・`cos(1.5)`＝どちらもコード） |

判定器を作る過程で自分の誤りを 2 つ見つけた。**小数点をメソッド呼び出しと誤認**して 15 件の数式を落としていた（`0.99¹⁰⁰ ≒ 0.366`）ことと、**`expression` の中の `exp` を関数名と誤認**していたこと。実装時も同じ検算（コーパス全件の目視）を行うこと。

### 6.4 逃げ道

| したいこと | 書き方 |
|---|---|
| 確実に数式にする | `$…$` / `$$…$$` で明示する |
| 確実にコードのままにする | 言語付きフェンス（```` ```ruby ````）に置く |
| 何が数式になったか知る | `vs build --log` が章ごとの変換件数を、`--log=debug` が全式を出す |

インラインで「コードのままにしたい」を明示する手段は用意していない。判定を保守的にすること（コードのしるしを拒否優先にすること・1 文字は式にしないこと）で足りるかを実測で確かめる方針で、本書 `contents/` 27 ファイルに当てた実測では該当が **1 件**だった（§13.8）。

## 7. 実装設計

### 7.1 部品

```
MathSpanDetector（判定器・新規）      どのコードスパン／フェンスが数式か
    └─ 数式と判定したものを $…$ / $$…$$ へ置き換える（ワークスペース内のみ）
          ↓
MathTransformer（既存）               $…$ を拾って SVG 化
    └─ PlainMathTranspiler（変換器・新規）  素の表記 → TeX
          ↓
        MathJax → SVG
```

**判定器と変換器を分けるのが要。** 変換器は純粋関数で単体テストしやすく、判定器は誤判定を後から詰められる。変換器から先に作れる（§8）。

### 7.2 `PlainMathTranspiler`（変換器・純粋関数）

`lib/vivlio_starter/cli/pre_process/plain_math_transpiler.rb`（`MathTextRenderer` と対になる置き場所。あちらは消費者が `EpubBuilder` なので `build/`、こちらは `MathTransformer` なので `pre_process/`）。

```ruby
PlainMathTranspiler.plain?(src)   # 素の表記のしるしを含むか（§5.1）
PlainMathTranspiler.to_tex(src)   # 素の表記 → TeX。含まなければ src をそのまま返す
```

`StringScanner` の逐次消費（`MathTextRenderer` と同型）。`module_function`・状態なし・Nokogiri 非依存・CONFIG 非依存・例外を投げない。閉じ括弧が無い `√(x` 等は、その位置から先を原文のまま通す。

### 7.3 `MathSpanDetector`（判定器）

`lib/vivlio_starter/cli/pre_process/math_span_detector.rb`。

```ruby
MathSpanDetector.math?(text)                    # 1 つの綴りが数式か（§6.2）
MathSpanDetector.transform(content, ...)        # コードスパン／フェンスを $…$ / $$…$$ へ
```

- フェンスの解釈は **`Masking.replace_top_level_fences` を使う**（独自解析を書かない。`notation-implementation-guide.md` §2 の再実装禁止リスト）。
- インラインコードスパンの走査は、フェンス処理の**後**に行う（フェンス内のコードスパンを拾わないため）。
- 置換結果に `$` が含まれると数式の切り出しが壊れるので、`$` を含む綴りは数式にしない。

### 7.4 パイプラインへの組み込み

`MarkdownPreprocessor#run` の **`transform_math!` の直前**に `detect_plain_math!` を置く。

```ruby
transform_terminal_blocks!   # $ を含む端末例を先にリテラル化（既存の理由）
…
process_code_includes!
detect_plain_math!           # ← 追加。` … ` / 言語なしフェンス → $…$ / $$…$$
transform_math!              # 既存。$…$ を SVG 化
```

- `transform_terminal_blocks!` より**後**でなければならない（`$ echo $A$B` を数式にしないため。既存のコメントと同じ理由）。
- `process_code_includes!` より**後**（取り込んだソースを数式にしないため）。
- `transform_math!` の直**前**（`$…$` を作る側なので）。

### 7.5 `MathTransformer` への組み込み

`enqueue_formulas` の 1 箇所だけを変える。

```ruby
tex = PlainMathTranspiler.to_tex(latex)
queue << { key: digest(display, tex), latex: tex, display:, original:,
           plain: tex != latex, placeholder: }
```

- **`key` と `latex` は起こした後の TeX**。キャッシュキーが表記のゆれで割れず、`$x²$` と `$x^{2}$` が同じ SVG を共有する。
- **`original` は素のまま**。描画失敗時に本文へ戻すのは著者が書いた文字列でなければならない。

### 7.6 `alt` は触らない。TeX は `data-vs-tex` で渡す

`build_img` が付ける `alt` には**今までどおり著者の原文**を入れる。`alt` の消費者が 2 人いて、必要とするものが逆だからである。

| 消費者 | 必要なもの |
|---|---|
| `EpubBuilder#textify_simple_math_for_kindle!` | **TeX**（`MathTextRenderer` へ食わせる） |
| `EpubBuilder#extract_lead_text`（章扉リードの焼き込み） | **人が読める文字列**（画像に焼く） |

`alt` を TeX にすると章扉に `\sqrt{2}` と焼かれ、素のままにすると Kindle が式を拒否して px 固定 SVG へ落ちる。よって属性を分ける——インライン枝に、起こした式のときだけ `data-vs-tex="…"` を足す。`textify_simple_math_for_kindle!` 側は 1 行:

```ruby
latex = img['data-vs-tex'].to_s.empty? ? strip_math_delimiters(img['alt']) : img['data-vs-tex']
```

これで `x²+y²` が Kindle でもテキスト化される（起こす前は `²` で拒否され SVG のままだった）。**本仕様は Kindle の追従性も一緒に改善する。**

### 7.7 触らないもの

`MathTextRenderer` / `convert_math_units_for_epub!` / `mathjax_to_svg.mjs` / ディスプレイ数式の見た目 / PDF・クリーン EPUB の経路。`book.yml` にキーを増やさない（`config-key-criteria-guidelines.md`。「数式にしない」＝「黙って壊れる」なので選ぶ価値のある選択肢ではない）。

## 11. 考慮した代替案（不採用）

| 案 | 不採用理由 |
|---|---|
| **`vs lint --fix` で `$…$` へ書き換えてから組む** | 原稿を変えないなら著者に一手間を要求する理由が無い。Kindle 劣化処理が既に逆向きの自動変換を本番で行っており、自動判定は新しい原則ではない |
| **`$\sqrt{n}$` のように LaTeX を原稿へ書き込む** | LaTeX を知らない著者が自分の原稿を読めなくなる。`a^(p-1)` の `a` を `b` に直す、というごく普通の編集ができなくなり、機能の目的を壊す（§4） |
| **地の文の裸の数式も変換する** | 囲む範囲が機械で決まらない。実測: `5.32 × 10¹⁴` は全体が式、`√2:1 ≒ 1.414` は `√2` だけが式。さらに `周り 7×7 マス`・`12ヶ月×30日＝360日`・`3×3 に変えたり` のような寸法・数え上げが実在し、`×` `÷` は地の文で数式のしるしにならない |
| **日本語を `\text{}` で素通しする（手当てなし）** | PDF に Type 3 が混入し（実測 +2 件・OS の明朝）、EPUB/Kindle はリーダーの `serif` 任せになる。§3 の 2 つの手当てとセットなら採れる——手当てなしで通すことだけを不採用にする |
| 素の表記専用の新デリミタ（`` `math:…` `` 等） | 著者は既にバッククォートと `$…$` を使っている。3 つ目を覚えさせない（`notation-implementation-guide.md` 大原則 1） |
| ギリシャ文字を `\pi` へ、`×` を `\times` へ正規化 | 出力が完全に同一（§1-3）。規則と表が増えるだけ |
| `MathTextRenderer` と同じ全体拒否方式 | 素の表記と TeX は混在しうるので、全体拒否は「直せるものを直さない」だけになる（§5.3） |
| `alt` に TeX を入れる（属性を増やさない） | `extract_lead_text` が章扉へ `\sqrt{2}` と焼く。`alt` の消費者 2 人が必要とするものが逆（§7.6） |

## 12. `problems.yml`（`workbook`）は特別扱いしない — 確認済み

`problems.yml` は部ごとの `contents/part1.md`〜`part12.md` へ展開される予定で、`body: |` ブロックスカラーの中身は**そのまま Markdown になる**。実物を確認したところ、YAML の中に書かれているのは普通のフェンスとコードスパンだった:

```yaml
  body: |
    半径 r の円について、面積と円周の長さを求めてみましょう。…

    ```
    面積　　　 = π × r × r （= πr²）
    円周の長さ = 2 × π × r （= 2πr）
    ```

    …多くの言語では標準ライブラリに定数として用意されています（たとえば `Math::PI` や `M_PI`）。
```

ブロックスカラーの字下げが外れれば列 0 のフェンスとコードスパンになるので、**判定器は生成後の `contents/part*.md` を見るだけでよい**。YAML を読む経路は要らない。

なお、この例は §3 の型（日本語ラベル ＝ 純数式）と、`` `Math::PI` ``（コードのしるし `::` で確実に弾かれる）が同居している。`problems.yml` 由来の式は本の数式の主要部分になる見込みなので、§10 の検証には**展開後の `part*.md`** を使う。

## 13. 実装記録 — 第 1 段階（変換器）2026-08-19

`PlainMathTranspiler` を実装し、`MathTransformer`・`EpubBuilder` へ組み込んだ。**第 2 段階（判定器）は未実装**なので、いま効くのは著者が `$…$` / `$$…$$` で明示した式だけである。

### 13.1 実測が仕様を書き換えた

§5.2 の変換表は**下書きより大幅に短くなった**。MathJax の出力を 1 記号ずつ確認したところ、`≡ ≈ ≒ ≠ ≦ ∈ → ° ∞ ... ! −`・`·`(U+00B7)・`∑`(U+2211)・`∫`・`f'(x)` は**そのままで正しく描かれる**と分かったため、表から外した。触らない記号は壊しようがないので、規則を減らすこと自体が安全側に効く。

逆に、下書きに無かった変換が 4 つ増えた。どれも実測で初めて見つかった:

| 発見 | 実測 |
|---|---|
| **`・`（U+30FB）が丸ごと消える** | `a・b` → `𝑎𝑏`。似た `·`（U+00B7）は無事——この 2 つは見た目が近く挙動が違う |
| **`Σ`（U+03A3）は総和記号にならない** | `Σx` → `𝛴𝑥`（斜体の変数）。`∑`（U+2211）なら正しい |
| **関数名が 1 文字ずつ斜体になる** | `tanθ` → `𝑡𝑎𝑛𝜃` |
| **TeX の特殊文字が黙って壊す** | `50% + 1` → `50`（`%` から後ろがコメント）。`a#b` `a&b` は TeX エラー |

### 13.2 `~` は空白である（波ダッシュを半角にしてはならない）

全角→半角の一括変換に穴があった。`～`（U+FF5E）を `~` にすると、**TeX の `~` は改行しない空白**なので、範囲を表す `g^1〜g^(p-1)` が `g^1 g^(p-1)` に化ける。`〜`（U+301C）も含めて `\sim` へ送るようにした。全角変換は「見た目が同じ半角に置く」だけでは済まない、という一般則の実例。

### 13.3 `\begin{aligned}` の `&` を壊しかけた（§10-3 の検査が捕まえた）

`%` `#` `&` を一律に退避したところ、本書 `96-sample.md` の九九の表（`\begin{aligned}` を使う式）で `&=` が `\&=` になり、桁揃えが壊れた。**環境の中では `&` は正しい TeX** である。

`\begin{` を含む式では `&` `#` を退避しないようにした（`%` は例外で常に退避する。素のままだと後ろが丸ごと消えるため）。環境を使う式は LaTeX を知っている著者が書いたものだ、という判断でよい。

**この退行を見つけたのは §10-3 の検査そのもの**——「本書の既存数式のキャッシュキーが 1 つも変わらないこと」を確かめる手順が、そのまま既存 TeX の破壊を検出した。仕様に書いた検証手順が実際に仕事をした形なので、第 2 段階でも同じ検査を回すこと。

### 13.6 Kindle のテキスト化を落としていた（未コミットのうちに発見）

変換器が `sin(x)` → `\sin(x)`、`mod` → `\bmod` に起こす一方、`MathTextRenderer` は
`\sin` も `\bmod` も知らない（ホワイトリストが LaTeX で書かれた原稿だけを見て作られたため）。
その結果、**変換前ならテキスト化できていた式が SVG へ落ちる**ようになっていた。

実測: コーパス 280 種のうち **34 種が退行・47 種が改善**。差し引きは正だが、34 種は純粋な損失。

**修理ではなく、経路を変えて消す**（段階③）。`MathTextRenderer` が拒否したとき SVG でなく
**著者の原文テキスト**へ落とせば、`\sin(x)` は Kindle の通り道に乗らない。素の表記は
そのまま読める形で書かれているので、これで追従率は 20% → 100% になる（§3-2.3）。

**教訓**: 変換器の出力語彙を変えたら、**その出力を食う後段の受理集合を全部突き合わせる**こと。
今回は「出力しうるトークン」を列挙して 1 つずつ `MathTextRenderer` に通して見つけた。
場合分けを頭でやると必ず抜ける。

### 13.5 積み残し — 日本語を含む式の手当ては第 3 段階へ

実ビルドで `$$下限 = p̂ − 1.96 × √( p̂(1−p̂) / n )$$` を通したところ、`<text font-family="serif">下</text>` が出た。

**本仕様による退行ではない**——変換前の生の式を MathJax へ直接渡しても同じ `<text>` が出る（実測）。以前から `$$下限$$` と書けば同じ SVG になっていた。

対策は §3 に書いたとおり 2 つ（フォント埋め込み＋ラスター対）で、**第 3 段階**として実装する。それまでは、日本語を含む数式を明示的に書くと PDF に Type 3 が混ざる。

**`rake test:type3` では捕まらない。** あれは本書を全章ビルドして Type 3 = 0 を見るが、本書の数式に日本語を含むものは **0 件**なので、この経路を踏まない。第 3 段階では `fixtures/type3/verify.sh` の形（日本語入りの数式 SVG 単体を組んで数える）で回帰を押さえること——今回の対照実験がそのまま雛形になる。

### 13.7 実装記録 — 段階③④⑤（2026-08-20）

**③ Kindle インラインの落とし先を 3 段にした。** `MathTextRenderer` が拒否したら SVG でなく
著者の原文テキストへ落とす。素の表記はそのまま読める形で書かれているので、変換を挟まない。

実測（`workbook` コーパス 280 種）:

| 落とし先 | 種数 |
|---|---|
| HTML（変数が斜体・真の `<sup>`） | 57 (20%) |
| **著者の原文テキスト** | 223 (79%) |
| SVG のまま | **0** |
| → フォントサイズに追従 | **280 (100%)** |

**判定を「変換されたか」から「素の表記で書かれたか」へ直した。** 最初 `plain: tex != latex`
としていたが、`a × b ÷ c` のように**変換が要らない素の表記**（記号がそのまま正しく描かれる）に
印が付かず、LaTeX で書かれた式と区別できなかった。実測でこの取り違えが追従率を 27 ポイント
落としていた（73% → 100%）。正しい判定は **TeX の構文（`\command`・`{}`）を含まないこと**。

**④ Kindle のディスプレイ数式を PNG にした。** `Σ` や `∫` を含む大きな式を独立行に組むのが
ディスプレイ数式の意図なので、テキスト化せず組版を保つ。KFX の SVG 対応が不確実な点にも効く。
クリーン EPUB はベクタのまま（§3-2.2）。`rsvg-convert` 不在時は SVG のまま警告して続行する。

**⑤ `<text>` を含む SVG に書体を埋め込んだ。** 実パイプラインで PDF を焼いて確認:

| PDF | Type 3 | 日本語の埋め込まれ方 |
|---|---|---|
| 対照（ASCII のみ） | 1 | — |
| 日本語入りの数式 SVG | **1**（＝対照） | `ZenKakuGothicNew-Bold`（CID TrueType） |

**縮退の落とし穴**: 書体を解決できない環境で `font-family` だけ専用名へ書き換えると、
**存在しないファミリを指すだけで従来（`serif`）より悪くなる**。埋め込みに失敗したら名前も
変えないこと。テストを書いていて気づいた。

**キャッシュキーは日本語を含む式だけ書体を混ぜる。** 埋め込む書体が SVG の中身を変えるので、
著者が書体を替えたら焼き直す必要がある（notes §5.1 が showcase で踏んだ取りこぼし）。
日本語を含まない式のキーは書体に依存しないまま保つ——本書の既存数式 34 件でキー変化 0 件を確認。

### 13.8 実装記録 — 段階②（判定器）2026-08-20

`MathSpanDetector` を新設し、`MarkdownPreprocessor#run` の `transform_math!` 直前へ入れた。

**判定は「コードのしるしがあれば拒否」を先に置く。** 逆向き（数式のしるしがあれば数式）にすると
`array[i] * 2` のようなコードを拾う。フェンスは `Masking.replace_top_level_fences` で先に
処理し、数式でないものはプレースホルダへ退避してからインライン走査に入る——そうしないと
フェンスの中のコードスパンを拾う。

**実測（`workbook` 166 ファイル）**: 54 ファイルが変換され、インライン 326 箇所・
ディスプレイ 17 箇所が数式になった。起こした 275 式を MathJax へ通して**TeX エラー 0 件・
`<text>` 混入 0 件**。前回の試作分類（§6.3）と突き合わせると、取りこぼし 18 種はすべて
日本語入り（§3.4 の意図した動作）で、新たに 3 種（`Hₙ`・`det(A)` ほか）を拾った。誤検出 0。

**複数行のディスプレイは `\begin{aligned}` で揃える。** 1 行ずつ独立した `$$` にすると、
`X_(N-k) = …` に続く `= …` の導出が揃わない。最初の関係演算子の前に `&` を置く。
コーパスの内訳は 1 行 48 件・2〜4 行 22 件。

**1 文字の綴りは式にしない。** 本書 `32-metrics.md` の「`・` で連結し」で踏んだ——記号
そのものを説明している箇所を数式にしていた。実測でこの規則が落とすのはコーパス全体で
`λ` 1 種だけで、2 文字以上は `√n` `Σx` `eˣ` `n³` `2²` のように本物の式が並ぶ。

**計測の誤りを 1 つ踏んだ（実装のバグではない）。** 生テキストを雑な正規表現で走査して
「`<text>` 混入 1 件」を得たが、追うとコードスパンの中の `$`（正規表現アンカーの解説）を
数式の区切りと読んでいた。実パイプラインは `extract_code_spans` で保護するので起きない。
**計測器自身も疑うこと**——判定器を 2 回、計測器を 1 回、この作業だけで直している。
