## 2. 調査で分かったこと

### 2.1 2 回目の組版で直るのは、ほぼ索引だけ

本書の Step 8 の結果は、用語集 0 件・本文 † 0 件・索引 314 件（範囲表記 14 か所）。2 回目の組版は 312 ページ全部を組み直すが、変わるのは巻末の索引だけである。

**本文 † と用語集のバックリンクが 0 件なのは本書に限らない。** 2026-08-16（`1f8c3425`・`build-mode-parity-spec.md` §4.1）から、† は**章ごとの初出にだけ**付き、用語集のバックリンクも † 1 個につき 1 本しか作られない。本文 † の重複除去は「同じページに同じ語の † が二つ」、バックリンクの重複除去は「同じ語のバックリンクが同じページを指す」ときに働くが、同じ章の中では語ごとに † が一つしかなく、章はかならず改ページで始まる（`chapter_pagebreak: any` でも改ページはする）。したがって**どちらも起こりえない**。2026-07 の調査（`backlink-dedup-pdf-map-spec.md` §3）で本文 † が 239 件あったのは、全出現に † を付けていた頃の数字である。

**ついでに見つかった誤判定。** `BacklinkDeduplicator#write_if_changed!` は、Nokogiri で書き出した文字列と元の文字列を比べて「変わったか」を決める。書き出しで空白と `</body>` の位置がずれるだけで「変わった」になり、本書では 1 件も消していない `_glossarypage.html` が毎回「更新ファイル」に数えられていた。索引に重複が 1 件も無い本でも、これだけで 2 回目の組版が走る。消した件数で判定するよう直す（§4.7）。

### 2.2 消したリンクの飛び先は、組み直した PDF から消える

vivliostyle が `/Dests` に書き出すのは**リンクの飛び先になっている id だけ**である（`build-pipeline-pitfalls-notes.md` §4）。索引から消したリンクの飛び先（本文の `idx-*`）は、2 回目の PDF ではどこからも指されないので `/Dests` に載らない。

実際に、2 回目の PDF からページ対応を取って重複除去をやり直すと、消すリンクの集合は同じでも、範囲表記（連続ページの判定）が 1 か所も作られなかった。対応の取れないリンクの `page` が `nil` になり、連続が途切れるためである。

**先回りの判定を確かめるには、消したリンクを飛び先として残しておく必要がある。**

### 2.3 大きさ 0 のリンクは、飛び先だけを残す

2 文書の小さな本で、リンクの隠し方ごとに `/Dests` とリンク注釈を調べた（vivliostyle CLI 11.3.3 / core 2.45.1）。

| リンクの隠し方 | 飛び先が `/Dests` に載るか | リンク注釈 |
| :--- | :---: | :---: |
| 隠さない | 載る | 作られる |
| 親を `display: none` | **載らない** | 作られない |
| 親を `position: absolute; width: 0; height: 0; overflow: hidden` | **載る** | **作られない** |

3 行目の形なら、紙面にも PDF の注釈にも何も残さずに、飛び先だけを `/Dests` に残せる。

### 2.4 原稿を直したとき、前回の判定がどれだけ当たるか

基準のビルド A に対して、原稿を 3 通りに直して組み、1 回目の組版の PDF で重複除去をやり直した。判定（どのリンクを残すか・範囲表記の組み方）が A と同じなら「当たり」である。比べ方は、A 自身で重複除去をやり直すと、ビルドの結果とバイト一致することで確かめた。

| | 直し方 | ページの動いた飛び先 | 判定の変わった索引の項目 | 結果 |
| :--- | :--- | ---: | ---: | :--- |
| B1 | 21 章の 1 語を 1 字短くした | 0 / 1402 | 0 / 209 | 当たり |
| B2 | 12 章の途中に 3 行の段落を足した | 12 / 1402 | 3 / 209 | 外れ |
| B3 | 44 章の途中に 2 行の段落を足した | 0 / 1402 | 0 / 209 | 当たり |

B2 でも、ページが動いたのは 12 章の中だけだった。章は改ページで始まるので、ずれはその章の中で吸収され、ほかの章へは広がらない。外れるのは「直した章の中で、索引語のページが動き、しかもそれで判定が変わる」ときに限られる。

### 2.5 巻末だけなら 4.3 秒で組める

本文用の `entries.sections.js` から、用語集・後書き・索引・扉・権利ページ・奥付だけを残して組むと、21 ページを **4.3 秒**で組めた（全体は 55 秒前後）。ただし索引のページ番号は `target-counter` で数えるので、本文を含まない組版では数字が出ない（§3 の案 B の課題）。

### 2.6 縮小版の差し替えは、2 回目の組版に相乗りしている

`shrink oversized images` は 1 回目の PDF で画像の実効解像度を測り、`pdf/` の HTML を縮小版へ差し替える。反映されるのは 2 回目の組版である（`image-format-per-target-spec.md` §3.6）。

本書では、ステージング時（1 回目の前）にも測定後にも同じ 248 件を差し替えていた。測定の結果はキャッシュに残り、続けて組むときは 1 回目の前に反映済みになる。ただし初回のビルドや画像を替えたときは、測定後の差し替えで HTML が変わりうる。**2 回目を省くのは、測定後の差し替えで HTML が変わらなかったときに限る。**

### 2.7 本文 PDF の並びとノンブル

`_sections.pdf` の並びは「前書き → 目次 → 部扉と本文 → 付録 → 用語集 → 後書き → 索引 → 扉 → 権利ページ → 奥付」。扉・権利ページは結合（Step 10）で先頭へ移る。ノンブルは前付がローマ数字（`page: front`）、本文は最初の章（`body.chapter-first` の `@page body-start:nth(1)`）で 0 に戻る。案 B で索引に数字を書き込むなら、この規則を Ruby で再現する必要がある。

## 4. 案 A の仕様

### 4.1 流れ

```
（前回の記録があるとき）
Step 7 の前（ステージングの後）
  - pdf/ の索引・用語集の dedup 前の HTML を退避する
  - 前回のページ対応で重複を除き（判定 D0）、消したリンクを「証拠のリンク」として文書末に残す
Step 7  1 回目の組版（判定 D0 の索引で組む）
        shrink oversized images（差し替えで HTML が変わったかを記録する）
Step 8  Phase 1: 1 回目の PDF からページ対応を取る（証拠のリンクのおかげで、消した分も取れる）
        Phase 2: 退避した dedup 前の HTML に、新しいページ対応で重複除去をやり直す（判定 D1）
        判定:   D1 の HTML が D0 の HTML（証拠のリンクを除く）と同じ
                かつ 縮小版の差し替えで HTML が変わっていない
                → 2 回目の組版を省く
                そうでなければ → D1 の HTML を書き、今までどおり 2 回目を組む
        記録:   使ったページ対応を次回のために保存する
（前回の記録が無いとき）今までどおり。記録だけ保存する
```

### 4.2 記録

- 保存するもの: 1 回目（外れて組み直したときは 1 回目）の PDF から取ったページ対応のうち、`idx-*` と `gls-src-*` のアンカー → ページ。本書で 1,965 件、JSON で数十 KB。
- 置き場: `.cache/vs/` の下（`vs clean --all` で消え、次の 1 回は今までどおり 2 回組む）。分冊では巻ごとに別のファイルにする（`Volumes.selection_key` を名前に入れる）。`vs build --volume all` は巻ごとに別のプロセスで組むので、ファイルが分かれていれば互いを壊さない。
- 読めない・形が違う記録は、黙って無いものとして扱う（今の道へ戻るだけで、出来上がりは変わらない）。

### 4.3 判定のやり直しに使う元の HTML

1 回目の組版の前に、`pdf/` にステージング済みの `_indexpage.html`・`_glossarypage.html` を退避する（例: `pdf/.dedup-originals/`）。`html/` の原本は画像の差し替え前で、`pdf/` の写しとは中身が違うので使わない。退避先は entries に入らないので組版には混ざらない。

判定の比べ合わせは「同じ元の HTML に、同じ `BacklinkDeduplicator` を、前回と今回のページ対応で当てた結果の文字列が同じか」で行う。ページ対応そのものを比べると、判定に効かないページのずれ（B3 のような吸収）まで外れに数えてしまう。

### 4.4 証拠のリンク

- 消したリンクは、その文書（`_indexpage.html`・`_glossarypage.html`）の `</body>` の直前に、まとめて置く。

  ```html
  <div class="vs-dedup-witness" aria-hidden="true">
    <a href="21-markdown-tutorial.html#idx-5d81fb039821-11"></a>
    …
  </div>
  ```

- CSS は `position: absolute; inline-size: 0; block-size: 0; overflow: hidden;`（§2.3 の 3 行目）。`display: none` にしてはいけない（飛び先が消える）。
- **`<dd>` の中には置かない。** 範囲表記にしていない `<dd>` は `a:not(:last-child)::after` でカンマを付けているので、後ろに兄弟が増えると最後の番号にもカンマが付く。
- 置くのは PDF の組版用の `pdf/` の写しだけ。EPUB・Kindle は `html/` の原本から作るので影響しない。
- 外れて組み直すときの D1 の HTML には置かない（今までどおりの HTML になる）。

### 4.5 縮小版の差し替えとの関係

`shrink oversized images` が `pdf/` の HTML を書き換えたかを、差し替えの前後で記録する（書き換えた文書の数を返す・または前後のダイジェストを比べる）。書き換えていれば、判定が当たっても 2 回目を組む。

### 4.6 本文の † は先回りしない

本文の † の重複除去は本文の HTML を変え、行の折り返しとページを動かしうる。証拠を残すには、消した † の id を同じ位置に大きさ 0 で残す細工も要る。今の † の付け方では本文 † の重複は起こりえない（§2.1）ので、**この版では本文 † を先回りしない。** 下の 2 つは、† の付け方が将来変わったときのための安全弁で、今の作りでは働かない。

- 前回の記録で本文 † の除去が 1 件以上あった本は、先回りを使わず今までどおり組む。
- 今回の 1 回目で本文 † の除去が 1 件以上出たら、外れとして今までどおり組み直す。

### 4.7 「変わったか」の誤判定を直す

`write_if_changed!` の文字列比較をやめ、消した件数（と範囲表記にした件数）で書くかどうかを決める（§2.1）。案 A と独立に効くので、先に入れてよい。

### 4.8 ログ

- 当たり: `log_info` で「前回のページ対応がそのまま使えたため、2 回目の組版を省きました」。ふだんの表示（warn 以上）には出さない。所要時間が縮むこと自体が著者への知らせになる。
- 外れ: `log_info` で外れた理由（判定が変わった・縮小版を差し替えた・本文 † を除いた）を一つ添える。

### 4.9 ほかの経路

- **入稿用 PDF（閲覧用から導出）**: 閲覧用 PDF を経由するので、そのまま効く。
- **入稿用 PDF のみ（個別レンダ）**: Step 8 は本文 PDF が無いとページ対応のために 1 回組む（`extract_page_mapping`）。この組版も先回りの HTML で組めば、同じ確かめ方が使える。2 回目はもともと組まない（`rebuild_pdf: false`）ので、ここで得をするのは判定の正しさだけ。実装時に、この経路で証拠のリンクが入稿用 PDF へ持ち込まれないことを確かめる。
- **単章ビルド・索引が無効な本**: Step 8 が走らないので関係しない。

## 5. テスト

- `BacklinkDeduplicator`: 証拠のリンクを付けるとき、消したリンクが文書末の `div.vs-dedup-witness` にそろい、`<dd>` の中身は今までと同じ。
- 判定の比べ合わせ: 同じページ対応なら「当たり」、判定に効かないずれ（同じページの中で動く）でも「当たり」、判定が変わるずれなら「外れ」。
- `write_if_changed!`: 1 件も消さない文書を書き出さない（`files_modified` に入らない）。
- Orchestrator: 記録が無い・壊れている・本文 † がある・縮小版を差し替えた、のそれぞれで今の道へ戻る。
- 実ビルド（`rake test:layout` か手で）: 何も直さずに 2 回組むと、2 回目の Step 8 が 2 秒ほどで終わり、出来た PDF の索引が 1 回目とバイト一致の文字になる（`pdftotext` で比べる）。

## 6. 実装のときに確かめること

1. 証拠のリンクを数百本置いた索引が、置かないときと同じページ数・同じ組み方になるか（§2.3 は 1 本で確かめただけ）。
2. 証拠のリンクの飛び先が、「宛先名を短くする」段（`DestinationNames.shorten!`）で余計な宛先として残っても害がないか。残る数と PDF の大きさの増え方を測る。
3. 範囲表記の `<dd class="resolved">` を含む索引でも、比べ合わせがバイト単位で安定するか（Nokogiri の書き出しが同じ入力で同じ出力になるか）。

§6 の三点は次のとおり。

1. 証拠のリンク（本書で 332 本）を置いても、ページ数・組み方は変わらない（当たりの回の文字がバイト一致）。
2. 増えるのは PDF の宛先だけ（1660 → 1992 件・2.8KB）。リンク注釈は増えない。「宛先名を短くする」段も問題なく通る。
3. Nokogiri の書き出しは同じ入力で同じ出力になり、範囲表記を含む索引でも比べ合わせは安定した。

### 7.2 落とし穴: 範囲表記で捨てるリンクも証拠に残す

最初の実装では、何も直さずに組み直しても外れた（今回のほうが 9 件多く消した）。範囲表記（`compress_page_ranges!`）は「12, 13, 14, 15」を始点と終点のリンクだけにして、**間のリンクを捨てる**。これは「消したリンク」に数えていなかったので証拠に残らず、今回の PDF で間のページの飛び先（本書で 14 か所・18 本）が `/Dests` から消えた。今回の判定ではそのリンクの `page` が `nil` になって「対応の無いリンク」として消され、範囲も作れなかった。`build_page_range` で間のリンクも証拠へ回すようにして解消した。

この誤りは、外れとして組み直す道に入るので出来上がりは壊さない。ただし外れの判定が「ページ対応の欠け」から来ていても区別できないので、証拠の取りこぼしは「何も直さずに組み直しても外れる」形でしか見えない。テスト（`test_should_keep_removed_links_as_witness_outside_dd`）で間のリンクを押さえた。

### 7.3 古い記録からの 1 回目

7.2 を直す前の記録（間のリンクの飛び先が欠けている）から組むと、1 回だけ外れて組み直し、その回の記録で直る。記録は毎回の 1 回目の PDF から作り直すので、欠けた記録が残り続けることはない。

### 7.4 確かめていない経路

- 入稿用 PDF だけを組む経路（`rebuild_pdf: false`）と分冊（巻ごとの記録）は単体テストだけで、実ビルドはしていない。
