## 1. 前提

- 本の種類の順序は、縦書きの小説 → 絵本 → 動く絵本。三つとも 2.0 に含める（`v2-design-research-brief.md` §5）。
- 見た目が変わる変更（HTML の構造など）は 2.0 で入れる。1.x の小さな版には入れない。
- 技術書典の 6 冊（登録の締切 2026-12-06）は 1.x で組む。2.0 の作業は、この 6 冊の作業を妨げない。
- 実装は Opus が段階ごとに行う。各段階は、仕様書の該当の節を読めば着手できるように書いてある。段階の途中で仕様書と実物が食い違ったら、実装を進める前にユーザーに知らせる。

### 2.2 順序の理由

- **S0 を最初に置く。** S1〜S7 の完了の条件は、どれも「技術書の出力が変わらない」である。比べる相手（基準）と比べる道具が無いと、どの段階も完了を言えない。
- **S1 を S2 より先に置く。** 契約 HTML の表は、CSS がどのクラスを選んでいるかの一覧でもある。層に分けるときに、規則をどの層へ入れるかの判断に使える。
- **S2 → S3 → S4 の順。** S2 と S3 は CSS だけを触り、S4 は Ruby だけを触る。S3 は `epub_builder.rb` の中の CSS の処理（`sanitize_epub_css!`・`bundle_book_settings_for_epub!`）を無くすので、S4 の分割の対象が減る。
- **S5 は S2〜S4 と独立している。** 設定と段の表だけを触る。手が二つあるなら、CSS の作業と並行して進められる。同じファイル（`pipeline.rb`・`common.rb`）を S4 と S5 が触るので、並行するなら S4 より先に S5 を終える。
- **S6 は S1・S3・S5 の後。** テーマは、契約 HTML（S1）・層と平らな CSS（S2・S3）・`theme.name` と種類の既定値（S5）の三つを前提にする。
- **S7 は入口に実験を置く。** 公式テーマを vs の HTML に当てて組めるかは、まだ確かめていない。実験の結果で、取り込みの範囲を決める（`theme-contract-spec.md` §9 の S7）。小説の既定のテーマは vs が書くので、S7 の結果は S8 を止めない。S7 と S8 は入れ替えてもよい。
- **S8 → S9 → S10 の順**は、ユーザーの方針（縦書きの小説 → 絵本 → 動く絵本）による。小説は今の出力の形（リフロー）のまま軸を一つ変える本で、絵本は固定レイアウトという新しい経路を足す本、動く絵本は絵本に素材を一つ足す本である。

### 2.3 単独で公開できるか

| 問い | 答え |
| :--- | :--- |

## 3. 確かめ方（共通）

### 3.1 写しの本

確かめのビルドは、リポジトリの中ではなく、本を複製したディレクトリで行う。

- `scripts/build_copy.rb`（S0 で作る）が、本の素材（`config/`・`contents/`・`stylesheets/`・`themes/`・`images/`・`covers/`・`codes/`・`data/`・`templates/`・`package.json`）を作業用のディレクトリへ複製し、`node_modules` はリンクで済ませ、`book.yml` に上書きを当ててから、作業ツリーの `bin/vs build` を走らせる。
- 上書きは必ず次の二つを含む。`output.pdf_preview.close_existing_windows: false`（確かめのビルドが、ユーザーの開いているプレビューの窓を閉じないようにする）と、`output.targets`（比べたい出力先）。
- 長いビルドは `caffeinate -i` を付けて走らせる（開発機は 1 分でスリープする）。
- `v2` の作業ツリーから `rake reinstall` はしない。ユーザーが普段使う `vs` は 1.x のままにする。

### 3.2 基準（S0 で作る）

master の、`v2` を切った時点のコミットで、次の本を組み、出力を基準として残す。置き場はリポジトリの外（`../vivlio-starter-v2-baseline/`）とし、コミットしない。基準のディレクトリには、組んだコミットのハッシュと、道具の版（`@vivliostyle/cli`・Chromium・Kindle Previewer・Ruby）を書いたファイルを置く。

| 基準 | 本と設定 | 出力先 |
| :--- | :--- | :--- |
| B1 | 本書（今の `book.yml`） | `pdf`・`print_pdf`・`epub`・`kindle` |
| B2 | 本書で `theme.style: simple` | `pdf` |
| B3 | 本書で `page.section_pagebreak: true`・`chapter_pagebreak: recto`・`page.use: b5_standard` | `pdf` |
| B4 | 分冊の確かめに使った本（`multivolume-spec.md` の確かめの本）の 1 巻 | `pdf`・`epub` |
| B5 | B1 を `VIVLIO_PDF_PLUGIN=disable` で | `pdf` |

- B1 の Kindle は、KPF に加えて、Kindle 用の EPUB（`--no-clean` で残す）・変換の記録・変換の中間生成物の `computedstyle`（`scripts/kfx_probe.rb` の読み方。`kindle-css-compatibility-notes.md` §2.1）・Kindle Previewer の画面（章扉・節見出し・囲み・コード・表・索引・用語集・前書き・付録・奥付の 10 か所）を残す。
- B1 の EPUB は、Apple Books の画面を同じ 10 か所で残す（開き方と消し方は `v2-feasibility-notes.md` §7）。
- 基準を作ったら、同じコミットでもう一度 B1 を組み、PDF の画素の差が 0、EPUB の中身の差が §3.4 の「無視する差」だけであることを確かめる。これで、比べる道具が、ビルドごとに変わる値を差として数えないことを確かめる。
- 道具の版が上がったとき（Vivliostyle・Chromium・Kindle Previewer）は、基準を作り直す。その版の基準を組んだコミットを作業ツリーで取り出して組む。

**基準の版（`v2-post-s3-consultation.md` §5.6 の 1）。** 見た目を変える変更（§4.1）が入ると、S0 の基準とは一致しなくなる。許す差を表で持つ方法は採らない。画素の比べは許容 0 を原則にしており（§3.3）、差を許したページでは新しい差を見分けられなくなるためである。基準を作り直して版を付ける。

| 版 | 組むコミット | 前の版から変わったもの |
| :--- | :--- | :--- |
| r1 | master の、`v2` を切った時点（S0 の基準） | — |
| r2 | S3 の完了の後、1.0.1 を取り込んだコミット（`e01448df`）。2026-11-16 に作成（§8.11） | S2-4（B4 の前書きの 3 ページ）、#132（PDF の付録のページ・Kindle の付録の囲みの色）、S3-4（Kindle の 46 種類）、1.0.1 の原稿の追記（22 章で 1 ページ増える）と #133（キーの書体）・#135（寄せの中の段落） |
| r3 | S6 の完了の後、S7 の前（下の「r3」）。未作成 | 変数の名前・CSS の読む順（theme 層とテーマの出力先の CSS）・画像の置き場・CSS のコメントの `EpubBuilder`・（決めた場合は）節リード |

**r3（`v2-s6-consultation.md` §4.9）。** S6 の間は r2 のままとし、S6 の完了も r2 と比べる。S6 の変更は見た目を変えず、r2 との比べ（PDF は画素、HTML はバイト単位、CSS は計算値、Kindle は中間生成物）は最後まで成り立つ。途中で上げても、組み直しと画面の撮り直しが増えるだけで、比べられるものは増えない。r3 は、S6 の完了のコミットの後、S7 の前に、1 回だけ次の順で作る。

1. S6 の完了のコミット（r2 と比べ、差が `theme-contract-spec.md` §9 の S6 の「EPUB の比べ」の説明のつく字面の差だけ）。
2. CSS のコメントの `EpubBuilder`（S4 で消したクラスの名前。14 か所・7 ファイル）を直すコミット。S6 の中に入れないのは、EPUB の CSS の字面を変え、S6-1・S6-3 の「前後でバイト単位で同じ」の比べに関係の無い差が混ざるためである。
3. 節リードの決定（§4.1 の決まりで、この時点に置いてある）。見た目を変えるなら、ユーザーの了承を得てコミットする。
4. r3 を作る（B1〜B5 を全部組み直す・B1 を二度組む・画面を撮り直す）。`VERSIONS.md` の「前の版から変わったもの」に、上の表の行の中身を書く。


- 置き場は `../vivlio-starter-v2-baseline/r2/` のように、版ごとのディレクトリとする。前の版は消さずに残す（S0 の基準は `r1`）。
- r2 の起点は、相談文では S3-4 のコミット（`6aabe1cb`）だった。その後、master の 1.0.1 を `v2` へ取り込んだので、取り込みのコミットを起点にする（S4 は取り込みの後のコードを分割するため）。
- B4 は、本の `stylesheets/` を作業ツリーのものに差し替えた写しで組む（手を入れていない雛形の本に `vs upgrade` を掛けたのと同じ形）。S6-3 からは、作業ツリーの `themes/` も置く（`themes/standard/` が無いと 🔴 で止まる）。1.x の CSS のまま v2 で組むと、書体が読めず、ページ数も変わる。
- 新しい版は、B1〜B5 の全部を組み直す。段階の確かめの出力（`check/` の下）を基準に流用しない。確かめの出力は、途中のコミットで組んだものや、一部の基準しか組んでいないものを含むためである。
- B1 は二度組み、PDF の差が 0 ページ、EPUB の差が §3.4 の「無視する差」だけであることを、版ごとに確かめる。S3 で入った生成（`AuthorPriority`・`LiteralResolver`）が、組むたびに同じ出力を返すことの確かめを兼ねる。
- Kindle Previewer と Apple Books の 10 か所の画面を撮り直す。Kindle の Location は CSS で変わるので、着いた頁を文字で確かめて、場所の表を作り直す。
- 基準のディレクトリの `VERSIONS.md` に、前の版から変わったものを書く。新しい版は「前の版に、説明のついた差だけを足したもの」であり、その鎖は各段階の実装記録（S3 は `css-layer-restructure-spec.md` §10.5〜§10.10）が支える。
- 見た目を変える変更が後から入ったときは、変わった出力先の基準だけを組み直して、版を上げる（r3…）。
- 各仕様書の完了の条件の「S0 の基準」は、「その時点の基準」（最新の版）と読み替える（§4.1）。

### 3.3 PDF の比較

- `scripts/pdf_pixel_diff.rb <基準の PDF> <新しい PDF> [--out <ディレクトリ>]`（S0 で作る）。両方の PDF をページごとに画像にし（`pdftoppm`・100dpi）、画素を比べ（ImageMagick の `compare -metric AE`・許容 0）、違うページの番号と、差の画像を出す。ページ数が違えば、それも報告する。
- 完了の条件に「全ページの画素が一致する」と書いた段階は、この道具の報告が 0 ページであることを指す。
- 差が出たら、差の画像でどの部品かを特定し、原因の規則を直す。「差は小さいので許す」とはしない。例外は、仕様書がその段階で明示したもの（`css-layer-restructure-spec.md` §8 の `flat_literal` の参考の比較）だけとする。
- 文字の位置だけを比べる場合（配色のテーマで色だけが変わることの確かめなど）は、`pdftotext -bbox` の座標を比べる。

### 3.4 EPUB の比較

- `scripts/epub_diff.rb <基準の EPUB> <新しい EPUB>`（S0 で作る）。両方を展開し、ファイルの一覧の差と、テキストのファイル（XHTML・CSS・OPF・NCX）の差を出す。画像と書体は、ハッシュで比べる。
- 無視する差は、道具の中の表に明示する。今分かっているのは、OPF の更新の日時（`dcterms:modified`）だけである。S0 で二度組んで見つかった差を足す。
- どの段階でどの差を許すかは、各仕様書の完了の条件に書いてある（S1 は `role` 属性の追加、S3 は CSS のファイルの形、S4 の第二段階は属性の順と空白）。それ以外の差があれば、完了としない。
- EPUBCheck がエラー・警告とも 0 であることを、毎回確かめる。

### 3.5 Kindle の比較

Kindle は、変換の後の表示を機械で比べられない。次の三つを組にして確かめる。

1. **変換の記録**: Enhanced Typesetting が Supported で、出力が KPF（Mobi でない）。エラーが 0。警告は、基準と同じコードだけ。
2. **計算済みの値**: 変換の中間生成物（`preprocessed/*.xhtml`）の `computedstyle` を、基準と比べる。色・寸法・`display` の値が同じであること。S3 で CSS の作り方を変えるので、S3 の小段階ごとに比べる。
3. **画面**: Kindle Previewer で、§3.2 の 10 か所を基準の画面と見比べる。組み直したら、Kindle Previewer を終了してから開き直す。

2 が同じでも 3 を省かない。KFX は、計算済みの値を描画の側で捨てることがある（`kindle-css-compatibility-notes.md` §2 の `calc()`）。

### 3.6 設定の組み合わせ

`settings` 層と、設定で変わる段（単章・preflight・分冊）は、B1 だけでは通らない経路がある。S2・S5・S6 の完了の条件には、B2〜B4 との比較と、次の実行を含める。

- 単章のビルド（`bin/vs build 21`）と `bin/vs preflight` が通る。
- `rake test`・`rake test:standard`・`rake test:layout` が通る。
- S4・S6・S11 では `rake test:release` を通す（1 段ずつ走らせ、記録をファイルへ残す。中断した段をそのまま走らせ直さない）。

**S6 の時点（`v2-s6-consultation.md` §4.3）。** 小段階の番号は `theme-contract-spec.md` §9 の S6。

## 5. 既存の本の移行

### 5.1 `book.yml`

| 対象 | 2.0 での扱い | 著者がすること |
| :--- | :--- | :--- |
| `book.type` が無い | `techbook` として読む | なし。`vs upgrade` が、新しいキーとして `type: techbook` を足す（今の「新しいキーを足す」仕組み。`BookKeyInserter`） |
| `page.writing_mode`・`page.layout`・`theme.name`・`lint.ruleset`・`notation.web_novel` が無い | 既定値（横書き・リフロー・`standard`・`technical`・無効）で読む | なし。`vs upgrade` が足す |
| `theme:` 節（`color`・`style`・`frontispiece.*`・`ornament.*`・`markers.*`・`lead_size` など） | そのまま `standard` テーマのオプションとして読む | なし |
| `output.epub.layout`・`output.kindle.layout` | 廃止。読まずに案内を出す（`config-retirement-guidelines.md`） | なし。`vs upgrade` が行を消す |
| それ以外のキー | 変えない | なし |

- 2.0 で廃止するキーは、この 2 つだけである。`theme:` 節のキーを残すのは、技術書の `book.yml` の中でいちばん著者が手を入れている節で、名前を変える利益が移行の手間に見合わないためである。
- 「旧キーを読む期間」は置かない。廃止の型は「読まずに、どうすればよいかを案内する」で、2 つのキーは `reflowable` しか有効な値が無かったので、読まなくても結果は変わらない。
- 個別の仕様（小説・絵本）でキーが増えても、技術書の `book.yml` には載せない（種類ごとの雛形。`v2-architecture-spec.md` §2.6）。`vs upgrade` が足す新しいキーは、その本の種類の雛形にあるキーだけとする。

### 5.2 原稿

原稿（`contents/*.md`）と `catalog.yml` は、書き換えが要らない。

- 記法は足すだけで、変えない。
- 小説投稿サイトの記法（`|漢字《かんじ》`・`《《…》》`）は、`notation.web_novel` が有効な本でだけ読む。技術書の既定は無効なので、原稿の中のこれらの字の並びは、今と同じに組まれる。
- 行内の属性の記法（`[文字]{.class}`）は、どの本でも読む。今の原稿に、`]` の直後に `{.` が続く箇所があると、組まれ方が変わる。`vs upgrade` が原稿を走査し、該当の箇所があれば 🟡 でファイル名と行番号を示す（コードの中は除く）。本書には該当が無いことを S8 で確かめる。

### 5.3 `stylesheets/` とテーマ

`vs upgrade` は、`config/scaffold.lock` の `scaffold_version` が 2.0 より前の本を、次の順で移す。

1. **変えるものを全部見せる。** 消すファイル・置くファイル・退避するファイル・`book.yml` に足すキーと消すキー・`custom.css` の置き換えの行を一覧にし、確認を取る。「いいえ」なら何も変えない。
2. **1.x の雛形の CSS を片付ける。** `stylesheets/` の、1.x の雛形にあったファイル（`custom.css` を除く 26 ファイルと `_README.md`）を、`scaffold.lock` のハッシュと比べる。
   - 一致する（著者が変えていない）ファイルは消す。
   - 一致しない（著者が変えた）ファイルは、`stylesheets/_v1/` へ移す。
3. **2.0 の配置を置く。** `stylesheets/` の新しい配置（`css-layer-restructure-spec.md` §3.1）と、`themes/standard/` を置く。
4. **扉絵・節絵の画像。** `stylesheets/images/` の、雛形にあった画像は `themes/standard/images/` に置き換わるので消す。著者が足した画像（`scaffold.lock` に無いもの）は、そのまま残す。`theme.frontispiece.image` などの画像の指定は、(1) 本の直下からのパス、(2) `stylesheets/images/` の中の名前、(3) テーマの `images/` の中の名前、の順に探すので、1.x の指定のまま通る。

6. **`scaffold.lock` を 2.0 の内容に書き換える。**
7. **退避したファイルがあれば、次にすることを示す。**

   ```

           stylesheets/_v1/components.css
           stylesheets/_v1/table.css

   ```

- 移行は、Git の作業ツリーがきれいな状態で行うよう、最初に確かめる。変更があれば、コミットしてから行うよう案内して止まる。移行の結果は 1 つのコミットにまとめられる。

## 6. 1.x との並行

### 6.1 ブランチと作業ツリー

| 項目 | 決まり |
| :--- | :--- |
| 2.0 の作業 | `v2` ブランチ。作業ツリーは `../vivlio-starter-v2` |
| 1.x の保守 | master（今と同じく直接コミットする） |
| 修正の流れ | master → `v2` の一方向。`v2` の変更を master へ戻さない |
| `v2` のコミット | 段階（小段階）ごとに、ユーザーの了承を得てから |
| `rake reinstall` | `v2` の作業ツリーからは実行しない。確かめは作業ツリーの `bin/vs` で行う |

### 6.2 master を `v2` へ取り込むとき

- 取り込みは、段階の区切り（小段階の完了の後、次に着手する前）に行う。段階の途中では取り込まない。比べる相手（基準）が動くと、差の原因が分からなくなる。
- 取り込んだ変更が、技術書の出力を変えるもの（CSS の修正・後処理の修正）なら、master のそのコミットで基準を作り直す（§3.2）。
- 衝突しやすい場所と、解き方:

  | 場所 | 解き方 |
  | :--- | :--- |
  | `stylesheets/*.css`（S2 の後は、`v2` に同じファイルが無い） | master の修正を、`v2` の対応するファイル（`parts/`・`targets/`・`themes/standard/`）へ手で写す。マージのコミットの説明に、どの修正をどこへ写したかを書く |
  | `lib/project_scaffold/` | どちらの側でもよいので衝突を解き、`ruby scripts/copy_to_scaffold.rb` で作り直す。手では合わせない |
  | `build/epub_builder.rb`（S4 の後は、`v2` に無い） | master の修正を、`v2` の対応するファイル（`build/transforms/`・`build/epub/`）へ手で写す |
  | `config/book.yml`・`config_keys.rb` | 両方の変更を残す。`config_keys_test.rb` が、食い違いを見つける |

- S2 と S4 は、master との差が大きくなる段階である。着手の直前に master を取り込み、短い期間で終える。master の CSS は当面変えない予定（2026-11-14 ユーザー確認）なので、S2 は技術書典の締切（12/6）を待たずに着手できる。master の CSS を変えることになった場合は、上の表のとおり手で写す。

### 6.3 1.x の保守

- 期間: 2.0 の公開から 3 か月。
- 中身: 不具合の修正と、依存の更新だけとする。新しい機能は入れない。
- 2.0 の公開の前に master で行う予定の作業（`PLANNED.md`・`v2-design-research-brief.md` §5）は、今までどおり master で行い、`v2` へ取り込む。
  - Ruby 4.1.0 への対応（2026-12-25 の公開の後）
  - Kindle Previewer 3 の扱いの削除（2027 年 1 月）
  - 文字の色を変えるインライン記法（`PLANNED.md`・1.1.0 で公開したいもの）。これは `v2-architecture-spec.md` §7.1 の「行内の属性の型」と同じ仕組みである。master で 1.1.0 として作り、`v2` はマージで受ける。2.0 の傍点と縦中横（手で指定）は、その仕組みにクラスを足すだけになる。S8 より前に master で作られていなければ、S8 で `v2` に作る（master へは戻さない）

### 6.4 ユーザーの本の移行

- 時期: S11。技術書典の 6 冊は、1.x で組んで頒布した後に移す。頒布の前には移さない。
- 手順（1 冊ごと）:
  1. 1.x で、四つの出力先（その本が使っているもの）を組み、出力を残す。
  2. 本をブランチに分け、2.0 の `vs upgrade` を掛ける。
  3. 2.0 で組み、`scripts/pdf_pixel_diff.rb` で PDF を比べる。差のあるページを、ユーザーが見て判断する。
  4. Kindle を出している本は、Kindle Previewer の画面を見比べる。
  5. ユーザーが了承したら、ブランチをマージする。
- 分冊の本（上下巻）は、巻ごとに 1〜4 を行う。
- 移行で見つかった不具合は、2.0 の不具合として `v2` で直す。6 冊を移し終えるまでは、2.0.0 を公開しない（§4.3 の 3）。

### 8.4 S2-3 `!important` を無くす（2026-11-14）

作ったもの・仕様と違えたこと・確かめた結果は `css-layer-restructure-spec.md` §10.3。ここには、確かめ方（§3）について分かったことを書く。

- **`css_cascade_diff.rb` は、選択子を書き換えた規則を比べない。** 道具は前後の宣言を「文脈・選択子・プロパティ・値」の鍵で突き合わせるので、選択子を書き換えた規則は「なくなった規則」と「増えた規則」になり、勝ち負けの比べから外れる。S2-3 では節リードの選択子を絞ったので、その分を別の方法で確かめた。同じ XHTML（組み上がった EPUB を展開したもの）に、前の版と後の版の入口を平らにした CSS を当て、Chromium で全要素と `::before`・`::after` の計算値を取り、要素ごとに比べる（画面と印刷の両方の媒体）。使い捨てのスクリプトで行い、比べ方が差を拾うことは、simple と image の見出しで節リードの余白の計算値が違うことで確かめた。S3 で、Kindle の中間生成物の比べと合わせて道具にする。

### 8.5 S2-4 前書き・後書きをそろえる（2026-11-15）

作ったもの・仕様と違えたこと・確かめた結果は `css-layer-restructure-spec.md` §10.4。ここには、確かめ方（§3）について分かったことを書く。

- **ページの種類が読む規則を変えたら、計算値を全文書で比べる。** S2-3 の比べ方（同じ HTML に前後の CSS を当て、Chromium で全要素と `::before`・`::after` の計算値を取る）を、PDF 用 HTML（層ありの入口と平らにした CSS）・EPUB・Kindle 用 EPUB の全文書に広げた。前の版の CSS は、そのリビジョンの `EntryWriter` と `Flattener` で作る。道具にした（`scripts/css_computed_diff.rb`。Chromium の部分は `scripts/css_computed_styles.mjs`）。
  - 計算値は `document.fonts.ready` を待ってから取る。待たないと、同じ CSS どうしでも、書体の読み込みの途中で組まれた要素の高さが違う。
  - 疑似要素は `content` が `none` でも項目を残す。前後で `content` の有無が変わると、要素の並びがずれて突き合わせられなくなる。
  - 背景画像の `url()` は、前と後の CSS を置いた場所の名前が入るので、置き場の部分をそろえてから比べる。
- **本書に無い記法は、章の HTML を前書きに付け替えて確かめる。** 前書きに当たる規則が変わったので、本書の章・付録の HTML の body のクラスを `preface` に付け替え、前後の CSS を当てて比べた（`css_computed_diff.rb --as preface`）。囲み・見出し・図など、本書の前書きに無い記法でどう変わるかが、ビルドせずに一覧になる。
- **Chromium は Vivliostyle だけのプロパティを計算しない。** `text-spacing`・`margin-break`・`string-set` は計算値に出ないので、新しく当たる規則を CSS の文字列で拾って読む。S2-4 では、見出しの `text-spacing: no-autospace` が前書きの h1〜h3 に当たるのを見つけ、打ち消した。
- **Kindle の中間生成物で差 0 でも、`:is()` の規則は画面で確かめる。** 変換の前処理は KFX の描画が捨てる規則を映さない。S2-4 で、`:is()` を含む打ち消しの規則に別の打ち消しをまとめかけた（KFX では両方消える）。前書き・後書きの 9 画面を、前後の KPF で撮って比べた。Kindle Previewer の窓の番号と位置は、基準の `tools/kindle_window.rb` で取る（JXA で `$.CFBridgingRelease` を使うと osascript が落ちたので、`ObjC.castRefToObject` で包む）。
- **Kindle の中間生成物は、S2-3 の記録（`check/s2-3-b1/kindle-record/`）と比べる。** S2-4 の記録は `check/s2-4-b1/kindle-record/`（一回分）。比べるのは `scripts/kindle_record_diff.rb`（S1 からの使い捨てのスクリプトを道具にした）。`style` 属性は宣言の単位で比べ、並び順だけの違いを外す。

### 8.6 S3-1 平らな CSS（2026-11-15）

作ったもの・仕様と違えたこと・確かめた結果は `css-layer-restructure-spec.md` §10.5。ここには、確かめ方（§3）について分かったことを書く。

- **EPUB の CSS は、規則の単位で比べる。** CSS をどこで書き換えるかを変えた段階（組み上がった EPUB を開いて後片付けする → 生成の段で落とす）では、出力の CSS の空白とコメントが変わる。crass で規則に分け、コメントと空白を外した文字列の多重集合と並びを比べた。差 0 なら、表示は前の段階と同じと言える。比べ方が差を拾うことは、クリーン EPUB と Kindle 用 EPUB（WebP と data URI の宣言が違う）で確かめた。
- **層を外したときの検査は、組み上がった HTML で絞った数を見る。** 静的に挙がる組の数は判定の広さで 8 にも 842 にもなるが、本書と B4 の HTML で両方の選択子に当たる要素がある組は 4 組だった。どちらの数で判断するかで、問題の大きさの見え方が変わる（`v2-flat-cascade-consultation.md` §2）。
- **`VS_CSS_FORM=flat` の確かめは、入口のファイルの中身も見る。** 環境変数が届かないと層ありのまま組まれ、画素は当然一致する。組んだ写しの `.cache/vs/entry-*.css` に `@layer`・`@import` が無いことを確かめてから比べた。
- **zsh では `set -- $変数` で語が分かれない。** 確かめのシェルの一行で使うと、`cd` に失敗した `find` がホームディレクトリを走査した。比べの使い捨ての処理は Ruby で書く（CLAUDE.md の決まりのとおり）。

### 8.7 S3-2 規則の集約（2026-11-15）

作ったもの・仕様と違えたこと・確かめた結果は `css-layer-restructure-spec.md` §10.6。ここには、確かめ方（§3）について分かったことを書く。

- **規則を別の層へ移したら、同じ選択子で覆っている規則を探す。** `stylesheets/` の Kindle の規則を target 層へ移すと、`book-settings.css`（settings 層）が同じ選択子で後から覆っていた規則が負けた。規則の文字列の比べ（移した規則の数と中身は前後で同じ）では見つからず、組み上がった HTML に前後の CSS を当てた計算値の比べで見つかった。層をまたぐ移動では、計算値の比べを先に走らせる。
- **比べの道具も、ビルドと同じ CSS を作っているか確かめる。** `css_computed_diff.rb` は target 層なしで平らにしていた。S3-1 までは target 層が空だったので差が出なかったが、S3-2 の移動を比べると、EPUB と Kindle に移した規則が後の側に入らない。道具の CSS の作り方を `Css::Bundle` に合わせた。生成物の分け方を変えたときは、後の側にだけ新しいコードで生成した `book-settings*.css` を渡す（`--after-settings`）。
- **検査が見ている HTML が、出力と同じ段のものか確かめる。** ビルドの層の検査は、HTML の書き換えの前に走っており、Kindle の規則を一つも見ていなかった（S3-1 から）。検査の報告が 0 でも、組み上がった HTML に同じ検査を当てて数と突き合わせる。

### 8.8 S3-3a リテラル化（2026-11-15）

作ったもの・仕様と違えたこと・確かめた結果は `css-layer-restructure-spec.md` §10.7。ここには、確かめ方（§3）について分かったことを書く。

- **Kindle の見た目のモデルは、Chromium の計算値ではなく中間生成物である。** `css_computed_diff.rb` の Chromium は `var()` を解くので、Kindle で捨てられていた宣言も効いたものとして計算する。Kindle Previewer の前処理は `var()` を含む宣言を捨てるので、中間生成物の `computedstyle`・`style` が、Kindle に届いている宣言を映す。部品の層まで値に解いたとき、計算値の比べでは差が小さく見え（`:has()` などの数十要素）、中間生成物では 26,310 要素が変わった。Kindle に届く宣言を変える段では、中間生成物を先に比べる。
- **比べの道具の判定の前提を、出力の見出しで確かめる。** `css_computed_diff.rb` は、出力の行に判定したページの種類（`（chapter・flat・screen）`）を出している。S3-2 から全部が `chapter` だったが、差 0 の報告では見出しを読まないので気づかなかった。差が出たときに、付録の差の原因を追って見つけた。
- **確かめの写しの元は、CSS を直した後に作り直す。** custom.css を書き足した写しの元を、`targets/kindle.css` を直す前の写しから作っていたため、1 規則が欠けたまま組んだ。元を作業ツリーと `diff -r` で比べてから組む。

### 8.9 S3-3b `custom.css` を平らな CSS でも勝たせる（2026-11-15）

作ったもの・仕様と違えたこと・確かめた結果は `css-layer-restructure-spec.md` §10.9。ここには、確かめ方（§3）について分かったことを書く。

- **著者の CSS の効き方は、出力先が組み替えた HTML でも確かめる。** 付けない場合の決まり（`style` 属性に当たるなら付けない）は、PDF にもある `style` 属性を前提にしていた。Kindle は写真の並びを表に組み替えて `style` 属性を付けるので、`table { … }` の 1 行が章の束の全部の表で付かなくなった。単体のテストは PDF の HTML の形で書いていたので見つからず、写しの本を Kindle まで組んで、中間生成物の表の幅を数えて見つかった。
- **計算値は、組み方の違いと勝ち負けの違いを分けて数える。** Chromium の表の幅は、PDF の `.text-table`（横並びの片側）で 0 になる。勝つ宣言は PDF と EPUB で同じで、違うのは箱の組み方である。比べの道具は「勝った値」ではなく「組んだ大きさ」を返すので、食い違いが出たら、まずその要素の組み方が出力先で同じかを見る。
- **`kindle_record_diff.rb` の「位置と大きさを除く」は、`contentTop`・`contentBottom` を除かない。** 余白を足した写しでは、後ろの要素の大半がこの二つだけで差に数えられた。差の数が大きいときは、プロパティの名前ごとに数え直してから読む。

### 8.10 S3-4 Kindle に部品の値を届ける（2026-11-15）

作ったもの・仕様と違えたこと・確かめた結果は `css-layer-restructure-spec.md` §10.10。ここには、確かめ方（§3）について分かったことを書く。

- **中間生成物の差は、`style` で数える。** 部品の層を解いて届いた宣言は、ほとんどが `computedstyle` に出ず（`computedstyle` の差は図のキャプションの字の大きさだけ）、`style` に出た。`kindle_record_diff.rb` の合計は `contentTop`・`contentBottom` の差で数万になるので、プロパティ・前後の値・要素ごとに数え直してから読む（使い捨ての集計で行った）。
- **Location は CSS で変わる。** 本文の文字が同じ EPUB でも、CSS を変えると同じ頁が別の Location に出る（第 1 章の扉が S3-3b では 130、S3-4 では 148）。基準の表の Location で撮った前後の画面は、別の頁どうしになる。画素の近さで頁を探す方法も、文字の頁どうしが近く出て使えなかった。撮った頁を `tesseract -l jpn` で読み、本文の中の位置を求めて、目的の文字列のある頁まで Location を寄せて撮った（使い捨ての道具。スクラッチに置いた）。ある Location へ移動すると、その Location を含む頁ではなく、近くの頁の先頭が出ることがある。目的の頁が出ないときは、矢印のキーで頁を送る。
- **Kindle Previewer は Mac の書体で描く。** 書体の名前が届くと、Previewer は Mac に入っている書体（HackGen）を使う。端末には無い書体なので、画面が端末と違う。書体を埋め込まない Kindle には、総称の名前だけを渡す。
