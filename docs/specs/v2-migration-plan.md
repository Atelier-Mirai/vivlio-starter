## 1. 前提

- 本の種類の順序は、縦書きの小説 → 絵本 → 動く絵本。三つとも 2.0 に含める（`v2-design-research-brief.md` §5）。
- 見た目が変わる変更（HTML の構造など）は 2.0 で入れる。1.x の小さな版には入れない。
- 技術書典の 6 冊（登録の締切 2026-12-06）は 1.x で組む。2.0 の作業は、この 6 冊の作業を妨げない。
- 実装は Opus が段階ごとに行う。各段階は、仕様書の該当の節を読めば着手できるように書いてある。段階の途中で仕様書と実物が食い違ったら、実装を進める前にユーザーに知らせる。

### 2.2 順序の理由

- **S0 を最初に置く。** S1〜S7 の完了の条件は、どれも「技術書の出力が変わらない」である。比べる相手（基準）と比べる道具が無いと、どの段階も完了を言えない。
- **S1 を S2 より先に置く。** 契約 HTML の表は、CSS がどのクラスを選んでいるかの一覧でもある。層に分けるときに、規則をどの層へ入れるかの判断に使える。
- **S2 → S3 → S4 の順。** S2 と S3 は CSS だけを触り、S4 は Ruby だけを触る。S3 は `epub_builder.rb` の中の CSS の処理（`sanitize_epub_css!`・`bundle_book_settings_for_epub!`）を無くすので、S4 の分割の対象が減る。
- **S5 は S2〜S4 と独立している。** 設定と段の表だけを触る。手が二つあるなら、CSS の作業と並行して進められる。同じファイル（`pipeline.rb`・`common.rb`）を S4 と S5 が触るので、並行するなら S4 より先に S5 を終える。
- **S6 は S1・S3・S5 の後。** テーマは、契約 HTML（S1）・層と平らな CSS（S2・S3）・`theme.name` と種類の既定値（S5）の三つを前提にする。
- **S7 は入口に実験を置く。** 公式テーマを vs の HTML に当てて組めるかは、まだ確かめていない。実験の結果で、取り込みの範囲を決める（`theme-contract-spec.md` §9 の S7）。小説の既定のテーマは vs が書くので、S7 の結果は S8 を止めない。S7 と S8 は入れ替えてもよい。
- **S8 → S9 → S10 の順**は、ユーザーの方針（縦書きの小説 → 絵本 → 動く絵本）による。小説は今の出力の形（リフロー）のまま軸を一つ変える本で、絵本は固定レイアウトという新しい経路を足す本、動く絵本は絵本に素材を一つ足す本である。

### 2.3 単独で公開できるか

| 問い | 答え |
| :--- | :--- |
| 各段階の後、`v2` ブランチは使える状態か | 使える。S1〜S7 は技術書の出力を変えないことを完了の条件にしているので、どの段階の後でも、本書と技術書典の本を `v2` の `bin/vs` で組める |
| 1.x の小さな版として出す段階はあるか | 無い。層に分ける S2 は見た目を変えないが、著者の本の `stylesheets/` を全部入れ替える更新になる（`css-layer-restructure-spec.md` §8）。HTML が変わる S1 は 2.0 に限る方針である |
| 2.0.0 の前に、途中の版を配るか | §7 の論点 1。配るなら、S7 の後（基盤ができ、技術書が 2.0 の仕組みで組める）と、S8 の後（小説が組める）が区切りになる |

## 3. 確かめ方（共通）

### 3.1 写しの本

確かめのビルドは、リポジトリの中ではなく、本を複製したディレクトリで行う。

- `scripts/build_copy.rb`（S0 で作る）が、本の素材（`config/`・`contents/`・`stylesheets/`・`themes/`・`images/`・`covers/`・`codes/`・`data/`・`templates/`・`package.json`）を作業用のディレクトリへ複製し、`node_modules` はリンクで済ませ、`book.yml` に上書きを当ててから、作業ツリーの `bin/vs build` を走らせる。
- 上書きは必ず次の二つを含む。`output.pdf_preview.close_existing_windows: false`（確かめのビルドが、ユーザーの開いているプレビューの窓を閉じないようにする）と、`output.targets`（比べたい出力先）。
- 長いビルドは `caffeinate -i` を付けて走らせる（開発機は 1 分でスリープする）。
- `v2` の作業ツリーから `rake reinstall` はしない。ユーザーが普段使う `vs` は 1.x のままにする。

### 3.2 基準（S0 で作る）

master の、`v2` を切った時点のコミットで、次の本を組み、出力を基準として残す。置き場はリポジトリの外（`../vivlio-starter-v2-baseline/`）とし、コミットしない。基準のディレクトリには、組んだコミットのハッシュと、道具の版（`@vivliostyle/cli`・Chromium・Kindle Previewer・Ruby）を書いたファイルを置く。

| 基準 | 本と設定 | 出力先 |
| :--- | :--- | :--- |
| B1 | 本書（今の `book.yml`） | `pdf`・`print_pdf`・`epub`・`kindle` |
| B2 | 本書で `theme.style: simple` | `pdf` |
| B3 | 本書で `page.section_pagebreak: true`・`chapter_pagebreak: recto`・`page.use: b5_standard` | `pdf` |
| B4 | 分冊の確かめに使った本（`multivolume-spec.md` の確かめの本）の 1 巻 | `pdf`・`epub` |
| B5 | B1 を `VIVLIO_PDF_PLUGIN=disable` で | `pdf` |

- B1 の Kindle は、KPF に加えて、Kindle 用の EPUB（`--no-clean` で残す）・変換の記録・変換の中間生成物の `computedstyle`（`scripts/kfx_probe.rb` の読み方。`kindle-css-compatibility-notes.md` §2.1）・Kindle Previewer の画面（章扉・節見出し・囲み・コード・表・索引・用語集・前書き・付録・奥付の 10 か所）を残す。
- B1 の EPUB は、Apple Books の画面を同じ 10 か所で残す（開き方と消し方は `v2-feasibility-notes.md` §7）。
- 基準を作ったら、同じコミットでもう一度 B1 を組み、PDF の画素の差が 0、EPUB の中身の差が §3.4 の「無視する差」だけであることを確かめる。これで、比べる道具が、ビルドごとに変わる値を差として数えないことを確かめる。
- 道具の版が上がったとき（Vivliostyle・Chromium・Kindle Previewer）は、基準を作り直す。master の `v2` を切った時点のコミットを作業ツリーで取り出して組む。

### 3.3 PDF の比較

- `scripts/pdf_pixel_diff.rb <基準の PDF> <新しい PDF> [--out <ディレクトリ>]`（S0 で作る）。両方の PDF をページごとに画像にし（`pdftoppm`・100dpi）、画素を比べ（ImageMagick の `compare -metric AE`・許容 0）、違うページの番号と、差の画像を出す。ページ数が違えば、それも報告する。
- 完了の条件に「全ページの画素が一致する」と書いた段階は、この道具の報告が 0 ページであることを指す。
- 差が出たら、差の画像でどの部品かを特定し、原因の規則を直す。「差は小さいので許す」とはしない。例外は、仕様書がその段階で明示したもの（`css-layer-restructure-spec.md` §8 の `flat_literal` の参考の比較）だけとする。
- 文字の位置だけを比べる場合（配色のテーマで色だけが変わることの確かめなど）は、`pdftotext -bbox` の座標を比べる。

### 3.4 EPUB の比較

- `scripts/epub_diff.rb <基準の EPUB> <新しい EPUB>`（S0 で作る）。両方を展開し、ファイルの一覧の差と、テキストのファイル（XHTML・CSS・OPF・NCX）の差を出す。画像と書体は、ハッシュで比べる。
- 無視する差は、道具の中の表に明示する。今分かっているのは、OPF の更新の日時（`dcterms:modified`）だけである。S0 で二度組んで見つかった差を足す。
- どの段階でどの差を許すかは、各仕様書の完了の条件に書いてある（S1 は `role` 属性の追加、S3 は CSS のファイルの形、S4 の第二段階は属性の順と空白）。それ以外の差があれば、完了としない。
- EPUBCheck がエラー・警告とも 0 であることを、毎回確かめる。

### 3.5 Kindle の比較

Kindle は、変換の後の表示を機械で比べられない。次の三つを組にして確かめる。

1. **変換の記録**: Enhanced Typesetting が Supported で、出力が KPF（Mobi でない）。エラーが 0。警告は、基準と同じコードだけ。
2. **計算済みの値**: 変換の中間生成物（`preprocessed/*.xhtml`）の `computedstyle` を、基準と比べる。色・寸法・`display` の値が同じであること。S3 で CSS の作り方を変えるので、S3 の小段階ごとに比べる。
3. **画面**: Kindle Previewer で、§3.2 の 10 か所を基準の画面と見比べる。組み直したら、Kindle Previewer を終了してから開き直す。

2 が同じでも 3 を省かない。KFX は、計算済みの値を描画の側で捨てることがある（`kindle-css-compatibility-notes.md` §2 の `calc()`）。

### 3.6 設定の組み合わせ

`settings` 層と、設定で変わる段（単章・preflight・分冊）は、B1 だけでは通らない経路がある。S2・S5・S6 の完了の条件には、B2〜B4 との比較と、次の実行を含める。

- 単章のビルド（`bin/vs build 21`）と `bin/vs preflight` が通る。
- `rake test`・`rake test:standard`・`rake test:layout` が通る。
- S4・S6・S11 では `rake test:release` を通す（1 段ずつ走らせ、記録をファイルへ残す。中断した段をそのまま走らせ直さない）。

## 4. 各段階の完了の条件

各仕様書の該当の節が正典である。ここには、仕様書に無い S0 と S11 の条件と、全段階に共通の決まりを書く。

### 4.1 全段階に共通

- 段階（小段階）ごとにコミットする。コミットの前に、ユーザーの了承を得る。
- 段階の完了を報告するときは、比べた結果（違ったページの数・EPUB の差の件数・Kindle の三つ）を数字で添える。確かめていないものは、確かめていないと書く。
- `lib/` を変えたら `rake test` と `bundle exec rubocop`、`stylesheets/`・`themes/`・`config/`・`contents/` を変えたら `ruby scripts/copy_to_scaffold.rb` を行う。
- 仕様書と違う実装にした箇所は、その仕様書の末尾に「実装記録」の節を足して書く。段階がすべて終わった仕様書は `docs/archives/` へ移し、`STATUS.md` から行を消す。

### 4.2 S0 基準と道具

- 作るもの: `scripts/build_copy.rb`・`scripts/pdf_pixel_diff.rb`・`scripts/epub_diff.rb`、§3.2 の基準 B1〜B5。
- 完了の条件:
  1. B1〜B5 の出力と、道具の版の記録が、基準のディレクトリにある。
  2. 同じコミットで B1 を二度組み、PDF の差が 0 ページ、EPUB の差が「無視する差」だけ。
  3. わざと CSS を 1 か所変えた写し（本文の文字の色を変える）で、`pdf_pixel_diff.rb` が差のあるページを報告する（道具が差を見つけられることの確かめ）。
- 確かめ方: 上の 2 と 3 の実行の記録。

### 4.3 S11 移行と公開

- 作るもの: §5 の `vs upgrade` の 2.0 への移行、マニュアル（本書の原稿）の更新、移行の手引き、`CHANGELOG.md`。
- 完了の条件:
  1. 1.0.0 の `vs new` で作った本（手を入れていない雛形）に、2.0 の `vs upgrade` を掛け、`vs build` が通る。PDF の全ページの画素が、同じ本を 1.0.x で組んだものと一致する。
  2. §5.5 の移行の見本（`custom.css` で今の名前の変数を使い、雛形の CSS を 1 つ直した本）で、`vs upgrade` が §5 のとおりに働き、確認に「いいえ」と答えると何も変わらない。
  3. ユーザーの本（技術書典の 6 冊を含む）を 2.0 へ移し、移行の前後の PDF を見比べて、ユーザーが了承する（§6.4）。
  4. `rake test:release` が通る。対応する Ruby の全部の版で `rake test:versions` が通る。
  5. 本の `Gemfile` で `vivlio-starter` を `~> 1.0` に固定した 1.x の本が、2.0 を入れたマシンでも `bundle exec vs build` で 1.x のまま組める。
- 確かめ方: 1 と 2 は一時のディレクトリで行う（`vs upgrade` は、写しの本で走らせても brew・npm・gem の更新がマシンに効くので、道具の更新の部分は差し替えて走らせる）。

## 5. 既存の本の移行

### 5.1 `book.yml`

| 対象 | 2.0 での扱い | 著者がすること |
| :--- | :--- | :--- |
| `book.type` が無い | `techbook` として読む | なし。`vs upgrade` が、新しいキーとして `type: techbook` を足す（今の「新しいキーを足す」仕組み。`BookKeyInserter`） |
| `page.writing_mode`・`page.layout`・`theme.name`・`lint.ruleset`・`notation.web_novel` が無い | 既定値（横書き・リフロー・`standard`・`technical`・無効）で読む | なし。`vs upgrade` が足す |
| `theme:` 節（`color`・`style`・`frontispiece.*`・`ornament.*`・`markers.*`・`lead_size` など） | そのまま `standard` テーマのオプションとして読む | なし |
| `output.epub.layout`・`output.kindle.layout` | 廃止。読まずに案内を出す（`config-retirement-guidelines.md`） | なし。`vs upgrade` が行を消す |
| それ以外のキー | 変えない | なし |

- 2.0 で廃止するキーは、この 2 つだけである。`theme:` 節のキーを残すのは、技術書の `book.yml` の中でいちばん著者が手を入れている節で、名前を変える利益が移行の手間に見合わないためである。
- 「旧キーを読む期間」は置かない。廃止の型は「読まずに、どうすればよいかを案内する」で、2 つのキーは `reflowable` しか有効な値が無かったので、読まなくても結果は変わらない。
- 個別の仕様（小説・絵本）でキーが増えても、技術書の `book.yml` には載せない（種類ごとの雛形。`v2-architecture-spec.md` §2.6）。`vs upgrade` が足す新しいキーは、その本の種類の雛形にあるキーだけとする。

### 5.2 原稿

原稿（`contents/*.md`）と `catalog.yml` は、書き換えが要らない。

- 記法は足すだけで、変えない。
- 小説投稿サイトの記法（`|漢字《かんじ》`・`《《…》》`）は、`notation.web_novel` が有効な本でだけ読む。技術書の既定は無効なので、原稿の中のこれらの字の並びは、今と同じに組まれる。
- 行内の属性の記法（`[文字]{.class}`）は、どの本でも読む。今の原稿に、`]` の直後に `{.` が続く箇所があると、組まれ方が変わる。`vs upgrade` が原稿を走査し、該当の箇所があれば 🟡 でファイル名と行番号を示す（コードの中は除く）。本書には該当が無いことを S8 で確かめる。

### 5.3 `stylesheets/` とテーマ

`vs upgrade` は、`config/scaffold.lock` の `scaffold_version` が 2.0 より前の本を、次の順で移す。

1. **変えるものを全部見せる。** 消すファイル・置くファイル・退避するファイル・`book.yml` に足すキーと消すキー・`custom.css` の置き換えの行を一覧にし、確認を取る。「いいえ」なら何も変えない。
2. **1.x の雛形の CSS を片付ける。** `stylesheets/` の、1.x の雛形にあったファイル（`custom.css` を除く 26 ファイルと `_README.md`）を、`scaffold.lock` のハッシュと比べる。
   - 一致する（著者が変えていない）ファイルは消す。
   - 一致しない（著者が変えた）ファイルは、`stylesheets/_v1/` へ移す。
3. **2.0 の配置を置く。** `stylesheets/` の新しい配置（`css-layer-restructure-spec.md` §3.1）と、`themes/standard/` を置く。
4. **扉絵・節絵の画像。** `stylesheets/images/` の、雛形にあった画像は `themes/standard/images/` に置き換わるので消す。著者が足した画像（`scaffold.lock` に無いもの）は、そのまま残す。`theme.frontispiece.image` などの画像の指定は、(1) 本の直下からのパス、(2) `stylesheets/images/` の中の名前、(3) テーマの `images/` の中の名前、の順に探すので、1.x の指定のまま通る。
5. **`custom.css` の変数の名前。** 今の名前（`--theme-accent`・`--color-link` など）を新しい名前（`--book-*`）へ置き換える。置き換えなくても動く（`css-layer-restructure-spec.md` §7.2）ので、ここだけを断ることもできる。
6. **`scaffold.lock` を 2.0 の内容に書き換える。**
7. **退避したファイルがあれば、次にすることを示す。**

   ```
   🟡 雛形の CSS のうち、変更のあった 2 ファイルを stylesheets/_v1/ へ移しました
           stylesheets/_v1/components.css
           stylesheets/_v1/table.css
           2.0 では、これらのファイルは読み込まれません
           変更した規則を stylesheets/custom.css へ写してください（custom.css は、ほかのどの CSS よりも優先されます）
   ```

- 著者が直した雛形の CSS を、新しい配置へ自動で移すことはしない。ファイルの分け方が変わるので、三方向のマージ（`upgrade-three-way-merge-spec.md`）の「同じファイルの祖先」が無い。直した規則を `custom.css` へ写せば、層の外なので必ず効く。
- 退避したファイルの、雛形との差分を見たい著者のために、`vs upgrade` は、差分の出し方（1.x の gem の雛形との `diff`）を 1 行で示す。1.x の gem が残っていない場合は、示さない。
- 移行は、Git の作業ツリーがきれいな状態で行うよう、最初に確かめる。変更があれば、コミットしてから行うよう案内して止まる。移行の結果は 1 つのコミットにまとめられる。

### 5.4 2.0 で見た目が変わりうる箇所

技術書の出力は変えないことを各段階の条件にしているが、著者の `custom.css` によっては変わる箇所がある。移行の手引きに書く。

| 箇所 | 変わる理由 | 確かめ方 |
| :--- | :--- | :--- |
| 1.x で効いていなかった `custom.css` の規則が効く | `custom.css` が層の外になり、詳細度に関係なく勝つ（`css-layer-restructure-spec.md` §7.1） | 移行の前後の PDF を見比べる |
| `custom.css` が、内部のクラス（`theme-contract-spec.md` §2.1）を選んでいる | 内部のクラスは 2.x の間に変わりうる | `vs preflight` が、`custom.css` の選ぶクラスのうち、契約 HTML の保証に無いものを 💡 で示す |
| 章の frontmatter の `link` で足した CSS | 層の外になり、今より強くなる | 同上 |
| EPUB の中の CSS のファイルの構成 | 平らな 1 枚になる | 表示は変わらない |

## 6. 1.x との並行

### 6.1 ブランチと作業ツリー

| 項目 | 決まり |
| :--- | :--- |
| 2.0 の作業 | `v2` ブランチ。作業ツリーは `../vivlio-starter-v2` |
| 1.x の保守 | master（今と同じく直接コミットする） |
| 修正の流れ | master → `v2` の一方向。`v2` の変更を master へ戻さない |
| `v2` のコミット | 段階（小段階）ごとに、ユーザーの了承を得てから |
| `rake reinstall` | `v2` の作業ツリーからは実行しない。確かめは作業ツリーの `bin/vs` で行う |
| 2.0 の公開 | `v2` を master へマージし、1.x の保守は `1.x` ブランチ（公開の時点の master から切る）へ移す |

### 6.2 master を `v2` へ取り込むとき

- 取り込みは、段階の区切り（小段階の完了の後、次に着手する前）に行う。段階の途中では取り込まない。比べる相手（基準）が動くと、差の原因が分からなくなる。
- 取り込んだ変更が、技術書の出力を変えるもの（CSS の修正・後処理の修正）なら、master のそのコミットで基準を作り直す（§3.2）。
- 衝突しやすい場所と、解き方:

  | 場所 | 解き方 |
  | :--- | :--- |
  | `stylesheets/*.css`（S2 の後は、`v2` に同じファイルが無い） | master の修正を、`v2` の対応するファイル（`parts/`・`targets/`・`themes/standard/`）へ手で写す。マージのコミットの説明に、どの修正をどこへ写したかを書く |
  | `lib/project_scaffold/` | どちらの側でもよいので衝突を解き、`ruby scripts/copy_to_scaffold.rb` で作り直す。手では合わせない |
  | `build/epub_builder.rb`（S4 の後は、`v2` に無い） | master の修正を、`v2` の対応するファイル（`build/transforms/`・`build/epub/`）へ手で写す |
  | `config/book.yml`・`config_keys.rb` | 両方の変更を残す。`config_keys_test.rb` が、食い違いを見つける |

- S2 と S4 は、master との差が大きくなる段階である。着手の直前に master を取り込み、短い期間で終える。master の CSS は当面変えない予定（2026-11-14 ユーザー確認）なので、S2 は技術書典の締切（12/6）を待たずに着手できる。master の CSS を変えることになった場合は、上の表のとおり手で写す。

### 6.3 1.x の保守

- 期間: 2.0 の公開から 3 か月。
- 中身: 不具合の修正と、依存の更新だけとする。新しい機能は入れない。
- 2.0 の公開の前に master で行う予定の作業（`PLANNED.md`・`v2-design-research-brief.md` §5）は、今までどおり master で行い、`v2` へ取り込む。
  - Ruby 4.1.0 への対応（2026-12-25 の公開の後）
  - Kindle Previewer 3 の扱いの削除（2027 年 1 月）
  - 文字の色を変えるインライン記法（`PLANNED.md`・1.1.0 で公開したいもの）。これは `v2-architecture-spec.md` §7.1 の「行内の属性の型」と同じ仕組みである。master で 1.1.0 として作り、`v2` はマージで受ける。2.0 の傍点と縦中横（手で指定）は、その仕組みにクラスを足すだけになる。S8 より前に master で作られていなければ、S8 で `v2` に作る（master へは戻さない）
- 1.x の保守を終える条件: 期間が過ぎていること、かつ、ユーザーの本（技術書典の 6 冊を含む）が 2.0 へ移し終わっていること（§6.4）。

### 6.4 ユーザーの本の移行

- 時期: S11。技術書典の 6 冊は、1.x で組んで頒布した後に移す。頒布の前には移さない。
- 手順（1 冊ごと）:
  1. 1.x で、四つの出力先（その本が使っているもの）を組み、出力を残す。
  2. 本をブランチに分け、2.0 の `vs upgrade` を掛ける。
  3. 2.0 で組み、`scripts/pdf_pixel_diff.rb` で PDF を比べる。差のあるページを、ユーザーが見て判断する。
  4. Kindle を出している本は、Kindle Previewer の画面を見比べる。
  5. ユーザーが了承したら、ブランチをマージする。
- 分冊の本（上下巻）は、巻ごとに 1〜4 を行う。
- 移行で見つかった不具合は、2.0 の不具合として `v2` で直す。6 冊を移し終えるまでは、2.0.0 を公開しない（§4.3 の 3）。
