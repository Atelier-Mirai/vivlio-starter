# 索引マークアップ `[用語]` が索引語にならず、`[<h1>]` が本物の見出しになる

> 作成日: 2026-08-11
> ステータス: **実装待ち**
> 対象: 著者が明示した `[用語]` / `[用語|読み]` が索引に載らない不具合と、`[<h1>]` が生タグとして組まれる不具合（2026-08-11 発見）
> 関連: `lib/vivlio_starter/cli/pre_process/markdown_preprocessor.rb`（`strip_index_markup!`）, `lib/vivlio_starter/cli/index_markup.rb`（綴りの正典）, `lib/vivlio_starter/cli/build/pipeline.rb`（`run_step4_index_processing`）
> 先例: `inline-footnote-index-collision-spec.md`（同じ `[…]` 綴りをめぐる 3 箇所コピーの解消。`IndexMarkup` はそこで生まれた）

## 0. なぜこの仕様書があるか

**明示記法が 1 つも機能していない。** 著者が索引に載せたくて書いた `[基本情報技術者]` `[404]` `[!DOCTYPE]` は、角括弧だけ外れて素のテキストになる。`[<h1>]` に至っては生の `<h1>` として VFM に渡り、**本物の章見出しになって目次と PDF アウトラインを汚染する**。

先例（`inline-footnote-index-collision-spec.md`）は「同じ判定が 3 箇所へコピーされていた」問題を `IndexMarkup` へ引き上げて解いた。今回はその続きで、**引き上げ切れていなかったもう 1 つの知識**——「索引スキャナが走らないとき、記法をどう素のテキストへ落とすか」——が前処理側にベタ書きのまま残っていたことが原因である。

アドホックに条件を 1 つ足すのではなく、**何を正典に引き上げるべきか**を決めるためにこの仕様書を書く。

## 1. 症状

`contents/` にこう書く。

```markdown
[HTML]は、文書構造を記述します。
[基本情報技術者]とは、IT資格の中で最も基礎的な資格です。
[引数|ひきすう]は、関数に与える値です。
[404]は、ページが見つからないことを示すHTTPステータスコードです。
[!DOCTYPE]は、文書の種類を示すHTMLの宣言です。
[<h1>]は、見出しタグです。
[</h1>]は、閉じタグです。
```

意図は **7 つすべてが索引語になること**。実際はこうなる（`vs build` 全章・実測）。

| 記法 | 結果 |
| --- | --- |
| `[HTML]` | 索引語になる。ただし**明示記法が効いた結果ではない**——同梱辞書に `HTML` があり、自動索引が裸の `HTML` を拾っただけ |
| `[基本情報技術者]` `[引数\|ひきすう]` `[404]` `[!DOCTYPE]` | 角括弧だけ外れて素通し。索引に載らない |
| `[<h1>]` `[</h1>]` | **本物の見出し要素**になる。間の文章を巻き込み、目次に「は、見出しタグです。」という章が現れる |

生成 HTML:

```html
<h1 class="vs-h-marker" data-heading="は、見出しタグです。" data-h1="は、見出しタグです。"
    id="は、見出しタグです。" data-chapter="01-computer-journey">は、見出しタグです。</h1>
```

**単章ビルド（`vs build <章>`）でも同じ**。`<h1>` `</h1>` が消え、「は、見出しタグです。」だけが本文に残る。

## 2. 原因

### 2.1 前処理が、索引スキャナより先に括弧を外している

`markdown_preprocessor.rb:113` が `strip_index_markup!` を**無条件で**呼ぶ。

```ruby
def strip_index_markup!
  # 索引記法 [用語|読み] を用語テキストのみに展開する。
  # IndexMatchScanner（Step 4）がフルビルド時に <dfn> タグを付与するが、
  # 単章ビルドでは Step 4 がスキップされるため、ここで記法を除去して
  # VFM に渡す前にプレーンテキストにしておく。
```

コメントのとおり、これは**索引スキャナが走らない経路のための代替**である。ところがモード判定が無い。パイプラインの順序は

```
Step 3 前処理（括弧を外す）  →  Step 4 索引スキャン（外れた後なので何も見つからない）
```

なので、全章ビルドでも先に括弧が消える。スキャナは `[404]` に出会えない。

`[HTML]` だけ生き残るのは、自動索引（辞書）が**裸の `HTML`** を拾うためで、明示記法とは無関係である。

### 2.2 素のテキストへ落とすときにエスケープしない

```ruby
inner   # [<h1>] → <h1> をそのまま返す
```

一方、索引スキャナは必ずエスケープする。

```ruby
escaped_term = CGI.escapeHTML(term_text)   # index_match_scanner.rb:620
```

**同じ「索引語を表示する」処理が 2 箇所にあり、エスケープの有無が食い違っている。** 到達していれば `&lt;h1&gt;` と印字されたはずのものが、前処理側では生タグのまま VFM へ渡る。

これは §2.1 とは独立した欠陥で、**単章ビルドでは §2.1 を直しても残る**。

### 2.3 仕様側の意図は明確

```ruby
# index_markup.rb:58
def skip_term?(term_text)
  return true if term_text.nil? || term_text.empty?
  # 脚注参照 [^id]。著者が意図的にマークアップした [!] [&&] [<h1>] は除外しない
  term_text.start_with?('^')
end
```

`[<h1>]` を名指しで「除外しない」と書いてある。**実装が仕様に追いついていない**状態であり、仕様変更ではなく実装の欠落として扱う。

## 3. 索引スキャナが走らない経路（実測）

`strip_index_markup!` の存在理由そのものなので、正確に列挙する。

| 経路 | 索引スキャン | 根拠 |
| --- | --- | --- |
| `vs build`（全章） | **走る** | `register_full_mode_steps` に `index scan and build` |
| `vs preflight` | **走る** | `register_preflight_steps` に同上 |
| `vs build <章>`（単章） | 走らない | `register_single_mode_steps` に当該ステップが無い |
| `index_glossary.enabled: false` | 走らない | `run_step4_index_processing` の第 1 ガード |
| catalog を絞った実行 | 走らない | 同 第 2 ガード（`full_catalog_scope?`） |

**「走るかどうか」は 3 つの独立した条件の合成**であり、しかも 2 つはステップ内部にある。前処理がこれを再計算すると、条件が増えたときに必ず片方が stale になる（`IndexMarkup` が生まれたときと同じ形）。

## 4. 設計

### 4.1 引き上げるもの 1 ── 索引語の「素のテキスト表現」

`IndexMarkup` は**綴りの正典**だが、「素のテキストへ落とした姿」を持っていない。そのため前処理と索引スキャナが別々に実装し、エスケープが食い違った。

```ruby
module IndexMarkup
  # 索引タグを付けられないときの、素のテキスト表現。
  # `[<h1>]` のようにタグの形をした語が生 HTML として流出しないよう、必ずエスケープする。
  # 索引スキャナが <dfn> を作るときの CGI.escapeHTML と表裏一体で、両者は同じ規則に従う。
  def plain_text(term_text)
    CGI.escapeHTML(term_text.include?('|') ? term_text.split('|', 2).first : term_text)
  end
end
```

読み（`|` 以降）を落とす規則も、いまは前処理にしかない。ここへ寄せる。

**なぜ `Masking` ではないのか**は既存コメントの理由（記法の知識は記法のモジュールが持つ）がそのまま当てはまる。

### 4.2 引き上げるもの 2 ── 「索引スキャンが走るか」の述語

§3 の 3 条件を 1 箇所に集約し、前処理とパイプラインの両方がそれを見る。

```ruby
module IndexCommands
  # このビルドで索引スキャンが走るか。
  # 前処理の代替（strip_index_markup!）を出すかどうかの判断もここを見る——
  # 判定を 2 箇所に置くと、条件が増えたとき片方が必ず取り残される。
  def scan_will_run?(entries:) = index_enabled? && full_catalog_scope?(entries) && !single_mode?
end
```

`run_step4_index_processing` の 2 つのガードは、この述語を呼ぶ形に置き換える（ログ文言は現状を維持する。著者に理由を伝える情報なので減らさない）。

### 4.3 前処理の変更

```ruby
# 索引スキャナ（Step 4）が走らないビルドでのみ、記法を素のテキストへ落とす。
# 走るビルドで落としてしまうと、Step 3 → Step 4 の順序上、スキャナが記法を
# 見る前に消えてしまい、著者が明示した索引語が 1 つも登録されない。
def strip_index_markup!
  return if IndexCommands.scan_will_run?(entries: ...)
  ...
  IndexMarkup.plain_text(inner)
end
```

### 4.4 採らない案

| 案 | 退ける理由 |
| --- | --- |
| 前処理を Step 4 の**後**へ動かす | 索引スキャナは Markdown を書き換えるので、残った記法の判定が二重になる。順序変更は他の前処理の前提（§4.3 の依存）も壊す |
| `strip_index_markup!` をやめ、記法を VFM へ素通しする | 単章ビルドで `[404]` が括弧つきで印字される。著者が最も頻繁に回す経路の見た目が壊れる |
| `skip_term?` に `<` 始まりを足す | **症状を隠すだけ**。`[<h1>]` は索引語にしたいという著者の意図（§2.3）に反する |
| 前処理でモードを受け取る引数を足す | 述語を持たない案は §3 の 3 条件を呼び出し側で再計算することになり、`IndexMarkup` を作ったときと同じ二重管理に戻る |

## 5. 期待される結果

| 記法 | 全章ビルド | 単章ビルド |
| --- | --- | --- |
| `[基本情報技術者]` | `<dfn class="index-term">基本情報技術者</dfn>` ＋ 索引に掲載 | `基本情報技術者`（素のテキスト） |
| `[引数\|ひきすう]` | 同上（読み `ひきすう`） | `引数` |
| `[404]` `[!]` `[&&]` `[\|\|]` `[!DOCTYPE]` | 索引語 | 素のテキスト |
| `[<h1>]` `[</h1>]` | 索引語（表示は `<h1>`・HTML としては `&lt;h1&gt;`） | `&lt;h1&gt;`（**見出しにならない**） |
| `[^1]` | 変換しない（脚注参照） | 同左 |

## 6. テスト

`notation-implementation-guide.md` §7 の流儀に従う。

1. **`IndexMarkup.plain_text`**: 読みの切り落とし・エスケープ（`<h1>` → `&lt;h1&gt;`）・`&` の二重エスケープ回避
2. **述語**: §3 の 5 経路それぞれで `scan_will_run?` が期待どおり
3. **前処理**: 述語 true で記法温存 / false で素のテキスト化
4. **温存**: コードフェンス内・インラインコード内の `[404]` はどちらの経路でも不変（既存の `extract_code_spans` 経路）
5. **回帰（実ビルド）**: `test/vivlio_starter/fixtures/notation/04-index-markup.md` を全章・単章の両方で組み、
   - 明示した語がすべて索引に載る
   - **幽霊見出しが生まれない**（`h1`〜`h6` に「は、」で始まるものが無い）

5 は本仕様書と同時に作った記法網羅フィクスチャが担当する。**このフィクスチャは現行版で 4 件を検出済み**で、修正の検証にそのまま使える。

## 7. 影響範囲

- 全章ビルドで明示記法が索引に載るようになるため、**既存書籍の索引語数が増える**。`index.target_terms` の目安を超える可能性があるが、明示記法は著者の意思表示なので閾値の対象外（`process_term` に早期リターンが無いのは意図的）。
- `[<h1>]` を書いていた原稿では、これまで幽霊見出しだったものが索引語に変わる。**目次と PDF アウトラインが変わる**ので、実書籍で目視確認が要る。

## 8. 備考：発見の経緯

別書籍（`vs new` で作った実プロジェクト）を通したときに、目次に「第2章 は、見出しタグです。」という章題が現れたのが最初の兆候だった。そのときは原稿の癖と判断して流しており、**著者の指摘を受けて初めて不具合と分かった**。

本書（マニュアル）は `[<h1>]` のような記法を原稿に書いていないため、全章ビルドでも `rake test` でも一度も露見していない。同じ構図の事故が同日に 2 件（前書きの `📚` による Type 3 混入・引用内コードへの索引タグ注入）起きており、いずれも「本書に無い書き方は検査を素通りする」ことが共通の原因である。記法網羅フィクスチャはこの穴を埋めるために作った。
