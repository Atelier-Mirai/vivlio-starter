# vs pdf:read の構造復元（見出し・段落・リスト・コード・表）仕様書（案）

> **状態**: 経路 A（§3）は実装済み（2026-10-04・§10 に実装記録）。経路 B（§4）は未着手。§7 の論点は 8 件すべて決定。§8 の `vs build` 側は、コードの行番号の `aria-hidden` 化だけを行った。
> 関連: `pdf-read-ocr-postprocess-spec.md`（OCR 後処理）。

## 0. 結論（先出し）

- `vs pdf:read` が今つくる Markdown は「文字の並び」だけで、**見出し・コードの囲み・表・`:::` ブロックは全モードで 0 件**しか戻らない（§1）。文字の拾い上げは 97〜98% に届いているので、これからの改善は**構造の復元**が中心になる。
- 構造は 2 つの経路で戻す。
  - **経路 A（構造ツリー）**: PDF がタグ付き（Tagged PDF）なら、構造ツリーの `H1`〜`H6`・`P`・`L/LI`・`Table`・`Code`・`Figure`・`BlockQuote` をそのまま Markdown へ写す。`vs build` の PDF はこれだけで原稿の骨格がほぼ戻る。
  - **経路 B（紙面の推定）**: タグが無い PDF は、文字の大きさ・位置・繰り返しから推定する。本文より大きく短い行を見出しとし、ページをまたいで同じ位置に出る行を柱・ノンブルとして除く。
- 対象は**一般の PDF**とする。Vivlio Starter が組んだ紙面だけに効く手がかり（`MEMO` のラベル、`♣`、`A-1` の節番号）には頼らない。
- 置き場所は **MIT の本体**（§6・決定）。プラグインは画像と OCR に専念し、OCR の結果も同じ経路 B へ流す。

## 1. 現状（2026-10-04 の実測）

対象は `contents/97-sample.md` を `vs build 97` した PDF（23 頁）。不具合 4 件を直した後の数字。原稿の列は当初の物差しで数えたもので、コードの中のコメントとコメントにした表を含む（§9 で訂正した。正しくは見出し 33・表の行 43）。

| | 原稿 | Standard | Enhanced | OCR |
|---|---|---|---|---|
| 見出し（`#`） | 36 | 0 | 0 | 3 |
| コードの囲み | 3 | 0 | 0 | 0 |
| 表の行 | 52 | 0 | 0 | 3 |
| `:::` ブロック | 38 | 0 | 0 | 0 |
| 脚注の参照 | 7 | 1 | 1 | 1 |

構造が戻らないことで、次の崩れも起きている。

- 見出しが本文に続けて 1 行になる（「♣ 学校を去り、入学試験に落ちるミュンヘンのギムナジウムは…」）。
- 表のセルがつながり、数値として読めなくなる（「2.2」と「5.32」が「2.25.32」になる）。
- コードに行番号が混ざり、字下げが消える。Enhanced では英字のあいだの空白も消える（`defthreshold_frequency`）。
- 脚注の番号が本文の行頭に付く（「1があるに違いない」）。

## 2. 一般の PDF と構造ツリー

構造ツリーは PDF 1.4 で入った**任意**の仕組みで、PDF に必ずあるものではない。持つかどうかは作ったソフトと書き出しの設定で決まる。

| 作り手 | 構造ツリー |
|---|---|
| Chrome の印刷・Puppeteer（Vivliostyle を含む） | 付く。`vs build` の PDF もこれ |
| Word・PowerPoint の「PDF として保存」 | 既定で付く（アクセシビリティ用のタグ） |
| InDesign | 書き出しで「タグ付き PDF」を選んだときだけ |
| LaTeX | 通常は付かない（tagpdf で付ける試みが進んでいる） |
| スキャナ・macOS の「PDF として保存」 | 付かない |
| PDF/UA に準拠した PDF | 必ず付く（規格の要件） |

したがって経路 A だけでは足りず、タグの無い PDF のために経路 B が要る。経路 A を先に作るのは、当たったときの効果が大きく、推定を含まず確実だからである。

### 2.1 `vs build` の PDF の構造ツリー（実測）

`97-sample.pdf` の構造ツリーにある要素の数:

```
P 145 / TD 91 / Figure 64 / Code 48 / TR 41 / Strong 38 / Aside 33 / LI 20 / Lbl 20
H3 19 / H2 13 / Art 13 / TH 11 / BlockQuote 9 / Link 6 / Caption 5 / Table 4 / L 4
Ruby 3 / RT 3 / H1 1 / Document 1（ほかに NonStruct 3,182）
```

- 見出しは `H1`（章題）・`H2`（節）・`H3`（項）で、原稿の `#`・`##`・`###` と一致する。
- コードは `Figure` の中に `Caption`（ファイル名）と `Code` が入る。インラインのコードも `Code`。
- **数式は `Figure` の `Alt` に TeX のまま入る**（`$E=mc^2$`、`$$ \nu_0 = \frac{\phi}{h} $$`）。紙面では SVG なので文字としては取れないが、構造ツリーからは原稿どおりに戻せる。
- 画像の `Figure` は `Alt` に代替テキストを持つ（「アインシュタインを描いた挿絵」）。
- **柱とノンブルは `Aside`** に入る（「付録 A 挑戦することの贈り物」「23」）。タグで確実に除ける。
- **脚注の本文はタグが付かず `NonStruct` の中**にある。`Note` ではない。

### 2.2 調査の落とし穴

HexaPDF で構造ツリーを辿るときは、子の配列が `Array` ではなく `HexaPDF::PDFArray` で来る。`is_a?(Array)` で分岐すると根の直下で止まり、「`Document` と `NonStruct` しかない」と誤って結論する（2026-10-04 に一度そう判定した）。

## 3. 経路 A: 構造ツリーから戻す

### 3.1 要素と Markdown の対応

| 構造要素 | Markdown |
|---|---|
| `H1`〜`H6` | `#`〜`######`。PDF の `H1` が複数あっても、最初の `H1` を章題として扱う |
| `H`（段階なし） | 入れ子の深さから段階を決める |
| `P` | 段落。段落のあいだは空行で区切る |
| `L` / `LI` / `Lbl` / `LBody` | `Lbl` が数字なら `1.`、記号なら `-` のリスト |
| `Table` / `TR` / `TH` / `TD` | パイプの表。`TH` のある行を見出し行にする |
| `Figure`（`Code` を含む） | ```` ``` ```` の囲み。`Caption` があれば ```` ```lang:ファイル名 ```` の形にする |
| `Code`（段落の中） | `` ` `` で囲む |
| `Figure`（画像） | `![Alt](抽出した画像)`。Enhanced で画像を抜いたときだけ参照を書く |
| `Figure`（`Alt` が `$…$`） | `Alt` の TeX をそのまま書く（数式） |
| `BlockQuote` | `> ` |
| `Ruby` / `RB` / `RT` | `{親文字|ルビ}` |
| `Strong` / `Em` | `**…**` / `*…*` |
| `Link` | 文字だけを残す（行き先は PDF 内のページなので持ち帰らない） |
| `Aside` | 捨てる（§3.3） |
| `Note` | 脚注 `[^n]` |
| `Artifact`（マーク付き内容） | 捨てる（規格上「本文ではない」印） |
| `NonStruct` / `Div` / `Sect` / `Art` / `Part` | 入れ物なので、中身だけを辿る |

### 3.2 文字と要素のつなぎ方

構造要素は本文の文字を MCID（マーク付き内容の番号）で指す。各ページの描画命令を読みながら `BDC … /MCID n … EMC` の範囲に描かれた文字を集め、MCID ごとの文字列（と座標・大きさ）を作ってから、構造ツリーを辿って要素ごとに連結する。

pdf-reader（MIT）だけで作れることを試作で確かめた。`PDF::Reader::PageTextReceiver` を継承して `begin_marked_content_with_pl` / `end_marked_content` を受け、文字を描く命令の前後で増えた文字を、その時点の MCID へ割り当てる。

**増えた文字は公開メソッドの `runs` で数える**（論点 7-3 で決定）。絞り込みをすべて外して呼ぶ（`rect: nil, skip_zero_width: false, skip_overlapping: false, merge: false`）と、受け取った文字の一覧がそのまま返るので、命令の前後の数の差が新しく描かれた文字になる。内部の変数 `@characters` を直接読む方法と結果は完全に一致し、速さの差も小さい。

| 方式 | 97-sample.pdf（23 頁） | cyberguardian.pdf（244 頁） | pdf-reader の内部への依存 |
|---|---|---|---|
| 公開メソッド `runs` の数の差 | 1.15 秒 | 4.21 秒 | なし |
| 内部変数 `@characters` を読む | 0.50 秒 | 3.76 秒 | あり（版が上がると壊れうる） |

`runs` を毎回呼ぶ手間は、1 ページの文字数の 2 乗で増える。文字の極端に多いページで遅くなったら、そのページだけ内部の変数を読む方式に切り替えることを考える。

**`begin_marked_content_with_pl` を受けるときは `super` を呼ぶ。** pdf-reader 2.16 はこのメソッドで ActualText（画像化された文字などに添える代替の文字）を扱っている。呼ばずに上書きすると、その対応を壊す（最初の試作はそうなっていた）。

### 3.3 経路 A でも座標を使うところ

- **行の区切り**: `Code` の中の改行は構造ツリーに無い。行は y 座標で分け、字下げは x 座標から空白の数に直す。
- **コードの行番号**: `vs build` の PDF では、行番号を `aria-hidden` にして `Code` から外した（§8）。それより前に作った PDF と一般の PDF では `Code` の中に入っているので、論点 7-4（§7.1）の規則で外す。
- **脚注**: タグの無い脚注は経路 B の判定（§4.5）で拾う。

### 3.4 経路 A を使うかの判定

構造ツリーがあっても、中身が薄い PDF はある（全体を `P` 1 つで包むだけ、など）。**本文の文字の 9 割以上が `NonStruct` 以外の要素に属する**ときだけ経路 A を使い、それ以外は経路 B へ落とす（しきい値は論点 7-5）。

**実例**: `jouhoukagakuronsyu0_72_5.pdf`（InDesign CS6 で書き出した論文・18 ページ）は「タグ付き」だが、構造ツリーが覆っているのは表紙の 3 項目（題・著者・誌名）だけで、本文にはタグが無い。要素の種類も独自名（`Story`・`NormalParagraphStyle`・`Span`）で、標準の種類へは対応表（`RoleMap`）を引いて読み替える必要がある。この PDF は 9 割の条件を満たさないので経路 B で読む。タグの有無ではなく、覆っている文字の割合で判定する理由がここにある。

**構造ツリーを辿るときの注意**: InDesign の PDF では、子の配列の要素が参照（`HexaPDF::Reference`）のまま渡ってくる。Chrome の PDF では起きなかった。参照は解決してから辿る。

## 4. 経路 B: 紙面から推定する

タグの無い PDF と OCR の結果に使う。入力は「ページごとの行（文字列・x・y・幅・文字の大きさ・フォント名）」で、PDF の文字からでも OCR の行からでも作れる形にする。

### 4.1 本文の大きさを決める

全文字を大きさごとに数え、最も多い大きさを本文とする。`97-sample.pdf` では 10.5pt が 73.9% で本文になる（次に多いのは 9.2pt のコード 17.3%）。

### 4.2 見出し

次をすべて満たす行のまとまりを見出しとする。

- 文字の大きさが本文の 1.15 倍以上（太字のフォントなら同じ大きさでもよい）
- 1〜2 行で終わる（3 行以上続くなら、大きな文字の段落とみなす）
- 行末が句点で終わらない

段階は、見出しになった大きさを大きい順に並べて `#`・`##`・`###` を振る。

`97-sample.pdf` の実測では、章題 31.2pt・節 23.4pt・項 12.8pt に分かれる。ただし**章のリード文が 12.6pt で、項の見出しとほぼ同じ大きさ**になる。大きさだけで決めるとリード文が見出しになるので、行数と句点の条件が要る。

### 4.3 柱・ノンブル

いまは `pdf_read.text_area` の mm 指定で版面の外を除いている。一般の PDF は版面がまちまちで、利用者が mm を測って書くのは負担が大きい。次のように置き換える。

- **ページをまたいで、ほぼ同じ位置に同じ文字列が出る行**を柱とする（偶数・奇数ページで左右が入れ替わる形も含める）。
- 同じ位置に**連番の数字**が出る行をノンブルとする。
- `text_area` は、推定が外れたときに人が範囲を指定する手段として残す（論点 7-6）。

### 4.4 段落とリスト

- 行と行のあいだが本文の行送りより広いところで段落を切る。
- 行頭が 1 字下がっていれば新しい段落とする（和文の段落の書き方）。
- 前の行が版面の右端まで届かずに終わっていれば、そこで段落が終わったとみなす。
- 行頭が `1.`・`(1)`・`・`・`•`・`-` で始まる行の並びをリストとする。

いまの MeCab による改行の補正（`MecabNewlineCleaner`）は、段落を切ったあとの行の連結に使う。

### 4.5 脚注

本文より小さい文字で、ページの下部にあり、行頭が番号で始まるまとまりを脚注とする。本文の中で、同じ番号が小さい文字（上付き）で出ている箇所を参照とし、`[^n]` で結ぶ。

### 4.6 コード

フォント名が等幅（`Mono`・`Courier`・`Code` などを含む）の行の並びを、```` ``` ```` で囲む。字下げは x 座標から空白の数に直し、英字のあいだの空白を詰めない（Enhanced で `def threshold` が `defthreshold` になる崩れを止める）。行頭が 1 から始まる連番ならそれを外す。

### 4.7 表（後回し）

罫線と文字の位置から表を組み立てるのは難しく、外れたときの崩れも大きい。列の対応まで推定する組み立ては扱わず、経路 A の `Table` を戻す。タグの無い PDF では、セルの区切りを失わない程度にとどめる案を出している（論点 7-7・§7.2）。

## 5. 対象外

- Vivlio Starter の紙面だけに効く手がかり（`MEMO`・`COLUMN` などのラベル、`♣`、`A-1` の節番号）から `:::` ブロックを戻すこと。一般の PDF を戻すコマンドなので扱わない。
- 縦書き・段組みの読み順の推定。
- 表の推定（§4.7）。

## 6. 置き場所（MIT の本体か、AGPL のプラグインか）

**決定: 構造の復元は MIT の本体に置く。** プラグインは画像の抜き出しと OCR に専念し、OCR の結果を「行（文字列・座標・高さ）」として本体へ返す。本体は PDF の文字でも OCR の行でも、同じ経路 B で構造を戻す。

- 文字の層がある PDF なら、プラグインを入れていなくても構造が戻る。`vs build` の PDF やタグ付きの PDF の多くはここに入る。
- 経路 B の判定が 1 か所にまとまる。OCR の行の高さから文字の大きさを見積もれば、スキャンした PDF でも見出しが戻る。
- プラグインとの取り決め（`read` の JSON）は変わる。`page_chunks`（組み上がった文字列）に加えて、行の座標と大きさ、画像の位置を返す形にする。

もう一つの案は、構造の復元をプラグインの HexaPDF 側に置くことである。HexaPDF は描画命令とフォントの情報を扱いやすく、試作は楽になる。ただし AGPL を入れない利用者には構造が戻らず、Standard Mode との差が大きくなる。

## 7. 論点と決定

| # | 論点 | 決定 |
|---|---|---|
| 1 | 置き場所 | **MIT の本体**（§6） |
| 2 | 実装の順 | 経路 A → 経路 B の見出しと柱 → 段落・リスト → 脚注・コード |
| 3 | pdf-reader の内部への依存 | **公開メソッド `runs` の数の差で割り当てる**（§3.2）。内部の変数は読まない |
| 4 | コードの行番号 | **1 ずつ増える連番が全行にあれば外す**。始まりは 1 でなくてよい（抜粋の 28・29・30 も外す）。1 以外から始まるときは、開始番号を Vivlio Starter の記法 `#L28` で書き戻す（§7.1） |
| 5 | 経路 A に切り替えるしきい値 | 本文の文字の 9 割 |
| 6 | `text_area` の扱い | 既定では使わず、指定したときだけ効かせる |
| 7 | 表 | **経路 B でも列を推定して表に仮組みする**。推定した表には、確かめるよう促すコメントを添える（§7.2） |
| 8 | 物差し | `scripts/pdf_read_score.rb` に置いた（§9） |

### 7.1 コードの行番号（論点 4）

`vs build` の PDF では、行番号は紙面の文字として描かれている（`::before` の `counter(linenumber)`）。字下げは x 座標から戻せる（例: 本文開始 76.6pt、字下げした行 98.8pt で 2 字ぶん）。原稿は次のとおり。

````markdown
```ruby:photoelectric.rb
# 光電効果のしきい周波数を求める
PLANCK = 6.62607015e-34   # プランク定数 h [J·s]

def threshold_frequency(work_function_ev)
  work_function_j = work_function_ev * EV
  work_function_j / PLANCK
end
```
````

**行番号を外した場合**（行頭の連番が全行にあるときだけ外す案）:

````markdown
```ruby:photoelectric.rb
# 光電効果のしきい周波数を求める
PLANCK = 6.62607015e-34 # プランク定数 h [J·s]

def threshold_frequency(work_function_ev)
  work_function_j = work_function_ev * EV
  work_function_j / PLANCK
end
```
````

原稿とほぼ同じになる。違いは、桁をそろえるための連続した空白が 1 つに縮むことくらいである（PDF からは空白の数ではなく位置しか取れないため）。`vs build` で組み直すと、行番号は Vivlio Starter がまた付ける。

**行番号を残した場合**:

````markdown
```ruby:photoelectric.rb
1 # 光電効果のしきい周波数を求める
2 PLANCK = 6.62607015e-34 # プランク定数 h [J·s]
3
4 def threshold_frequency(work_function_ev)
5   work_function_j = work_function_ev * EV
6   work_function_j / PLANCK
7 end
```
````

- `vs build` で組み直すと、行番号が二重になる（`1  1 # 光電効果の…`）。
- コードとして正しくなくなる。色分け（シンタックスハイライト）が崩れ、写して実行することもできない。
- 行番号が本文の一部である資料（行番号で説明を参照するソースの全文掲載など）では、残っていたほうが原本に忠実である。

**参考: いまの出力**（Standard Mode）は、行番号が残り、行のあいだに空行が入り、字下げが消え、囲みも付かない。

```
1 # 光電効果のしきい周波数を求める

2 # ν₀ = φ / h

3 PLANCK = 6.62607015e-34# プランク定数 h [J·s]
```

**途中から始まる抜粋**: 原稿の ```` ```include:gravitational_lensing.rb:28-30``` ```` は、紙面で `28`・`29`・`30` と元のファイルの行番号で描かれる。判定は「1 から始まる」ではなく「**1 ずつ増える**」で見るので、この抜粋も外す。外した開始番号は、Vivlio Starter の記法で書き戻す。

````markdown
```ruby:gravitational_lensing.rb#L28
# 太陽の縁をかすめる光の曲がり角
deflection_rad = gravitational_deflection(SOLAR_MASS, SOLAR_RADIUS)
deflection_arcsec = to_arcseconds(deflection_rad)
```
````

組み直すと、紙面の行番号はまた 28 から始まる。`#L` はファイル名の直後に書く記法なので、ファイル名（`Caption`）の無いコードでは開始番号を書き戻せない。そのときは番号を外したうえで、元の開始番号をコメントで残す。

**折り返した行**: 長い行は紙面で折り返し、2 行目以降には番号が付かない（ぶら下げ字下げで、コードの開始位置にそろう）。番号の無い行は、直前の番号付きの行の続きとして連結し、「全行に連番があるか」の判定からは外す。

**連番とみなさない形**: 番号が飛ぶ（1, 2, 5）、同じ番号が続く、一部の行にしか番号が無い。こうした行頭の数字はコードの一部（Markdown の番号付きリストを説明するコードなど）かもしれないので、外さない。

### 7.2 表（論点 7）

いまはどのモードでも表を組み立てない。原稿の表（`| 金属 | 仕事関数 φ / eV | しきい周波数 / Hz |` と 3 行）は、次のように崩れる。

- **Standard**: 表全体が 1 行につながり、後ろの段落まで続く。セルの区切りが消えるので数値が読めない（「2.2」と「5.32」が「2.25.32」）。
  `表 H-1: 光電効果のしきい周波数金属仕事関数 φ / eV しきい周波数 / Hzカリウム2.25.32 × 10¹⁴ナトリウム2.35.56 × 10¹⁴金5.11.23 × 10¹⁵注意: しきい周波数より低い光を…`
- **Enhanced**: 見出し行はつながり、データ行はセルごとに改行される（「カリウム」「2.2」「5.32×10¹⁴」が別々の行）。数値は読めるが、どの列かは分からない。
- **OCR**: Standard と同じく 1 行につながり、数字も崩れる（「5.32 X 1014」）。

経路 A（構造ツリー）がある PDF では、`TR`・`TH`・`TD` からそのまま表を組める。

**タグの無い PDF でも、列を推定して表に仮組みする**（決定）。97 章の表 H-1 で試したところ、文字の位置だけから原稿と同じ表が組めた。

```
| 金属 | 仕事関数 φ / eV | しきい周波数 / Hz |
| --- | --- | --- |
| カリウム | 2.2 | 5.32 × 10¹⁴ |
| ナトリウム | 2.3 | 5.56 × 10¹⁴ |
| 金 | 5.1 | 1.23 × 10¹⁵ |
```

列の推定は「表のどの行にも文字が無い縦の隙間」を探して、そこを列の境目にする。左揃え（金属）・中央揃え（仕事関数）・右揃え（しきい周波数）が混ざっていても、各列の文字が占める横の範囲は重ならないので、隙間で分けられる。見出しの行もデータの行も同じ境目で切るので、`|` の数が行ごとに食い違うことはない。

- **文字は 1 字ずつの位置で見る**。pdf-reader は同じ行の文字を 1 つのまとまりに結合し（`runs` の既定）、そのまとまりがセルのあいだの空白まで覆うので、結合をやめて（`merge: false`）から隙間を探す。
- **隙間の幅は小さい**。表 H-1 では列のあいだが 6pt しか空いていなかった（「ナトリウム」の終わりが 229pt、「仕事関数」の始まりが 235pt）。しきい値は 4pt 程度にする。和文の文字のあいだは 0pt なので、取り違えにくい。
- **推定した表には、確かめるよう促すコメントを添える**（`<!-- pdf:read: 列を推定して組んだ表です。列の対応を確かめてください -->`）。

仮組みで外れやすい形と、その扱い:

| 形 | 起きること | 扱い |
|---|---|---|
| セルの中で折り返した文字 | 1 つのセルが 2 行に分かれ、行が増える | 行のあいだが本文の行送りより狭ければ、同じ行として連結する |
| 結合したセル（colspan） | 見出しの 1 セルが 2 列にまたがり、隙間が見つからない | またがった列は空のセルにする。崩れはコメントで知らせる |
| 列のあいだがほとんど空いていない表 | 隙間が見つからず、1 列の表になる | 表にせず、いまの段落のまま残す |
| 罫線だけで区切った表 | 文字の隙間は狭くても、罫線の位置が分かる | 罫線（描画命令の線）も列の境目の手がかりに使う（後回し） |

表の範囲（どこからどこまでが表か）は、「列の境目が同じ位置にそろった行が 3 行以上続く」ところとする。表のキャプション（「表 H-1:」）が直前にあれば、手がかりに加える。

## 8. `vs build` 側の改善（調査結果）

小さな HTML を Vivliostyle で PDF にし、構造ツリーがどう変わるかを確かめた（Vivliostyle CLI 11.3.3・Chrome 153）。

| 書き方 | 構造ツリー |
|---|---|
| `<span aria-hidden="true">A-1</span>`（見出しの番号） | **構造ツリーから外れる**。紙面には描かれる |
| `<span aria-hidden="true">1 </span>`（コードの行番号） | **`Code` から外れる** |
| `::before { content: "B-2" / "" }`（代替テキストを空に） | 外れない。Chrome はこの指定を構造ツリーに使わない |
| `::before { content: counter(…) }`（いまの行番号） | `Code` の文字に入る |
| 脚注 `<span role="doc-footnote">`（いまの書き方） | `NonStruct` |
| 脚注 `<aside role="doc-footnote">`・`role="note"`・`role="doc-endnote"` | `NonStruct` |
| 脚注 `<aside>`（役割なし） | `Aside`（柱・ノンブルと同じ） |

- **脚注は `NonStruct` のままにする**（決定）。`Note` にすることは HTML の書き方では実現できず（Chrome はどの書き方でも `Note` を作らない）、PDF を組んだあとに構造ツリーを書き換える必要がある。構造要素には ID などの手がかりが無いので、脚注の本文と文字を照らし合わせることになり、印刷用 PDF の導出・dedup との順序も確かめ直すことになる。PDF の中で脚注はわずかで、そのための改造に見合わない。`pdf:read` は脚注を経路 B（§4.5）で拾う。
- **見出しの番号（`A-1`・`♣`）は残す**（決定）。`aria-hidden` で外すことはできるが、読み上げソフトで「節 A-1」と聞こえるほうが親切である。`pdf:read` は、一般の PDF のためにどのみち要る「見出しの行頭の番号を外す」処理で扱う。
- **コードの行番号は `aria-hidden` で `Code` から外す**（決定・実装済み）。行番号は読み上げても意味が無く、写したコードにも混ざる。`::before` の連番をやめ、`PdfBuilder#convert_code_pre_lines!` が各行の先頭に `<span class="vs-code-ln" aria-hidden="true">1</span>` を実際の要素として入れる（class 名は Kindle 向けの注入と同じ）。開始番号は `pre` の `data-start`（`#L28`）から取る。

## 9. 物差しと合格の目安

`scripts/pdf_read_score.rb` で、原稿と `vs pdf:read` の出力を突き合わせる。

```zsh
ruby scripts/pdf_read_score.rb contents/97-sample.md 出力1.md [出力2.md …]
```

- **文字の一致**: 原稿から記法を外し、`codes/` の取り込みを展開し、数式を除いた文字列を基準に、空白を無視して文字単位で比べる（再現率・適合率・F 値）。出力の側にも同じく記法を外してから比べる（`#` や `|` を文字として数えると、構造を戻すほど適合率が下がるため）。脚注のように位置が動いた文字は、一致しなかった分として数える。
- **英字の語**: 3 文字以上の英字の語がどれだけ戻ったか。コードの識別子の崩れ（`metal` → `metat`）を拾う。
- **構造の数**: 見出し・コードの囲み・表の行・`:::` ブロック・脚注の参照と本文・画像・リストの項目。コードの囲みの中の行と、`<!-- … -->` でコメントにした原稿は数えない。

**物差しの数え違いを直した（2026-10-04）。** 当初の物差しは、コードの囲みの中の `# コメント` を見出しとして数え、コメントにした表（97 章の 1 つめの SI の表）の行も数えていた。そのため原稿の数が見出し 36・表の行 52 と多く出ていた。正しくは見出し 33・表の行 43 である。

合格の目安。対象はいずれも `contents/97-sample.md` を `vs build 97` した PDF。

| 段階 | 目安 |
|---|---|
| 経路 A（構造ツリー） | 見出し 33/33・コードの囲み 5/5・脚注の本文 4/4・表の行 43/43・F 値 97% 以上 |
| 経路 B（タグを外した同じ PDF） | 見出し 30/33 以上（9 割）・コードの囲み 5/5・F 値 95% 以上 |

経路 B は、同じ PDF から構造ツリーを外したものを作って測る（原稿という正解があるため）。`:::` ブロックは一般の PDF からは戻さないので、目安に入れない。

2026-10-04 の実測（物差しを直した後）:

| | 見出し | コードの囲み | 表の行 | 脚注の参照 | 脚注の本文 | リストの項目 | F 値 | 英字の語 |
|---|---|---|---|---|---|---|---|---|
| 原稿 | 33 | 5 | 43 | 7 | 4 | 20 | — | 250 |
| 経路 A の前（Standard） | 0 | 0 | 0 | 1 | 0 | 0 | 95.5% | — |
| 経路 A（両モード） | 33 | 5 | 43 | 7 | 4 | 20 | 97.0% | 239 |

経路 A は、行番号を `Code` に含む前の PDF（`sources/97-sample.pdf`）でも、`aria-hidden` にした後の PDF でも、同じ Markdown を返す。F 値に届かない残りは、紙面にだけある文字（`MEMO`・`COLUMN` のラベル、`@chapref` が展開した章題と「p.??」、QueryStream が展開した本のカード）と、脚注の本文の位置が動いた分である。

## 10. 実装記録（経路 A・2026-10-04）

置き場所は本体（MIT）の `lib/vivlio_starter/cli/pdf/` の 3 つのファイル。

| ファイル | 役目 |
|---|---|
| `marked_content_receiver.rb` | ページを読み、MCID ごとに文字と画像の位置を集める（公開メソッド `runs` の数の差）。どの MCID にも属さない文字も取っておく |
| `structure_reader.rb` | 構造ツリーを辿って要素の木にする。RoleMap の読み替え、MCR、子が参照のまま来る形を扱う。覆う割合（`coverage`）を出す |
| `structure_markdown.rb` | 要素の木を Markdown へ写す |

`PdfReadCommand#convert_structured` が両モードで最初に試し、覆う割合が 9 割に届かなければ nil を返して、これまでの読み方へ任せる。構造ツリーの無い PDF は、ページを読まずに 0 と答える（507 ページの PDF で 53 秒かかっていた）。Enhanced Mode では、プラグインに OCR を切って画像だけを抜き出させ、`Figure` と描かれた位置の重なりで結ぶ。`page_separator` は使わない。

実装して分かったこと:

- **Chrome は空白を文字として描かない。** 語のあいだの空白は、文字の隙間から戻す。本物の空白は 0.28 字ほどあり、欧文どうしは 0.15 字より広ければ空白とする。和文が絡む隙間は、両端揃えで字間が広がる（実測で最大 0.25 字）うえ、和欧間のアキ（0.125 字前後）もあるので、行ごとに和文どうしの字間の中央値を引いてから 0.2 字で見る。長音「ー」と中黒「・」は Unicode の文字種で和文に入らないので、別に足す。
- **構造ツリーはページごとに作られる。** ページをまたいだ段落は 2 つの `P` に分かれる。段落の頭を 1 字下げる組み方なら（2 行以上の段落の過半で判定）、次のページの頭が下がっていないことで続きと見る。下げない組み方なら、前の段落が文末で終わっていないことで見る。句点だけで決めると、「」」で終わる 1 行の段落を次の段落とつないでしまう。
- **行番号の判定は、隙間で区切ってから数字を読む。** 34 行目の「3.times」のように、行番号のすぐ後のコードが数字で始まると「343」と読んでしまう。
- **`aria-hidden` の行番号は、どのマークにも入らない文字として紙面に描かれる。** `Code` の中に番号が無いときは、コードの左に並ぶ構造ツリーの外の数字を行の頭へ戻してから、同じ規則（§7.1）で外す。これで開始番号（`#L28`）と、折り返した行の見分けが戻る。
- **脚注は 2 度描いて決める。** 1 度目で、本文の候補（本文より小さい字で番号から始まる段落）と参照（本文の 0.9 倍以下で 0.15 字以上持ち上がった数字）を集める。2 度目で、両方そろった番号だけを `[^n]` にする。上付きの指数を脚注と取り違えないため。脚注の本文は次の見出しの手前へまとめて置く。ページの下で割り込ませると、ページをまたいだ段落をつなげなくなる。
- **座標は Integer で来ることがある。** 重なりの割合や字下げの字数は `fdiv` で割る（画像の結び付けが 0 になっていた）。
