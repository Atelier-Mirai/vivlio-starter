# vs pdf:read の構造復元（見出し・段落・リスト・コード・表）仕様書（案）

> **状態**: 経路 A（§3）と、文字の層のある PDF の経路 B（§4）は実装済み（2026-10-04・§10・§11 に実装記録）。OCR の語を経路 B へ流す取り決め（§6）も実装済み（§12）。§7 の論点は 8 件すべて決定。§8 の `vs build` 側は、コードの行番号の `aria-hidden` 化だけを行った。
> 関連: `pdf-read-ocr-postprocess-spec.md`（OCR 後処理）。

## 0. 結論（先出し）

- `vs pdf:read` が今つくる Markdown は「文字の並び」だけで、**見出し・コードの囲み・表・`:::` ブロックは全モードで 0 件**しか戻らない（§1）。文字の拾い上げは 97〜98% に届いているので、これからの改善は**構造の復元**が中心になる。
- 構造は 2 つの経路で戻す。
  - **経路 A（構造ツリー）**: PDF がタグ付き（Tagged PDF）なら、構造ツリーの `H1`〜`H6`・`P`・`L/LI`・`Table`・`Code`・`Figure`・`BlockQuote` をそのまま Markdown へ写す。`vs build` の PDF はこれだけで原稿の骨格がほぼ戻る。
  - **経路 B（紙面の推定）**: タグが無い PDF は、文字の大きさ・位置・繰り返しから推定する。本文より大きく短い行を見出しとし、ページをまたいで同じ位置に出る行を柱・ノンブルとして除く。
- 対象は**一般の PDF**とする。Vivlio Starter が組んだ紙面だけに効く手がかり（`MEMO` のラベル、`♣`、`A-1` の節番号）には頼らない。
- 置き場所は **MIT の本体**（§6・決定）。プラグインは画像と OCR に専念し、OCR の結果も同じ経路 B へ流す。

対象は `contents/97-sample.md` を `vs build 97` した PDF（23 頁）。不具合 4 件を直した後の数字。原稿の列は当初の物差しで数えたもので、コードの中のコメントとコメントにした表を含む（§9 で訂正した。正しくは見出し 33・表の行 43）。

| | 原稿 | Standard | Enhanced | OCR |
|---|---|---|---|---|
| 見出し（`#`） | 36 | 0 | 0 | 3 |
| コードの囲み | 3 | 0 | 0 | 0 |
| 表の行 | 52 | 0 | 0 | 3 |
| `:::` ブロック | 38 | 0 | 0 | 0 |
| 脚注の参照 | 7 | 1 | 1 | 1 |

構造が戻らないことで、次の崩れも起きている。

- 見出しが本文に続けて 1 行になる（「♣ 学校を去り、入学試験に落ちるミュンヘンのギムナジウムは…」）。
- 表のセルがつながり、数値として読めなくなる（「2.2」と「5.32」が「2.25.32」になる）。
- コードに行番号が混ざり、字下げが消える。Enhanced では英字のあいだの空白も消える（`defthreshold_frequency`）。
- 脚注の番号が本文の行頭に付く（「1があるに違いない」）。

## 2. 一般の PDF と構造ツリー

構造ツリーは PDF 1.4 で入った**任意**の仕組みで、PDF に必ずあるものではない。持つかどうかは作ったソフトと書き出しの設定で決まる。

| 作り手 | 構造ツリー |
|---|---|
| Chrome の印刷・Puppeteer（Vivliostyle を含む） | 付く。`vs build` の PDF もこれ |
| Word・PowerPoint の「PDF として保存」 | 既定で付く（アクセシビリティ用のタグ） |
| InDesign | 書き出しで「タグ付き PDF」を選んだときだけ |
| LaTeX | 通常は付かない（tagpdf で付ける試みが進んでいる） |
| スキャナ・macOS の「PDF として保存」 | 付かない |
| PDF/UA に準拠した PDF | 必ず付く（規格の要件） |

したがって経路 A だけでは足りず、タグの無い PDF のために経路 B が要る。経路 A を先に作るのは、当たったときの効果が大きく、推定を含まず確実だからである。

### 2.1 `vs build` の PDF の構造ツリー（実測）

`97-sample.pdf` の構造ツリーにある要素の数:

```
P 145 / TD 91 / Figure 64 / Code 48 / TR 41 / Strong 38 / Aside 33 / LI 20 / Lbl 20
H3 19 / H2 13 / Art 13 / TH 11 / BlockQuote 9 / Link 6 / Caption 5 / Table 4 / L 4
Ruby 3 / RT 3 / H1 1 / Document 1（ほかに NonStruct 3,182）
```

- 見出しは `H1`（章題）・`H2`（節）・`H3`（項）で、原稿の `#`・`##`・`###` と一致する。
- コードは `Figure` の中に `Caption`（ファイル名）と `Code` が入る。インラインのコードも `Code`。
- **数式は `Figure` の `Alt` に TeX のまま入る**（`$E=mc^2$`、`$$ \nu_0 = \frac{\phi}{h} $$`）。紙面では SVG なので文字としては取れないが、構造ツリーからは原稿どおりに戻せる。
- 画像の `Figure` は `Alt` に代替テキストを持つ（「アインシュタインを描いた挿絵」）。
- **柱とノンブルは `Aside`** に入る（「付録 A 挑戦することの贈り物」「23」）。タグで確実に除ける。
- **脚注の本文はタグが付かず `NonStruct` の中**にある。`Note` ではない。

### 2.2 調査の落とし穴

HexaPDF で構造ツリーを辿るときは、子の配列が `Array` ではなく `HexaPDF::PDFArray` で来る。`is_a?(Array)` で分岐すると根の直下で止まり、「`Document` と `NonStruct` しかない」と誤って結論する（2026-10-04 に一度そう判定した）。

### 2.3 ToUnicode を持たない日本語の書体（2026-10-09）

市販の技術書の PDF には、ヒラギノや新ゴを、字の番号（CID）をそのまま符号にする `Identity-H` で埋め込み、Unicode への対応表（ToUnicode）を付けないものが多い。pdf-reader はそのとき CID をそのまま Unicode とみなすので、本文が丸ごと化ける（「MOSFET」が「.04'&5」、「図」が「ਤ」）。題材 23 本のうち 11 本は日本語のほぼすべてが、ほかに 3 本は一部がこれで化けており、経路 A・B の推定は化けた字の上で動いていた。

PDF の仕様（ISO 32000-1 9.10.2）は、ToUnicode が無く、子の書体の `CIDSystemInfo` が Adobe の既定の字の集まり（Adobe-Japan1 など）なら、その集まりの CID → Unicode の表で字を求めると定めている。HexaPDF（プラグインの OCR の要否の判定）はそうしているが、pdf-reader はしていない。

- **方法**: pdf-reader が書体を作るところ（`PDF::Reader::Font#initialize`）に割り込み、`Type0`・符号が `Identity-H`/`Identity-V`・子の書体が `Adobe`/`Japan1` の書体に表を当てる（`AdobeJapan1Unicode`）。ToUnicode が無ければ表を ToUnicode の代わりにし、あれば ToUnicode で引けなかった字だけを表で補う（`Exercise D` の ToUnicode は「小」「整」「設」「値」などを欠き、poppler も落とす。HexaPDF と同じ順）。Font は元の辞書を持ち歩かないので、後から `CIDSystemInfo` を見られない。
- **単純な書体の ToUnicode の欠け**: pLaTeX（dvipdfmx）の英字の書体（`SFRM1000` など）は、ToUnicode に合字「ff」の 1 字だけを書き、ほかの字は書体の符号表（Encoding）で読ませる。pdf-reader は ToUnicode があると符号表を見ないので、『実践 Rust Web 開発 5』の「Axum は Tokio（非同期の実行 環境）の上に作られた」から英字の語とコードがすべて消えていた。Type 0 以外の書体では、ToUnicode で引けなかった字だけを符号表で読む（`ToUnicodeFallback`。poppler と同じ）。Type 0 の符号は字形の番号なので、符号表からは読まない。
- **表**: Adobe の `mapping-resources-pdf` の `pdf2unicode/Adobe-Japan1-UCS2`（BSD 3 条項）を手を加えずに同梱する。`cmap-resources` の `cid2code.txt` は、新ゴ・ヒラギノの `90msp`（比例幅）が使う仮名（CID 12063 以降）に Unicode を持たず、仮名がすべて消えるので使わない（poppler の `pdftotext` も同じ理由で仮名を落とす）。
- **異体字セレクタ**: 表は斜線の無い「0」などを「0」+ U+FE00 のように書くが、本文の字としては要らないので外す。
- **Differences のずれ**: pdf-reader は、符号表の `Differences` に字の名前の一覧に無い名前（「`zero.a`」のような接尾辞付きの別字形）があると、それを飛ばすときに番号を進め忘れ、後ろの字が 1 つずつ前の番号にずれる。Rust-tutorial のコードでは行番号の「0」（`zero.a`）が空白に、空白が名前の分からない字「▯」になっていた（2 冊で 3,387 字）。Type 0 以外の書体では `Differences` を読み直し、名前の一覧に無い名前は字の名前の決まりどおり接尾辞（「.」から後ろ）を外して引く。ToUnicode があればそれが先。
- **TeX の記号の書体（CMSY）の 0〜31 番**: 符号表（Encoding）を持たない `CMSY` は、書体の中の並びで字を決めるが、pdf-reader は標準の符号表で読むので、箇条書きの点（15 番）や `≤`・`×` が名前の分からない字「▯」になる（『実践 Rust Web 開発 5』の箇条書きが点と本文の 2 列の表になっていた）。0〜31 番は標準の符号表では空きなので、`CMSY`（OMS）の並びで補う。14 番（openbullet）と 15 番（bullet）は箇条書きの点として「◦」「•」にする。32 番以降（平方根の根号を「p」で見分ける §4.8）は変えない。dvipdfmx が符号を付け直した `CMSY`（Differences 付きの符号表。『エッセンス』では 2 番が `circlecopyrt`）は並びが違うので除く。
- **康熙部首と合字**: ToUnicode を持つ PDF でも、漢字を康熙部首の字（「行」を U+2F8F「⾏」）に、英字の合字を 1 字（「ff」を U+FB00「ﬀ」）に当てるものがある（`practicaltests-jp-3.pdf` は「行」「一」「方」など 2,500 字あまり）。見た目は同じでも検索や `vs lint` の辞書に掛からないので、字を受け取るところ（`MarkedContentReceiver`）で U+2F00〜2FD5 と U+FB00〜FB06 だけを NFKC で戻す。
- **Shift_JIS・UTF-16 の符号**: Word が書き出した論文の PDF は、MS 明朝・MS ゴシックを埋め込まず、符号を Shift_JIS（`90ms-RKSJ-H` など名前が `RKSJ-H`/`RKSJ-V` で終わる符号表）か UTF-16（`UniJIS-UTF16-H`・`UniJIS-UCS2-H`）のまま書き、ToUnicode も付けない。pdf-reader はこれらの符号表を知らず、1 バイトずつ標準の符号表で読むので本文が丸ごと化ける。`Type0` の書体の符号表の名前から文字コードを決め、Shift_JIS は 1 バイト目（0x81〜0x9F・0xE0〜0xFC）で 1〜2 バイトに、UTF-16 は 2 バイトずつ（サロゲートの組は 4 バイト）に区切って 1 字ずつ読む（`PredefinedCMap`）。ToUnicode があればそれで引く。字の幅は子の書体の `W` が CID で引くので符号からは引けず（符号から CID への表は大きいので同梱しない）、半角の字（Shift_JIS の 1 バイトの字、UTF-16 の ASCII と半角カナ）を 500、ほかを子の書体の `DW` とみなす。EUC（`EUC-H`）など、ほかの既定の符号表は題材が無いので扱わない。
- **TeX のビットマップの Type 3 の書体**（2026-10-10）: dvips が TeX の書体をビットマップの Type 3 で埋め込んだ PDF（論文 `heidelberg`）は、書体に名前が無く、字の名前を「102」のような番号にする。0〜31 番は名前で引けず、合字の「fi」「ff」や数式の「−」「π」が「▯」になっていた（100 字あまり）。字の名前がすべて番号の Type 3 の書体は、持っている字の番号で TeX の書体の種類を見分け、その並びで 0〜31 番を補う（`ToUnicodeFallback`）。英字が 3 字以上で「<」「>」（60・62 番。本文の書体では「¡」「¿」）を持てば数式の書体（OML。11 番から α β γ…）、ほかの英字の多い書体は本文の書体（OT1。11〜15 番が ff fi fl ffi ffl。字に重ねて描くアクセントの 18〜24 番は補わない）、英字をほとんど持たないものは記号の書体（OMS。CMSY と同じ並び）。0〜31 番はどのみち「▯」になるので、見当が外れても「▯」が別の字になるだけ。
- **Type 3 の書体の字の大きさ**: pdf-reader は字の大きさ（`Tf`）に書体の行列（`FontMatrix`）を入れない。同じ PDF は字形をビットマップの単位で描いて `Tf` を 0.18 にするので、字の大きさが 0.2pt になり、語の中のわずかな空き（「b」と「o」の 0.36pt）を空白とみなして「b orn」「Lab oratory」と読み、見出しも見つからなかった。Type 3 の書体に限り、小文字（無ければ数字）の幅の中央値を字の大きさの半分とみなして大きさを見積もる（`MarkedContentReceiver#size_scale`）。見積もりが `Tf` の 0.5〜2 倍に収まる書体（ふつうの作りの Type 3）は `Tf` のまま。小文字も数字も無い書体（記号 1 字）は、そのページで最後に見積もった倍率を使う。
- **ToUnicode が別の字を康熙部首に当てる**（2026-10-10）: IPSJ の論文は、見出しの頭の「◼」（CID 12238）と空白（CID 1）を ToUnicode で「⿎」（U+2FCE）に当て、受け手が NFKC で戻すと「鼓鼓計算機による素数の探索」になっていた。Adobe-Japan1 の書体で ToUnicode が康熙部首（U+2F00〜2FD5）を返し、表の字がそれを NFKC で戻した字と違うときは表の字を使う（`AdobeJapan1Unicode::WithFallback`）。「行」を「⾏」に当てる PDF（practicaltests）は表の字と同じなので ToUnicode のまま。
- **Mathematical Pi の書体**: Linotype の数式記号の書体は字の名前を「H9266」のような番号にし、書き出したソフトが ToUnicode に Symbol 書体の慣習の英字（π を「p」）や名前の末尾の数字（= を「5」・− を「2」）を書く（IPSJ の論文の「f(x)51/x2a50」）。この書体に限り、ToUnicode より先に字の名前で読む（H9251 から α β γ… の順。H11001〜H11005 は + − × ÷ =。`ToUnicodeFallback`）。
- 日本語以外の字の集まり（Adobe-GB1・CNS1・Korea1・KR）は、題材が無いので扱わない。同じ表が同じリポジトリにあり、足すのは表と名前の対応だけで済む。

## 3. 経路 A: 構造ツリーから戻す

### 3.1 要素と Markdown の対応

| 構造要素 | Markdown |
|---|---|
| `H1`〜`H6` | `#`〜`######`。PDF の `H1` が複数あっても、最初の `H1` を章題として扱う |
| `H`（段階なし） | 入れ子の深さから段階を決める |
| `P` | 段落。段落のあいだは空行で区切る |
| `L` / `LI` / `Lbl` / `LBody` | `Lbl` が数字なら `1.`、記号なら `-` のリスト |
| `Table` / `TR` / `TH` / `TD` | パイプの表。`TH` のある行を見出し行にする |
| `Figure`（`Code` を含む） | ```` ``` ```` の囲み。`Caption` があれば ```` ```lang:ファイル名 ```` の形にする |
| `Code`（段落の中） | `` ` `` で囲む |
| `Figure`（画像） | `![Alt](抽出した画像)`。Enhanced で画像を抜いたときだけ参照を書く |
| `Figure`（`Alt` が `$…$`） | `Alt` の TeX をそのまま書く（数式） |
| `BlockQuote` | `> ` |
| `Ruby` / `RB` / `RT` | `{親文字|ルビ}` |
| `Strong` / `Em` | `**…**` / `*…*` |
| `Link` | 文字だけを残す（行き先は PDF 内のページなので持ち帰らない） |
| `Aside` | 捨てる（§3.3） |
| `Note` | 脚注 `[^n]` |
| `Artifact`（マーク付き内容） | 捨てる（規格上「本文ではない」印） |
| `NonStruct` / `Div` / `Sect` / `Art` / `Part` | 入れ物なので、中身だけを辿る |

### 3.2 文字と要素のつなぎ方

構造要素は本文の文字を MCID（マーク付き内容の番号）で指す。各ページの描画命令を読みながら `BDC … /MCID n … EMC` の範囲に描かれた文字を集め、MCID ごとの文字列（と座標・大きさ）を作ってから、構造ツリーを辿って要素ごとに連結する。

pdf-reader（MIT）だけで作れることを試作で確かめた。`PDF::Reader::PageTextReceiver` を継承して `begin_marked_content_with_pl` / `end_marked_content` を受け、文字を描く命令の前後で増えた文字を、その時点の MCID へ割り当てる。

**増えた文字は公開メソッドの `runs` で数える**（論点 7-3 で決定）。絞り込みをすべて外して呼ぶ（`rect: nil, skip_zero_width: false, skip_overlapping: false, merge: false`）と、受け取った文字の一覧がそのまま返るので、命令の前後の数の差が新しく描かれた文字になる。内部の変数 `@characters` を直接読む方法と結果は完全に一致し、速さの差も小さい。

| 方式 | 97-sample.pdf（23 頁） | cyberguardian.pdf（244 頁） | pdf-reader の内部への依存 |
|---|---|---|---|
| 公開メソッド `runs` の数の差 | 1.15 秒 | 4.21 秒 | なし |
| 内部変数 `@characters` を読む | 0.50 秒 | 3.76 秒 | あり（版が上がると壊れうる） |

`runs` を毎回呼ぶ手間は、1 ページの文字数の 2 乗で増える。文字の極端に多いページで遅くなったら、そのページだけ内部の変数を読む方式に切り替えることを考える。

**`begin_marked_content_with_pl` を受けるときは `super` を呼ぶ。** pdf-reader 2.16 はこのメソッドで ActualText（画像化された文字などに添える代替の文字）を扱っている。呼ばずに上書きすると、その対応を壊す（最初の試作はそうなっていた）。

### 3.3 経路 A でも座標を使うところ

- **行の区切り**: `Code` の中の改行は構造ツリーに無い。行は y 座標で分け、字下げは x 座標から空白の数に直す。
- **コードの行番号**: `vs build` の PDF では、行番号を `aria-hidden` にして `Code` から外した（§8）。それより前に作った PDF と一般の PDF では `Code` の中に入っているので、論点 7-4（§7.1）の規則で外す。
- **脚注**: タグの無い脚注は経路 B の判定（§4.5）で拾う。

### 3.4 経路 A を使うかの判定

構造ツリーがあっても、中身が薄い PDF はある（全体を `P` 1 つで包むだけ、など）。**本文の文字の 9 割以上が `NonStruct` 以外の要素に属する**ときだけ経路 A を使い、それ以外は経路 B へ落とす（しきい値は論点 7-5）。

**実例**: `jouhoukagakuronsyu0_72_5.pdf`（InDesign CS6 で書き出した論文・18 ページ）は「タグ付き」だが、構造ツリーが覆っているのは表紙の 3 項目（題・著者・誌名）だけで、本文にはタグが無い。要素の種類も独自名（`Story`・`NormalParagraphStyle`・`Span`）で、標準の種類へは対応表（`RoleMap`）を引いて読み替える必要がある。この PDF は 9 割の条件を満たさないので経路 B で読む。タグの有無ではなく、覆っている文字の割合で判定する理由がここにある。

**構造ツリーを辿るときの注意**: InDesign の PDF では、子の配列の要素が参照（`HexaPDF::Reference`）のまま渡ってくる。Chrome の PDF では起きなかった。参照は解決してから辿る。

## 4. 経路 B: 紙面から推定する

タグの無い PDF と OCR の結果に使う。入力は「ページごとの行（文字列・x・y・幅・文字の大きさ・フォント名）」で、PDF の文字からでも OCR の行からでも作れる形にする。

### 4.1 本文の大きさを決める

全文字を大きさごとに数え、最も多い大きさを本文とする。`97-sample.pdf` では 10.5pt が 73.9% で本文になる（次に多いのは 9.2pt のコード 17.3%）。

**字の幅で測る**（2026-10-09）: 字の数でなく、字の幅の合計がいちばん大きい大きさを本文とする。和文の 1 字は英字の 2 字分の幅を取るので、字の数で数えると英字の多い小さな字が本文を上回る。論文 `73-4-218` は 8pt の英字（参考文献・数式）が 8,456 字、9.2pt の本文が 6,840 字で、本文の大きさを 8pt と取り違え、本文がすべて見出しと太字になっていた。pLaTeX の『実践 Rust Web 開発 5』も、9pt のコードを本文の大きさとしていた（和文の本文は 9.6pt）。題材 29 本のうち変わるのはこの 2 本だけ。

**本文の書体の印を外す**: 本文の大きさでいちばん多い書体を本文の書体とし、それが太字（名前・ForceBold・太さ 600 以上）か、名前が等幅の書体でないのに等幅の印（FixedPitch）を持つなら、その書体の字の太字・等幅の印を外して行を組み直す。論文 `73-4-218` の本文は「FutoMinA101Pro-Bold」で、本文がすべて強調（`**`）になる。Word の論文 `TS42-3_017` の本文は等幅の印を持つ MS ゴシックで、英数字がすべて行内のコードになる。名前が等幅の書体（Courier・HackGen・SFTT など）は外さない（コードの多い本では、コードの書体が本文の大きさでいちばん多いことがある）。

### 4.2 見出し

次をすべて満たす行のまとまりを見出しとする。

- 文字の大きさが本文の 1.15 倍以上（太字のフォントなら同じ大きさでもよい）
- 1〜2 行で終わる（3 行以上続くなら、大きな文字の段落とみなす）
- 行末が句点で終わらない

段階は、見出しになった大きさを大きい順に並べて `#`・`##`・`###` を振る。

`97-sample.pdf` の実測では、章題 31.2pt・節 23.4pt・項 12.8pt に分かれる。ただし**章のリード文が 12.6pt で、項の見出しとほぼ同じ大きさ**になる。大きさだけで決めるとリード文が見出しになるので、行数と句点の条件が要る。

### 4.3 柱・ノンブル

いまは `pdf_read.text_area` の mm 指定で版面の外を除いている。一般の PDF は版面がまちまちで、利用者が mm を測って書くのは負担が大きい。次のように置き換える。

- **ページをまたいで、ほぼ同じ位置に同じ文字列が出る行**を柱とする（偶数・奇数ページで左右が入れ替わる形も含める）。
- 同じ位置に**連番の数字**が出る行をノンブルとする。
- `text_area` は、推定が外れたときに人が範囲を指定する手段として残す（論点 7-6）。
- **回して描いた字**（2026-10-09）: 版面の外のつめに縦に組んだ章の印（「Chapter 1」「リポジトリを作ってみよう」）は、字ごとに別の行になり、繰り返しでは見分けにくい。字を描く行列で進む向きが縦に近い字と、縦書きの書体（符号表の名前が `-V` で終わる）の字に印を付け、最初の字が版面の外にあるまとまりは 1 ページだけでも落とす。縦書きの字は pdf-reader が横に進めて位置を出すので、正しいのは最初の字の位置だけ。本文の行頭に接していても、ふつうの字とは別のまとまりにする。版面が決まらないページ（図や画面写真の多いページ）では、回した字に限って、同じ側（偶数・奇数）のページでいちばん多い版面で見る（ほかの字にまで広げると、版面の広い目次のページ番号を落とす）。

### 4.4 段落とリスト

- 行と行のあいだが本文の行送りより広いところで段落を切る。
- 行頭が 1 字下がっていれば新しい段落とする（和文の段落の書き方）。
- 前の行が版面の右端まで届かずに終わっていれば、そこで段落が終わったとみなす。
- 行頭が `1.`・`(1)`・`・`・`•`・`-` で始まる行の並びをリストとする。

いまの MeCab による改行の補正（`MecabNewlineCleaner`）は、段落を切ったあとの行の連結に使う。

### 4.5 脚注

本文より小さい文字で、ページの下部にあり、行頭が番号で始まるまとまりを脚注とする。本文の中で、同じ番号が小さい文字（上付き）で出ている箇所を参照とし、`[^n]` で結ぶ。

### 4.6 コード

フォント名が等幅（`Mono`・`Courier`・`Code` などを含む）の行の並びを、```` ``` ```` で囲む。字下げは x 座標から空白の数に直し、英字のあいだの空白を詰めない（Enhanced で `def threshold` が `defthreshold` になる崩れを止める）。行頭が 1 から始まる連番ならそれを外す。

pLaTeX の本のコード（2026-10-09。『実践 Rust Web 開発 5』で推定した表が 527 → 4 個、コードの囲みが 0 → 658 個）:

- **等幅の書体名**: TeX の等幅は `CMTT`（OT1）のほか、T1 符号の `SFTT`（cm-super）・`ECTT`（EC）。pLaTeX の本は `SFTT` が多く、名前の一覧に無かったのでコードが 1 つも囲みにならず、行番号付きの行がすべて表になっていた。
- **引用符**: TeX の等幅は、紙面ではまっすぐな `'`・`` ` `` を `quoteright`・`quoteleft` の名前で持つので「’」「‘」として読める。`CMTT`・`SFTT`・`ECTT` の字に限って、まっすぐな字に戻す。
- **行番号のコロン**: 「`1: @import`」のように番号の直後にコロンを置く形も、コロンごと行番号として外す。
- **キャプションの番号の見出し**: 「リスト 1.8: app/assets/flash.css.scss」のように、ファイル名の前に「リスト 1.8:」「List 2-3:」が付いた行もキャプションにし、見出しは外してファイル名だけを残す。
- **コードの中の和文**: pLaTeX はコードの中の和文を和文の書体で描くので、「`13: <th>削除</th>`」の行は等幅の字が 9 割に届かない。和文を除いた字がすべて等幅で、行頭の等幅の行番号が前後の行と 1 ずつ続く行もコードにする。行内のコードで始まる本文の行（「`NKF` は…」）は行番号が無いので外れる。
- **網掛け**: ascmac は網掛けの地を `TeX-ascgrp` の「A」を敷き詰めて描き、囲みの角を `TeX-ascmac` の字で描く。拾うとコードの字の間に「A」が挟まって表になるので、この 2 つの書体の字は拾わない。

### 4.7 表（後回し）

罫線と文字の位置から表を組み立てるのは難しく、外れたときの崩れも大きい。列の対応まで推定する組み立ては扱わず、経路 A の `Table` を戻す。タグの無い PDF では、セルの区切りを失わない程度にとどめる案を出している（論点 7-7・§7.2）。

### 4.8 論理式の否定の線と平方根

TeX は論理式の否定（Ā・$\overline{A+B}$）の上の線を、字ではなく細い横線で描く。読み取ると線が消え、式の意味が変わる（ド・モルガンの定理が「A + B = A · B」になる）。細い横線（高さ 1.2pt 以下・幅 2pt 以上。図形の中のサブパスごとに見て、両端がそろい上下に接するものは 1 本にまとめる）の真下の字の並びを、次をすべて満たすとき否定の線の下の字とみなし、`$\overline{…}$` にする。重なった線は入れ子にする（外側は幅の広い線、同じ幅なら高い線）。

- 線が行のベースラインより字の大きさの 0.5〜1.6 倍上にあり、両端が下の字の並びの両端と半字以内でそろう。
- 下の字が英数字を含み、和文の字と大きな隙間（表の罫線は升目をまたぐ）を含まず、半分以上が数式の書体（`MATH_FONT_NAME`）。表の罫線や見出しの飾りの枠の下の字は本文の書体なので外れる。
- 平方根の横棒（根号が線の左端にくっつくか、線の下に入り込む）でも、分数の線（線にほとんど接して上に字があるか、線の上の行が線の幅に収まる）でもない。

平方根（√）も、TeX は根号の字（CMSY・CMEX の「p」〜「t」。横棒の高さから下へ垂れ下がる字）と細い横棒で描く。根号の字の右端が横棒の左端に接し（0.6pt 以内）、字の基準の高さが横棒とそろう（1pt 以内。「√」の字なら横棒より下）とき、横棒の下でいちばん近い行の字の並び（横棒は行のベースラインより字の大きさの 0.3〜2.5 倍上。入れ子の外側の横棒は高い）を `$\sqrt{…}$` にする。中身は数字だけのこともあるので、数式の書体は求めない。否定の線と入れ子にでき（`$\sqrt{2+\sqrt{2}}$`）、置き換えた根号の字は本文から除く。

### 4.9 筆算

数を右そろえで縦に並べ、横線を引いた計算（筆算）は、横線が消えると数が段落やコードにばらける。否定の線・平方根に使わなかった細い横線を起点に、その幅の中の行を上下にたどり、次をすべて満たす範囲を筆算とし、別行立ての数式にする。

- 横線のすぐ上の行と、上の横線の上の 1〜2 行（割り算は商の 1 行）、下の横線の下の行が、どれも数と演算記号だけ（`CALC_ROW`。16 進の A〜F・基数の「(2)」を含む）。字のまとまりは 1 つで、2 つ目を認めるのは 1 つ目が演算記号 1 字のときだけ（表の行は升目ごとに分かれる）。
- 幅の 6 割以上が重なって幅の近い（0.6〜1.6 倍）横線が、字の大きさの 10 倍以内で続き、間の行がすべて数の行なら、1 つの筆算の横線（掛け算・割り算）。
- 一番上の横線のすぐ下の行が「除数)被除数」なら割り算。

書き方は `$$\begin{array}{r} … \end{array}$$`。数は原本と同じ等幅（`\mathtt`）で書き、行の右端の差を `\phantom{0}` で埋めて桁をそろえる。横線は `\hline`。割り算は `除数\enclose{longdiv}{被除数}` とし、引く数の行（すぐ下に横線のある行）を `\underline` にする。筆算の字は行から除き、かたまりは上端の高さ、続いて左から順に置く（横に並んだ 2 進・8 進・16 進の筆算）。

### 4.10 2 段組み（2026-10-09）

2 段に組んだ本文は、同じ高さの左右の行が 1 行につながり、段の間の隙間が表の列の境目になっていた（`gitlab.pdf` で表 194 個）。行を組んだあと（柱・つめを落としたあと）に、段の境目で行を左右に分け、2 段の区間ごとに左の段を読み終えてから右の段を読む順に並べる（`LayoutStructure#split_columns`）。

- **段の境目**: 字の大きさの 0.8 倍以上の隙間を 1 つだけ持つ 10 字以上の行のうち、隙間の左の部分の右端がそろう（両端揃えの段は境目の手前で止まる）行が 3 行以上あるところ。そろう行の左右の部分は、どちらも 8 字ぶん以上の幅がいる。行末の句読点を段の外へぶら下げると隙間は字の 0.9 倍ほどに縮み、字の左端が段の右端にそろう。左右の段の幅の比は 0.75〜1.33（2 段組みの段の幅はほぼ等しい）。表の升目（右端がそろわない・幅が狭い・列の幅が違う）、囲みの中の 2 列の一覧や図のラベル（右端がそろわない）、字間を広げた見出し（隙間がいくつもある）、等幅の字が半分以上の行（コードの中の 2 字以上の空白）は数えない。
- **ページをまたいだ境目**: 2 段の区間が 2 行しかないページは、ページの中では境目が決まらない。同じ側のページの 3 割以上で境目が見つかる本なら、その側で見つかり、両側を合わせて 3 回以上見つかった境目（紙面の型がいくつかあると位置が違う）を試し、いちばん多くの行を 2 段の区間に入れるものを借りる。数を両側で合わせるのは、左右の余白を入れ替えない短い論文のため（2026-10-10。4 ページの論文 `245` は奇数ページが 2 枚で、題と要旨のある 1 ページ目は自分では境目が決まらない）。1 段組みの本の数ページだけの段組み（索引など）は広げない。
- **行の分け方**: 境目は左の段の右端から右の段の左端までの帯で見る。帯の中に半字以上の隙間があり、左の部分が段の右端にそろうか文末で終わる行を、隙間で左右に分ける。どちらでもない行（囲みの中の一覧）、等幅の字が半分以上の行（コード）、境目をまたぐ行（全幅の見出し・図）は分けない。
- **区間**: 左右に分ける行が 2 行以上続くところ。境目をまたぐ行、段の幅に収まる見出し（字の大きさが違う行）、行送りの 2.5 倍を超える空きで切る。その上下には、同じ段の行頭にあって行送りの 1.5 倍以内に続く片側だけの行（段の長さの違い・段落の終わり）を足す。左右の段で行の高さ（ベースライン）がずれる紙面では左右に分ける行が 1 行も無いので、片側だけの行が全幅の行を挟まずに続き（行送りの 2.5 倍以内）、左右とも 3 行以上あって左右が 3 回以上入れ替わるところも区間にする（2026-10-10。論文 `245` の 1 ページ目は、全幅の題と要旨の下で右の段の行が左の段の行の間の高さに並ぶ）。
- **段落**: 左の段の行は段の右端を、右の段の行は段の左端を基準に、右端まで届くか・字下げかを見る。左の段の右端まで届いた行から右の段の頭へ字下げせずに続けば、同じ段落にする。
- **画像**: 画像は上端の高さで差し込むが、文のかたまりは並べ直さない（右の段の上の段落は、左の段の下の段落より高い位置にある）。

`gitlab.pdf` で、推定した表は 194 → 36 個（本文の 2 段組みは用語集の 1 個。残りは本物の表・図のラベル・行番号付きのコード）。

### 4.11 線で描いた図（2026-10-09）

回路図・関係図・矢印の図のように、埋め込みの画像ではなく線と図形で描いた図は、プラグインが取り出せず、図の中のラベル（「S：ソース」「（a）」）だけが本文に散らばっていた。ページに描いた図形から図の範囲を見つけ、埋め込みの画像と同じく図として扱う（`VectorFigures`）。範囲の上の字は図のラベルとして本文から除き、図は描いた高さに置く。Enhanced Mode では、範囲を `pdftoppm`（poppler）で 300dpi の PNG に切り抜き（`page-035-figure-01.png`）、画像として差し込む。Standard Mode と経路 A（構造ツリー）では探さない／描き出さない（経路 A の図は `Figure` の `Alt` で戻る）。

- **図形**: 受け手（`MarkedContentReceiver`）が、塗り・線引きのたびに図形の外接矩形を、曲線を含むか・斜めの線を含むか・塗ったかの印付きで覚える（`Shape`）。
- **部品**: ページ幅の 85% を超える図形、ページの半分を超える図形、文やコードの行（12 字以上の行・等幅の字が 4 字以上で半分を超える行）を囲む図形（囲みの枠・吹き出し）は除く。
- **まとまり**: 8pt 以内で接する図形をつなぎ、曲線か斜めの線を含み、図形が 5 つ以上、幅 40pt・高さ 30pt 以上のものを図の候補にする。表の罫線や囲みの枠は縦横の線と長方形だけなので候補にならない。
- **ラベル**: 候補の近く（行の高さの 1.5 倍以内）の短い行を範囲に入れ、入れた行の近くの行も続けて入れる。キャプション（「図」「表」で始まる行）、回して描いた字（つめ）、本文の行（10 字以上でページ幅の 4 割を超えて伸び、字が行の 7 割以上を占める。式の周りの空きで切れた切れ端も含む）は入れない。20pt 以内の候補は 1 つの図にまとめる（「(a)」「(b)」の 2 つを並べた図）。
- **除くもの**: 本文の行が範囲の上端か下端にかかれば、その行を外すように縮め、中ほどを通るなら図にしない。範囲の中に、25 字以上の行・本文の 1.5 倍以上の字（章の題の飾り枠）・コードの行 2 行以上（コードと実行結果を矢印でつないだ組）・20 を超える行（線で描いた字の表）があるか、字が範囲の 15% を超えて占めるものは図にしない。埋め込みの画像と範囲の 3 割を超えて重なるもの（画面写真の上に引いた注記の枠と矢印）と、埋め込みの画像の半分を超えて含むもの（図と画像の結び付けを取り違える）も除く。
- **2 段組みのページ**（2026-10-10）: 右の段の図の端のラベル（論文 `245` の「U0」）は、左の段の本文の行と同じ高さに並ぶと、1 行にまとめたときに本文の行の字とみなされてラベルから外れ、そこから上へ続くラベルの鎖も切れていた。ページの真ん中で分けた 8 字以上の切れ端のうち、左半分に収まるものの右端と右半分に収まるものの左端がどちらも 3 つ以上そろうページを 2 段組みとみなし、本文の行を真ん中をまたぐ隙間で分ける。6 字以下で文末で終わらない切れ端は本文の行の字としない（段落の最後の短い行や吹き出しの文はラベルにしない）。また 2 段組みのページでは、ラベルを入れて字が多くなりすぎただけ（20 を超える行・字が範囲の 15% を超える）で除いた図を、ラベルを入れる前の範囲で確かめ直す（文・見出し・コードを含んで除いたものは確かめ直さない。1 段組みのページでは、式を線で描いた本の記号の一覧表や、式の空きで切れた本文の行を含む範囲が図になるので確かめ直さない）。
- **残る取り違え**: 行の中の式を線で描いた本文の行は、字が空いて本文の行と見分けられず、その行の下の線で描いた式と一緒に図になることがある（行は本文から消え、図の中に残る）。1 行だけのコードを矢印でつないだ実行結果も図になる。

- 表の推定（§4.7）。

## 6. 置き場所（MIT の本体か、AGPL のプラグインか）

**決定: 構造の復元は MIT の本体に置く。** プラグインは画像の抜き出しと OCR に専念し、OCR の結果を「行（文字列・座標・高さ）」として本体へ返す。本体は PDF の文字でも OCR の行でも、同じ経路 B で構造を戻す。

- 文字の層がある PDF なら、プラグインを入れていなくても構造が戻る。`vs build` の PDF やタグ付きの PDF の多くはここに入る。
- 経路 B の判定が 1 か所にまとまる。OCR の行の高さから文字の大きさを見積もれば、スキャンした PDF でも見出しが戻る。
- プラグインとの取り決め（`read` の JSON）は変わる。`page_chunks`（組み上がった文字列）に加えて、行の座標と大きさ、画像の位置を返す形にする。

もう一つの案は、構造の復元をプラグインの HexaPDF 側に置くことである。HexaPDF は描画命令とフォントの情報を扱いやすく、試作は楽になる。ただし AGPL を入れない利用者には構造が戻らず、Standard Mode との差が大きくなる。

### 7.1 コードの行番号（論点 4）

`vs build` の PDF では、行番号は紙面の文字として描かれている（`::before` の `counter(linenumber)`）。字下げは x 座標から戻せる（例: 本文開始 76.6pt、字下げした行 98.8pt で 2 字ぶん）。原稿は次のとおり。

````markdown
```ruby:photoelectric.rb
# 光電効果のしきい周波数を求める
PLANCK = 6.62607015e-34   # プランク定数 h [J·s]

def threshold_frequency(work_function_ev)
  work_function_j = work_function_ev * EV
  work_function_j / PLANCK
end
```
````

**行番号を外した場合**（行頭の連番が全行にあるときだけ外す案）:

````markdown
```ruby:photoelectric.rb
# 光電効果のしきい周波数を求める
PLANCK = 6.62607015e-34 # プランク定数 h [J·s]

def threshold_frequency(work_function_ev)
  work_function_j = work_function_ev * EV
  work_function_j / PLANCK
end
```
````

原稿とほぼ同じになる。違いは、桁をそろえるための連続した空白が 1 つに縮むことくらいである（PDF からは空白の数ではなく位置しか取れないため）。`vs build` で組み直すと、行番号は Vivlio Starter がまた付ける。

**行番号を残した場合**:

````markdown
```ruby:photoelectric.rb
1 # 光電効果のしきい周波数を求める
2 PLANCK = 6.62607015e-34 # プランク定数 h [J·s]
3
4 def threshold_frequency(work_function_ev)
5   work_function_j = work_function_ev * EV
6   work_function_j / PLANCK
7 end
```
````

- `vs build` で組み直すと、行番号が二重になる（`1  1 # 光電効果の…`）。
- コードとして正しくなくなる。色分け（シンタックスハイライト）が崩れ、写して実行することもできない。
- 行番号が本文の一部である資料（行番号で説明を参照するソースの全文掲載など）では、残っていたほうが原本に忠実である。

**参考: いまの出力**（Standard Mode）は、行番号が残り、行のあいだに空行が入り、字下げが消え、囲みも付かない。

```
1 # 光電効果のしきい周波数を求める

2 # ν₀ = φ / h

3 PLANCK = 6.62607015e-34# プランク定数 h [J·s]
```

**途中から始まる抜粋**: 原稿の ```` ```include:gravitational_lensing.rb:28-30``` ```` は、紙面で `28`・`29`・`30` と元のファイルの行番号で描かれる。判定は「1 から始まる」ではなく「**1 ずつ増える**」で見るので、この抜粋も外す。外した開始番号は、Vivlio Starter の記法で書き戻す。

````markdown
```ruby:gravitational_lensing.rb#L28
# 太陽の縁をかすめる光の曲がり角
deflection_rad = gravitational_deflection(SOLAR_MASS, SOLAR_RADIUS)
deflection_arcsec = to_arcseconds(deflection_rad)
```
````

組み直すと、紙面の行番号はまた 28 から始まる。`#L` はファイル名の直後に書く記法なので、ファイル名（`Caption`）の無いコードでは開始番号を書き戻せない。そのときは番号を外したうえで、元の開始番号をコメントで残す。

**折り返した行**: 長い行は紙面で折り返し、2 行目以降には番号が付かない（ぶら下げ字下げで、コードの開始位置にそろう）。番号の無い行は、直前の番号付きの行の続きとして連結し、「全行に連番があるか」の判定からは外す。

**連番とみなさない形**: 番号が飛ぶ（1, 2, 5）、同じ番号が続く、一部の行にしか番号が無い。こうした行頭の数字はコードの一部（Markdown の番号付きリストを説明するコードなど）かもしれないので、外さない。

### 7.2 表（論点 7）

いまはどのモードでも表を組み立てない。原稿の表（`| 金属 | 仕事関数 φ / eV | しきい周波数 / Hz |` と 3 行）は、次のように崩れる。

- **Standard**: 表全体が 1 行につながり、後ろの段落まで続く。セルの区切りが消えるので数値が読めない（「2.2」と「5.32」が「2.25.32」）。
  `表 H-1: 光電効果のしきい周波数金属仕事関数 φ / eV しきい周波数 / Hzカリウム2.25.32 × 10¹⁴ナトリウム2.35.56 × 10¹⁴金5.11.23 × 10¹⁵注意: しきい周波数より低い光を…`
- **Enhanced**: 見出し行はつながり、データ行はセルごとに改行される（「カリウム」「2.2」「5.32×10¹⁴」が別々の行）。数値は読めるが、どの列かは分からない。
- **OCR**: Standard と同じく 1 行につながり、数字も崩れる（「5.32 X 1014」）。

経路 A（構造ツリー）がある PDF では、`TR`・`TH`・`TD` からそのまま表を組める。

**タグの無い PDF でも、列を推定して表に仮組みする**（決定）。97 章の表 H-1 で試したところ、文字の位置だけから原稿と同じ表が組めた。

```
| 金属 | 仕事関数 φ / eV | しきい周波数 / Hz |
| --- | --- | --- |
| カリウム | 2.2 | 5.32 × 10¹⁴ |
| ナトリウム | 2.3 | 5.56 × 10¹⁴ |
| 金 | 5.1 | 1.23 × 10¹⁵ |
```

列の推定は「表のどの行にも文字が無い縦の隙間」を探して、そこを列の境目にする。左揃え（金属）・中央揃え（仕事関数）・右揃え（しきい周波数）が混ざっていても、各列の文字が占める横の範囲は重ならないので、隙間で分けられる。見出しの行もデータの行も同じ境目で切るので、`|` の数が行ごとに食い違うことはない。

- **文字は 1 字ずつの位置で見る**。pdf-reader は同じ行の文字を 1 つのまとまりに結合し（`runs` の既定）、そのまとまりがセルのあいだの空白まで覆うので、結合をやめて（`merge: false`）から隙間を探す。
- **隙間の幅は小さい**。表 H-1 では列のあいだが 6pt しか空いていなかった（「ナトリウム」の終わりが 229pt、「仕事関数」の始まりが 235pt）。しきい値は 4pt 程度にする。和文の文字のあいだは 0pt なので、取り違えにくい。
- **推定した表には、確かめるよう促すコメントを添える**（`<!-- pdf:read: 列を推定して組んだ表です。列の対応を確かめてください -->`）。

仮組みで外れやすい形と、その扱い:

| 形 | 起きること | 扱い |
|---|---|---|
| セルの中で折り返した文字 | 1 つのセルが 2 行に分かれ、行が増える | 行のあいだが本文の行送りより狭ければ、同じ行として連結する |
| 結合したセル（colspan） | 見出しの 1 セルが 2 列にまたがり、隙間が見つからない | またがった列は空のセルにする。崩れはコメントで知らせる |
| 列のあいだがほとんど空いていない表 | 隙間が見つからず、1 列の表になる | 表にせず、いまの段落のまま残す |
| 罫線だけで区切った表 | 文字の隙間は狭くても、罫線の位置が分かる | 罫線（描画命令の線）も列の境目の手がかりに使う（後回し） |

表の範囲（どこからどこまでが表か）は、「列の境目が同じ位置にそろった行が 3 行以上続く」ところとする。表のキャプション（「表 H-1:」）が直前にあれば、手がかりに加える。

## 8. `vs build` 側の改善（調査結果）

小さな HTML を Vivliostyle で PDF にし、構造ツリーがどう変わるかを確かめた（Vivliostyle CLI 11.3.3・Chrome 153）。

| 書き方 | 構造ツリー |
|---|---|
| `<span aria-hidden="true">A-1</span>`（見出しの番号） | **構造ツリーから外れる**。紙面には描かれる |
| `<span aria-hidden="true">1 </span>`（コードの行番号） | **`Code` から外れる** |
| `::before { content: "B-2" / "" }`（代替テキストを空に） | 外れない。Chrome はこの指定を構造ツリーに使わない |
| `::before { content: counter(…) }`（いまの行番号） | `Code` の文字に入る |
| 脚注 `<span role="doc-footnote">`（いまの書き方） | `NonStruct` |
| 脚注 `<aside role="doc-footnote">`・`role="note"`・`role="doc-endnote"` | `NonStruct` |
| 脚注 `<aside>`（役割なし） | `Aside`（柱・ノンブルと同じ） |

- **脚注は `NonStruct` のままにする**（決定）。`Note` にすることは HTML の書き方では実現できず（Chrome はどの書き方でも `Note` を作らない）、PDF を組んだあとに構造ツリーを書き換える必要がある。構造要素には ID などの手がかりが無いので、脚注の本文と文字を照らし合わせることになり、印刷用 PDF の導出・dedup との順序も確かめ直すことになる。PDF の中で脚注はわずかで、そのための改造に見合わない。`pdf:read` は脚注を経路 B（§4.5）で拾う。
- **見出しの番号（`A-1`・`♣`）は残す**（決定）。`aria-hidden` で外すことはできるが、読み上げソフトで「節 A-1」と聞こえるほうが親切である。`pdf:read` は、一般の PDF のためにどのみち要る「見出しの行頭の番号を外す」処理で扱う。
- **コードの行番号は `aria-hidden` で `Code` から外す**（決定・実装済み）。行番号は読み上げても意味が無く、写したコードにも混ざる。`::before` の連番をやめ、`PdfBuilder#convert_code_pre_lines!` が各行の先頭に `<span class="vs-code-ln" aria-hidden="true">1</span>` を実際の要素として入れる（class 名は Kindle 向けの注入と同じ）。開始番号は `pre` の `data-start`（`#L28`）から取る。

## 9. 物差しと合格の目安

`scripts/pdf_read_score.rb` で、原稿と `vs pdf:read` の出力を突き合わせる。


- **文字の一致**: 原稿から記法を外し、`codes/` の取り込みを展開し、数式を除いた文字列を基準に、空白を無視して文字単位で比べる（再現率・適合率・F 値）。出力の側にも同じく記法を外してから比べる（`#` や `|` を文字として数えると、構造を戻すほど適合率が下がるため）。脚注のように位置が動いた文字は、一致しなかった分として数える。

## 10. 実装記録（経路 A・2026-10-04）

置き場所は本体（MIT）の `lib/vivlio_starter/cli/pdf/` の 3 つのファイル。

| ファイル | 役目 |
|---|---|
| `marked_content_receiver.rb` | ページを読み、MCID ごとに文字と画像の位置を集める（公開メソッド `runs` の数の差）。どの MCID にも属さない文字も取っておく |
| `structure_reader.rb` | 構造ツリーを辿って要素の木にする。RoleMap の読み替え、MCR、子が参照のまま来る形を扱う。覆う割合（`coverage`）を出す |
| `structure_markdown.rb` | 要素の木を Markdown へ写す |

`PdfReadCommand#convert_structured` が両モードで最初に試し、覆う割合が 9 割に届かなければ nil を返して、これまでの読み方へ任せる。構造ツリーの無い PDF は、ページを読まずに 0 と答える（507 ページの PDF で 53 秒かかっていた）。Enhanced Mode では、プラグインに OCR を切って画像だけを抜き出させ、`Figure` と描かれた位置の重なりで結ぶ。`page_separator` は使わない。

実装して分かったこと:

- **Chrome は空白を文字として描かない。** 語のあいだの空白は、文字の隙間から戻す。本物の空白は 0.28 字ほどあり、欧文どうしは 0.15 字より広ければ空白とする。和文が絡む隙間は、両端揃えで字間が広がる（実測で最大 0.25 字）うえ、和欧間のアキ（0.125 字前後）もあるので、行ごとに和文どうしの字間の中央値を引いてから 0.2 字で見る。長音「ー」と中黒「・」は Unicode の文字種で和文に入らないので、別に足す。
- **構造ツリーはページごとに作られる。** ページをまたいだ段落は 2 つの `P` に分かれる。段落の頭を 1 字下げる組み方なら（2 行以上の段落の過半で判定）、次のページの頭が下がっていないことで続きと見る。下げない組み方なら、前の段落が文末で終わっていないことで見る。句点だけで決めると、「」」で終わる 1 行の段落を次の段落とつないでしまう。
- **行番号の判定は、隙間で区切ってから数字を読む。** 34 行目の「3.times」のように、行番号のすぐ後のコードが数字で始まると「343」と読んでしまう。
- **`aria-hidden` の行番号は、どのマークにも入らない文字として紙面に描かれる。** `Code` の中に番号が無いときは、コードの左に並ぶ構造ツリーの外の数字を行の頭へ戻してから、同じ規則（§7.1）で外す。これで開始番号（`#L28`）と、折り返した行の見分けが戻る。
- **脚注は 2 度描いて決める。** 1 度目で、本文の候補（本文より小さい字で番号から始まる段落）と参照（本文の 0.9 倍以下で 0.15 字以上持ち上がった数字）を集める。2 度目で、両方そろった番号だけを `[^n]` にする。上付きの指数を脚注と取り違えないため。土台の字が数式の書体（`MATH_FONT_NAME`。CMMI・Symbol・モリサワの MMa（立体の `MMaCentury-Regular` を除く）など）なら指数とみなし、参照にしない（2026-10-10。IPSJ の論文の「1/x²」が「1/x[^2-2]」になっていた）。脚注の本文は次の見出しの手前へまとめて置く。ページの下で割り込ませると、ページをまたいだ段落をつなげなくなる。
- **座標は Integer で来ることがある。** 重なりの割合や字下げの字数は `fdiv` で割る（画像の結び付けが 0 になっていた）。

## 11. 実装記録（経路 B・2026-10-04）

本体（MIT）の `layout_structure.rb` が、ページの文字・画像・小さな図形から要素の木（経路 A と同じ `StructureReader::Element`）を組み、`StructureMarkdown` が写す。空白・行番号・脚注・ページをまたぐ段落の結合は経路 A と共通になる。`PdfReadCommand#convert_structured` は、経路 A に当たらず、9 割以上のページに文字の層（10 字以上）があるときに経路 B を使う。スキャンした PDF は、これまでどおり OCR の経路へ回る。

タグを外した 97 章の PDF（HexaPDF で `StructTreeRoot` を消したもの）で、構造の数は経路 A とすべて同じになった（§9）。ほかの題材での所要時間は、Ruby Best Practices（328 ページ）11 秒、cyberguardian（244 ページ）8 秒、H21-takase（19 ページ）0.8 秒。

推定の規則（§4 からの変更を含む）:

- **読む順は座標で決める。** Chrome は囲み・見出し・コードを本文の後に描くので、描いた順は使えない。ベースラインがそろう字を 1 行にし（小さく持ち上がった脚注の参照は同じ行に入れる）、上から並べる。段組みの読み順は推定しない（§5）。
- **見出し**: 本文の 1.15 倍以上で、本文と違う書体（太字・別のフォント）の行。文末（「。」「．」、英字に続くピリオド）で終わる行は見出しにしない（2026-10-10。OCR の字の層で段落の最後の短い行が大きく出た Smith の論文）。書体が本文と同じなら 1.4 倍以上を求める（本のカードの書名 13〜14pt を見出しにしないため）。3 行以内で終わるかたまりを 1 つの見出しにし、4 行以上なら大きな字の段落（章のリード）とする。段階は、かたまりの中でいちばん大きい字の大きさを大きい順に並べ、4% 以内の差を同じ段階にまとめて振る（いちばん多い字の大きさで測ると、「A-12」と「参考書籍」のように番号と題の字数が同じとき揺れる）。見出しの横に添えた番号（題の左にある行）は先に読む。
- **柱とノンブル**: ページの最上行・最下行のうち、次の行から行送りの 1.8 倍より離れ（2026-10-10 から、本文より小さい字の 2 行のかたまりも候補にする。ほかに 3 行以上あるページに限る。IPSJ の論文の「Vol.2014-ARC-208 No.19」と「2014/1/24」）、同じ高さに max(2, ページ数の 25%) ページ以上出る行。文字列（数字を除く）が 2 ページ以上で同じか、数字だけなら落とす。版面の左右の外に置いた柱・ノンブル・つめは本文と同じ高さに並んで行に混ざるので、1 字を超える隙間で区切ったまとまりのうち、版面の外にあり、数字だけか同じ位置に 2 ページ以上出るものを落とす。版面は、ページ幅の 4 割を超える本文の行で、いちばん多い行頭と行末の位置とする（最小・最大で測ると、つめの混ざった行で広がる。行頭の多さだけで測ると、表やコードの多いページで表の行頭を版面と取り違え、コードの行番号を落とした）。等幅の字は落とさない。
- **ページをまたぐ段落**（2026-10-10）: 図や表のキャプション（「図 9-8」「Figure 3」で始まり、番号の後に助詞や読点が続かない段落）は、文末の「。」が無くても次のページの段落につなげない（Rust-tutorial で 50 か所あまり、ページの下のキャプションが次のページの段落の頭につながっていた）。
- **段落**: 字の大きさが変わる、行間が行送りの 1.35 倍を超える、前の行が右端より 2 字以上手前で止まる、全角の文末（「。」「」」など）で終わる前の行が右端より 1 字を超えて手前で止まる（和文は両端をそろえて組むので、段落の途中の行は右端まで届く。字下げした 1 行だけの段落の後に字下げした段落が続くと、字下げの比べ方では切れない。2026-10-09）、次の行の頭が 0.5 字以上下がる、のどれかで切る。右端と左端はその段落の行と次の行で測る（先の段落の幅の広い行まで含めると、囲みの中の狭い段落が 1 行ずつ切れた）。左端の見積もりに使う先の行は、次の行と右端がそろい、左へ 1.5 字以内のものに限る（画像の下で全幅に戻った次の段落の行を含めると、回り込んだ段落の最後の行が切れた）。次の行も短いと右端の比べ方では切れないので、文末で終わりページの本文の右端より手前で止まった行の後でも切る（中央に置いた引用やコードのファイル名を前の段落に吸い込んでいた）。
- **リスト**: 行頭が「・」「1.」「(1)」などで、その後に少し隙間がある行。本文の 1.15 倍以上の字の行（「■コラム: …」の題）はリストにしない。Chrome は箇条書きの「•」を文字ではなく 4pt 四方の塗りつぶしで描くので、受け手が小さな塗りつぶしの図形を集め、行の左にあれば頭とみなす。項目は、版面の右端より手前で止まった行で終わる。
- **コード**: 等幅の書体の字が 9 割を占める行。行内のコードが多い本文の行（8 割台）と分かれる。直前のファイル名だけの 1 行はキャプションにする。行内では等幅の連なりを行内のコードにする（英数字を含まない連なり、たとえば等幅の書体で補った上付きの「⁵」は除く）。
- **表**（§7.2）: どの行にも字の無い 4pt 以上の縦の隙間が 3 行以上そろうところ。半分以上の行を左右に分ける隙間だけを列の境目にする（中央揃えの見出しの行だけが作る隙間で列が増えた）。行の間隔は字の 1.1 倍以上を求め、数式のフォント（CMMI・CMSY など）が 3 割を超える行は除く（分数を含む数式を表にしていた）。
- **ルビ**: 本文の行のすぐ上の、仮名だけの小さな行。中心がルビの範囲に入る字を親文字にする。英字の小さな飾り（見出しの上の「Section」）はルビにしない。
- **画像**: 描かれた上端の高さで読む順に差し込む。画像（ページの 6 割未満の大きさ）の上に描かれた文字は図の注釈として本文から除く。
- **擬似太字**: 同じ字を少しずらして 2 度描く PDF がある（「2-2-2」が「22--22--22」になる）。字と高さで引いて、0.3 字以内に重なる同じ字を 1 つにする。2 度目は描く順が離れていることがあるので、直前の数字だけを見る比べ方では捕まらない。
- **目次と索引の項目**（2026-10-07）: 点線のリーダー（`. . .`・`・・・`・`……`）とページ番号で終わる行は、その後で必ず段落を切る。点（`.`・`．`・`・`・`･`・`·`）は 3 字以上、三点リーダー（`…`・`‥`・`⋯`）は 1 字で点 3 つぶんなので 1 字以上をリーダーとみなす（2026-10-09。『GPU の育てかた』は半角の中黒 `･`、『エッセンス』は `·` で、項目がつながっていた）。リーダーが版面の右端まで届くので、右端の比べ方では次の項目とつながっていた（TeX の目次が 2〜3 項目ずつ、`cyberguardian` の目次が 2 項目ずつ）。ページ番号の前の隙間は縦にそろうが、表の行にも数えない（`探究Rustプログラミング`・`RustでつくるRust`・`practicaltests` の目次が表になっていた）。ページの最後の項目に、次のページの頭の行（柱の「CONTENTS」）もつなげない。題材 23 本で比べ、変わったのは目次・索引のある 7 本で、目次と索引の外の行は変わらなかった。2 段組みの索引で左右の項目が 1 行に並ぶのは、段組みを推定しないため残る。
- **太字**: 本文の中の太字の連なりを `**…**` にする。2 行以上の段落がまるごと太字なら、強調ではなく段落の書体（リード文）とみなして印を付けない。脚注の番号が太字だと `**1.**` になるので、脚注の本文の判定は印を外した文字で見る。

経路 B で戻らないもの: 数式（紙面では図形で、文字が無い）、引用の区切り、会話文の並び、段組みの読み順。フォントに文字の対応表が無い PDF（古い pTeX の論文、図の中の文字）は文字化けし、経路 B では直せない。

論点 6 の決定に合わせ、`pdf_read.text_area` の既定値を無し（`nil`）にし、雛形の `book.yml` では値を空にした。

## 12. 実装記録（OCR の語を経路 B へ・2026-10-04）

§6 の取り決めを、行ではなく**語**の単位で実装した。プラグイン（1.2.0・未公開）の `read` の結果に `page_words`（OCR したページだけ語の一覧。`text`・`x`・`y`・`width`・`size`・`conf`、座標は pt）と `page_sizes` を足した。本体の `OcrPage` が語の幅を字数で割って 1 字ずつの文字にし、文字の層のあるページの受け手と並べて `LayoutStructure` に渡す。語のあいだの空白は文字の隙間から決まるので、OCR が和文の字のあいだに入れる空白（プラグインの `collapse_ocr_japanese_spaces` が詰めていたもの）も同じ規則で詰まる。`config/ocr_corrections.yml` の補正は、組み上がった Markdown のコードの囲みの外にかける（本体の `OcrCorrections`）。語を返さない古いプラグインなら、これまでの読み方（`page_chunks`）に戻る。

スキャンした 97 章（`97-sample-ocr.pdf`）で、F 値はこれまでの 88.7% から 89.1% になり、章と節の見出しと、行番号の付いたコードの囲みが戻った。

OCR で分かったこと:

- **行の枠の高さは字の大きさにならない。** 括弧・ルビ・下に伸びる字で揺れ、本文の行を見出しと取り違えた。和文の字はほぼ正方形なので、行の中の和文の字の幅の中央値で見積もる（和文が 3 字に満たない行は枠の高さの 8 割）。
- **語の枠は重なる。** 語を均等に割った字を左から並べ直すと「言葉の遅い」が「言の遅葉い」、「1879年3月」が「187年93月」になる。同じ行の中では、前の字の右端より左へ戻さず、OCR が返した順を保つ。
- **書体が分からない。** 等幅でコードを、太字や別の書体で見出しを見分けられない。コードは、行頭の数字が前後の行と 1 ずつ続くこと（行番号）で見る。見出しは本文の 1.4 倍以上の行だけになる。
- **見出しの段階が細かく分かれすぎる。** 大きさの差を 10% までまとめ、見出しが 1 つしかない段階は（いちばん上を除き）すぐ下の段階に寄せる。図の中の字を読んだ大きな字が段階を作り、節や項を押し下げていた。
- **図の中の字の確信度は本文と変わらない**（44〜46）。確信度では除けない。絵の領域の検出（`pdf-read-ocr-postprocess-spec.md`）で扱う。確信度 20 未満の語だけを捨てる。
