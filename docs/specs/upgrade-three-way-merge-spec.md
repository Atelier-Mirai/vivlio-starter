# `vs upgrade` の競合を 3-way マージで自動合流させる

> 作成日: 2026-08-12
> ステータス: **実装待ち（優先度低）**
> 対象: 雛形と著者が**同じファイルの別の場所**を変えたとき、著者に聞かずに両立させる
> 関連: `upgrade-conflict-review-spec.md`（本仕様書の親。競合を「見える・選べる」ようにする側）
> 出自: 親仕様書の (b) を切り出したもの。効果は確かにあるが**急がない**と判断した——理由は §6

## 0. なぜ別仕様書に分けたか

親仕様書 `upgrade-conflict-review-spec.md` は 4 つの改善を並べていたが、**規模と緊急度が一段違う**ものが 1 つ混ざっていた。

親のほうは「見えていない変更が `y` で承認されてしまう」という**事故そのもの**を止める話で、数十行で終わる。こちらは**そもそも聞かずに済ませる**話で、新しい仕組み（共通祖先の保管）を持ち込む。

同じ仕様書に置くと、前者がリリースに間に合わない理由になりかねない。切り離す。

## 1. 障害：lock はハッシュしか持っていない

3-way マージには 3 つの中身が要る。

| | 中身の在りか |
| --- | --- |
| **祖先**（`vs new` 当時の雛形） | **無い** |
| 現物（著者のファイル） | プロジェクト内 |
| 新版（新しい雛形） | 新しい gem 内 |

`config/scaffold.lock` は照合用のダイジェストだけを持つ。

```yaml
scaffold_version: 1.0.0-rc.2
files:
  ".gitignore": sha256:5bd1228cb66a849d9a10ded53ce664bc905b4085a3f3f065a3a1a407c8243e4b
```

ハッシュからは「変わったか」しか分からず、**「どこが変わったか」は復元できない**。親仕様書の初稿には「lock は共通祖先である。3-way の材料はすでにそろっている」と書いたが、**これは誤り**だった。材料は足りていない。

## 2. 共通祖先をどう調達するか

`scaffold_version` が記録されているので、版を特定する手がかりはある。

### 案 A: 旧版の gem から読む

RubyGems は `gem update` しても**旧版をアンインストールしない**（`gem cleanup` を明示的に叩くまで残る）。実測でも 2 つの版が同居していた。

```
vivlio-starter (1.0.0.pre.rc.2, 1.0.0.pre.rc.1)
```

`scaffold_version` の版の `lib/project_scaffold/` をそのまま祖先として使える。**プロジェクト側に何も保存しなくてよい**のが利点。

弱点は、`gem cleanup` 済み・別マシンへ移動・rbenv の Ruby を入れ替えた、といった場合に**祖先が消えている**こと。

### 案 B: 基準をプロジェクトに保存する

`vs new` と `vs upgrade` の完了時に、テキストファイルだけを `.cache/vs/scaffold-base/` へ複製する。

| | 数 |
| --- | --- |
| 雛形の全ファイル | 7,748 |
| うち画像 | 7,560 |
| **複製対象（css/yml/js/json、原稿を除く）** | **70 ファイル・500KB** |

画像はバイナリで、そもそもマージできない。**マージし得るものだけ**を持てば 500KB で済む。

### 採用：A → B のフォールバック

旧 gem があればそれを使い、無ければ保存した基準を使う。**どちらか一方が欠けても動く**。

祖先がどちらの経路でも得られないファイルは、現行どおり 2-way の競合として著者に尋ねる——親仕様書の (c)(d) が入っていれば、そこで事故は起きない。

## 3. マージ本体は既製品を使う

`git merge-file` が使える。実測で、離れた変更（1 行目と 9 行目）が衝突なしに両立した。

```
$ git merge-file -p mine base theirs
MINE
l2 … l8
THEIRS
```

隣接した変更は 1 つの衝突としてまとめられる。これは望ましい挙動で、**近すぎる変更を機械が勝手に混ぜない**という保険になっている。

`git` は macOS の Xcode Command Line Tools に同梱で、`vs doctor` が CLT の有無を既に見ている。とはいえ `git` が無い環境では**静かに 2-way へ落とす**（エラーにしない）。

自前で diff3 を書く選択肢もある（既存の `lcs_diff` が使える）が、**マージは境界条件が多く、枯れた実装に任せるほうが安い**。

## 4. 3-way の後に残った競合

自動合流できなかったものは、定義上「**双方が同じ場所を変えた**」＝ 適用すれば著者の変更が消える場所である。それを名指しする。

```
⚠️ 適用すると、あなたの変更 1 箇所が失われます（バックアップ: .cache/vs/upgrade-backup/…）
```

親仕様書の (d) 要約も「`-` 行＝あなたの現在の内容」と読める文言にしてあるが、**3-way を通した後は「本当に失われる場所だけが残っている」**という強い意味が出る。この警告に意味が出るのは 3-way が入ってからなので、こちらへ置く。

## 5. 一括操作キー

残った競合に対してのみ、まとめて処理する手段。

| キー | 動作 |
| --- | --- |
| `a` | 以降すべて適用 |
| `s` | 以降すべてスキップ |
| `q` | 中断（ここまでの適用は保持） |

`git add -p` の慣習に合わせる。

**ただし現時点では不要と判断している。** §6 のとおり通常の更新では競合が数件に収まり、逐一 y/n で困らない。件数が実際に増えてから足す。**これを先に足すのは、見ずに承認する道を広げるだけになる。**

## 6. 優先度が低い理由

**通常の `1.0.0` → `1.1.0` では、競合はほとんど起きない。**

競合の条件は「雛形も著者も同じファイルを変えた」である。著者が触るのは `custom.css` など数ファイル、マイナー更新で変わる雛形も数〜十数ファイル。**交差は 0〜3 件**にとどまる。

3-way を入れて減るのは、その 0〜3 件が 0〜1 件になる程度である。

「数十〜数百件の競合」は**旧リポジトリを複製して原稿を書いた**という特殊な経路の数字だった（実測 26 件全部が競合）。手で持ってきたファイルは lock と食い違うためで、これは正規の移行手順ではない。**この場面は想定から外す**と決めた（2026-08-12）。

したがって本仕様書は「あると嬉しい」であり、**親仕様書の (a)(c)(d) が入っていれば実害は無い**。

## 7. 規模の見積もり

| 部品 | 行数 |
| --- | --- |
| 基準の保存（テキストのみ複製） | 約 30 |
| 旧 gem からの取得 ＋ フォールバック | 約 30 |
| `git merge-file` のラッパ | 約 30 |
| 分類・適用への組み込み | 約 40 |
| テスト | 約 120 |
| **合計** | **約 250（lib は 130 ほど）** |

見合わせるほどの規模ではない。**急がないだけで、いずれ入れる価値はある。**

## 8. テスト

`notation-implementation-guide.md` §7 の流儀に従う。`upgrade_commands_test.rb` と同じく一時ディレクトリと DI で完結し、実ビルドを伴わない。

1. **自動合流**: 祖先に対し、雛形が先頭・著者が末尾を変えた → 質問されず両方が残る
2. **真の競合**: 双方が同じ行を変えた → 従来どおり質問になる
3. **祖先の調達 A**: 旧版 gem の雛形が祖先として使われる
4. **祖先の調達 B**: 旧版 gem が無いとき `.cache/vs/scaffold-base/` が使われる
5. **祖先なし**: どちらも無いファイルは 2-way の競合へ落ちる（例外を投げない）
6. **git なし**: `git` が見つからない環境で 2-way へ落ちる
7. **バイナリ**: 画像は基準の複製対象に入らない
