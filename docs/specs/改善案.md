## この文書の書き方

- **1 項目 = 1 見出し**（`## 番号. 題`）。番号は気づいた順の通し番号で、優先度ではない。新しい項目は末尾に番号を続けて足し、**番号は振り直さない**（「改善案 #12」のように引けるようにするため）。
- 見出しの直後に、次の 3 行を置く。
  - **対象** — 章ファイル名と節見出し。行番号は原稿を直すとずれるので、節見出しで書く。
  - **種別** — `原稿`（文章の直し）／`実装`（コードの改修）／`調査`（動作や事実の確認）／`検討`（方針を決める）。複数当てはまるときは並べる。
  - **状態** — `未着手`／`検討中`／`調査済み`（答えは出たが、直すのは後の段）／`決定`（方針が決まり、直すのは後の段）／`対応済み（日付）`。
- 本文は **現状**（いまの記述や挙動。引用で示す）と **提案**（どうしたいか）に分ける。答えを知りたいことは **問い** に書く。
- 対応が済んだら状態を `対応済み（日付）` に改め、下の一覧表も合わせて直す。
- 一覧表の **段** は進める順番を表す。1 = 調査（コードと動作を確かめる）、2 = 方針を決める、3 = 小さな実装、4 = 章ごとの書き直し。実装を先に済ませてから原稿を書き、章は判断が出そろってから一度で仕上げる。

## 4. 画像属性の真偽値を `border=on` でも書けるようにする

- **対象**: 記法（`22-extentions.md`「画像に枠を引く `.bordered`」）
- **種別**: 実装
- **状態**: 対応済み（2026-09-28）

**現状**:

```markdown
![](screenshot.webp){.bordered width=60%}
```

**提案**: これも許容してはどうか。

```markdown
![](screenshot.webp){border=on width=60%}
```

**対応（2026-09-28）**: 画像の枠を `border=on` / `border=off` で指定するようにし、`.bordered` は撤去した（ユーザー提案: `{width=30% align=right .bordered}` はクラスが値つきの属性に混ざって違和感がある）。前処理（`markdown_preprocessor.rb` の `transform_image_borders!`）が `border=on` を `.vs-bordered`、`border=off` を `.vs-borderless` へ読み替え、CSS（`chapter-common.css`）がこの内部クラスで枠を付ける／外す。コード領域は書き換えない。`{.bordered}`・`:::{.bordered}`・不正な値（`border=yes` など）は、`validate_image_borders!` が行番号と直し方を添えて 🟡 で知らせる。`vs import`（Re:VIEW の `border=on`）も `border=on` を出すように直した。

**調べて分かったこと**: 22 章は「`.bordered` が要るのはキャプションのない画像とサイドイメージの中の画像」と書いていたが、実際には VFM が段落に単独で置いた画像をすべて `figure` で包むため、キャプションの有無によらず**既定で枠が付いていた**。`.bordered` は事実上なにもしておらず、役に立つのは既定の枠を外す `border=off` のほうだった。22 章と 90 章は実態に合わせて書き直した。`border=on` が効くのは文中に置いた画像（`figure` に包まれない）だけ。

検証用プロジェクトで組み、既定の枠・`border=off`（キャプションなし／あり）・文中の画像の `border=on` を紙面で確かめた。

**注意**: CSS は著者のプロジェクト側に複製されて使われるので、既存のプロジェクトでは `vs upgrade` で `stylesheets/` を更新するまで `border=off` が効かない（旧 `.bordered` はそれまで効き続ける）。雛形へは `copy_to_scaffold.rb` で同期する。

**気づき**: 文中に置いた画像は `width=10%` が効かず本文の幅いっぱいに広がり、その行の文字も均等割りで間延びする（#53）。

## 5. 記法の登場順

- **対象**: `22-extentions.md`
- **種別**: 検討
- **状態**: 決定（2026-09-28）

**問い**: 記法を紹介する順番は、いまのままで適切か。

**決定（2026-09-28）**: 第 4 段で 22 章を書き直すときに決める。#7 の見出し統一と同時に手を入れる。2026-09-28 時点の順は「注記・補足 → 画像 → 図 → 段組 → 表 → 配置 → 装飾 → リスト → コード → 数式 → 余白」。

**対応（2026-09-29）**: 前章と同じ「文字 → リスト → コード → 表 → 画像 → 数式」の順にそろえ、紙面全体の調整（段組・余白・改ページ）、ビルド時の差し込み、専用章への案内を後ろに置いた。新しい順は「基本（クラスの組み合わせを含む）→ リード文 → 注記・補足 → テキストの配置 → 会話文 → キーボードのキー → リスト装飾 → コードと実行結果 → 表 → 画像 → 書籍紹介カード → 図解注釈 → SVG → mermaid → 数式 → 段組 → 余白・改ページ → ビルド時の差し込み → 専用章」。`.terminal`・`.output`・`.diagram` の枠は「注記・補足」から「コードと実行結果」へ移し、脚注の節は前章と重なるので外した。並べ替えだけのコミットと、中身の書き直しのコミットを分けた。

## 6. `crop` に CSS 式の 3 値指定を許す

- **対象**: `22-extentions.md`「`crop` — 画像の周囲を切り落とす」
- **種別**: 実装
- **状態**: 対応済み（2026-09-28）

**現状**:

> 画像の余分な周囲は、画像属性の `crop` で削げます。値は CSS と同じ「上・右・下・左」の時計回りで、1 つ（四辺共通）・2 つ（上下／左右）・4 つのいずれかで書きます。

```markdown
# 上下左右を均等に
![](Einstein.webp){crop="50"}

# 上下 30、左右 100
![](Einstein.webp){crop="30 100"}

# 上 30 / 右 250 / 下 60 / 左 100（px でも可）
![](Einstein.webp){crop="30 250 60 100"}
```

## 9. 生の `<kbd>` も受け付けるか

- **対象**: `22-extentions.md`「キーボード入力 `〘 〙`」
- **種別**: 調査・機能
- **状態**: 対応済み（2026-09-29）

**現状**:

> 半角の `<kbd>` を毎回書くのは手間なので、全角括弧で囲むだけで `<kbd>` タグに変換されます。

**問い**: `〘Ctrl + S〙` ではなく `<kbd>Ctrl + S</kbd>` と直接書いた場合も、変換されるか（そのまま通るか）。

**調査結果（2026-09-28）**: 生の `<kbd>` もそのまま通り、紙面は `〘 〙` と同じになる。`〘 〙` は後処理で `<kbd>` へ置き換えているだけで（`replacement_rules.rb`）、見た目は `kbd` 要素に当てた CSS（キーキャップ書体 `keyfont`）が決めるため。`vs build` で三通りを組んで確かめた。

- `<kbd>Ctrl</kbd> + <kbd>S</kbd>` … `〘Ctrl〙 + 〘S〙` と同じ
- `〘Ctrl + S〙` … `+` までキーキャップになる（`Ctrl`・`+`・`S` の 3 つが並ぶ）

直す必要はない。22 章で「`<kbd>` を直接書いても同じ」と一言添えるかは、第 4 段で決める。

**補足（2026-09-29・ユーザー提案）**: `〘Ctrl〙 + 〘S〙` は IME を切り替えながら打つことになり、`<kbd>Ctrl</kbd>+<kbd>S</kbd>` はキーごとにタグを閉じて開き直すので、どちらも入力が煩雑。`<kbd>Ctrl + S</kbd>` を `<kbd>Ctrl</kbd> + <kbd>S</kbd>` と等価にする。`〘 〙` は読みやすさのために残す。

**対応（2026-09-29）**: 後処理 `split_kbd_combinations!`（`post_process.rb`）で、子要素を持たない `<kbd>` の中身を `+` で分ける。

- 区切りとみなす `+` は、前後を空白で挟んだもの（`Ctrl + S`）か、前後が空白以外の文字に接したもの（`Ctrl+S`）。前後の空白は書いたとおりに残す。
- `+` のキーそのものは残す。`<kbd>+</kbd>` は分けず、`<kbd>Ctrl + +</kbd>`・`<kbd>Ctrl++</kbd>` は最後の `+` をキーにする。
- `〘 〙` は置換規則で先に `<kbd>` になるので、`〘Ctrl + S〙` も分かれる（上の調査結果の「`+` までキーキャップ」は解消）。
- 22 章に `<kbd>` を直接書く例と組み合わせの書き方を加え、90 章の早見表に `<kbd>Ctrl + S</kbd>` を足した。

## 12. QR コードに寸法を直接指定する構文

- **対象**: `22-extentions.md`「`@qr:URL` — QR コード」
- **種別**: 実装・検討
- **状態**: 対応済み（2026-09-28）

**気づき**: `vs lint` は `@qr:URL です` の空白に「リンクの後にスペースを入れません」（ja-space-around-link）と指摘する（大きさの指定の有無によらず、以前から）。従って空白を消すと、`@qr:https://…です` の「です」まで URL として読まれ、別の QR になる。lint で `@qr:URL` をリンクとして扱わないようにする必要がある。

## 出力の流れと構造化出力

:::{.section-lead}
`vs metrics` は章の解析を並列で走らせながら、表示は章番号順に整列します。この節では、その出力の流れと `--json` / `--yaml` の中身をまとめます。詳しく知りたい方向けの説明なので、書くことに集中したいときは読み飛ばして構いません。キャッシュと並列実行の仕組みは「開発者向けガイド」の章にあります。
:::

### ストリーミング出力

`vs metrics` は次の順で進行します。

1. **章別リストの逐次出力** — 章の解析は並列で走りますが、表示は章番号順に整列されます。先に解析の終わった章があっても順番を追い越さず、前の章が出そろってから続けて表示されます。`--sections`/`--warn`/章指定のフィルタはこの段階で適用され、対象が 1 章もなければ「対象章がありません」と表示されます。
2. **全体集計** — 全章の解析完了後に、基本情報・文構造・詳細分析（語彙難度・語彙多様度・読解難度）をまとめて表示します。
3. **推敲用の参考資料** — `--all` を指定したときだけ、章間のばらつき以降を続けて出力します。

棒グラフの縮尺は解析前の軽量スキャン（文字数の概算）で先に決めるため、章が出るたびに横幅が揺れ動くことはありません。

### 構造化出力の中身

`--json` / `--yaml` は以下の形式で出力します。

```json
{
  "stats": [
    { "path": "contents/01-intro.md", "chars": 1200, ... }
  ],
  "totals": {
    "chars": 2400,
    "avg_sentence_chars": 210.5,
    "vocabulary": { "mattr": 0.586, "kanji_ratio": 27.1, ... },
    "readability": { "score": 42.1, "label": "Standard" }
  },
  "advice": {
    "consistency": [ { "label": "漢字比率", "mean": 27.38, "high": [...], "low": [...] } ],
    "long_sentences": [ { "chapter_num": 3, "line": 274, "length": 118, "text": "…" } ],
    "sentence_rhythm": { "distribution": {...}, "monotone_runs": [...] },
    "content_words": [ { "word": "画像", "pos": "名詞", "count": 306 } ],
    "kanji_levels": { "ratios": [...], "lists": {...}, "locations": [...] }
  }
}
```

`totals` は Runner が各章の `tokens_map` / `basic_stats` / 読解難度の特徴量を合算した結果で、外部ツールが平均を再計算する必要はありません。読解難度（RS）は、章ごとの RS を単純平均するのではなく、各章の連や文の数といった特徴量を合算したうえで一度だけ算出します。語彙多様度（MATTR）は文書長に頑健な指標のため、全体値は各章 MATTR の語数加重平均で代表させます。`advice` は画面出力の `--all` 相当（参考資料）を構造化したものです。いずれもキャッシュに保存済みのため、章を再解析せずに再構成できます。
````

**問い**: この文章をどこに置くか（`61-developer.md`、`docs/specs/` のメモ、または破棄）。

**決定（2026-09-28）**: `61-developer.md` へ移す。`--json` を外部ツールで読む人には価値がある情報で、書き起こし直すのは手間なので残す。

**対応（2026-09-29）**: 61 章「メトリクス」の、キャッシュと並列実行の段落の後ろへ移した。キャッシュの素の値と全体値の計算方法（RS と MATTR）は 61 章に既にあったので重ねず、出力の順と `--json` の形だけを足した。JSON のキー名は `vs metrics --json --all` の実物と照らした。32 章の `--json` の節からは、内部の話を外して 61 章を参照するようにした。

## 44. `vs pdf:pages` の大量警告と対象 PDF の選び方

- **対象**: `44-build.md`「本のページを画像として保存する（vs pdf:pages）」・`vs pdf:pages`
- **種別**: 実装・調査
- **状態**: 対応済み（2026-09-28）

**現状**: 実行すると、次の警告が大量に表示される。

```
Syntax Error (26805338): Warning: name token is longer than what the specification says it can be
```

2026-09-28 に `vs build 97` で作った `97-sample.pdf` でも、`pdftotext` / `pdftoppm` で同じ警告が出た。`vs pdf:pages` 固有ではなく、生成した PDF の側に原因がありそう。

**提案**: デバッグして警告が出ないようにする。

**問い**: 複数の PDF がプロジェクトルート直下にある場合、どの PDF が選択されるのか。

**調査結果（2026-09-28）**:

- **警告の原因**: Vivliostyle が PDF に書く名前付きリンク先（named destination）の名前が、PDF 1.7 の実装上限 127 バイトを超えている。名前にはビルド時の HTML の URL が丸ごと埋め込まれる（例 `/viv-id-http:003a:002f:002flocalhost:003a13000:002fvivliostyle:002f:002ecache:002fvs:002fbuild:002fpdf:002f97-sample:002ehtml:0023fn1`、133 バイト）。97 章だけで 187 個あった。poppler 系のツール（`pdftoppm`・`pdftotext`）が 1 個ごとに警告し、`vs pdf:pages` はその標準エラーを素通しするので大量に出る。紙面とリンクの動作には影響しない。作業場所が `.cache/vs/build/pdf/` へ深くなったことで名前が長くなったとみられる。
- **対象の PDF**: 引数を省くと、全章ビルドの閲覧用 PDF（`Common.generate_output_filename('pdf')`、本書なら `vivlio_starter_v1.0.0.pdf`）を使う。ルート直下に単章の PDF が並んでいても、それらは選ばれない。別の PDF は `vs pdf:pages 97-sample` のように引数で指定する。

**直し方の候補**（第 3 段で選ぶ）: (a) `vs pdf:pages` が pdftoppm の該当警告だけを捨てる（手軽。PDF 自体は変わらない）、(b) ビルドの作業場所の URL を短くして 127 バイトに収める（根本対処。ただし長い章名では再び超えうる）、(c) ビルド後にリンク先の名前を短い名前へ付け替える（確実だが大きい）。

**決定（2026-09-28）**: (a) を採る。`vs pdf:pages` が pdftoppm の「name token is longer than …」の警告だけを捨てる。PDF 自体は変えない。(c)（リンク先の名前の付け替え）が要るかは、入稿用 PDF の検査でこの長さが問題になるかを確かめてから、別の項目で決める。

**対応（2026-09-28）**: (a) を実装した。`PdfToJpeg.execute!`（`pdf/pdf_to_jpeg.rb`）が `pdftoppm` を `Open3.capture3` で実行し、標準エラーから「name token is longer than …」の行だけを捨て、残りはそのまま表示する。`vs pdf:pages` と、同じ処理を使う PDF のラスタライズの両方に効く（ビルド中の表の回転 `rotate_table_images.rb` は、もともと標準エラーを捨てている）。テストを 1 件追加。本書の `97-sample.pdf` で、`pdftoppm` を直接実行すると 12 件出る警告が、`vs pdf:pages` では 0 件になり、23 ページを画像化できることを確かめた。

**気づき**: 調査結果に「`vs pdf:pages 97-sample` のように引数で指定する」と書いたが、実際には `.pdf` を省くと「対象の PDF が見つかりません」で止まる。前提条件の確認（`guards/pdf_artifact_check.rb`）が入力をそのまま調べ、`.pdf` を補うのは後段の処理だけのため。確認でも `.pdf` を補うよう直した（`vs pdf:rasterize`・`vs pdf:compress` も同じ確認を使う）。44 章で対象 PDF の選び方を説明するのは、第 4 段の書き直しで行う。
