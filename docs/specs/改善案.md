## この文書の書き方

- **1 項目 = 1 見出し**（`## 番号. 題`）。番号は気づいた順の通し番号で、優先度ではない。新しい項目は末尾に番号を続けて足し、**番号は振り直さない**（「改善案 #12」のように引けるようにするため）。
- 見出しの直後に、次の 3 行を置く。
  - **対象** — 章ファイル名と節見出し。行番号は原稿を直すとずれるので、節見出しで書く。
  - **種別** — `原稿`（文章の直し）／`実装`（コードの改修）／`調査`（動作や事実の確認）／`検討`（方針を決める）。複数当てはまるときは並べる。
  - **状態** — `未着手`／`検討中`／`調査済み`（答えは出たが、直すのは後の段）／`決定`（方針が決まり、直すのは後の段）／`対応済み（日付）`。
- 本文は **現状**（いまの記述や挙動。引用で示す）と **提案**（どうしたいか）に分ける。答えを知りたいことは **問い** に書く。
- 対応が済んだら状態を `対応済み（日付）` に改め、下の一覧表も合わせて直す。
- 一覧表の **段** は進める順番を表す。1 = 調査（コードと動作を確かめる）、2 = 方針を決める、3 = 小さな実装、4 = 章ごとの書き直し。実装を先に済ませてから原稿を書き、章は判断が出そろってから一度で仕上げる。

## 4. 画像属性の真偽値を `border=on` でも書けるようにする

- **対象**: 記法（`22-extensions.md`「画像に枠を引く `.bordered`」）
- **種別**: 実装
- **状態**: 対応済み（2026-09-28）

**現状**:

```markdown
![](screenshot.webp){.bordered width=60%}
```

**提案**: これも許容してはどうか。

```markdown
![](screenshot.webp){border=on width=60%}
```

**対応（2026-09-28）**: 画像の枠を `border=on` / `border=off` で指定するようにし、`.bordered` は撤去した（ユーザー提案: `{width=30% align=right .bordered}` はクラスが値つきの属性に混ざって違和感がある）。前処理（`markdown_preprocessor.rb` の `transform_image_borders!`）が `border=on` を `.vs-bordered`、`border=off` を `.vs-borderless` へ読み替え、CSS（`chapter-common.css`）がこの内部クラスで枠を付ける／外す。コード領域は書き換えない。`{.bordered}`・`:::{.bordered}`・不正な値（`border=yes` など）は、`validate_image_borders!` が行番号と直し方を添えて 🟡 で知らせる。`vs import`（Re:VIEW の `border=on`）も `border=on` を出すように直した。

**調べて分かったこと**: 22 章は「`.bordered` が要るのはキャプションのない画像とサイドイメージの中の画像」と書いていたが、実際には VFM が段落に単独で置いた画像をすべて `figure` で包むため、キャプションの有無によらず**既定で枠が付いていた**。`.bordered` は事実上なにもしておらず、役に立つのは既定の枠を外す `border=off` のほうだった。22 章と 90 章は実態に合わせて書き直した。`border=on` が効くのは文中に置いた画像（`figure` に包まれない）だけ。

検証用プロジェクトで組み、既定の枠・`border=off`（キャプションなし／あり）・文中の画像の `border=on` を紙面で確かめた。

**注意**: CSS は著者のプロジェクト側に複製されて使われるので、既存のプロジェクトでは `vs upgrade` で `stylesheets/` を更新するまで `border=off` が効かない（旧 `.bordered` はそれまで効き続ける）。雛形へは `copy_to_scaffold.rb` で同期する。

**気づき**: 文中に置いた画像は `width=10%` が効かず本文の幅いっぱいに広がり、その行の文字も均等割りで間延びする（#53）。

## 9. 生の `<kbd>` も受け付けるか

- **対象**: `22-extensions.md`「キーボード入力 `〘 〙`」
- **種別**: 調査・機能
- **状態**: 対応済み（2026-09-29）

**現状**:

> 半角の `<kbd>` を毎回書くのは手間なので、全角括弧で囲むだけで `<kbd>` タグに変換されます。

**問い**: `〘Ctrl + S〙` ではなく `<kbd>Ctrl + S</kbd>` と直接書いた場合も、変換されるか（そのまま通るか）。

**調査結果（2026-09-28）**: 生の `<kbd>` もそのまま通り、紙面は `〘 〙` と同じになる。`〘 〙` は後処理で `<kbd>` へ置き換えているだけで（`replacement_rules.rb`）、見た目は `kbd` 要素に当てた CSS（キーキャップ書体 `keyfont`）が決めるため。`vs build` で三通りを組んで確かめた。

- `<kbd>Ctrl</kbd> + <kbd>S</kbd>` … `〘Ctrl〙 + 〘S〙` と同じ
- `〘Ctrl + S〙` … `+` までキーキャップになる（`Ctrl`・`+`・`S` の 3 つが並ぶ）

直す必要はない。22 章で「`<kbd>` を直接書いても同じ」と一言添えるかは、第 4 段で決める。

**補足（2026-09-29・ユーザー提案）**: `〘Ctrl〙 + 〘S〙` は IME を切り替えながら打つことになり、`<kbd>Ctrl</kbd>+<kbd>S</kbd>` はキーごとにタグを閉じて開き直すので、どちらも入力が煩雑。`<kbd>Ctrl + S</kbd>` を `<kbd>Ctrl</kbd> + <kbd>S</kbd>` と等価にする。`〘 〙` は読みやすさのために残す。

**対応（2026-09-29）**: 後処理 `split_kbd_combinations!`（`post_process.rb`）で、子要素を持たない `<kbd>` の中身を `+` で分ける。

- 区切りとみなす `+` は、前後を空白で挟んだもの（`Ctrl + S`）か、前後が空白以外の文字に接したもの（`Ctrl+S`）。前後の空白は書いたとおりに残す。
- `+` のキーそのものは残す。`<kbd>+</kbd>` は分けず、`<kbd>Ctrl + +</kbd>`・`<kbd>Ctrl++</kbd>` は最後の `+` をキーにする。
- `〘 〙` は置換規則で先に `<kbd>` になるので、`〘Ctrl + S〙` も分かれる（上の調査結果の「`+` までキーキャップ」は解消）。
- 22 章に `<kbd>` を直接書く例と組み合わせの書き方を加え、90 章の早見表に `<kbd>Ctrl + S</kbd>` を足した。

## 12. QR コードに寸法を直接指定する構文

- **対象**: `22-extensions.md`「`@qr:URL` — QR コード」
- **種別**: 実装・検討
- **状態**: 対応済み（2026-09-28）

**現状**:

```markdown
サンプルコードはこちら: @qr:https://github.com/Atelier-Mirai/vivlio-starter
```

> - 既定のサイズは 18mm 角です。変えたいときは `stylesheets/custom.css` に `.vs-qr { width: 25mm; }` のように書きます。
> - URL は `http://` / `https://` で始め、空白か `)` の手前までが読み取られます。

**提案**: 次のように直接指定できると良い。**どのような構文が書きやすいかは要検討。**

```markdown
@qr:https://github.com/Atelier-Mirai/vivlio-starter{width=25mm}
```

**決定（2026-09-28）**: `@qr:URL{width=25mm}` と書けるようにする。画像の `{width=…}` と同じ書き方で、URL には `{` を使えない決まりなので、URL との境目を取り違えない。以前の仕様（`at-directive-tier1-spec.md`）は「custom.css で足りる」として見送っていたが、1 個だけ大きさを変えたい場面に応える。

**気づき**: `vs lint` は `@qr:URL です` の空白に「リンクの後にスペースを入れません」（ja-space-around-link）と指摘する（大きさの指定の有無によらず、以前から）。従って空白を消すと、`@qr:https://…です` の「です」まで URL として読まれ、別の QR になる。lint で `@qr:URL` をリンクとして扱わないようにする必要がある。

## 16. 数値にアンダースコアの区切りを許す

```

## 17. 日付に和暦を許す

- **対象**: `25-querystream.md`
- **種別**: 実装
- **状態**: gem に実装済み・リリース待ち（2026-09-28）

**提案**: こちらも可能にしたい。

```yaml

```

````markdown
## 出力の流れと構造化出力

:::{.section-lead}
`vs metrics` は章の解析を並列で走らせながら、表示は章番号順に整列します。この節では、その出力の流れと `--json` / `--yaml` の中身をまとめます。詳しく知りたい方向けの説明なので、書くことに集中したいときは読み飛ばして構いません。キャッシュと並列実行の仕組みは「開発者向けガイド」の章にあります。
:::

### ストリーミング出力

`vs metrics` は次の順で進行します。

1. **章別リストの逐次出力** — 章の解析は並列で走りますが、表示は章番号順に整列されます。先に解析の終わった章があっても順番を追い越さず、前の章が出そろってから続けて表示されます。`--sections`/`--warn`/章指定のフィルタはこの段階で適用され、対象が 1 章もなければ「対象章がありません」と表示されます。
2. **全体集計** — 全章の解析完了後に、基本情報・文構造・詳細分析（語彙難度・語彙多様度・読解難度）をまとめて表示します。
3. **推敲用の参考資料** — `--all` を指定したときだけ、章間のばらつき以降を続けて出力します。

棒グラフの縮尺は解析前の軽量スキャン（文字数の概算）で先に決めるため、章が出るたびに横幅が揺れ動くことはありません。

### 構造化出力の中身

`--json` / `--yaml` は以下の形式で出力します。

```json
{
  "stats": [
    { "path": "contents/01-intro.md", "chars": 1200, ... }
  ],
  "totals": {
    "chars": 2400,
    "avg_sentence_chars": 210.5,
    "vocabulary": { "mattr": 0.586, "kanji_ratio": 27.1, ... },
    "readability": { "score": 42.1, "label": "Standard" }
  },
  "advice": {
    "consistency": [ { "label": "漢字比率", "mean": 27.38, "high": [...], "low": [...] } ],
    "long_sentences": [ { "chapter_num": 3, "line": 274, "length": 118, "text": "…" } ],
    "sentence_rhythm": { "distribution": {...}, "monotone_runs": [...] },
    "content_words": [ { "word": "画像", "pos": "名詞", "count": 306 } ],
    "kanji_levels": { "ratios": [...], "lists": {...}, "locations": [...] }
  }
}
```

`totals` は Runner が各章の `tokens_map` / `basic_stats` / 読解難度の特徴量を合算した結果で、外部ツールが平均を再計算する必要はありません。読解難度（RS）は、章ごとの RS を単純平均するのではなく、各章の連や文の数といった特徴量を合算したうえで一度だけ算出します。語彙多様度（MATTR）は文書長に頑健な指標のため、全体値は各章 MATTR の語数加重平均で代表させます。`advice` は画面出力の `--all` 相当（参考資料）を構造化したものです。いずれもキャッシュに保存済みのため、章を再解析せずに再構成できます。
````

**問い**: この文章をどこに置くか（`61-developer.md`、`docs/specs/` のメモ、または破棄）。

**決定（2026-09-28）**: `61-developer.md` へ移す。`--json` を外部ツールで読む人には価値がある情報で、書き起こし直すのは手間なので残す。

## 44. `vs pdf:pages` の大量警告と対象 PDF の選び方

- **対象**: `44-build.md`「本のページを画像として保存する（vs pdf:pages）」・`vs pdf:pages`
- **種別**: 実装・調査
- **状態**: 対応済み（2026-09-28）

**現状**: 実行すると、次の警告が大量に表示される。

```
Syntax Error (26805338): Warning: name token is longer than what the specification says it can be
```

2026-09-28 に `vs build 97` で作った `97-sample.pdf` でも、`pdftotext` / `pdftoppm` で同じ警告が出た。`vs pdf:pages` 固有ではなく、生成した PDF の側に原因がありそう。

**提案**: デバッグして警告が出ないようにする。

**問い**: 複数の PDF がプロジェクトルート直下にある場合、どの PDF が選択されるのか。

**調査結果（2026-09-28）**:

- **警告の原因**: Vivliostyle が PDF に書く名前付きリンク先（named destination）の名前が、PDF 1.7 の実装上限 127 バイトを超えている。名前にはビルド時の HTML の URL が丸ごと埋め込まれる（例 `/viv-id-http:003a:002f:002flocalhost:003a13000:002fvivliostyle:002f:002ecache:002fvs:002fbuild:002fpdf:002f97-sample:002ehtml:0023fn1`、133 バイト）。97 章だけで 187 個あった。poppler 系のツール（`pdftoppm`・`pdftotext`）が 1 個ごとに警告し、`vs pdf:pages` はその標準エラーを素通しするので大量に出る。紙面とリンクの動作には影響しない。作業場所が `.cache/vs/build/pdf/` へ深くなったことで名前が長くなったとみられる。
- **対象の PDF**: 引数を省くと、全章ビルドの閲覧用 PDF（`Common.generate_output_filename('pdf')`、本書なら `vivlio_starter_v1.0.0.pdf`）を使う。ルート直下に単章の PDF が並んでいても、それらは選ばれない。別の PDF は `vs pdf:pages 97-sample` のように引数で指定する。

**直し方の候補**（第 3 段で選ぶ）: (a) `vs pdf:pages` が pdftoppm の該当警告だけを捨てる（手軽。PDF 自体は変わらない）、(b) ビルドの作業場所の URL を短くして 127 バイトに収める（根本対処。ただし長い章名では再び超えうる）、(c) ビルド後にリンク先の名前を短い名前へ付け替える（確実だが大きい）。

**決定（2026-09-28）**: (a) を採る。`vs pdf:pages` が pdftoppm の「name token is longer than …」の警告だけを捨てる。PDF 自体は変えない。(c)（リンク先の名前の付け替え）が要るかは、入稿用 PDF の検査でこの長さが問題になるかを確かめてから、別の項目で決める。

**対応（2026-09-28）**: (a) を実装した。`PdfToJpeg.execute!`（`pdf/pdf_to_jpeg.rb`）が `pdftoppm` を `Open3.capture3` で実行し、標準エラーから「name token is longer than …」の行だけを捨て、残りはそのまま表示する。`vs pdf:pages` と、同じ処理を使う PDF のラスタライズの両方に効く（ビルド中の表の回転 `rotate_table_images.rb` は、もともと標準エラーを捨てている）。テストを 1 件追加。本書の `97-sample.pdf` で、`pdftoppm` を直接実行すると 12 件出る警告が、`vs pdf:pages` では 0 件になり、23 ページを画像化できることを確かめた。

**気づき**: 調査結果に「`vs pdf:pages 97-sample` のように引数で指定する」と書いたが、実際には `.pdf` を省くと「対象の PDF が見つかりません」で止まる。前提条件の確認（`guards/pdf_artifact_check.rb`）が入力をそのまま調べ、`.pdf` を補うのは後段の処理だけのため。確認でも `.pdf` を補うよう直した（`vs pdf:rasterize`・`vs pdf:compress` も同じ確認を使う）。44 章で対象 PDF の選び方を説明するのは、第 4 段の書き直しで行う。
**原稿（2026-09-29）**: 44 章に、引数を省くと書籍全体の閲覧用 PDF（`<name>_v<version>.pdf`）を使うこと、単章の PDF は選ばれないこと、別の PDF は `vs pdf:pages 97-sample` のように指定すること、保存先が `<PDF の名前>_images/` であることを書いた。

## 62. 参照リンクと自動リンクの URL も脚注にする

- **種別**: 実装
- **状態**: 対応済み（2026-09-29）

**現状**: 印刷した本ではリンクをたどれないので、リンク先の URL を脚注に書き出している。ところが対象はインラインリンク `[文字](https://…)` だけで、参照リンク（`[文字][id]` と `[id]: https://…`）と自動リンク（`<https://…>`）は脚注にならず、紙面から URL が消える。21 章の書き直し（#2）で試験用の原稿を組んで気づいた。21 章にはひとまず「印刷する本では、インラインリンクで書いてください」と書いてある。

## 63. スペルチェックが欧文の人名を割る

- **対象**: `lint/tokenizer.rb` の `extract_words`
- **種別**: 実装
- **状態**: 対応済み（2026-09-29）

**現状**: 単語を `/[a-zA-Z]+(?:-[a-zA-Z]+)*/` で切り出すので、アクセント記号の付いた文字で語が割れる。21 章の表の `Håkon Wium Lie` は `kon` として指摘され、辞書に `Håkon` を足しても消えない（辞書に届くのは割れた後の `kon`）。`Gödel`・`Poincaré`・`Erdős` も同じ。21 章に残る唯一の指摘がこれ。

**調べたこと**: git の履歴では、Rouge による推定（`Rouge::Lexer.guess`）は `vs import`（Re:VIEW からの変換で言語名を補う）にしか入ったことがなく、ビルドの側に実装された形跡は見つからない。22 章の記述は 2026-04-26 のコミット `6a62df72`（コード強調表示の不具合解消）で書かれていた。実装が失われたのではなく、書いた時点で実装が伴っていなかった可能性が高い。

- 出力例との区別: 実行結果やログを言語名なしのフェンスで書いている原稿は、推定で色が付くと読みにくくなる。`.output` / `.terminal` / `.diagram` の中は対象外にする。

## 95. qpdf の JSON 更新がオブジェクトストリームの中の更新を捨てる

**現状**: #81 の実装中（2026-09-30）、全章ビルドの閲覧用 PDF で、ページのリンク 5,404 件のうち 1,504 件の更新（リンク先の名前の付け替え）が反映されていなかった。qpdf（12.4.1）の `--update-from-json` は成功を返し、警告も出さない。反映されなかったオブジェクト（例: 606 番）も、反映されたオブジェクト（例: 88 番）も、どちらもオブジェクトストリームの中にあった。オブジェクトストリームを外した PDF（`--object-streams=disable`）に対してなら、すべて反映された。Prawn で作った小さな PDF では再現しない。#81 は、オブジェクトストリームを外してから書き換える形で避けた。

**対応（2026-09-30）**: `QpdfJson.read` が、読む前にオブジェクトストリームを外した形へ書き直すようにした（`unpack_object_streams!`。qpdf は書き直すときに番号を振り直すので、read より前に行う）。これで `QpdfJson` を使う 4 か所（座標ずらし 2 回・重ね合わせ・リンク先の名前の付け替え）すべてで、更新が反映される。直したあとは、44 章の PDF と最初の全章ビルドの PDF のどちらでも、どの組み合わせ・順番でも捨てられた更新は 0 件だった。外したぶん中間ファイルは大きくなるが、仕上げ（アウトラインの書き込み・`DestinationNames`）でストリームを作り直す。`qpdf_json_test.rb` を新設した（現象そのものは vivliostyle の PDF でしか再現しないので、read のあとにストリームが残らないことと、更新が反映されることを確かめる）。

## 98. `vs index:auto` の候補の質を上げる

- **対象**: `index_candidate_extractor.rb`・`scoring_engine.rb`（候補の抽出と順位付け）

- 2 字の語も拾う。ただし「場合」「方法」のような一般語で埋まらないよう、見出しに出る・`[用語|読み]` で手動登録された語と同じ形・複数の章に出る、などで絞る。
- 見出し（`##`〜`####`）に出る語に加点し、その節を主要参照の候補にする。
- 断片を落とす: 助詞・指示語で終わる語、ラベル ID（`@` 始まり）、数値と単位、90 番台の早見表の表の中だけに出る語、英字の複合固有名の一部。

- **名詞連続**: 語の間の空白を保って連結する（「閲覧用 PDF」「CSS 組版」が本文と一致する）。接頭辞を次の名詞に付ける（「単章ビルド」「同梱画像」。以前は「章ビルド」「梱画像」）。行ごとに解析し、行をまたいで語をつながない。

## 100. 用語集だけに載せる語を、原稿に書く方法がない

- **対象**: 手動登録の記法（`[用語|読み]`）・`UnifiedIndexManager#extract_manual_markup_terms`・`IndexMatchScanner`、33 章「索引に語を登録する」
- **種別**: 検討・実装
- **状態**: 対応済み（2026-10-02）

**現状**: `px`・`em` のような単位は、本の全体に散らばるので、索引より用語集（フラグ `g`）に向く。索引に載せると、主要参照のない語は出現したページがすべて並ぶ（主要参照があれば、主要参照＋最大 8 か所に絞られる。`index.max_sub_references`）。用語集だけなら、索引には載らず、章ごとの最初の 1 か所に † が付いて用語集へ案内する。

ところが、原稿に書ける手動登録の記法は「索引に載せる」の意味しか持たない（2026-10-01 に確かめた）。
- `vs index:auto` は、原稿の `[px|px]` を見るたびに、辞書の語へ索引のフラグ `i` を足し直す（`merge_terms!(manual_terms, flags: 'i')`。`merge_flags` が `g` に `i` を足して `ig` にする）。レビューファイルで `[g]` に変えても、次の実行で `ig` に戻る。
- ビルドでも、`[px|px]` と書いた箇所は索引語として組まれる。

そのため、用語集だけに載せるには「原稿に `[px|px]` と書いて登録 → レビューファイルで `[g]` に変えて説明文を書き `vs index:apply` → 原稿の `[px|px]` をただの `px` に戻す」と回り道をすることになる。最後の手順を忘れると索引にも戻り、しかも気づきにくい。

**問い**:
- 辞書で `g` だけの語に、原稿の `[px|px]` の箇所が索引語として組まれたとき、索引ページにその語は載るか（載るなら、`g` だけの語が 1 ページぶん索引に出ている）。
- 手動登録の記法は「必ず辞書に入れる」の意味なのか、「索引に載せる」の意味なのか。33 章の説明はどちらで書かれているか。

**提案**（実装時に決める）:
- **案 A: 辞書の判断を優先する**。辞書にすでにある語は、手動登録の記法を見てもフラグを足さない（`g` の語は `g` のまま）。ビルドも、`g` だけの語は記法の箇所を索引語にせず、用語集の語として扱う。新しい書き方を覚えずに済み、レビューファイルで決めたことが原稿の記法に上書きされない。最初の登録だけは `i` になるので、用語集だけにするにはレビューで 1 度 `[g]` に変える。
- **案 B: 用語集だけを示す書き方を足す**（例: 読みの後ろに印を付ける `[px|px|g]`）。原稿だけで意図が完結するが、記法が増え、`IndexMarkup` の綴りの解釈・lint・33 章の説明に手が入る。
- 案 A で足りるかを先に確かめ、足りなければ案 B を検討する。

**調査（2026-10-01）**: 問いの 1 つめは「載る」。辞書で `g` だけの語でも、原稿に `[px|px]` と書いた箇所は、ビルドで索引に入る（`IndexMatchScanner#process_term` は辞書のフラグを見ない）。#101 と合わせて `index-glossary-registration-spec.md` で扱う。

## 101. 「主要参照を付けない」という判断が辞書に残らない

- **対象**: `UnifiedIndexManager#suggest_main_references`・`apply_main_references!`、辞書の `main`、レビューファイルの `m?`
- **種別**: 検討・実装
- **状態**: 対応済み（2026-10-02）

**現状**: 主要参照が未指定の登録語には、`vs index:auto` が毎回、機械の推測を `[im?12]` の形で書き込む。書き換えずに `vs index:apply` すると、推測がそのまま採用される（「そのままだと採用されます」は凡例に書いてある仕様）。ところが、著者が「この語には主要参照を付けない」と決めても、辞書には `main` が無いという状態しか残らず、「まだ決めていない」と区別できない。そのため、次の `vs index:auto` でまた推測が付き、apply のたびに採用されてしまう。

2026-10-01 に確かめた例: #99 の見直しで、Git（12 章に 1 回出るだけで、説明箇所ではない）とトラブルシューティング（10 章の節見出しに出る）は、あえて主要参照を外した。確認のためにレビューファイルを書き換えずに apply すると、Git は 12 章、トラブルシューティングは 51 章が主要参照になった（確認の実行だったので元に戻した）。ふだんの作業では、著者が気づかないうちに推測が入る。

**問い**:
- 「付けない」をどう記録するか（辞書に `main: none` のような値を持つ／推測を採用するのは著者が `?` を消したときだけにする、など）。
- 推測をそのまま採用する今の既定は、手間を減らすためのものだった（`index-main-reference-section-spec.md` R2）。既定を「採用しない」に変えると、その手間が戻る。

**#100 と合わせて、登録の仕組み全体を整理する**: 索引・用語集の語の扱いには、手動登録・自動抽出・用語集・索引・登録済み・見直し候補・登録語・推奨候補・一般候補・一般語・見出しから拾った語・除外語・主要参照あり／推測／なし、と多くの場合分けがあり、著者がいまどうなっているのかを把握できない（ユーザーの指摘）。#100（用語集だけに載せる語を原稿に書けない）と #101 は、個別に直すと場合分けがさらに増えるので、仕様書に起こして、より簡便・簡潔な形に整理してから実装する（`index-glossary-registration-spec.md`。2026-10-01 に方針を決めた）。

**対応（2026-10-02・#100 と #101）**: `index-glossary-registration-spec.md` で登録の仕組み全体を整理し、§4.3 の順で実装した。優先の順位を「辞書（著者の判断）＞原稿の記法＞機械の推測」の 1 本にした。#101 は、主要参照の欄が空の索引語に `main: []`（付けない）を記録し、推測はまだ決めていない語にだけ付ける。#100 は、原稿の `[語]` を「辞書にない語を登録する入口」とし、辞書で `g` だけの語はビルドでも用語集の語として扱う（索引に載せない）。あわせて、棄却した語の `[語]` は登録せずに知らせる、棄却するとき原稿の印も外すか確かめる、レビューファイルを 4 つの節に整理して見直し候補をなくす、`vs index:plan` の画面を見直す、を入れた。33 章・41 章・`book.yml` のコメントも合わせた。

## 103. 辞書の見出し語の綴りを、レビューファイルで直せない

**追補（2026-10-03）**: 原稿に古い綴りが残っていれば、原稿も直すかを確かめるようにした（`ManuscriptMarkup.spelling_places`・`respell!`、`UnifiedIndexManager#confirm_manuscript_respelling`）。当初は原稿を書き換えず `vs lint` に任せるつもりだったが、lint は空白の違いしか見ないので、「ラベル ID」を「ラベル id」や「label id」へ直すと、原稿の古い綴りは索引に載らないまま、どこからも知らされなかった。「はい」なら空白の揺れも含めて古い綴りを直し、「いいえ」なら索引に載らないことを知らせる。英数字の語の途中（「Type 3」に対する「Type 30」）と、すでに新しい綴りで書いた範囲（「Type 3」を「Type 3 フォント」へ直すときの「Type 3 フォント」）は直さない。空白の揺れの照合は lint と共有する（`TermPattern.spacing_insensitive`）。

## 104. 索引ライブラリの export/import が、使っていない語の考え方と噛み合っていない

- **対象**: `IndexCommands::IndexLibrary`（`vs index:export` / `vs index:import`）、レビューファイルの 5 節、33 章「索引ライブラリを別の本へ持ち運ぶ」・91 章
- **種別**: 検討・実装
- **状態**: 対応済み（2026-10-03）

**きっかけ（2026-10-03）**: `vs index:plan`・`auto`・`apply` の見直し（#99〜#103）を終えたので、同じ `vs index` の仲間の export/import も見直した。コマンド自体は壊れていないが、`index-glossary-registration-spec.md` で入れた「使っていない語」（説明文だけを残した語）と噛み合っていない。

**現状**:
- 取り込んだ用語集の語は、すべて `g` で辞書に入る。用語集のページは辞書の `g` の語を出現の有無に関係なく載せるので、新しい本の原稿に出てこない語まで用語集に並ぶ。5 節でそのまま apply すれば外れるが、取り込むたびに同じ手間がかかる。
- 書き出すのは `g` の語だけで、使っていない語の説明文は運ばれない。本から本へ引き継ぐと、途中の本で使わなかった語の説明文が消える。
- 取り込んだ語のうち原稿に出てこない使っていない語と棄却した語は 5 節に並ぶ。ライブラリを重ねるほど、本に固有の片付けるべき語が埋もれる。
- 新しい本で棄却した語でも、取り込みが用語集の語として足す（既存優先の原則に反する）。`--prefer-import` は印を足し合わせ、索引だけの語が用語集にも載る。
- ログは「reject」、33 章は「外した語」と書き、ほかの節の「棄却した語」とそろっていない。

**決定（2026-10-03）**: `--prefer-import` は廃止する（ユーザーの判断。オプションで規則が分かれると著者に分かりにくい）。取り込みはいつも追記だけにする（仕様書 §3.5）。

## 105. 辞書に無い語でも、英字と和文の境目の空白の揺れを `vs lint` で見つける

- **対象**: `Lint::ProseChecker`（新しいルール）、31 章
- **種別**: 検討・実装
- **状態**: 対応済み（2026-10-04）

**きっかけ（2026-10-04）**: 索引のレビューで、3 節に「CMYK 版」と「CMYK版」、「RGB 版」と「RGB版」が両方並んでいた。本書は「CSS 組版」「Type 3 フォント」と同じく、英字と和文の境目に半角空白を入れる方針で、43 章の 3 行を直した。辞書に載せた語なら `index-term-spacing`（#102）が指摘するが、載せていない語の揺れは見つからない。

**現状（2026-10-04 に数えた。97 章・コード・URL を除く）**: 英字の語と、隣り合う漢字・カタカナの並びの組を数えると、空白ありだけの組が 259、空白なしだけの組が 28、両方が混在している組が 8 だった。
- 混在している 8 組: CSS 組版（あり 10・なし 4。なしはすべて 96 章の書名の紹介文で `no-lint` の中）・裸 URL・EPUB 用・PDF 内・Web ページ・HTML タグ・付録 A・JPEG 画像（なしはどれも 1 か所）。
- 空白なしだけの組には、辞書の語「自動ID」と、同じ形の「手動ID」「予約ID」「システム予約ID」（25 章）、JIS 第一水準（32 章）、図の中の「処理A」「処理B」（23 章）、96 章の書名などがある。詰めて書くのが意図どおりの語も多い。
- textlint の同種のルール（`ja-space-between-half-and-full-width`）は入っていない。

**案**:
- **A（推奨）: 本の中で混在している組だけを指摘する**。同じ組が空白ありでも書かれているとき、空白なしの箇所を「`EPUB用` => `EPUB 用`」と知らせ、`--fix` で空白を入れる。直す向きは方針どおり空白ありに固定する（件数の多いほうへ寄せない。#103 で多数決を採らなかったのと同じ理由）。本書では 10 か所ほどで、誤検出がほぼ出ない。
- B: 英字と漢字・カタカナが空白なしで接する箇所をすべて指摘する。方針を本全体に徹底できるが、本書では 40 か所ほどが新たに出て、「自動ID」のように辞書や著者が意図して詰めた語まで指摘する。
- どちらの案でも、ひらがなとの境目（「Markdown で」「IDの」）は見ない。助詞の前の空白は書き手によって揺れが大きく、方針も決めていないため。

**検討（2026-10-04）**: A では、本の中で一貫して「Kindle用」と書いていると指摘されない。「ビルドすると、EPUB 用、Kindle用のファイルができます」のように並ぶと揃っていないのに、組ごとに見ているので気づけない（ユーザーの指摘）。B は「自動ID」まで指摘する。間を取る案として、和文の側の語ごとに揃っているかを見る案（C: 「EPUB 用」があれば「Kindle用」も指摘する）を数えたところ、本書で 17 か所だったが、「裸 URL」「CSS 組版」のように偶然そろった語まで拾い、場当たり的になる。

**決定（2026-10-04）**: D「英字の語に付く和文の語を一覧で持ち、その語だけを見る」で進める（ユーザーの判断）。
- 一覧は lint のデータファイルに置き、気づいた語を足していく。英字の語の後ろに付く語（用・版・内・外・側・製・系・型・式・法・案・方式・形式・方法・画像・変換・自体・タグ・ページ・ファイル・記法・表記・対応・互換・以外・以上・以下・未満・全体・単位・環境・向け・経由・番号）と、前に付く語（付録・図・表・リスト・例・案・方式）。「A 案」「A 方式」「Newton 法」はユーザーの挙げた例。
- 一覧の語の直後に漢字・カタカナが続くときは別の語の一部とみなす（「API用語」の「用」は拾わない）。前に付く語も、直前に漢字・カタカナがあれば拾わない。
- 英字で始まる語だけを見る。数字と助数詞の間（「50ページ」「図1-1」）は別の慣習なので対象外。ひらがなとの境目と、一覧に無い語（「自動ID」）は見ない。
- 直す向きは空白ありに固定し、`--fix` で直す。本書では 13 か所ほど（svg画像・png画像・JPEG画像・ID自体 2・付録A・付録B・EPUB用・CMYK変換・PDF内・HTMLタグ・JIS外・HEX表記）。

**対応（2026-10-04）**: ルール `affix-spacing` を足した（`ProseChecker#affix_spacing_findings`・`fix_affix_spacing`、一覧は `lint/data/affixes.yml`）。参照名（`@ch-build`）・リンク先・URL・脚注の名前・HTML タグ・コードは、位置を保ったまま伏せてから照らす（`@ch-build用` を `@ch-build 用` にすると参照が切れる）。本書の原稿で、変更前のコミットと全指摘を突き合わせ、増えたのはこのルールの 13 件だけだった。`--fix` を原稿の写しに当て、13 か所だけが直ることを確かめた。94 章の「付録A」「付録B」は、システムが付ける名前（`付録 A`・`HeadingProcessor`）と食い違っていた。
