# 画像形式をターゲットごとに最適化する

> 作成日: 2026-08-16
> ステータス: **実装待ち**
> 対象: `lib/vivlio_starter/cli/resize.rb`, `lib/vivlio_starter/cli/pre_process/image_path_normalizer.rb`, `lib/vivlio_starter/cli/build/image_optimizer.rb`
> 関連: `print-pdf-full-bleed-notes.md`（入稿用 PDF の画質要件）

## 0. なぜこの仕様書があるか

**「軽いから WebP へ統一する」という判断が、PDF では正反対に働いていた。**

`vs resize` は png / jpg / jpeg をすべて WebP へ変換し、原稿の `![](foo.png)` も前処理で `foo.webp` へ差し替えている。ファイル単体では確かに小さくなる。ところが**PDF に入った瞬間に 7 倍に膨らむ**。

```
images/24-cross-reference/Einstein.webp   286 KB   ← 素材
  ↓ PDF に埋め込まれると
1408x768 の画像オブジェクト              2.0 MB   ← 7 倍
```

本書の PDF 97.2 MB のうち **91.4 MB（94%）が画像**で、その大半がこの膨張によるものである。

## 1. 原因は PDF 仕様にある

**PDF は WebP を格納できない。** ISO 32000 が定める画像フィルタは次のものだけで、WebP は PDF 2.0 でも追加されていない。

| フィルタ | 中身 | 再圧縮 |
|---|---|---|
| `DCTDecode` | **JPEG** | **不要**（ストリームをそのまま格納） |
| `JPXDecode` | JPEG 2000 | 不要 |
| `FlateDecode` | zlib（**可逆**） | デコード＋再圧縮が必要 |
| `CCITTFaxDecode` / `JBIG2Decode` | 白黒二値 | — |

したがって WebP を渡された Chromium は、**デコードして生ビットマップに戻し、Flate で圧縮し直す**。写真的な絵は可逆圧縮ではほとんど縮まない（実測: 圧縮率 73〜81%）。

**JPEG なら再圧縮が起きない。** 実測で裏付けた（2026-08-16・24 章の単章ビルド）。

```
Einstein.webp（WebP のまま）  PDF 7,148,170 バイト
同じ絵を JPEG に差し替え      PDF 4,837,777 バイト   （−32.3%）
```

### 1.1 ターゲットごとに最適な形式が違う

| ターゲット | 最適 | 根拠（実測） |
|---|---|---|
| **PDF** | **JPEG** | WebP は Flate で 7 倍に膨張。JPEG はそのまま格納 |
| **EPUB** | **WebP** | ZIP へ素材のまま入る。同じ絵で WebP 286 KB / JPEG 331 KB（**WebP が 14% 小さい**） |
| **Kindle** | **JPEG / PNG** | KFX が WebP 非対応（`EpubBuilder` が既に変換している） |

**つまり「1 つの形式に統一する」こと自体が誤りだった。** EPUB では WebP が正しく、PDF では JPEG が正しい。現在の実装は EPUB に最適化した形式を PDF にも流用している。

透過を持つ絵は JPEG にできないため PNG を使う（後述 §3.2）。

## 2. もう一つの問題: 解像度が素通し

`resize` の対象は `patterns = %w[png jpg jpeg JPG JPEG PNG]` で、**すでに WebP のファイルはリサイズされない**。`max_px`（標準 1600）が効かず、素材の解像度がそのまま紙面に載る。

実測（本書 PDF・オブジェクト単位）:

| 中身 | 個数 | 容量 | 表示解像度 |
|---|---|---|---|
| 挿絵（1408×768） | 15 | **36.8 MB** | 447〜584 ppi |
| 素材見本の花（2048×2048） | 11 | **33.5 MB** | **668 ppi** |
| 表紙・裏表紙（2894×4091） | 2 | 6.3 MB | 350 ppi ✅ |
| 章扉（2880×4153） | 1 | 3.1 MB | 368 ppi ✅ |
| 節絵（2880×1205） | 1 | 0.66 MB | — ✅ |

**生成側（表紙・章扉・節絵）は 350 dpi 前後で正しく作られている。** 過剰なのは著者が置いた素材のほうで、挿絵は 1408px を紙面 63mm に置くため 567 ppi、花の見本は 2048px を 78mm に置くため 668 ppi になっている。印刷に必要なのは 350 ppi なので、画素数にして 2〜3.6 倍を運んでいる。

**なお XObject の共有は正しく働いている。** 章扉は 1 オブジェクトを 17 ページ、節絵は 258 ページが参照しており、ここに無駄はない（調査当初は共有されていないと誤認したが、実データで否定された）。共有が効いている章扉＋節絵は合わせて 3.8 MB（全体の 4%）にすぎず、**削るべきは素材側**である。

## 3. 方針

### 3.1 素材は「PDF に最適な形式」で保持し、EPUB 向けに WebP を派生させる

現在は逆（WebP を持ち、Kindle 向けにだけ JPEG を派生）になっている。PDF が主成果物であること、および PDF だけが形式変換のペナルティを受けることから、向きを反転させる。

```
  素材（JPEG / PNG）
    ├→ PDF   … そのまま（DCTDecode で無変換格納）
    ├→ EPUB  … WebP へ変換（14% 小さい）
    └→ Kindle … そのまま（既存の変換経路がそのまま使える）
```

### 3.2 形式の選択規則

| 素材の性質 | 形式 | 理由 |
|---|---|---|
| 写真・イラスト（透過なし） | **JPEG** | PDF へ無変換で入る。非可逆だが元から写真 |
| 透過が必要（章扉・節絵・アイコン） | **PNG** | JPEG は透過を持てない。Flate になるが、透過素材は元々 Flate 以外に選択肢がない |
| 図・スクリーンショット（色数が少ない） | **PNG** | 可逆で小さく、文字が滲まない |
| ベクタ | **SVG** | 現状どおり |

判定は自動で行う（`magick identify` の `%A`＝透過の有無と `%k`＝色数）。**著者に選ばせない**——形式の選択は本仕様が扱う機械的な最適化であり、著者の関心事ではない。

### 3.3 解像度は紙面基準で決める

`max_px` という画素数の上限ではなく、**「紙面に置いたとき 350 ppi になる画素数」**を上限とする。

- 紙面での表示幅は原稿の `{width=40%}` と版面幅から決まる
- 版面幅が分かるのはビルド時なので、`resize` 単体では決められない
- したがって上限は**判型から算出**する（A4 版面 = 約 170mm なら、全幅の絵で 170/25.4×350 ≒ 2340px）

**過剰な素材だけを縮める。** 足りない素材を拡大してはならない（画質が上がらないうえ容量だけ増える）。

## 4. 実装

### 4.1 変更するもの

| 対象 | 変更 |
|---|---|
| `ResizeCommands` | WebP 一択をやめ、§3.2 の規則で出力形式を選ぶ。上限を判型由来の画素数にする |
| `ImagePathNormalizer` | `.png` → `.webp` の固定差し替えをやめ、**ターゲットごとに解決先を変える** |
| `ImageOptimizer` | PDF 枝では素材をそのまま、EPUB 枝では WebP 派生を使うよう振り分ける |
| `EpubBuilder` | Kindle 変換は現行のまま（素材が JPEG になるので変換自体が減る） |

### 4.2 やらないこと

- **Ghostscript 圧縮を既定 on にしない。** `/ebook` は 150 dpi へ落として全画像を JPEG 化するため入稿に耐えない。`/prepress`（300 dpi 維持）でも 97.2 MB → 21.1 MB と有効だが、**再エンコードで見た目が変わる**リスクがあり、過去に見出しの変色という実害も出ている。本仕様は「そもそも膨らませない」ことで解決し、圧縮は選択肢のまま残す
- **既存の WebP 素材を一括変換しない。** 著者の `images/` を書き換えるのは破壊的である。§5 の移行導線で扱う

## 5. 移行

既存プロジェクトは `images/` に WebP を持っている。PDF ビルド時に WebP を見つけたら、**ビルドを止めずに** 🟡 で知らせる。

```
🟡 PDF に WebP 画像が 15 件あります（PDF は WebP を格納できないため約 7 倍に展開されます）
        → vs resize --to-jpeg で JPEG へ変換すると PDF が小さくなります
        → 例: images/24-cross-reference/Einstein.webp（286 KB → PDF 内で 2.0 MB）
```

変換は著者が明示的に実行する（`vs resize --to-jpeg`）。元ファイルは残す。

## 6. 検証

1. **単章ビルドでのサイズ比較** — 24 章（挿絵 3 枚）で WebP 版と JPEG 版を組み、PDF サイズを比較する。基準値は 7,148,170 → 4,837,777 バイト（実測済み）
2. **符号化方式の確認** — `pdfimages -list` の `enc` 列が `jpeg` になること。現状は大きい画像がすべて `image`（Flate）
3. **表示解像度の確認** — 中央値が 350 ppi 近辺に収まること。現状は 564 ppi
4. **EPUB のサイズが増えないこと** — WebP 派生が効いていれば現状（29 MB）と同等のはず
5. **Kindle の実機確認** — 素材が JPEG になっても KFX の表示が変わらないこと

## 7. 見込み

本書の PDF 97.2 MB に対して:

| 施策 | 削減見込み | 根拠 |
|---|---|---|
| 挿絵 15 枚を JPEG へ | 36.8 MB → 約 5 MB | 1 枚 2.0 MB → 0.33 MB（実測） |
| 素材見本 11 枚を 350 ppi へ | 33.5 MB → 約 10 MB | 画素数が 668→350 ppi で 27% |
| 合計 | **97 MB → 40 MB 前後** | 圧縮をかけずに |

さらに `/prepress` 圧縮を併用すれば一桁台に入るが、§4.2 のとおり既定にはしない。
