# 画像形式をターゲットごとに最適化する

> 作成日: 2026-08-16
> ステータス: **実装待ち**
> 対象: `lib/vivlio_starter/cli/resize.rb`, `lib/vivlio_starter/cli/pre_process/image_path_normalizer.rb`, `lib/vivlio_starter/cli/build/image_optimizer.rb`
> 関連: `print-pdf-full-bleed-notes.md`（入稿用 PDF の画質要件）

## 0. なぜこの仕様書があるか

**「軽いから WebP へ統一する」という判断が、PDF では正反対に働いていた。**

`vs resize` は png / jpg / jpeg をすべて WebP へ変換し、原稿の `![](foo.png)` も前処理で `foo.webp` へ差し替えている。ファイル単体では確かに小さくなる。ところが**PDF に入った瞬間に 7 倍に膨らむ**。

```
images/24-cross-reference/Einstein.webp   286 KB   ← 素材
  ↓ PDF に埋め込まれると
1408x768 の画像オブジェクト              2.0 MB   ← 7 倍
```

本書の PDF 97.2 MB のうち **91.4 MB（94%）が画像**で、その大半がこの膨張によるものである。

## 1. 原因は PDF 仕様にある

**PDF は WebP を格納できない。** ISO 32000 が定める画像フィルタは次のものだけで、WebP は PDF 2.0 でも追加されていない。

| フィルタ | 中身 | 再圧縮 |
|---|---|---|
| `DCTDecode` | **JPEG** | **不要**（ストリームをそのまま格納） |
| `JPXDecode` | JPEG 2000 | 不要 |
| `FlateDecode` | zlib（**可逆**） | デコード＋再圧縮が必要 |
| `CCITTFaxDecode` / `JBIG2Decode` | 白黒二値 | — |

したがって WebP を渡された Chromium は、**デコードして生ビットマップに戻し、Flate で圧縮し直す**。写真的な絵は可逆圧縮ではほとんど縮まない（実測: 圧縮率 73〜81%）。

**JPEG なら再圧縮が起きない。** 実測で裏付けた（2026-08-16・24 章の単章ビルド）。

```
Einstein.webp（WebP のまま）  PDF 7,148,170 バイト
同じ絵を JPEG に差し替え      PDF 4,837,777 バイト   （−32.3%）
```

### 1.2 PDF 内のサイズは、素材のファイルサイズでは決まらない

1 枚を追うと分かる（`Einstein.webp` 1408×768・2026-08-17 実測）。

| 形式 | サイズ | 何が起きているか |
|---|---|---|
| WebP（素材） | **280 KB** | 非可逆。目に見えない情報を捨てて縮んでいる |
| ↓ デコード | 3,168 KB | PDF は WebP を格納できないので生ビットマップへ戻す |
| ↓ Flate で再圧縮 | **1,963 KB** | **可逆**。1 ビットも捨てないので写真はほとんど縮まない |
| （JPEG なら） | 441 KB | `DCTDecode` でそのまま格納。デコードすら起きない |

`pdfimages` が報告する PDF 内の実測値 2.0 MB と、この 1,963 KB がほぼ一致する。**膨らんでいるのではなく、非可逆で縮んでいたものが可逆へ戻されている。**

ここから重要な性質が出る——**PDF 内のサイズは画素数だけで決まる**。挿絵 15 枚は素材が 122〜299 KB とばらつくが、どれも 1408×768 なので生ビットマップは 3.09 MB で同じになり、PDF 内も約 2.45 MB へ揃う。素材が小さい絵ほど倍率が大きく見えるのは分母が違うだけで、分子は同じである（合計 **2.69 MB → 36.8 MB ＝ 13.7 倍**）。

したがって効く手は 2 つある。**JPEG 化**（素材のサイズがそのまま PDF のサイズになる）と**縮小**（画素数が減れば比例して減る）。透過素材は JPEG にできないので後者で対応する。

### 1.1 ターゲットごとに最適な形式が違う

| ターゲット | 最適 | 根拠（実測） |
|---|---|---|
| **PDF** | **JPEG** | WebP は Flate で 7 倍に膨張。JPEG はそのまま格納 |
| **EPUB** | **WebP** | ZIP へ素材のまま入る。同じ絵で WebP 286 KB / JPEG 331 KB（**WebP が 14% 小さい**） |
| **Kindle** | **JPEG / PNG** | KFX が WebP 非対応（`EpubBuilder` が既に変換している） |

**つまり「1 つの形式に統一する」こと自体が誤りだった。** EPUB では WebP が正しく、PDF では JPEG が正しい。現在の実装は EPUB に最適化した形式を PDF にも流用している。

透過を持つ絵は JPEG にできないため PNG を使う（後述 §3.2）。

## 2. もう一つの問題: 解像度が素通し

`resize` の対象は `patterns = %w[png jpg jpeg JPG JPEG PNG]` で、**すでに WebP のファイルはリサイズされない**。`max_px`（標準 1600）が効かず、素材の解像度がそのまま紙面に載る。

実測（本書 PDF・オブジェクト単位）:

| 中身 | 個数 | 容量 | 表示解像度 |
|---|---|---|---|
| 挿絵（1408×768） | 15 | **36.8 MB** | 447〜584 ppi |
| 素材見本の花（2048×2048） | 11 | **33.5 MB** | **668 ppi** |
| 表紙・裏表紙（2894×4091） | 2 | 6.3 MB | 350 ppi ✅ |
| 章扉（2880×4153） | 1 | 3.1 MB | 368 ppi ✅ |
| 節絵（2880×1205） | 1 | 0.66 MB | — ✅ |

**生成側（表紙・章扉・節絵）は 350 dpi 前後で正しく作られている。** 過剰なのは著者が置いた素材のほうで、挿絵は 1408px を紙面 63mm に置くため 567 ppi、花の見本は 2048px を 78mm に置くため 668 ppi になっている。印刷に必要なのは 350 ppi なので、画素数にして 2〜3.6 倍を運んでいる。

**なお XObject の共有は正しく働いている。** 章扉は 1 オブジェクトを 17 ページ、節絵は 258 ページが参照しており、ここに無駄はない（調査当初は共有されていないと誤認したが、実データで否定された）。共有が効いている章扉＋節絵は合わせて 3.8 MB（全体の 4%）にすぎず、**削るべきは素材側**である。

## 3. 方針

### 3.1 素材には触らず、ターゲットごとの派生を作る

**著者が置いたファイルが素材で、ビルドはそれを一切書き換えない。** 組版に渡すものだけを、ターゲットごとに派生させる。

```
  素材（著者が置いたまま・不変）
    ├→ PDF   … JPEG 派生（透過があれば PNG）＋ 必要なら縮小
    ├→ EPUB  … そのまま（WebP が最適。素材が WebP なら変換ゼロ）
    └→ Kindle … JPEG / PNG へ変換（現行の経路）＋ 1600px 上限
```

当初は逆向き——素材を PDF 最適形式（JPEG）で保持し、EPUB 向けに WebP を派生させる——を想定していたが、実装に入る段でこちらへ改めた（2026-08-17）。理由は 3 つある。

- **原本がもう残っていない。** 本書の `images/` は 78 件中 77 件が WebP のみで、素材を JPEG へ変換しても webp → jpeg の二段非可逆は避けられない。「素材を最適形式で持つ」ことの利点が、既存プロジェクトでは成立しない
- **素材を書き換えない原則と衝突する。** §3.5 と §4.2 で「素材の書き換えは破壊的である」と決めたのに、§3.1 だけがそれを求めていた
- **仕組みが増えない。** §3.6 の派生機構はどちらの道でも要る。そこへ形式変換を相乗りさせるだけで済み、移行導線（§5）も不要になる

EPUB が素材をそのまま使える点も大きい。§1.1 のとおり EPUB では WebP が最適なので、**既存プロジェクトでは変換が 1 件も起きない**。

#### 著者から見た使い方は変わらない

| | 現状 | 新設計 |
|---|---|---|
| 著者が置くもの | png / jpg（webp も可） | **同じ** |
| 原稿の書き方 | 置いたファイル名のまま | **同じ** |
| `vs resize` を著者が打つか | 打たなくてよい（`vs build` の Step 1 が呼ぶ） | **同じ** |
| ビルドが作るもの | `images/` に `.webp` を並置 | `.cache/vs/derived/` にターゲット別の派生 |
| `images/` が汚れるか | webp が増える | **増えない** |

変わるのは 3 点だけである。(1) 原稿に `.webp` と書く必要が消える、(2) `images/` に webp が増えなくなる、(3) 形式を著者が選ばなくてよい。

**素材は「原稿に書かれた拡張子のファイル」とする。** 無ければ拡張子違い（`.png` / `.jpg` / `.jpeg` / `.webp`）を探す——著者が `![](myawesome.jpg)` と書いて `myawesome.png` を置いていても拾えるようにする（現行の `image_exists_for?` が既に持っている挙動を、存在確認だけでなく解決にも使う）。既存プロジェクトの原稿は `.webp` と書いているので、そのまま WebP が素材になる。

### 3.2 形式の選択規則

| 素材の性質 | 形式 | 理由 |
|---|---|---|
| 写真・イラスト（透過なし） | **JPEG** | PDF へ無変換で入る。非可逆だが元から写真 |
| 透過が必要（章扉・節絵・アイコン） | **PNG** | JPEG は透過を持てない。Flate になるが、透過素材は元々 Flate 以外に選択肢がない |
| 図・スクリーンショット（色数が少ない） | **PNG** | 可逆で小さく、文字が滲まない |
| ベクタ | **SVG** | 現状どおり |

判定は自動で行う（`magick identify` の `%A`＝透過の有無と `%k`＝色数）。**著者に選ばせない**——形式の選択は本仕様が扱う機械的な最適化であり、著者の関心事ではない。

**`stylesheets/images/`（テーマ素材）は透過を保つ。JPEG へ変換してはならない。** 同梱の素材ライブラリとして著者が別用途に使うことがあり、EPUB / Kindle のダークテーマでは白く塗った矩形が浮く。得られるものも小さい——全素材を白でフラット化した実測で PDF は 97.2 → 93.1 MB（**4.2% 減**）にとどまり、扉絵・節絵は共有が効いていて合わせて 3.8 MB（全体の 4%）しかない。主戦場は本文側の 70 MB である。

### 3.3 解像度の上限はターゲットごとに違う

画素数の上限 `max_px` を 1 つ持つのをやめ、ターゲットごとに決める。根拠が三者三様だからである。

| ターゲット | 上限 | 根拠 |
|---|---|---|
| **PDF** | 判型から算出（A4 版面 170mm なら 170/25.4×350 ≒ **2340px**） | 印刷に必要な 350 ppi |
| **EPUB** | **2048px** | iPad Pro 12.9" の画面幅。ここを超える表示先が事実上ない |
| **Kindle** | **1600px** | 端末の画面幅は 1236px（Paperwhite 第 11 世代・1236×1648・300 ppi）。**KDP は配信料がファイルサイズに比例する**ので、表示されない画素にコストを払うことになる。Kindle アプリを iPad で読む場合を見て 1600px の余裕を持たせる |

Kindle だけ低いのは解像度が低いからではない——**現行機は 300 ppi あり、150 dpi では足りない**。効くのは画面の絶対的な幅と配信料である。

実装は `EpubBuilder` の Kindle 変換経路（WebP → JPEG/PNG）に縮小を足すだけでよく、新しいコマンドも設定キーも増えない。

**過剰な素材だけを縮める。** 足りない素材を拡大してはならない（画質が上がらないうえ容量だけ増える）。

### 3.4 上限では救えない無駄がある——実効解像度を測って知らせる

上限は「素材が大きすぎる」場合しか救えない。**同じ素材が用途によって違う大きさで置かれる**ケースは通り抜ける。

実例（2026-08-16 実測）。扉絵の素材は 2048×2048 で、章扉として全面に敷く分にはこの解像度が要る。ところが第 12 章「扉絵と装飾画像」は**同じ素材をカタログとして 2 列の表に並べている**。

```markdown
| ![suzuran](suzuran.webp) | ![ajisai](ajisai.webp) |
| 鈴蘭 `suzuran`           | 紫陽花 `ajisai`        |
```

`width` 指定がないため表の列幅、すなわち版面の約半分に収まる。実測すると **77.9mm 幅・668 ppi** で、350 ppi なら 1075px で足りるところに 2048px を運んでいる。画素数にして約 4 倍、この 11 個だけで **33.5 MB**（PDF 全体の 34%）を占める。

**この無駄は上限では検出できない。** 2048px は EPUB の上限（2048px）内に収まっており、素材としては何も間違っていないからである。悪いのは素材でも上限でもなく、**その置き場所**である。

したがって上限とは別に、**ビルド後の実効解像度を測って報告する**。

```
🟡 紙面に対して解像度が過剰な画像が 11 件あります（印刷に必要なのは 350 ppi）
        ajisai.webp     668 ppi（77.9mm 幅に 2048px）→ 1075px で十分
        …
        → 用途に合わせた縮小版を用意すると PDF が小さくなります
```

測り方は `pdfimages -list` の `x-ppi` 列で足りる（今回の調査もこれで行った）。

**用途はディレクトリで判別できる。** 置き場所が役割そのものだからである。

| 置き場所 | 役割 | 実効解像度の検査 |
|---|---|---|
| `stylesheets/images/` | テーマ素材。`ThemeImageResolver` が `theme-images/bundled/sakura_portrait.webp` などへ**合成して**使う | **対象外**。ページ全面に敷くのが前提で、350〜368 ppi と実測でも適正 |
| `images/<章>/` | 本文画像。`ImagePathNormalizer` がここへ正規化する | **対象**。置かれ方が原稿次第なので過剰になりうる |

同じ `sakura.webp` が両方に存在するのは重複ではなく、**役割が違う**。`stylesheets/images/bundled/` のものは章扉として全面に敷かれ、`images/42-frontispiece/` のものは第 12 章のカタログに並ぶ。前者に 2048px は必要で、後者には過剰——ファイルが同じでも判断が分かれるのは、置き場所が違うからである。

### 3.5 それでも自動では縮小しない

用途が判別できても、素材を機械が書き換えることはしない。理由は 2 つある。

- **素材の書き換えは破壊的である。** 著者が用意した原本を、ビルドが黙って上書きしてよい道理がない（§4.2 の「既存の WebP 素材を一括変換しない」と同じ理由）
- **同一の素材が、同じディレクトリ内で複数の大きさで置かれうる。** 表の中で小さく出し、別の節では全幅で出す、という原稿は正当である。縮めるなら**その素材の最大表示サイズ**を基準にしなければならず、1 箇所の ppi だけを見て決めてはならない

したがって**素材には**手を触れない。しかし報告だけで済ませると、著者に「用途ごとの縮小版を手で用意する」という重い仕事が残る。そこで §3.6 の派生を用意する。

### 3.6 派生を自動生成し、自動で差し替える

**著者は原稿を変えない。** `![](sakura.webp)` と書いたままで、ビルドが置き場所に応じた大きさの派生へ差し替える。

```
images/42-frontispiece/sakura.webp        ← 素材（著者のもの・不変）
  ↓ ビルドが必要なぶんだけ派生を作る
.cache/vs/derived/sakura_1280.jpg         ← 実際に組版へ渡すもの
```

原稿に `![](sakura_s.jpg)` のような名前を書かせてはならない。**どの大きさが要るかは、その画像がどこに置かれたかで決まる**（§3.4 のカタログの例）。著者が原稿を書く時点では版面も列幅も確定しておらず、判断材料がない。判断材料を持っているのは組版した後の機械のほうである。

#### 大きさは段階で持つ

必要な画素数ちょうど（`sakura_1075.jpg`）ではなく、段階（例 480 / 800 / 1280 / 2048）に丸める。同じ素材が似た大きさで何箇所にも置かれるとき、**段階なら 1 つの派生を使い回せる**。実寸だと 1075px と 1080px で別ファイルになり、キャッシュが無駄に増える。

#### 段階の選び方——必ず切り上げる

必要な画素数が段階のあいだに落ちたときは、**上の段階を選ぶ**。1075px 必要なら 800 ではなく **1280** を使う。

**下回らせてはならない。** 足りない解像度は後から取り戻せず、印刷では粗さとして残る。一方、切り上げによる容量の無駄は測れるし、許容できる範囲に収まる。

| 選び方 | 画素数（2048 比） | 得失 |
|---|---|---|
| 実寸 1075px | 27.5% | 最小。ただしキャッシュが効かない |
| **切り上げ 1280px** | **39%** | **11 ポイント損するが、使い回しが効く** |
| 切り下げ 800px | 15% | **350 ppi を下回る。採らない** |

本書のカタログ（1075px 必要・現状 2048px）で言えば、切り上げても **61% 減**である。実寸との差 11 ポイントは、キャッシュの単純さと引き換えにする価値がある。

境界の扱いも決めておく。

- **素材が必要画素数より小さいとき** — そのまま使う。**拡大してはならない**（画質は上がらず容量だけ増える。§3.3 と同じ原則）
- **必要画素数が最大段階を超えるとき** — 素材のまま使う。切り上げ先が無いので縮小しない
- **ちょうど段階に等しいとき** — その段階を使う（切り上げない）

#### 差し替える時機は、既存の 2 パスに相乗りする

`vs build` は既に PDF を 2 回組んでいる（索引のページ番号を確定するため。実測 111.55s + 111.72s）。この構造がそのまま使える。

1. **1 回目の組版** — 素材のまま組む
2. **Step 8（backlink dedup）** — ページ位置を測るついでに**実効解像度も測り**、過剰な画像の派生を作って HTML の参照を差し替える
3. **2 回目の組版** — 派生で組み直す

Step 8 は既に「1 回目の PDF から測って HTML を書き換え、組み直す」処理であり、**新しいパスを増やさずに済む**。派生の生成コストも安い（本文画像 79 枚・1 枚 0.37 秒・10 並列で約 6 秒。2026-08-16 の並列化が効く）。

#### 懸念は実測で否定された（2026-08-17）

差し替えでページ番号がずれれば、1 回目に測った索引の位置が無効になり、**この仕様が索引の仕組みごと壊す**。そこで実装より先に確かめた。第 12 章（`42-frontispiece.md`）の単章ビルドで、カタログの 12 枚を 2048px → 1280px に差し替えて突き合わせた結果:

| | 差し替え前 | 差し替え後 |
|---|---|---|
| 総ページ数 | 16 | **16** |
| テキストの座標 | — | **全 16 ページ 1249 語が 1pt も動かず一致** |
| 表示幅 | 77.97mm | **77.97mm** |
| ファイルサイズ | 43.58 MB | **21.11 MB**（−51.6%） |

**動かない理由も分かっている。** `base.css` と `chapter-common.css` の双方に `img { max-inline-size: 100% }` があり、intrinsic 幅（2048px ＝ 1536pt）は版面幅を大きく超えるため、表示幅は常にコンテナ側で決まる。しかも §3.6 は必要画素数へ**切り上げる**ので、intrinsic 幅は必ず表示幅の 3.6 倍以上（350ppi ÷ CSS の 96dpi）になる——この関係が崩れることはない。

#### ただし素材の寸法不揃いは列幅配分を動かす

検証の途中で見つかった。同梱素材 12 枚のうち `tsubaki.webp` だけが **2052×2048**（他は 2048×2048）で、**テーブルの列幅は列単位に全行共通で決まる**ため、この 4px が p4〜p7 の全行を 0.38pt（0.13mm）ずらしていた。素材を 2048×2048 に正すと表示解像度が 666/668ppi の混在から 668ppi に揃い、差し替え前後の座標も完全一致した。

画素数の変更が持つ性質ではないが、**著者の素材はどんな寸法でも来る**。差し替え時に元の画素数を `width` / `height` 属性として書き出し、intrinsic dimensions を凍結する。HTML 標準の挙動で、CSS の `max-inline-size` とも競合しない。

## 4. 実装

### 4.1 変更するもの

| 対象 | 変更 |
|---|---|
| **（新設）派生生成** | 素材 → ターゲット別の派生を `.cache/vs/derived/` に作る。形式は §3.2 の規則、画素数は §3.6 の段階で決める。差し替え時に元の画素数を `width` / `height` 属性へ書き出す |
| `ImagePathNormalizer` | `.png` → `.webp` の固定差し替え（`image_path_normalizer.rb:117`）を撤去し、**原稿に書かれた拡張子のファイルを素材として解決する**。無ければ拡張子違いを探す（§3.1） |
| `ImageOptimizer` | Step 1 の「`images/` へ `.webp` を並置する」処理を派生生成へ置き換える。SVG → lossless WebP（Type 3 対策）は役割が違うので残す |
| `EpubBuilder` | Kindle 変換は現行のまま ＋ 1600px 上限（§3.3） |
| `ResizeCommands` | `vs build` からは呼ばれなくなり、**素材そのものを縮めたい著者の明示コマンド**として残る（§3.5） |
| `ThemeImageResolver` | `resolve_image_path` は webp が無いと `vs resize:high` を呼ぶ。**`高精細` プリセットの `max_px` は 2000 なので、2048px のテーマ素材が黙って 2000px に縮む**。テーマ素材は縮小対象から外す（§3.2 の「透過を保つ」と同じ理由——素材ライブラリを劣化させない） |

### 4.2 やらないこと

- **Ghostscript 圧縮を既定 on にしない。** `/ebook` は 150 dpi へ落として全画像を JPEG 化するため入稿に耐えない。`/prepress`（300 dpi 維持）でも 97.2 MB → 21.1 MB と有効だが、**再エンコードで見た目が変わる**リスクがあり、過去に見出しの変色という実害も出ている。本仕様は「そもそも膨らませない」ことで解決し、圧縮は選択肢のまま残す
- **既存の WebP 素材を一括変換しない。** 著者の `images/` を書き換えるのは破壊的である。§5 の移行導線で扱う

## 5. 移行——要らなくなった

§3.1 を派生一本に改めたことで、**既存プロジェクトは何もしなくてよい**。`images/` が WebP のままでも、PDF には JPEG 派生が渡る。当初あった `vs resize --to-jpeg` の導線と、WebP を見つけて 🟡 で知らせる警告は、どちらも作らない。

原本（`.png` / `.jpg`）が同名で残っていればそちらを素材とみなすほうが二段非可逆を避けられるが、本書では 78 件中 77 件が WebP のみで原本が失われており、**この最適化が効く場面は実際には少ない**。§3.1 の「原稿に書かれた拡張子」規則で自然に決まるので、特別扱いはしない。

## 6. 検証

1. **単章ビルドでのサイズ比較** — 24 章（挿絵 3 枚）で WebP 版と JPEG 版を組み、PDF サイズを比較する。基準値は 7,148,170 → 4,837,777 バイト（実測済み）

8. ~~**派生への差し替えでレイアウトが動かないこと（§3.6・最優先）**~~ — **2026-08-17 検証済み**。42 章の単章ビルドで 2048px → 1280px に差し替え、総ページ数 16 で一致・全 16 ページ 1249 語が同一座標・サイズ −51.6%。詳細は §3.6。実装後は**全章ビルドで総ページ数と索引のページ番号を再確認**する（単章では摂動が小さいため）
