# 新規プロジェクトの作成（vs new）

:::{.chapter-lead}
前章では、`vs new` で作った雛形から最初の PDF を出力しました。本章では、そのときに生成されたディレクトリや設定ファイルを、もう少し詳しく見ていきます。`--yes` などのオプションやプロジェクト名の規則もまとめているので、新しい本を作るときだけでなく、構成を確かめたくなったときにも参照できます。すぐに原稿を書き始めたい場合は、必要な箇所だけ拾い読みして次章へ進んでください。
:::

## 基本的な使い方

:::{.section-lead}
`vs new` にプロジェクト名を渡すと、書籍情報を順に尋ねる対話形式の入力が始まります。ここで答えた内容は設定ファイルへ保存され、表紙や奥付にも使われます。
:::

```bash
vs new mybook
```

実行すると、次の質問が順に表示されます。答えが決まっていない項目は、何も入力せずに Enter を押せば既定値を使えます。書籍名や著者名は後から変更できるので、この段階ですべてを確定する必要はありません。

```
Vivlio Starter へようこそ！新しい書籍プロジェクトを作成します。

書籍名を入力してください（例: はじめての技術書づくり）: はじめての技術書づくり
副題を入力してください（任意。Enter でスキップ）:
著者名を入力してください（原稿を書いた人。例: 早乙女 遙香）: 早乙女 遙香
発行者・サークル名を入力してください（本を世に出す主体。お一人なら著者と同じでも可。例: アトリヱ未來）: アトリヱ未來

以下の設定でプロジェクトを作成します。

  プロジェクト名: mybook
  書籍名:         はじめての技術書づくり
  副題:           （なし）
  著者:           早乙女 遙香
  発行者:         アトリヱ未來

よろしいですか？ [Y/n]:
```

最後に入力内容を確認し、Enter または `Y` を押すとプロジェクトが作成されます。修正したい項目があれば、`n` を入力していったん中断し、もう一度実行できます。

:::{.column}
**著者と発行者の違い**

- **著者** — 原稿を書いた人（執筆者）。奥付の著者欄と著作権表示（&copy; …）に使われます。
- **発行者** — その本を世に出す主体（刊行の責任者）。商業出版なら出版社、同人・自費出版ならサークル名や屋号にあたります。

お一人で発行する場合は、著者と発行者が同じでも構いません。「著者＝本名・ペンネーム、発行者＝サークル名」のように使い分けることもできます。なお、印刷を依頼した印刷所は発行者とは別物です。
:::

## 生成されるプロジェクトの構成

`vs new mybook` を実行すると、原稿・画像・設定を分けて管理するために、次のディレクトリ構造が生成されます。ファイルの種類ごとに置き場所が決まっているため、原稿が増えても必要なものを探しやすくなります。

```
mybook/
  contents/       ← 原稿（Markdown ファイル）
  images/         ← 画像ファイル
  covers/         ← 表紙・裏表紙用の画像ファイル
  data/           ← 本文へ展開するデータ（YAML 形式）
  templates/      ← 章の雛形とデータ展開テンプレート
  sources/        ← 執筆資料や PDF ファイル置き場
  codes/          ← 本文へ取り込むサンプルコード
  stylesheets/    ← CSS スタイルシート
  config/         ← 各種設定ファイル
    book.yml      ← 書籍の設定
    catalog.yml   ← 章構成
    scaffold.lock ← 雛形マニフェスト（自動生成）
  README.md
  Gemfile
  package.json
  .gitignore
```

入力した書籍名や著者名は、`config/book.yml` に書き込まれます。どの項目も、後から `book.yml` を編集して変更できます。

`config/scaffold.lock` は、プロジェクトへ展開した雛形の内容を記録する自動生成ファイルです。`vs upgrade` はこの記録と現在のファイルを比べ、著者が編集したファイルと、雛形のままのファイルを判別します。内容は手で編集せず、ほかの設定ファイルと一緒に Git へコミットしてください。

## 各ディレクトリの役割

:::{.section-lead}
ここでは、各ディレクトリが何を受け持つのかを順に説明します。日々の執筆でよく使うのは `contents/` と `images/` で、ほかは必要な機能に応じて触れる場所です。今の段階で細部まで把握するより、「原稿はここ、画像はここ、設定はここ」と置き場所を掴んでおけば十分です。各ディレクトリの `_README.md` と本書後半の各章にも、必要なときに確認できる説明があります。
:::

### contents/

書籍の本文となる Markdown ファイルを置くディレクトリです。ファイル名には `NN-slug.md` 形式（例: `01-quickstart.md`）を使い、先頭の数字で章の並び順を表します。番号と内容を表す短い名前が並ぶので、ファイル一覧から章の位置を把握できます。

| 範囲 | 用途 |
|------|------|
| `00` | 前書き・はじめに |
| `01-89` | 通常の章 |
| `90-98` | 付録 |
| `99` | 後書き・おわりに |

```bash
vs create 11-intro     # 章ファイルと画像ディレクトリを生成
vs delete 11-intro     # 章を削除
vs rename 11 12        # 章番号を変更
vs renumber            # 章番号を一括で整列
```

ビルドの対象になるのは、`config/catalog.yml` に登録された章だけです。`catalog.yml` は本の**目次（章立て）を定義するファイル**で、どのファイルを、どの順番で、どの部に配置するかを記録します。登録していない Markdown はビルド・lint・metrics の対象になりません。そのため、構想中の下書きや一時的に外した原稿も、`contents/` に残しておけます。

ファイルは `PREFACE`（前書き）・`CHAPTERS`（本文）・`APPENDICES`（付録）・`POSTFACE`（後書き）の四つに分かれ、各章は拡張子 `.md` を省いたファイル名で登録します。`CHAPTERS` の下へ末尾に半角コロン `:` を付けたタイトルを置くと、その配下の章が一つの「部」にまとまり、部扉ページも生成されます。

```yaml
PREFACE:
  - 00-preface

CHAPTERS:
  - 第一部 はじめる:        # 末尾の「:」で「部」になる
      - 11-workflow
      - 12-quickstart
  - 第二部 書く:
      - 21-markdown-tutorial

APPENDICES:
  - 91-install

POSTFACE:
  - 99-postface
```

通常は、`catalog.yml` を手で編集する必要はありません。`vs create`・`vs delete`・`vs rename` で章を操作すると、対応する項目も更新されます。章の順番を細かく入れ替えるときや、部の名称を変更するときは、構造を確認しながら直接編集できます。

### images/

書籍内で使う画像ファイルを置くディレクトリです。画像は章ごとのサブディレクトリに分けて管理します。`vs create` で章を作成すると対応する画像ディレクトリも生成されるため、原稿と図版の関係を保ったまま整理できます。

画像の形式は PNG・JPG・WebP のどれでも構いません。`vs build` が PDF・EPUB・Kindle それぞれに適した形式へ変換して使います。変換した画像は作業用のフォルダ（`.cache/`）に作られるので、`images/` に置いた画像が書き換えられることはありません。

### covers/

書籍の表紙・裏表紙に使う画像ファイルを置くディレクトリです。設定に基づくカバー画像は、`vs cover` または `vs build` の実行時に生成されます。

`config/book.yml` の `output.cover` でテーマ名を指定します。`light` / `dark` は gem 同梱テンプレートを使用します。著者が用意した PNG/SVG を使う場合は `covers/frontcover_<theme>.png` を配置してください。

```bash
vs cover               # book.yml の設定に従ってカバー画像を生成
vs clean --cover       # 生成されたカバー画像を削除
```

### data/

原稿内へ展開する外部データを、YAML 形式で置くディレクトリです。同じ形の書誌情報や製品情報を何件も掲載するときに、QueryStream 記法と組み合わせて使います。本文へ同じ書式を繰り返し書かず、データと見せ方を分けて管理できます。

```markdown
= books                    # 全件展開
= books | tags=ruby        # タグで絞り込み
= books | -year | 3        # 年度降順・3件
```

データの展開テンプレートは `templates/` ディレクトリに配置します（`data/books.yml` → `templates/_book.md`）。

### templates/

章ファイルの雛形と、QueryStream のデータ展開テンプレートを置くディレクトリです。`vs create` で章を作ると、章番号の範囲に応じて `chapter.md`・`preface.md`・`appendix.md`・`postface.md` のいずれかが選ばれます。テンプレート内の `{{TITLE}}` は、章のスラッグへ置き換えられます。

`markdown_snippet.md` は章の雛形ではなく、利用できる記法を実例とともに並べた見本です。書き方を確かめたいときに開き、必要な部分を原稿へコピーして使えます。

章テンプレートを自分の執筆手順に合わせる方法は「ユーティリティ・コマンド集」で、QueryStream テンプレートの仕組みは「データ展開機能の使い方」で詳しく扱います。

### sources/

執筆の参考資料や素材を置くためのディレクトリです。ここに置いたファイルはビルドされないので、読者へ配布する原稿と手元の資料を分けて保管できます。`vs pdf:read` で PDF から Markdown を抽出するときには、入力ファイルの置き場所としても使えます。

```bash
vs pdf:read reference        # sources/reference.pdf を自動探索
```

### codes/

書籍に掲載するサンプルコードを置くディレクトリです。原稿へコードを貼り付ける代わりに、`include` 記法でファイルを参照できます。実行するコードと掲載するコードを一つのファイルに保てるため、修正の反映漏れを防げます。

`codes/sample.rb` を全文取り込むには次のように書きます。

````markdown
```include:sample.rb```
````

`codes/ruby/hello.rb` の 10〜20 行目だけを取り込むこともできます。

````markdown
```include:ruby/hello.rb:10-20```
````

書き方の詳細は「拡張記法リファレンス」の章の「コードインクルード」で解説します。

### stylesheets/

書籍のレイアウトとデザインを定義する CSS ファイルを置くディレクトリです。テーマカラーや扉絵などの基本設定は、`config/book.yml` の `theme` セクションで行います。`theme.css` はその設定からビルド時に生成されるため、独自の調整は `custom.css` に記述してください。役割を分けておくと、テーマを作り直してもカスタマイズが残ります。

### config/

書籍プロジェクトの設定ファイルをまとめるディレクトリです。書籍名から出力形式、章の順番、校正ルールまで、本の作り方を決める情報がここに集まっています。主なファイルは次のとおりです。詳しい項目は `config/_README.md` で確認できます。

| ファイル | 役割 |
|----------|------|
| `book.yml` | 書籍のメタデータ・ビルド設定（最重要） |
| `catalog.yml` | ビルド対象の章リスト（章の順序を定義） |
| `page_presets.yml` | 用紙サイズ等のプリセット定義 |
| `index_glossary_terms.yml` | 索引・用語集の登録済み用語 |
| `.textlintrc.yml` | textlint の校正ルール設定 |

## オプションとカスタマイズ

ここまで見てきた対話形式が `vs new` の基本ですが、用途に応じて動作を変えるオプションもあります。

| オプション | 説明 |
|------------|------|
| `--yes` / `-y` | 対話をスキップし既定の設定で作成する |
| `--log <level>` | ログレベル（`debug` など）を指定する |

### 対話をスキップする（--yes）

`--yes` オプションを付けると、すべての質問を省き、既定値でプロジェクトを作成します。書籍情報を後から `book.yml` に記入したい場合や、何度も検証用プロジェクトを作る場合に便利です。

```bash
vs new mybook --yes
```

既定値は以下のとおりです。

| 項目 | 既定値 |
|------|------------|
| 書籍名 | 新しい本 |
| 副題 | （空） |
| 著者名 | （空） |
| 発行者 | （空） |

### 同名のディレクトリがすでにあるとき

同名のディレクトリがすでに存在する場合は、エラーになります。`vs new` は新しいプロジェクトを作るコマンドなので、既存のディレクトリを変更したり、その中のファイルを上書きしたりしません。

```
エラー: ディレクトリ "mybook" はすでに存在します。
既存プロジェクトへ雛形の改良を取り込むには vs upgrade を使ってください（不足ファイルの追加もできます）。
  cd mybook && vs upgrade
```

既存のプロジェクトへ新しい雛形を取り込むときは、`vs upgrade` を使います。本体 gem・プロジェクトの雛形・外部ツールをまとめて更新し、不足しているファイルも追加します。詳しい使い方は「環境の診断と更新」の章で解説します。

### プロジェクト名のルール

プロジェクト名には**英数字・ハイフン・アンダースコア**のみ使用できます。

```bash
# OK
vs new mybook
vs new my-book
vs new my_book_2

# NG（エラーになります）
vs new "my book"
vs new my/book
```

### デバッグログ（--log=debug）

処理が途中で止まったときや、生成内容を詳しく確かめたいときは、デバッグログを表示できます。コピーしているファイルのパスや、内部で実行するコマンドが確認できます。

```bash
vs new mybook --yes --log=debug
```

## 作成後の次のステップ

プロジェクトを作成すると、続けて `vs doctor --fix` が実行されます。npm パッケージのインストールなど、原稿をビルドするために必要な環境がここでセットアップされます。`vs new` が終わった時点で、雛形を眺めるだけでなく、すぐに PDF を生成できる状態になります。

`vs doctor --fix` が完了しなかった場合も、作成済みのプロジェクトは残り、警告が表示されます。原因を確認したあと、プロジェクトの中で同じコマンドを再実行できます。

```bash
cd mybook
vs doctor --fix
```

環境が整ったら、まず雛形をビルドして、制作の出発点となる PDF を確認します。

```bash
cd mybook
vs build
```

PDF が開いたら、`contents/` のサンプルを自分の原稿へ少しずつ置き換えていけます。書籍名や判型、出力形式などを変えるときは `config/book.yml` を編集します。設定項目の意味は「config/book.yml リファレンス」の章で詳しく説明します。プロジェクトの構造が分かれば、原稿の置き場所と、紙面を整える設定の場所にも迷いにくくなります。
