# 文章校正

:::{.chapter-lead}
原稿を書き進めると、表記の揺れや英単語の綴りの誤りはどうしても紛れ込みます。`vs lint` は、日本語の校正と英語のスペルチェックをまとめて実行し、目で読むだけでは見落としやすい箇所を行番号付きで示すコマンドです。本章では、指摘の読み方、自動修正、指摘の外し方、書籍に合わせた調整を扱います。
:::

## vs lint とは

:::{.section-lead}
`vs lint` は原稿を検査し、直したほうがよい箇所を示します。指摘は修正の候補です。採るかどうかは、書籍の文体と文脈に照らして著者が決めます。
:::

`vs lint` は次の三つの検査を続けて実行します。

- **日本語校正**: 校正ツール textlint と Vivlio Starter 独自の規則で、表記の揺れ、です・ます調とだ・である調の混在、冗長な表現、長すぎる文、Markdown の記法の取り違えなどを見つけます。
- **スペルチェック**: 原稿の英単語の綴りの誤りを見つけます。技術用語や製品名の辞書を 50 以上内蔵しています。
- **コードブロックの言語名**: 言語名を書き忘れたコードブロックを見つけ、言語を推定します（@pageref:lint-code-language）。

次の箇所は検査しません。

- **記法**: コード、数式、属性記法（`{width=20%}`）、ふりがな記法（`{親文字|ふりがな}`）の読みと区切り記号、相互参照のラベル（`@ruby-sample`・`@pageref:…`）
- **出力例の囲み**: `:::{.output}`・`:::{.terminal}`・`:::{.showcase}` の中。実物の出力と一字一句合っている必要があるためです

## 基本的な使い方

:::{.section-lead}
引数を付けなければ全章を、章を指定すればその章だけを検査します。
:::

```bash
# catalog.yml に載っている全章を検査
vs lint

# 11-intro.md だけを検査
vs lint 11-intro

# 複数の章・範囲を指定
vs lint 11-intro 12-basics
vs lint 11-13
```

章は、ファイル名・番号・範囲のどれでも指定できます。書き方は @ch-chapter-management の章の @pageref:chapter-targets で説明しています。

## 実行結果の見方

:::{.section-lead}
指摘は、同じ種類のものを 1 行にまとめた集約表示で出力されます。件数の多い揺れを先にまとめて直し、そのあと個別の指摘を読む、という順で推敲できます。
:::

### 集約表示

指摘は原稿ごと・検査ごとに表にまとめられ、件数の多い順に並びます。

:::{.output}
```
📄 contents/11-intro.md  (日本語校正)
   12件  [missing-period] 文末に句点「。」がありません
         行: 4, 10, 13, 20, 26, 31, 70, 84, 117, 157, …
    8件  [prh] 以下 => 次
         行: 84, 122, 138, 162, 256, 304, 447, 460

📄 contents/11-intro.md  (スペルチェック)
    3件  bandle => bundle       行: 23, 88, 152
    2件  yestoday => yesterday  行: 47, 90
```
:::

各行の意味は次のとおりです。

- 先頭の件数: その規則（スペルチェックでは、その語）の指摘の件数
- `[missing-period]`: 指摘した規則の名前（日本語校正）
- `bandle => bundle`: 誤りと修正候補（スペルチェック）。候補が見つからないときは語だけを表示
- `行: …`: 指摘のある行番号。10 件を超えた分は `…` に省略

行番号は薄い青で表示され、押すとエディタでその行が開きます（表示は @pageref:lint-line-links の `line_links` で変えられます）。空白や字幅だけが違う指摘には、`（空白を追加）`・`（半角 → 全角）` のような注記が付き、半角の空白は `␣` で表示されます。

### 完了サマリー

最後に、件数の内訳と次に実行するコマンドが表示されます。

:::{.output}
```
✏️ 文章の品質チェックが完了しました
🟡 1080箇所に改善提案があります
   - 日本語校正: 674箇所
   - スペルチェック: 401箇所
   - コードブロックの言語名: 5箇所
💡 そのうち364箇所は自動修正可能です。
   vs lint --fix
```
:::

指摘がなければ、`✅ 文章チェックで課題は見つかりませんでした。` と表示されます。

## 自動修正

:::{.section-lead}
表記の揺れのように直し方が一つに決まる指摘は、`--fix` で自動修正できます。修正したあとの差分を確かめるところまでを、一つの作業として扱います。
:::

```bash
# 自動修正できる指摘をすべて直す
vs lint --fix

# 章を指定して直す
vs lint 11-intro --fix
```

修正すると、完了サマリーに `🔧 1ファイルへ自動修正を適用しました` と表示され、件数は修正したあとに残った指摘の数になります。

:::{.notice}
**`--fix` は原稿を直接書き換え、文脈を考慮しません。** 辞書の綴りに一致すれば、例文の中でも書き換えます。実行する前に Git などでコミットし、章を指定して実行したら、すぐに `git diff` で変わった行を確かめてください。表記の揺れを説明する文で「`ユーザ` と `ユーザー`」のようにわざと揺れた綴りを見せるときは、インラインコードで囲みます（コードは検査しません）。
:::

## 指摘を外す

:::{.section-lead}
固有名詞や引用、意図した表記の指摘は、外すことができます。外し方は次の四つで、効く範囲が違います。
:::

| 外したいもの | 使うもの | 効く範囲 |
| :--- | :--- | :--- |
| 原稿の特定の箇所 | `<!-- no-lint -->` | 日本語校正とスペルチェック |
| 本全体で、ある語句 | `config/textlint_allowlist.yml` | textlint の規則と交ぜ書き |
| 本全体で、ある英単語 | `config/spellcheck_user_dictionary.yml` | スペルチェック |
| 規則そのもの | `book.yml` の `disabled_rules` | その規則（全章） |

まず allowlist に語を書いて試し、同じ規則を何度も外していると気づいたら、規則ごと無効にする、という順が扱いやすいでしょう。`spellcheck_user_dictionary.yml` は @pageref:lint-spellcheck-dictionary で、`disabled_rules` は @pageref:lint-disabled-rules で説明します。

### 箇所を外す — `no-lint`

外したい行の直前に `<!-- no-lint -->` を置くと、次の 1 行が検査から外れます。まとまった範囲は `<!-- no-lint-start -->` と `<!-- no-lint-end -->` で囲みます。

```markdown
<!-- no-lint -->
htmx はサーバーとの通信を HTML 属性で記述できるライブラリです。

<!-- no-lint-start -->
ここは日本語校正もスペルチェックも行いません。
<!-- no-lint-end -->
```

`<!-- no-lint-end -->` を書き忘れると、そこから原稿の終わりまで指摘が出なくなります。そのため `vs lint` は、閉じ忘れを `[unclosed-suppression]` として指摘します。

マーカーは 1 行に単独で書きます。文中にインラインコードとして書いた `` `<!-- no-lint -->` ``（この文のような説明）は、マーカーとして扱いません。

### 語句を外す — allowlist

ある語句を本全体で検査から外すときは、`config/textlint_allowlist.yml` に書きます。1 行に 1 語句で、`#` から後ろはコメントです。スラッシュで囲むと正規表現になり、末尾にフラグも書けます。

```yaml
- "Web技術で「本」が作れるCSS組版Vivliostyle入門"  # 書名は直さない
- "基本情報技術者"  # 資格名称
- "既定"            # 「既定 => デフォルト」の指摘を外す。この本は「既定」で統一する
- "/マスター/"      # 長音を残す方針。マスターファイル・マスターキーもまとめて外れる
- "/[A-Z]{3,}/"     # 3 文字以上の大文字略語をまとめて外す
```

書名や引用の中の表記は、揺れていても著者の表記ではないので直しません。ここに書いて指摘を外します。

ここに書いた語句は、textlint のすべての規則と交ぜ書き（@pageref:lint-mazegaki）から指摘されなくなります。「この語はこの規則でだけ許したい」ときは、語句ではなく規則のほうを `disabled_rules` で無効にします。交ぜ書き以外の Vivlio Starter 独自の規則（弱い表現・数の表記など）は文の書き方を見る規則なので、allowlist では外れません。`<!-- no-lint -->` か `disabled_rules` を使います。

日本語は語を空白で区切らないので、複合語の継ぎ目に辞書の語と同じ文字の並びが現れ、別の語として指摘されることがあります（「プレビューアプリ」の中の「レビューア」など）。よくあるものは `vs lint` があらかじめ外してあります。この本だけの複合語で起きたときは、継ぎ目の形を正規表現で書くと、語を一つずつ追加するより漏れがありません。

## Vivlio Starter 独自の規則

:::{.section-lead}
textlint の規則に加えて、日本語の読み違いや Markdown の記法の取り違えを見つける規則があります。どれもビルドは成功するので、紙面を見るまで気づきにくい箇所です。
:::

| 見つけるもの | 規則名 | `--fix` |
| :--- | :--- | :---: |
| 交ぜ書き（`だ円` → `楕円`） | `mazegaki` | ○ |
| 漢字に見える康煕部首（`⽇本` の `⽇`） | `kanji-lookalike` | ○ |
| 索引・用語集の語と空白だけ違う書き方（`Type3 フォント`） | `index-term-spacing` | ○ |
| 英字の語と漢字・カタカナの間の空白（`EPUB用` → `EPUB 用`） | `affix-spacing` | ○ |
| 英字の語とひらがなの間の空白（`IDの` → `ID の`） | `hiragana-spacing` | ○ |
| 二通りに読める対比（比較の「と」に否定が続く文） | `ambiguous-comparison` | — |
| 文末の句点の打ち忘れ | `missing-period` | — |
| 長すぎる一文（既定 100 字） | `sentence-length` | — |
| 長すぎる丸かっこの補足（既定 60 字） | `long-parenthetical` | — |
| 断定を避ける言い回し（`かもしれません`・`思います`） | `ja-no-weak-phrase` | — |
| 数と「つ」の表記（`2 つ` → `二つ`。記号の個数は算用数字） | `kansuji-counter-suffix` | — |
| 和文どうしを空きなしで並べた半角スラッシュ（`前書き/後書き`） | `slash-between-japanese` | — |
| 英数字の直後の `*`・`_` が対になってできる強調（`A*探索` と `A*は`） | `accidental-emphasis` | — |
| かっこの隣の空白 | `space-around-brackets` | — |
| 4 スペースの字下げ（コードブロックにならない） | `indented-code-block` | — |
| 直前の行に続く `---`（改ページではなく見出しになる） | `setext-heading` | — |
| 1 ファイルに二つ目の章見出し（`#`） | `multiple-chapter-headings` | — |
| 閉じ忘れた `<!-- no-lint-start -->` | `unclosed-suppression` | — |

`--fix` が「—」の規則は、直し方が二通り以上あり、著者が選びます。たとえば句点の打ち忘れは、句点を打つか体言止めに直すかを選びます。規則名は集約表示の `[ ]` に出る名前で、`disabled_rules` に書くと規則全体を無効にできます。

以下では、使い方に補足が要る規則を説明します。

### 交ぜ書き @lint-mazegaki

熟語の一部の漢字だけをかなで書いた表記（`完ぺき`・`しきい値`・`ぜい弱`）を指摘し、`vs lint --fix` で漢字へ直します。`改ざん` や `せん断` のように、かな書きのほうが広く使われている語も指摘します。漢字とかなのどちらで書くかは著者の方針です。

かなで書くと決めた語は、`config/textlint_allowlist.yml` に書きます。指摘が出なくなり、`--fix` でも書き換えません。表外漢字はすべてかなで書く方針なら、`disabled_rules` に `mazegaki` と書いて規則全体を無効にするほうが早いでしょう。

MeCab をインストールすると、指摘できる語が増えます。語の切れ目を見ないと誤って指摘する語（`う回` は「使う回数」にも現れる）は、MeCab があるときだけ検査します。MeCab がなくても誤った指摘は増えません。インストールの方法は @chapref:ch-doctor を参照してください。

### 二通りに読める対比

<!-- no-lint -->
「B は A と同様に X しない」という文は、「A も X しない」とも「A とは違って B は X しない」とも読めます。対比を書くときは、両者の性質を別々の文で書きます。

<!-- no-lint-start -->
| | 文 |
| :--- | :--- |
| 直す前 | Ractor はスレッドと同じようにメモリを共有しない。 |
| 直した後 | スレッドはメモリを共有するが、Ractor は共有しない。 |
<!-- no-lint-end -->

指摘するのは「と同じように」「と同様に」「と同じく」のように、比較の「と」を伴う形だけです。

### 文末の句点の打ち忘れ

段落の最後の文字がひらがな（`…する`・`…です` のような用言の終わり）なのに句点がないと指摘します。体言止め（`**用途**: PDF閲覧、電子配布`）は指摘しません。箇条書き・見出し・表・引用と、段落全体が一つの強調になっている行（小見出しとして組まれます）も検査しません。助詞で終わって次のブロックへ続く文（`…という自然な習慣で`）は指摘されるので、`<!-- no-lint -->` で外します。

### 強調に化ける `*` と `_`

Markdown では、英数字の直後の `*` と `_` も強調の記号になります。同じ段落に次の `*`（`_`）があると、その間が強調（下線）になり、記号は二つとも紙面から消えます。

| 原稿 | 紙面 |
| :--- | :--- |
| `A*探索は…。A*は…` | 「A」の後ろから次の「A」までに下線が引かれ、`*` が消える |
| `p_k = a_k+p_(k-1)` | 「k = a_k+p」に下線が引かれ、`_` が 2 つ消える |

記号を字として見せるときは、前に `\` を付けて `A\*` と書きます。式は `$p_k$` のように数式にします。`A\*探索` と書いた語も、索引の辞書の `A*探索` に一致します。

指摘するのは、開きの記号の直前が英数字で、実際に強調ができる組だけです。`*書名*` のように空白や約物の後ろから始まる強調、和文の中の `*強調*`、対になる記号のない `a*b` は指摘しません。

## コードブロックの言語名 @lint-code-language

:::{.section-lead}
言語名を書き忘れたコードブロックを見つけて、言語を推定します。言語名がなくてもビルドは成功し、行番号も付くので、色分けされていないことには紙面を見るまで気づけません。
:::

コードブロックは、言語名を書くと色分けされます（@ch-extensions の章の @pageref:syntax-highlight）。`vs lint` は、言語名のないコードブロックの中身から言語を推定し、原稿ごとに報告します。行番号は、コードブロックの開始行（バッククォートの行）です。

:::{.output}
```
📄 contents/21-web.md  (コードブロックの言語名)
    3件  css と推定                               行: 40, 88, 152
    2件  javascript らしい（言語名の付け忘れ？）  行: 64, 97

💡 コードブロックに言語名を書くと色分けされます（「〜と推定」は vs lint --fix で書き込めます）
🤔 「〜らしい」は確かめきれなかったものです。--fix では書き込まないので、見て言語名を書いてください
   色を付けない文字（実行結果・ディレクトリの木など）は ```text と書くと、指摘は出なくなります
```
:::

- **〜と推定**: 推定が確かなものです。`vs lint --fix` で、コードブロックの開始行（` ``` ` → ` ```css `）へ言語名を書き込みます。
- **〜らしい**: 手がかりはあるものの、確かめきれなかったものです。`--fix` では書き込まないので、中身を見て言語名を書きます。

推定する言語は、その章で言語名を書いてあるコードブロックの言語に限ります。章に一つもなければ本全体の言語、本にもなければ主な 16 言語から選びます。それ以外の言語のコードは報告されないので、言語名を手で書いてください。

実行結果やディレクトリの木のように色を付けない文字は、言語名に `text` と書くと指摘されなくなります。`:::{.output}`・`:::{.terminal}`・`:::{.diagram}` の中のコードブロックは検査しません。1 行目が `$ ` か `% ` で始まる端末の記録は `shell-session` と推定します。`shell-session` は、`$ ` で始まる行だけをコマンドとして色分けし、出力の行はそのまま表示します。

言語の推定には Guesslang（npm パッケージ `@vscode/vscode-languagedetection`）を使います。`vs doctor --fix` でインストールできます。インストールしていないときは、言語名のないコードブロックの数とインストールの方法だけを表示します（`shell-session` の推定は Guesslang がなくても行います）。

## 英語スペルチェック

:::{.section-lead}
原稿の英単語の綴りを、内蔵の辞書と照らし合わせます。辞書にない語は綴りの誤りとして指摘されるので、この本で使う固有名詞や造語はユーザー辞書に登録します。
:::

内蔵の辞書は 50 以上あり、一般の英単語、主要なプログラミング言語の用語、クラウドやツールの製品名などを収めています。索引・用語集の辞書（`index_glossary_terms.yml`）に登録した英字の語も、正しい綴りとして扱います。

### ユーザー辞書と --register @lint-spellcheck-dictionary

スペルチェックで指摘された語は、`--register` を付けて実行すると、すべてユーザー辞書（`config/spellcheck_user_dictionary.yml`）に登録されます。登録した語は、内蔵の辞書の語と同じく正しい綴りとして扱われ、指摘されなくなります。

```bash
# 指摘された語をユーザー辞書へまとめて登録
vs lint --register
```

登録したら `config/spellcheck_user_dictionary.yml` を開き、正しい語だけを残してください。消した誤記は、次の `vs lint` でまた指摘されます。手で書き足すときは、1 行に 1 語を `- "htmx"` の形で書きます。

- `--register` はスペルチェックだけを実行します。
- 語は大文字小文字を区別せず、辞書順・重複なしに整えられます。ハイフンを含む語は、ハイフンを詰めた形（`vivliostarter`）でも正しい綴りとして扱います。
- このファイルはプロジェクトごとにあります。別の本でも使うときはコピーしてください。

### book.yml による設定

スペルチェックの動作は、`config/book.yml` の `spellcheck` で設定します。

```yaml
spellcheck:
  extra_dictionaries:      # 追加の辞書（初回実行時に取得）
    - ada
    - elixir
  check_code_blocks: false # コードブロックの中も検査するか（既定: false）
```

- **extra_dictionaries**: 内蔵の辞書にない言語・分野の辞書を追加します。初回の実行時にインターネットから取得し、`.cache/spellcheck-dictionaries/` に保存します。
- **check_code_blocks**: `true` にすると、コードブロックの中の英単語も検査します。

## book.yml で調整する

:::{.section-lead}
日本語校正の振る舞いは、`config/book.yml` の `lint` で書籍の文体に合わせます。文体に合わない規則を無効にしたり、許す表記を選んだりできます。
:::

```yaml
lint:
  # 無効にする規則（集約表示の [ ] に出る名前）
  disabled_rules:
    - arabic-kanji-numbers

  # 一文の最大文字数（0 で一文の長さを検査しない）。丸かっこの中は数えません
  sentence_length_max: 100

  # かっこ内の補足の最大文字数（0 で補足の長さを検査しない）
  parenthetical_length_max: 60

  # 「サーバ／パラメータ／フィルタ」など末尾の長音を省く文体なら true
  trim_long_vowel: true

  # インラインコードと和文の間のスペースを許すなら true
  allow_space_around_code: true

  # 全角と半角（英数・記号）の間のスペースを許すなら true
  allow_space_between_ja_en: true

  # 指摘の「行:」をクリックでエディタに開く（compact / path / off）
  line_links: compact
```

上の値は、どれも書かなかったときの既定値です。`book.yml` に書くのは文体の選択だけで、規則そのものを追加・削除するときは `config/.textlintrc.yml` を編集します（@pageref:lint-config-files）。どの設定も検査そのものを変えるので、`vs lint --fix` の振る舞いも同じように変わります。

### disabled_rules — 規則を無効にする @lint-disabled-rules

集約表示の `[ ]` に出る規則名を書くと、その規則全体を無効にできます。たとえば `arabic-kanji-numbers`（`一つ => 1つ`）と `kansuji-counter-suffix`（`1つ => 一つ`）は**逆の指摘をする規則**なので、書籍の方針に合わない側を無効にします。既定では、数を漢数字で書く側に合わせて `arabic-kanji-numbers` を無効にしています。

無効にした規則は、表示されず、`vs lint --fix` でも修正されず、件数にも数えません。Vivlio Starter 独自の規則も同じように書けます。`prh` と書くと、表記揺れの辞書がすべて無効になります（辞書の項目を一つずつ無効にすることはできません）。

### sentence_length_max と parenthetical_length_max — 文と補足の長さ

`sentence_length_max` は一文の長さの上限で、既定は 100 字です。数えるのは和文だけで、インラインコード・丸かっこの中・欧文は数えません。丸かっこの中の補足は別に検査し、その上限が `parenthetical_length_max`（既定 60 字）です。どちらも `0` にすると検査しません。一文の長さの上限は `.textlintrc.yml` に書いても反映されないので、この設定で変えます。

### trim_long_vowel — 末尾の長音

`true`（既定）では、「サーバ」「パラメータ」「フィルタ」のように**末尾の長音を省く文体**になります。同梱の辞書の `サーバ => サーバー` のような、末尾に長音を足すだけの指摘を出しません。著者が `config/textlint_rewrite.yml` に書いた規則（「この本では `ユーザー` と書く」など）は無効にしないので、この設定と両立します。

### `allow_space_*` — 和欧間のスペース

技術書では、`` `vs import` コマンド `` のように、インラインコードや英数字の前後にスペースを入れる書き方がよく使われます。`allow_space_around_code` はインラインコードと和文の間、`allow_space_between_ja_en` は全角と半角（英数・記号）の間のスペースを許します（どちらも既定は `true`）。規則そのものを無効にするので、`vs lint --fix` が意図して入れたスペースを削除することもありません。

### line_links — 行番号をクリックで開く @lint-line-links

集約表示の行番号の見せ方を選びます。

| 値 | 表示 | 下線 |
|---|---|---|
| `compact` | `行: 223`（薄い青） | 端末によっては付く |
| `path` | `行: contents/11-intro.md:223` | 付かない |
| `off` | `行: 223` | — |

既定は `compact` です。下線が気になるなら `path`、クリックしても何も起きない端末なら `off` を選びます。出力をファイルへ書き出したとき（`vs lint > report.txt`）は、どの設定でも行番号だけを出力します。

## 校正の設定ファイル @lint-config-files

:::{.section-lead}
日本語校正の規則と辞書は、`config/` のファイルに書きます。書籍の表記の方針をファイルに残しておけば、執筆が長く続いても同じ基準で原稿を見直せます。
:::

- `config/.textlintrc.yml`: textlint の設定（読み込む規則と辞書）
- `config/textlint_rewrite.yml`: この本の表記の辞書
- `config/textlint_allowlist.yml`: 日本語校正で指摘しない語句
- `config/textlint_dictionaries/`: 同梱の辞書（`vs upgrade` が更新するので編集しない）
- `config/spellcheck_dictionaries/`: スペルチェックの辞書
- `config/spellcheck_user_dictionary.yml`: スペルチェックのユーザー辞書

設定ファイルを削除してしまったときや、textlint がインストールされていないときは、`vs lint` はエラー（🔴）を出して止まります。どちらも `vs doctor --fix` で戻せます（@chapref:ch-doctor）。

### 読点・半角カンマの上限を変える

一文に打てる読点「、」と半角カンマ「,」の上限は、`config/.textlintrc.yml` に書いてあります。どちらも既定は 3 個です。

```yaml
rules:
  preset-ja-technical-writing:
    max-ten:
      max: 3    # 一文の読点「、」
    max-comma:
      max: 3    # 一文の半角カンマ「,」
```

上限を変える前に、指摘された文を句点で区切れないか読み直してみてください。`max-comma` が数えるのは半角カンマだけなので、和文で当たるのは数字の桁区切り（`2,894`）か欧文の語の並びです。桁区切りの数字が多い本では、`disabled_rules` に `max-comma` と書いて規則全体を無効にするほうが合います。

### 表記揺れの辞書に追加する

`CSS 組版` と `CSS組版` のような表記の揺れは、`config/textlint_rewrite.yml` に書くと指摘され、`vs lint --fix` でまとめて直せます。ここに書くのは**この本の表記**だけです（製品名・技術用語・誤字は同梱の辞書にあります）。

```yaml
rules:
  - expected: CSS 組版      # そろえたい表記
    patterns:              # そこへ直したい表記
      - 'CSS組版'
  - expected: ユーザー
    patterns:
      - /ユーザ(?!ー)/     # スラッシュで囲むと正規表現
    specs:                 # 書き換える例・書き換えない例
      - from: ユーザが使う
        to:   ユーザーが使う
      - from: ユーザーが使う
        to:   ユーザーが使う
```

`specs` を書いておくと、`vs lint` が辞書を読むたびに正規表現を試し、結果が `specs` と違えばエラーを表示して止まります。
