# 文章校正

:::{.chapter-lead}
原稿を重ねていくと、表記の揺れや英単語の綴り間違いは、どうしても紛れ込みます。`vs lint` は、Markdown 原稿に日本語校正（textlint）と英語のスペルチェックをまとめて実行し、目視だけでは見落としやすい箇所を洗い出すコマンドです。本章では、指摘の読み方から自動修正、書籍ごとの調整までを扱います。
:::

## vs lint とは

:::{.section-lead}
`vs lint` は、「日本語校正」と「英語スペルチェック」を一つのコマンドで実行します。ESLint や RuboCop がコードの気になる箇所を示すように、文章を読み返すきっかけを行番号付きで示します。指摘は修正候補であり、文章の正解を決めるものではありません。採用するかどうかは、書籍の文体や文脈に照らして判断できます。
:::

`vs lint` は次の二つを並行して実行します。

- **日本語校正（textlint）**: Node.js 製のオープンソース校正ツール textlint を利用し、日本語技術文書向けのルールで文章をチェックします。
- **英語スペルチェック**: Vivlio Starter 内蔵のスペルチェッカーが、原稿中の英単語の綴り誤りを検出します。50 以上の技術辞書を搭載しています。

あわせて、言語名を書き忘れたコードブロックも見つけます（@pageref:lint-code-language）。

### 主なチェック内容

<!-- no-lint -->
- **表記揺れの検出**: 「ユーザ」と「ユーザー」、「javascript」と「JavaScript」などの不統一を検出
- **文体の統一**: 「です・ます調」と「だ・である調」の混在をチェック
- **冗長表現の検出**: 助詞の重複、接続詞の連続使用などを指摘
- **一文の長さ**: 長すぎる文を指摘（最大文字数は設定可能）
- **日本語ならではの読み違い**: 交ぜ書き・ら抜き言葉・二通りに読める対比を検出（後述）
- **英単語の綴り誤り**: プログラミング言語・フレームワーク・略語などを誤記から保護
- **コードブロックの言語名**: 言語名のないコードブロックの言語を推定して、書き忘れを知らせる
- **自動修正**: 表記揺れなど一部の指摘は自動的に修正可能

## 基本的な使い方

:::{.section-lead}
引数を付けずに全章を確認するほか、章を指定して、いま書いている部分だけを確かめることもできます。
:::

```bash
# catalog.yml に載っている全章をチェック
vs lint

# 11-intro.md だけをチェック
vs lint 11-intro

# 複数の章・範囲を指定
vs lint 11-intro 12-basics
vs lint 11-13
```

章は、ファイル名・番号・範囲のどれでも指定できます。書き方は @ch-chapter-management の章の @pageref:chapter-targets で説明しています。

### 日本語校正かスペルチェックの片方だけを実行する

通常は両方が動きます。確認したい内容が決まっているときは、オプションで片方だけに絞れます。

```bash
# 日本語校正（textlint）のみを実行
vs lint --textlint-only

# スペルチェックのみを実行
vs lint --spellcheck-only
```

`--spellcheck-only` は textlint を使わないので、**textlint をまだ導入していない環境でも動作します**。どちらのオプションでも、コードブロックの言語名の確認は行いません。

## 実行結果の見方

:::{.section-lead}
結果は、同じ種類の指摘を 1 行へまとめた「集約表示」で出力されます。まず件数の多い揺れをまとめて直し、そのあと個別の指摘を読む、といった順序で推敲できます。
:::

### 集約表示

指摘はファイルごと・ルールごとに集約され、出現件数の多い順に並びます。件数が同じときは、最初の出現行が早いものから並びます。原稿を上から順に直していけるようにするためです。ラベルは `(日本語校正)` と `(スペルチェック)` の二つで、完了サマリーの内訳と同じ区分です。

:::{.output}
```
📄 contents/11-intro.md  (日本語校正)
   12件  [missing-period] 文末に句点「。」がありません
         行: 4, 10, 13, 20, 26, 31, 70, 84, 117, 157, …
    8件  [prh] 以下 => 次
         行: 84, 122, 138, 162, 256, 304, 447, 460

📄 contents/11-intro.md  (スペルチェック)
    3件  bandle => bundle       行: 23, 88, 152
    2件  yestoday => yesterday  行: 47, 90
```
:::

各行の意味は次のとおりです。

- 先頭の件数: そのルール（または語）の指摘が出た回数
- `[missing-period]`: 指摘したルール名（日本語校正）
- `bandle => bundle`: 誤りと修正候補（スペルチェック）。候補が見つからない場合は単語のみを表示
- `行: …`: 出現した行番号（最大 10 件まで。超過分は `…`）

**行番号はクリックできます。**薄い青で表示された番号を押すと、エディタでその行が開きます（後述の「`line_links`」で表示を変えられます）。

**違いが空白や字幅だけの指摘には、末尾に注記が付きます。** そのままでは同じ字が並んで見え、何を直せばよいか読み取れないためです。空白は `␣` で見せます。

:::{.output}
```
    1件  [spellcheck-tech-word] ␣） => ）（空白を削除）
    1件  [prh] CSS組版 => CSS␣組版（空白を追加）
    1件  [prh] (2026年) => （2026年）（半角 → 全角）
```
:::

### 完了サマリー

すべてのチェックが終わると、件数の内訳と次のアクションがまとめて表示されます。

:::{.output}
```
✏️ 文章の品質チェックが完了しました
🟡 1080箇所に改善提案があります
   - 日本語校正: 679箇所
   - スペルチェック: 401箇所
💡 そのうち364箇所は自動修正可能です。
   vs lint --fix
```
:::

課題が見つからなかった場合は、次のように表示されます。

:::{.output}
```
✅ 文章チェックで課題は見つかりませんでした。
```
:::

## 自動修正

:::{.section-lead}
表記揺れなど、文脈に左右されず置き換えられる指摘には、`--fix` オプションを利用できます。修正後の差分を確認するところまでを、一つの作業として考えてください。
:::

```bash
# 自動修正可能な指摘を修正
vs lint --fix

# 特定の章のみ自動修正
vs lint 11-intro --fix
```

:::{.notice}
**`--fix` は元のファイルを直接書き換え、文脈を読みません。** 辞書の綴りに当たれば、例文の中でも書き換えます。実行前に Git などへコミットしておき、`--fix` は章を指定してかけ、直後に `git diff` で変わった行を確かめてください。表記の揺れを説明する文で「`ユーザ` と `ユーザー`」のように**わざと揺れた綴りを見せるときは、インラインコードで囲みます**（コードは検査しません）。
:::

### 検査と自動修正の対象外になるもの

次の箇所や語・ルールは、そもそも `vs lint` の検査対象から外れます。指摘が出ないため、`--fix` でも書き換えられません。

- **記法**: コード、数式、属性記法（`{width=20%}`）、ふりがな記法（`{親文字|ふりがな}`）の読みと区切り記号、相互参照のラベル（`@ruby-sample`・`@pageref:…`）
- **出力例の囲み**: `:::{.output}`・`:::{.terminal}`・`:::{.showcase}` の中。実物の出力と一字一句合っていなければならないためです
- **除外の指定**: `<!-- no-lint-start -->` 〜 `<!-- no-lint-end -->` の範囲と `<!-- no-lint -->` の次の行、除外リストの語、`disabled_rules` で切ったルール

## チェックの部分的な除外

:::{.section-lead}
校正の対象にしたくない箇所には、`no-lint` コメントを使います。固有名詞や引用、意図した表記を残しながら、ほかの部分では検査を続けられます。日本語校正とスペルチェックの両方に共通する指定です。
:::

| 書き方 | 効く範囲 |
| :--- | :--- |
| `<!-- no-lint -->` | 次の 1 行だけ |
| `<!-- no-lint-start -->` 〜 `<!-- no-lint-end -->` | 囲んだ範囲 |

### 次の行だけ外す

いちばんよく使う形です。外したい行の直前に置きます。

```markdown
<!-- no-lint -->
htmx はサーバーとの通信を HTML 属性で記述できるライブラリです。
```

### 範囲で外す

辞書に載っていない語が続く節など、まとまった範囲を外すときに使います。

```markdown
<!-- no-lint-start -->
ここは textlint もスペルチェックも両方スキップされます。
表記揺れや綴りの誤りがあっても検出されません。
<!-- no-lint-end -->
```

**閉じ忘れると、そこから原稿の終わりまで指摘が止まります。**指摘が出ないことでしか現れない失敗なので、`vs lint` は閉じ忘れそのものを指摘します。

:::{.output}
```
    1件  [unclosed-suppression] `<!-- no-lint-start -->` が閉じられていません（`<!-- no-lint-end -->` を置くまで、以降の指摘がすべて止まります）
         行: 201
```
:::

### 書くときの注意

**コメントは行を独立させてください。**文中にインラインコードとして書いた `` `<!-- no-lint -->` ``（この文のような説明）は、マーカーとして扱いません。記法を解説する文章がそのまま lint を止めてしまわないようにするためです。

:::{.memo}
1.0 より前の書き方（`<!-- vs-lint-disable-next-line -->`・`<!-- vs-lint-disable -->`・`<!-- vs-lint-enable -->`）も、引き続き受け付けます。既存の原稿を書き換える必要はありません。
:::

## 日本語ならではの指摘

:::{.section-lead}
一般的な校正ルールに加えて、`vs lint` は日本語に固有の読み違いを四つ検出します。いずれも、書き手には意図が明らかでも、読者には別の意味で届きかねない表現です。単なる表記の統一とは違い、意味を確かめながら直す必要があります。
:::

### 交ぜ書き

熟語の一部の漢字だけをかなで書いた表記を指摘します。`vs lint --fix` で漢字へ直せます。

:::{.output}
```
    3件  [mazegaki] だ円 => 楕円
         行: 42, 88, 152
```
:::

由来は二つあります。

- **常用漢字表に入ったのに、かな書きが残っているもの** — `完ぺき`（完璧）・`破たん`（破綻）・`隠ぺい`（隠蔽）・`進ちょく`（進捗）・`危ぐ`（危惧）。2010 年の改定で「璧・綻・蔽・捗・惧」などが常用漢字になったため、いまは漢字で書けます。
- **いまも表外漢字のもの** — `だ円`（楕円）・`しきい値`（閾値）・`べき乗`（冪乗）・`うるう年`（閏年）・`けん引`（牽引）・`ぜい弱`（脆弱）・`かい離`（乖離）。

<!-- no-lint -->
`改ざん`（改竄）や `せん断`（剪断）、`宝くじ`（宝籤）のように、**かな書きのほうが主流になっている語も指摘します**。常用漢字表は 2000 字余りしかなく、そこに収まらない字を含む熟語は交ぜ書きで書かれるようになりました。JIS が「せん断」を採るのもそのためで、「剪断」が誤りだからではありません。

漢字とかなのどちらを選ぶかは**著者の方針**です。かなで通すと決めた語は `config/textlint_allowlist.yml` に書いてください。指摘が消えるだけでなく、`vs lint --fix` の置換対象からも外れます。表外漢字はすべて開く（かなで書く）方針なら、語を並べるより `disabled_rules` に `mazegaki` と書いてルールごと切るほうが早いでしょう。

```yaml
# config/textlint_allowlist.yml
- "せん断"   # JIS の表記に合わせる
- "改ざん"   # 読み手を選ぶ漢字は避ける
- "かぎ括弧" # この本は「かぎ括弧」で通す
```

**MeCab があると、指摘できる語が増えます。** 辞書のうち 150 語ほどは MeCab がなくても働き、残る約 1,900 語は MeCab があるときだけ加わります。`う回`（迂回）が「使う回数」にも現れるように、語の切れ目を見ないと誤って指摘する語があるためです。MeCab がない環境では、この約 1,900 語が指摘されないだけで、誤った指摘が増えることはありません。導入は @chapref:ch-doctor を参照してください。

直す先が一つに決まらない語（`そ上` は「俎上」とも「遡上」とも読める）や、全体がかなの語（`そご`・`はたん`）は、辞書に入れていません。`--fix` が原稿を壊さないようにするためです。

:::{.memo}
<!-- no-lint -->
`べき乗` のように、綴りが他の語に紛れる語は前後を見て判断します。「2 の**べき乗**」は指摘しますが、「予約す**べき乗**り換え」「行く**べき乗**客」は指摘しません。同様に `き損`（毀損）は「引**き損**なう」を、`き裂`（亀裂）は「引**き裂**く」を、`かく乱`（攪乱）は「とに**かく乱**暴」を避けます。
:::

:::{.column}
**「障碍」だけは交ぜ書きではありません**

`障害者`（障碍者）は漢字から漢字への置き換えなので、交ぜ書きの定義からは外れます。それでも同じ辞書に置いてあるのは、この語がたどってきた経緯のためです。

<!-- no-lint -->
`碍` は「隔たり」を表す字にすぎません。電柱の**碍子**（電線を支えながら絶縁する器具）に使われているとおり、字そのものに負の意味はありません。ところが常用漢字表に `碍` がないため「障害者」と書かれるようになり、今度は「害」の字を避けて「障がい者」という交ぜ書きが広まりました。「障碍」と書くのは、その流れを一つ前へ戻して正字に返す選択です。

<!-- no-lint -->
そのため `障がい`（障碍）と `障害者`（障碍者）は同じルールで扱います。対象は「障害者」という並びに限られ、「システム障害」や「障害物競走」は書き換わりません。
:::

### ら抜き言葉

<!-- no-lint -->
「見れる」「集めれる」のように、可能表現から「ら」が落ちた形を指摘します。書き言葉では避けるのが通例です。

:::{.output}
```
    2件  [no-dropping-the-ra] ら抜き言葉を使用しています。
         行: 11
```
:::

### 二通りに読める対比

<!-- no-lint -->
「B は A と同様に X しない」という形は、日本語として**二通りに読めます**。

- A も本来 X しない（A も否定の側）
- A とは違って B は X しない（A は肯定の側）

否定がどこまで係るかを語順で決められないため、文脈だけでは判別できません。読者が反対の意味で受け取っても、そのまま誤解が残ります。

対比を書きたいときは、両者の性質を独立した文でそれぞれ明示します。

<!-- no-lint-start -->
| | 文 |
| :--- | :--- |
| 直す前 | Ractor はスレッドと同じようにメモリを共有しない。 |
| 直した後 | スレッドはメモリを共有するが、Ractor は共有しない。 |
<!-- no-lint-end -->

この指摘は自動修正しません。どちらが X するのかは著者にしか分からないためです。指摘されるのは「と同じように」「と同様に」「と同じく」のように**比較の「と」を伴う形**だけです。「次のように動作しない」のような例示の「のように」は対象外です。

### 文末の句点の打ち忘れ

段落が句点で終わっていないと指摘します。

:::{.output}
```
    4件  [missing-period] 文末に句点「。」がありません
         行: 415, 425, 435, 446
```
:::

体言止めは句点を付けないほうが自然なので、指摘しません。見分けは**段落の最後の 1 文字**で行います。用言の終止形はひらがなで終わり（`…する`・`…です`・`…ます`）、体言止めは漢字・カタカナ・英数字・閉じかっこで終わるためです。

| 書き方 | 末尾 | 指摘 |
| :--- | :--- | :--- |
| 自分で描くことになります | `す` | 句点の打ち忘れ |
| `**用途**: PDF閲覧、電子配布` | `布` | 体言止めなので指摘しない |
| 大きな余白（1.5rem）で配置 | `置` | 同上 |
| 担当するのはプロジェクトマネージャー | `ー` | 同上（長音は用言ではない） |

箇条書き・見出し・表・引用の項目も対象外です。`**独自の装飾を追加する**` のように段落全体が強調一つの行（小見出しとして組まれます）や、`:::{.output}`・`:::{.terminal}` の中身も検査しません。

この指摘は自動修正しません。句点を足すのか、体言止めに直すのかは著者が決めることだからです。助詞で終わる形（`…という自然な習慣で` のように、文が次のブロックへ続くもの）は指摘が残るので、`<!-- no-lint -->` で抑えてください。

## 記法の取り違え

:::{.section-lead}
書いたつもりと Markdown の解釈がずれる箇所を三つ見つけます。いずれもビルドは成功するので、紙面を見るまで気づけません。正解が二択で、決められるのは著者だけなので、三つとも自動修正はしません。
:::

### 索引記法とまぎらわしい角括弧

`[語]` は索引に載せるための記法です。フラグ名や単位を説明するつもりで `[g]` `[eV]` のように書くと、その 1 文字が索引に載ってしまいます。

:::{.output}
```
    1件  [stray-index-markup] [g] は索引語として登録されます（コードなら `[g]` と囲む／索引に載せるなら [g|よみ] と仮名の読みを添える）
         行: 299
```
:::

指摘するのは**読みを添えていない、半角 1〜2 文字**の綴りだけです。`[CSS]` や `[PDF]` のような 3 文字は、索引語として自然なので指摘しません。直し方は二つあります。

- 記号として見せたいだけなら、バッククォートで囲んで `` `[g]` `` と書く
- 索引に載せたいなら、`[eV|いーぶい]` のように**仮名の読み**を添える

読みは並べ替えに使う欄です。意味を書く場所ではないので、`[eV|電子ボルト]` としても E の欄に並びます。意味は用語集の説明文へ書いてください。

### 4 スペースの字下げ

標準の Markdown には字下げでコードを示す書き方がありますが、Vivlio Starter は対応していません（@chapref:ch-markdown-tutorial を参照）。空行に挟まれた字下げの段落があると指摘します。

:::{.output}
```
    1件  [indented-code-block] 4 スペースの字下げはコードブロックになりません（コードならバッククォート 3 つのフェンスで囲んでください）
         行: 92
```
:::

リストの続きを字下げした行は指摘しません。指摘されるのはブロックの先頭 1 行だけなので、貼り付けた長いコードでも 1 件で済みます。

### 改ページのつもりの `---`

`---` は改ページですが、**直前の行に文が続いていると見出しになります**。Markdown の規則で見出しの解釈が優先されるためです。

:::{.output}
```
    1件  [setext-heading] 直前の行に続いているため、改ページではなく第 2 レベルの見出しになります（改ページにするなら前に空行を入れる／見出しにするなら ## を使う）
         行: 21
```
:::

`---` なら第 2 レベル、`===` なら第 1 レベルの見出しです。とくに `===` は章題と同じ階層なので、気づかないまま目次にも並びます。改ページにするなら**前に空行**を入れてください。

## コードブロックの言語名 @lint-code-language

:::{.section-lead}
言語名を書き忘れたコードブロックを見つけて、言語を推定します。言語名がなくてもビルドは成功し、行番号も付くので、色分けされていないことには紙面を見るまで気づけません。
:::

コードブロックは、言語名を書くと色分けされます（@ch-extensions の章の @pageref:syntax-highlight）。`vs lint` は、言語名のないコードブロックの中身から言語を推定し、原稿 1 ファイルごとに知らせます。

:::{.output}
```
📄 contents/21-web.md  (コードブロックの言語名)
    3件  css と推定            行: 40, 88, 152
    2件  html と推定           行: 12, 120
    1件  shell-session と推定  行: 200

💡 コードブロックに言語名を書くと色分けされます（vs lint --fix で書き込めます）
   色を付けない文字（実行結果・ディレクトリの木など）は ```text と書くと、指摘は出なくなります
```
:::

行番号は、コードブロックの開始行（バッククォートの行）です。

### 推定のしかた

推定は二段で行います。

1. 実行結果・ディレクトリの木・ログ・日本語の文章のように、コードでなさそうなものを除きます。
2. 残りを Guesslang で見分けます。Guesslang は、VS Code が言語の自動判定に使っている機械学習のモデルです。

言語の候補は、同じ章で言語名を書いてあるコードブロックの言語に絞ります。Ruby の章なら、言語名のないコードもまず Ruby だからです。章に一つも無ければ、本全体で書いてある言語から選びます。

迷うものは知らせません。確信が持てないとき（数行しかない短いコードなど）は、コードであっても知らせないことがあります。知らせなかったコードブロックには、言語名を手で書いてください。

### 言語名を書き込む

`vs lint --fix` を実行すると、推定した言語名をコードブロックの開始行へ書き込みます。

````markdown
```
.site-header {
  display: flex;
}
```
````

このコードブロックは、次のように書き換わります。{.aki}

````markdown
```css
.site-header {
  display: flex;
}
```
````

書き込んだあとは、ほかの自動修正と同じく `git diff` で確かめてください。推定が誤っていたら、その言語名を書き直します。

### 色を付けない文字には `text` と書く

実行結果やディレクトリの木のように、色を付けたくない文字を言語名なしのコードブロックに書いている場合もあります。コードと推定されてしまったときは、言語名に `text` と書くと、色分けされず、指摘も出なくなります。

`:::{.output}`・`:::{.terminal}`・`:::{.diagram}` の中のコードブロックは、言語名がなくても確認しません。

### 端末の記録は `shell-session` にする

1 行目が `$ ` か `% ` で始まるコードブロックは、コマンドとその出力を並べた端末の記録とみなし、`shell-session` と推定します。`shell-session` は、`$ ` で始まる行だけをコマンドとして色分けし、出力の行はそのまま残します。`bash` にすると、出力の行までコマンドとして色が付いてしまいます。

### Guesslang を導入する

言語の推定には Guesslang（npm パッケージ `@vscode/vscode-languagedetection`）を使います。`vs doctor --fix` で導入できます。導入していないときは、この確認だけを行わずに、次のように案内します（`shell-session` の推定は Guesslang が無くても行います）。

:::{.output}
```
💡 言語名のないコードブロックが 12 個あります。vs doctor --fix で Guesslang を入れると、言語を推定して知らせます
```
:::

## 英語スペルチェック

:::{.section-lead}
`vs lint` は日本語校正と同時に、原稿中の英単語の綴り誤りも検出します。プログラミング言語・フレームワーク・略語など幅広い技術用語に対応した辞書を内蔵しています。
:::

### チェック対象

- 原稿の Markdown に書いた英単語が対象です。
- コードブロック（` ``` `〜` ``` `）内は既定でチェック対象外です。
- Vivliostyle 拡張記法（`:::{.class}` など）や相互参照のラベル（`@ruby-sample`）の中の語も除外されます。
- 数式（`$…$` や `$$…$$`）の中も対象外です。

### 除外リストと --register

辞書に載っていない固有名詞や造語は「綴り誤り」として指摘されます。プロジェクト固有の語をまとめて許可語に加えたいときは、`--register` が便利です。

```bash
# 未知語を除外リストへ一括登録
vs lint --register
```

`--register` は、スペルチェックで未知だった語をすべて `config/spellcheck_allowlist.yml` へ追記します。登録後、不要な語を手で削れば、以後そのプロジェクトでは指摘されなくなります。

```yaml
- "ajisai"
- "htmx"
- "vivliostyle"
```

- `--register` は**スペルチェック専用の操作**です。`--spellcheck-only` を併記しなくても、日本語校正は実行されません。
- 形式は textlint 側の `textlint_allowlist.yml` と同じ YAML の並びです。大文字小文字は区別せず、辞書順・重複なしで自動的に整えられます。
- ハイフンを含む語は、詰めた形（`vivliostarter`）でも既知語として扱われます。
- このプロジェクト固有のファイルです。別の本でも使いたい場合はコピーしてください。

:::{.tip}
まず `vs lint --register` で指摘された語を一括登録し、`config/spellcheck_allowlist.yml` を開いて「本当に正しい語」だけを残します。消した誤記は、次回の `vs lint` で改めて指摘されます。
:::

### book.yml による設定

スペルチェックの動作は `config/book.yml` の `spellcheck` セクションで制御します。個別の語は `book.yml` ではなく、上の `config/spellcheck_allowlist.yml` に書きます。

```yaml
spellcheck:
  extra_dictionaries:      # オンデマンドダウンロード辞書（初回実行時に取得）
    - ada                  # Ada 言語の用語を追加したい場合
    - elixir               # Elixir 言語の用語を追加したい場合
  check_code_blocks: false # コードブロック内をチェックするか（既定: false）
```

- **extra_dictionaries**: 標準搭載辞書に含まれない言語・分野の辞書を追加します。初回実行時にインターネットから取得し、`.cache/spellcheck-dictionaries/` にキャッシュされます。
- **check_code_blocks**: `true` にするとコードブロック内の英単語もチェックします。

### 標準搭載辞書

次のような辞書が標準で搭載されています（50 以上のファイル）。

- **一般英単語**: SCOWL ベースの英単語辞書
- **技術用語**: HTML / CSS / JavaScript / TypeScript / Ruby / Python / Go / Rust / Java / Swift / Kotlin など主要言語の用語
- **略語・製品名**: AWS / Azure / GCP などクラウド、各種フレームワーク・ツール名
- **本ツール固有語**: `vivlio-starter-terms.txt`（textlint / yml / SCOWL など、標準辞書にない語）
- **索引用語**: プロジェクトの `index_glossary_terms.yml` に登録済みの英字語

## book.yml による調整（lint セクション）

:::{.section-lead}
日本語校正の細かな挙動は、`config/book.yml` の `lint` セクションで調整できます。書籍の文体に合わない規則を無効にしたり、許容する表記を指定したりするための設定です。
:::

```yaml
lint:
  # ルールごと丸ごと無効化したい textlint ルール ID（集約表示の [ ] 内の名前）
  disabled_rules:
    - arabic-kanji-numbers

  # 一文の最大文字数（0 で一文の長さを検査しない）。丸かっこの中は数えません
  sentence_length_max: 100

  # かっこ内の補足の最大文字数（0 で補足の長さを検査しない）
  parenthetical_length_max: 60

  # 「サーバ／パラメータ／フィルタ」等の末尾長音を省く文体なら true
  trim_long_vowel: true

  # インラインコードと和文の間のスペースを許容するなら true
  allow_space_around_code: true

  # 全角と半角（英数・記号）の間のスペースを許容するなら true
  allow_space_between_ja_en: true

  # 指摘の「行:」をクリックでエディタに開く（compact / path / off）
  line_links: compact
```

上の値は、どれも書かなかったときの既定値です。`book.yml` に置くのは**文体の選択**だけで、ルールそのものを足したり消したりするときは `config/.textlintrc.yml` を直接編集します。

どの設定も、表示から隠すのではなく検査そのものに効きます。そのため `vs lint --fix` の振る舞いも同じように変わります。

### disabled_rules（ルール単位の無効化）

集約表示に出るルール ID（`[ ]` 内の名前）を指定すると、そのルール全体を無効にできます。たとえば `arabic-kanji-numbers`（`一つ => 1つ`）と `kansuji-counter-suffix`（`1つ => 一つ`）のように**逆を向いたルール**は、書籍の方針に合わない側を切ると衝突が解消します。既定では、数を漢数字で書く側に合わせて `arabic-kanji-numbers` を無効にしています。

切ったルールは表示に出ず、`vs lint --fix` でも修正が当たりません。無効化した分は問題件数にも数えません。`prh` と書くと、表記揺れの辞書がすべて止まります（辞書の項目を一つずつは切れません）。

Vivlio Starter が独自に検査するルール（`mazegaki` / `ambiguous-comparison` / `stray-index-markup` / `indented-code-block` / `setext-heading` / `slash-between-japanese` / `space-around-brackets` / `long-parenthetical` / `kanji-lookalike` / `kansuji-counter-suffix` / `missing-period` / `sentence-length` / `ja-no-weak-phrase`）も、同じキーで無効にできます。特定の語だけを除外したいときは、ルール単位ではなく `config/textlint_allowlist.yml` を使います（後述）。

### sentence_length_max（一文の最大文字数）

一文の長さを指摘する `sentence-length` ルールの上限文字数です。既定は 100 文字で、文章の好みに応じて 80 や 120 などに変更できます。

**数えるのは和文だけです。**インラインコード・丸かっこの中・欧文は字数に入れません。読む負担が字数に比例しないためで、`` `:::{.sideimage-right}` `` のような記法は読み手にとって一つの塊です。丸かっこの中は読者が読み飛ばして本筋を追えるので外し、次の `parenthetical_length_max` で別に見ます。

**`0` を指定すると、一文の長さを検査しません。**

### parenthetical_length_max（かっこ内の補足の最大文字数）

独自ルール `long-parenthetical` の上限です。既定は 60 文字で、**句点で区切り、インラインコードと欧文を除いた和文**で数えます。`（yellow / orange / red / …）` のような値の列挙は補足ではなく一覧なので、字数に数えません。

**`0` を指定すると、補足の長さを検査しません。**

### trim_long_vowel（末尾長音の文体）

`true` にすると、「サーバ／パラメータ／フィルタ」のように**末尾の長音を省く技術文体**を選べます。同梱の辞書が出す `サーバ => サーバー` のような、末尾に長音を足すだけの指摘を切ります。既定は `true` です。

著者が `config/textlint_rewrite.yml` に書いた規則は切りません。「この本では `ユーザー` と書く」のように語を選んで長音を付けると決めた規則は、この設定と両立します。

### `allow_space_around_code` / `allow_space_between_ja_en`（和欧間スペースの許容）

技術書では、`` `vs import` コマンド `` のようにインラインコードや英数字の前後にスペースを入れる書き方がよく使われます。これらを許容したい場合は `true` にします（どちらも既定は `true`）。

- `allow_space_around_code`: インラインコードと和文の間のスペースを許容
- `allow_space_between_ja_en`: 全角と半角（英数・記号）の間のスペースを許容

ルールそのものを無効にするので、`vs lint --fix` を実行しても、意図的に入れたスペースが削除されることはありません。

### line_links（行番号をクリックで開く）

集約表示の `行: 223` をクリックすると、エディタでその行が開きます。表示の仕方は三つから選べます。

| 値 | 表示 | 下線 |
|---|---|---|
| `compact` | `行: 223`（薄い青） | 端末によっては付く |
| `path` | `行: contents/11-intro.md:223` | 付かない |
| `off` | `行: 223` | — |

既定は `compact` です。行番号だけの短い表示ですが、端末によってはリンクに下線が付きます。下線が気になるなら `path` を選ぶと、下線のないパスの表示になります。クリックしても何も起きない端末なら `off` にすると、表示が素の行番号に戻ります。

出力先が端末でないとき（`vs lint > report.txt` のようにファイルへ落とすとき）は、どの設定でも素の行番号です。

## 設定ファイルの場所

:::{.section-lead}
日本語校正の詳細なルールは、textlint の設定ファイルで管理します。書籍ごとの表記方針を設定として残しておけば、執筆が長期にわたっても同じ基準で原稿を見直せます。
:::

Vivlio Starter では、次の場所に設定ファイルが配置されています。

- `config/.textlintrc.yml`: textlint 本体の設定（フィルタ・ルール）
- `config/textlint_rewrite.yml`: 表記揺れ辞書（この本の表記）
- `config/textlint_allowlist.yml`: 除外リスト（書名・資格名称・この本の方針で通す語など）
- `config/textlint_dictionaries/`: 同梱の `prh` 辞書（固有名詞・技術用語・誤字・外来語の長音など。`vs upgrade` が更新するので編集しない）
- `config/spellcheck_dictionaries/`: 英語スペルチェック辞書
- `config/spellcheck_allowlist.yml`: スペルチェックのユーザー辞書（`--register` の追記先）

### 読点・半角カンマの上限を変える

一文に打てる読点「、」と半角カンマ「,」の上限は `config/.textlintrc.yml` に書いてあります。どちらも既定は 3 個です。

```yaml
rules:
  preset-ja-technical-writing:
    max-ten:
      max: 3    # 一文の読点「、」
    max-comma:
      max: 3    # 一文の半角カンマ「,」
```

読点が多い文は、句点で区切るか、語順を組み替えると読みやすくなることがあります。上限を変える前に、指摘された文を一度読み直してみてください。列挙や数値が原因なら設定を調整し、一文に内容を詰め込みすぎているなら文章を分けます。

`max-comma` が数えるのは**半角カンマだけ**で、和文の読点は `max-ten` が別に見ています。そのため和文でこの指摘に当たるのは、数字の桁区切り（`2,894 × 4,092 px`）か欧文の語の並び（`ImageMagick, qpdf, pdfinfo, Ghostscript`）のどちらかです。

:::{.output}
```
    1件  [max-comma] 一つの文に半角カンマが多すぎます（上限 3 個）。読点「、」で区切るか文を分けてください（数字の桁区切りも数えます）
         行: 201
```
:::

桁区切りの数字が多い本では、上限を 4 や 5 に広げるより、`book.yml` の `disabled_rules` に `max-comma` と書いて規則全体を無効にするほうが意図に合います。`max-ten` による読点の検査は残るので、和文の読みやすさは引き続き確認できます。

:::{.notice}
一文の長さ（`sentence-length`）だけは `.textlintrc.yml` ではなく `book.yml` の `lint.sentence_length_max` で変えます。`.textlintrc.yml` に書いても効きません。
:::

### 表記揺れ辞書の追加

`CSS 組版` と `CSS組版`、`ユーザー` と `ユーザ` のように、同じ語が違う表記で混ざることがあります。こうした揺れは `config/textlint_rewrite.yml` に登録すると検出できます。

ここに書くのは**この本の表記**だけです。製品名・技術用語・誤字のように、どの本にも当てはまるものは同梱の辞書が受け持ちます。

```yaml
rules:
  - expected: CSS 組版      # そろえたい表記
    patterns:              # そこへ直したい表記
      - 'CSS組版'
      - 'CSS組み版'
      - 'CSS 組み版'
```

`expected` が正しい表記、`patterns` がそこへ寄せたい表記です。登録すると `vs lint` が指摘し、`vs lint --fix` で一括修正できます。

:::{.output}
```
📄 contents/96-further-inspiration.md  (日本語校正)
    4件  [prh] CSS組版 => CSS␣組版（空白を追加）
         行: 11, 13
```
:::

`patterns` には正規表現も書けます。スラッシュで囲んでください。

```yaml
  - expected: ユーザー
    patterns:
      - /ユーザ(?!ー)/   # 後ろに長音が続くもの（ユーザー）には当てない
    specs:               # 当たってほしい例・当たってほしくない例
      - from: ユーザが使う
        to:   ユーザーが使う
      - from: ユーザーが使う
        to:   ユーザーが使う
```

`specs` を添えておくと、`vs lint` が辞書を読むたびに自己検査します。正規表現を直して期待と食い違えば、その場で止まって知らせます。

:::{.note}
**書名や引用は直さない**

書籍のタイトルや引用文に揺れた表記が含まれることがあります。それは著者の表記ではないので、直してはいけません。次項の `config/textlint_allowlist.yml` に登録して、指摘そのものを止めてください。

```yaml
# 書籍名（表記ゆれチェック除外）
- "Web技術で「本」が作れるCSS組版Vivliostyle入門"
```
:::

:::{.tip}
表記の揺れは原稿が長くなるほど増え、後から直すほど影響範囲が広がります。一つ見つけた時点で辞書へ登録しておけば、以降は書いた端から指摘されるので揺れがたまりません。
:::

### 除外リストの設定

特定の語句を textlint のチェック対象から完全に外したい場合は、`config/textlint_allowlist.yml` に登録します。1 行 1 語で、`#` から後ろはコメントです。

```yaml
# 書籍名（漢字連続チェック除外）
- "現代計算機科学"

# 資格名称
- "基本情報技術者"

# この本の方針で通す語
- "既定"  # 「既定 => デフォルト」を止める。この本は和語で通す
```

**スラッシュで囲むと正規表現**になります。末尾にフラグも書けます。

```yaml
- "/マスター/"      # 長音を残す方針。マスターファイル・マスターキーもまとめて外れる
- "/[A-Z]{3,}/"     # 3 文字以上の大文字略語をまとめて除外
- "/ゐ|ゑ/g"         # 旧仮名を全部
```

登録した語は**どのルールからも指摘されなくなります**。ルールを選んで免除することはできないので、「この語はこのルールだけ許したい」という場合は、その語ではなくルールのほうを `disabled_rules` で切ってください。

:::{.tip}
**語の一部が別の語に見えるとき。** 日本語は語を空白で区切らないので、複合語の継ぎ目に辞書の見出し語と同じ並びが偶然現れ、別の語として指摘されることがあります（「プレビューアプリ」の中の「レビューア」が校閲者と読まれる、など）。よくあるものは `vs lint` があらかじめ打ち消しているので、書くのはこの本だけの造語や複合語です。語を一つずつ足すと追いつかないので、正規表現で継ぎ目の形を書いてください。
:::

#### 除外の手段の使い分け

除外の方法は三つあり、効く範囲が違います。

| やりたいこと | 使うもの | 効く範囲 |
| :--- | :--- | :--- |
| 書名・固有名詞を本全体で除外 | `config/textlint_allowlist.yml` | その語（すべてのルール） |
| 原稿の特定の箇所だけ外す | `<!-- no-lint -->` | その行や範囲（スペルチェックにも効く） |
| ルールを丸ごと切る | `book.yml` の `disabled_rules` | そのルール（すべての原稿） |

まず allowlist に 1 語だけ書いて試し、同じルールを何度も除外していると気づいたら `disabled_rules` へ移す、という順序が扱いやすいでしょう。

## トラブルシューティング

:::{.section-lead}
textlint などのツールが見つからない・動かないときは、`vs doctor --fix` で導入し直してください（導入されるツールは @chapref:ch-doctor にまとめています）。ここでは、ツールを入れ直しても直らない症状を扱います。
:::

### 設定ファイルが見つからない

:::{.output}
```
🔴 textlint 設定ファイルが見つかりません: config/.textlintrc.yml
```
:::

プロジェクトのルートディレクトリで実行しているか確認してください。`vs lint` は必ず `config/.textlintrc.yml` を読みます。誤って消したり移動したりしていないかも確かめてください。

### 正しい語が綴り誤りとして指摘され続ける

正しい技術用語や固有名詞が繰り返し指摘される場合は、その語をユーザー辞書へ登録します。

```bash
vs lint --register
```

登録先は `config/spellcheck_allowlist.yml` です。手で書き足しても構いません。日本語校正で指摘され続ける語は、`config/textlint_allowlist.yml` に書きます。

## まとめ

:::{.section-lead}
校正は、原稿を一度で完成させる作業ではありません。書き進めながら `vs lint` を繰り返し使うと、表記の方針を保ったまま、内容の推敲に集中しやすくなります。
:::

本章では、次の使い方を見てきました。

- **表記の確認**: 表記揺れを検出し、書籍内の用語をそろえる
- **文章の見直し**: 冗長表現・文体の混在・長い文を、推敲の候補として拾う
- **綴りの確認**: 内蔵辞書とユーザー辞書を使い、英単語の誤記を見つける
- **コードブロックの確認**: 言語名の書き忘れを見つけ、推定した言語名を書き込む
- **校正作業の整理**: 集約表示で傾向を掴み、自動修正できる箇所を先に整える
- **書籍に合わせた調整**: `book.yml` の `lint` セクションや除外リストへ、文体の方針を反映する

まず一章だけを指定して実行すると、どのような指摘が出るかを無理なく確かめられます。指摘を採用した理由も、採用しなかった理由も、設定や辞書として少しずつ残していけます。そうして整えた校正の設定は、原稿が長くなるほど役に立ちます。
