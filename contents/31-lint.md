# 文章校正

:::{.chapter-lead}
原稿を重ねていくと、表記の揺れや英単語の綴り間違いは、どうしても紛れ込みます。`vs lint` は、Markdown 原稿に日本語校正（textlint）と英語のスペルチェックをまとめて実行し、目視だけでは見落としやすい箇所を洗い出すコマンドです。本章では、指摘の読み方から自動修正、書籍ごとの調整までを扱います。
:::

## vs lint とは

:::{.section-lead}
`vs lint` は、「日本語校正」と「英語スペルチェック」を一つのコマンドで実行します。ESLint や RuboCop がコードの気になる箇所を示すように、文章を読み返すきっかけを行番号付きで示します。指摘は修正候補であり、文章の正解を決めるものではありません。採用するかどうかは、書籍の文体や文脈に照らして判断できます。
:::

`vs lint` は次の二つを並行して実行します。

- **日本語校正（textlint）**: Node.js 製のオープンソース校正ツール textlint を利用し、日本語技術文書向けのルールで文章をチェックします。
- **英語スペルチェック**: Vivlio Starter 内蔵のスペルチェッカーが、原稿中の英単語の綴り誤りを検出します。50 以上の技術辞書を搭載しています。

あわせて、言語名を書き忘れたコードブロックも見つけます（@pageref:lint-code-language）。

### 主なチェック内容

<!-- no-lint -->
- **表記揺れの検出**: 「ユーザ」と「ユーザー」、「javascript」と「JavaScript」などの不統一を検出
- **文体の統一**: 「です・ます調」と「だ・である調」の混在をチェック
- **冗長表現の検出**: 助詞の重複、接続詞の連続使用、ら抜き言葉などを指摘
- **一文の長さ**: 長すぎる文を指摘（最大文字数は設定可能）
- **日本語と記法の取り違え**: 交ぜ書き・二通りに読める対比・見出しになってしまう `---` などを検出（後述）
- **英単語の綴り誤り**: プログラミング言語・フレームワーク・略語などを誤記から保護
- **コードブロックの言語名**: 言語名のないコードブロックの言語を推定して、書き忘れを知らせる
- **自動修正**: 表記揺れなど一部の指摘は自動的に修正可能

## 基本的な使い方

:::{.section-lead}
引数を付けずに全章を確認するほか、章を指定して、いま書いている部分だけを確かめることもできます。
:::

```bash
# catalog.yml に載っている全章をチェック
vs lint

# 11-intro.md だけをチェック
vs lint 11-intro

# 複数の章・範囲を指定
vs lint 11-intro 12-basics
vs lint 11-13
```

章は、ファイル名・番号・範囲のどれでも指定できます。書き方は @ch-chapter-management の章の @pageref:chapter-targets で説明しています。

確認したい内容が決まっているときは、`--textlint-only`（日本語校正だけ）か `--spellcheck-only`（スペルチェックだけ）で片方に絞れます。`--spellcheck-only` は textlint を使わないので、**textlint をまだ導入していない環境でも動作します**。どちらのオプションでも、コードブロックの言語名の確認は行いません。

## 実行結果の見方

:::{.section-lead}
結果は、同じ種類の指摘を 1 行へまとめた「集約表示」で出力されます。まず件数の多い揺れをまとめて直し、そのあと個別の指摘を読む、といった順序で推敲できます。
:::

### 集約表示

指摘はファイルごと・ルールごとに集約され、出現件数の多い順に並びます。ラベルは `(日本語校正)` と `(スペルチェック)` の二つで、完了サマリーの内訳と同じ区分です。

:::{.output}
```
📄 contents/11-intro.md  (日本語校正)
   12件  [missing-period] 文末に句点「。」がありません
         行: 4, 10, 13, 20, 26, 31, 70, 84, 117, 157, …
    8件  [prh] 以下 => 次
         行: 84, 122, 138, 162, 256, 304, 447, 460

📄 contents/11-intro.md  (スペルチェック)
    3件  bandle => bundle       行: 23, 88, 152
    2件  yestoday => yesterday  行: 47, 90
```
:::

各行の意味は次のとおりです。

- 先頭の件数: そのルール（または語）の指摘が出た回数
- `[missing-period]`: 指摘したルール名（日本語校正）
- `bandle => bundle`: 誤りと修正候補（スペルチェック）。候補が見つからない場合は単語のみを表示
- `行: …`: 出現した行番号（最大 10 件まで。超過分は `…`）

**行番号はクリックできます。**薄い青で表示された番号を押すと、エディタでその行が開きます（表示は後述の `line_links` で変えられます）。違いが空白や字幅だけの指摘には、`（空白を追加）`・`（半角 → 全角）` のような注記が付き、空白は `␣` で見せます。

### 完了サマリー

すべてのチェックが終わると、件数の内訳と次のアクションがまとめて表示されます。

:::{.output}
```
✏️ 文章の品質チェックが完了しました
🟡 1080箇所に改善提案があります
   - 日本語校正: 679箇所
   - スペルチェック: 401箇所
💡 そのうち364箇所は自動修正可能です。
   vs lint --fix
```
:::

課題が見つからなかった場合は、`✅ 文章チェックで課題は見つかりませんでした。` と表示されます。

## 自動修正

:::{.section-lead}
表記揺れなど、文脈に左右されず置き換えられる指摘には、`--fix` オプションを利用できます。修正後の差分を確認するところまでを、一つの作業として考えてください。
:::

```bash
# 自動修正可能な指摘を修正
vs lint --fix

# 特定の章のみ自動修正
vs lint 11-intro --fix
```

:::{.notice}
**`--fix` は元のファイルを直接書き換え、文脈を読みません。** 辞書の綴りに当たれば、例文の中でも書き換えます。実行前に Git などへコミットしておき、`--fix` は章を指定してかけ、直後に `git diff` で変わった行を確かめてください。表記の揺れを説明する文で「`ユーザ` と `ユーザー`」のように**わざと揺れた綴りを見せるときは、インラインコードで囲みます**（コードは検査しません）。
:::

次の箇所は、そもそも検査の対象外です。指摘が出ないため、`--fix` でも書き換えられません。

- **記法**: コード、数式、属性記法（`{width=20%}`）、ふりがな記法（`{親文字|ふりがな}`）の読みと区切り記号、相互参照のラベル（`@ruby-sample`・`@pageref:…`）
- **出力例の囲み**: `:::{.output}`・`:::{.terminal}`・`:::{.showcase}` の中。実物の出力と一字一句合っていなければならないためです
- **除外を指定した所**: 次節の三つの方法で外した箇所・語・ルール

## 指摘を外す

:::{.section-lead}
固有名詞や引用、意図した表記には、指摘を外す方法が三つあります。効く範囲が違うので、外したいものに合わせて選びます。
:::

| やりたいこと | 使うもの | 効く範囲 |
| :--- | :--- | :--- |
| 原稿の特定の箇所だけ外す | `<!-- no-lint -->` | その行や範囲（スペルチェックにも効く） |
| 書名・固有名詞を本全体で外す | `config/textlint_allowlist.yml` | その語（すべてのルール） |
| ルールを丸ごと切る | `book.yml` の `disabled_rules` | そのルール（すべての原稿） |

まず allowlist に 1 語だけ書いて試し、同じルールを何度も外していると気づいたら `disabled_rules` へ移す、という順序が扱いやすいでしょう。`disabled_rules` は @pageref:lint-disabled-rules で説明します。

### 箇所を外す — `no-lint`

外したい行の直前に `<!-- no-lint -->` を置くと、次の 1 行だけが外れます。辞書に載っていない語が続く節など、まとまった範囲は `<!-- no-lint-start -->` と `<!-- no-lint-end -->` で囲みます。

```markdown
<!-- no-lint -->
htmx はサーバーとの通信を HTML 属性で記述できるライブラリです。

<!-- no-lint-start -->
ここは textlint もスペルチェックも両方スキップされます。
<!-- no-lint-end -->
```

**閉じ忘れると、そこから原稿の終わりまで指摘が止まります。**そのため `vs lint` は、閉じ忘れそのものを `[unclosed-suppression]` として指摘します。

コメントは行を独立させてください。文中にインラインコードとして書いた `` `<!-- no-lint -->` ``（この文のような説明）は、マーカーとして扱いません。

### 語を外す — allowlist

特定の語句を、本全体でチェック対象から外すときは `config/textlint_allowlist.yml` に登録します。1 行 1 語で、`#` から後ろはコメントです。**スラッシュで囲むと正規表現**になり、末尾にフラグも書けます。

```yaml
- "Web技術で「本」が作れるCSS組版Vivliostyle入門"  # 書名は直さない
- "基本情報技術者"  # 資格名称
- "既定"            # 「既定 => デフォルト」を止める。この本は和語で通す
- "/マスター/"      # 長音を残す方針。マスターファイル・マスターキーもまとめて外れる
- "/[A-Z]{3,}/"     # 3 文字以上の大文字略語をまとめて外す
```

書名や引用に揺れた表記が含まれていても、それは著者の表記ではないので直しません。ここに登録して、指摘そのものを止めてください。

登録した語は**どのルールからも指摘されなくなります**。「この語はこのルールだけ許したい」という場合は、語ではなくルールのほうを `disabled_rules` で切ってください。

日本語は語を空白で区切らないので、複合語の継ぎ目に辞書の見出し語と同じ並びが現れ、別の語として指摘されることがあります（「プレビューアプリ」の中の「レビューア」など）。よくあるものは `vs lint` があらかじめ打ち消しているので、書くのはこの本だけの造語や複合語です。正規表現で継ぎ目の形を書くと、語を一つずつ足すより漏れがありません。

## Vivlio Starter 独自の規則

:::{.section-lead}
textlint の規則に加えて、日本語の読み違いや Markdown の記法の取り違えを見つける規則があります。どれもビルドは成功するので、紙面を見るまで気づきにくい箇所です。
:::

| 見つけるもの | 規則名 | `--fix` |
| :--- | :--- | :---: |
| 交ぜ書き（`だ円` → `楕円`） | `mazegaki` | ○ |
| 漢字に見える康煕部首（`⽇本` の `⽇`） | `kanji-lookalike` | ○ |
| 索引・用語集の語と空白だけ違う書き方（`Type3 フォント`） | `index-term-spacing` | ○ |
| 英字の語と漢字・カタカナの間の空白（`EPUB用` → `EPUB 用`） | `affix-spacing` | ○ |
| 英字の語とひらがなの間の空白（`IDの` → `ID の`） | `hiragana-spacing` | ○ |
| 二通りに読める対比（比較の「と」に否定が続く文） | `ambiguous-comparison` | — |
| 文末の句点の打ち忘れ | `missing-period` | — |
| 長すぎる一文（既定 100 字） | `sentence-length` | — |
| 長すぎる丸かっこの補足（既定 60 字） | `long-parenthetical` | — |
| 断定を避ける言い回し（`かもしれません`・`思います`） | `ja-no-weak-phrase` | — |
| 数と「つ」の表記（`2 つ` → `二つ`。記号の個数は算用数字） | `kansuji-counter-suffix` | — |
| 和文どうしを空きなしで並べた半角スラッシュ（`前書き/後書き`） | `slash-between-japanese` | — |
| かっこの隣の空白 | `space-around-brackets` | — |
| 4 スペースの字下げ（コードブロックにならない） | `indented-code-block` | — |
| 直前の行に続く `---`（改ページではなく見出しになる） | `setext-heading` | — |
| 1 ファイルに二つ目の章見出し（`#`） | `multiple-chapter-headings` | — |
| 閉じ忘れた `<!-- no-lint-start -->` | `unclosed-suppression` | — |

`--fix` が「—」の規則は、直し方が二通り以上あり、決められるのは著者だけです。たとえば句点の打ち忘れは、句点を足すのか体言止めに直すのかを選びます。規則名は集約表示の `[ ]` に出る名前で、`disabled_rules` に書けば規則ごと切れます。

以下では、著者の判断が要る規則を説明します。

### 交ぜ書き

熟語の一部の漢字だけをかなで書いた表記（`完ぺき`・`しきい値`・`ぜい弱`）を指摘し、`vs lint --fix` で漢字へ直せます。`改ざん` や `せん断` のように、かな書きのほうが主流になっている語も指摘します。漢字とかなのどちらを選ぶかは**著者の方針**です。

`config/textlint_allowlist.yml` にかなで通すと決めた語を書くと、指摘が消え、`--fix` の置換対象からも外れます。表外漢字はすべてかなで書く方針なら、`disabled_rules` に `mazegaki` と書いて規則ごと切るほうが早いでしょう。

**MeCab があると、指摘できる語が増えます。** 語の切れ目を見ないと誤って指摘する語（`う回` は「使う回数」にも現れる）は、MeCab があるときだけ検査します。MeCab がなくても誤った指摘が増えることはありません。導入は @chapref:ch-doctor を参照してください。

### 二通りに読める対比

<!-- no-lint -->
「B は A と同様に X しない」という形は、「A も X しない」とも「A とは違って B は X しない」とも読めます。読者が反対の意味で受け取っても、そのまま誤解が残ります。対比を書きたいときは、両者の性質を独立した文でそれぞれ明示します。

<!-- no-lint-start -->
| | 文 |
| :--- | :--- |
| 直す前 | Ractor はスレッドと同じようにメモリを共有しない。 |
| 直した後 | スレッドはメモリを共有するが、Ractor は共有しない。 |
<!-- no-lint-end -->

指摘されるのは「と同じように」「と同様に」「と同じく」のように**比較の「と」を伴う形**だけです。

### 文末の句点の打ち忘れ

段落が句点で終わっていないと指摘します。体言止め（`**用途**: PDF閲覧、電子配布`）は指摘しません。箇条書き・見出し・表・引用、段落全体が強調一つの行（小見出しとして組まれます）も対象外です。助詞で終わり、文が次のブロックへ続く形（`…という自然な習慣で`）は指摘が残るので、`<!-- no-lint -->` で抑えてください。

## コードブロックの言語名 @lint-code-language

:::{.section-lead}
言語名を書き忘れたコードブロックを見つけて、言語を推定します。言語名がなくてもビルドは成功し、行番号も付くので、色分けされていないことには紙面を見るまで気づけません。
:::

コードブロックは、言語名を書くと色分けされます（@ch-extensions の章の @pageref:syntax-highlight）。`vs lint` は、言語名のないコードブロックの中身から言語を推定し、原稿 1 ファイルごとに知らせます。行番号は、コードブロックの開始行（バッククォートの行）です。

:::{.output}
```
📄 contents/21-web.md  (コードブロックの言語名)
    3件  css と推定                               行: 40, 88, 152
    2件  javascript らしい（言語名の付け忘れ？）  行: 64, 97

💡 コードブロックに言語名を書くと色分けされます（「〜と推定」は vs lint --fix で書き込めます）
🤔 「〜らしい」は確かめきれなかったものです。--fix では書き込まないので、見て言語名を書いてください
```
:::

- **〜と推定**: 確かに推定できたものです。`vs lint --fix` で、コードブロックの開始行（` ``` ` → ` ```css `）へ言語名を書き込めます。
- **〜らしい**: 手がかりはあるものの、確かめきれなかったものです。`--fix` では書き込まないので、見て言語名を書いてください。

推定の候補は、同じ章（なければ本全体）で言語名を書いてあるコードブロックの言語に絞ります。どちらにも当たらないコードブロックは知らせないので、言語名を手で書いてください。

実行結果やディレクトリの木のように、色を付けたくない文字は言語名に `text` と書くと、指摘も出なくなります。`:::{.output}`・`:::{.terminal}`・`:::{.diagram}` の中のコードブロックは確認しません。1 行目が `$ ` か `% ` で始まる端末の記録は `shell-session` と推定します。`shell-session` は `$ ` で始まる行だけをコマンドとして色分けし、出力の行はそのまま残します。

言語の推定には Guesslang（npm パッケージ `@vscode/vscode-languagedetection`）を使い、`vs doctor --fix` で導入できます。導入していないときは推定せず、言語名のないコードブロックの数と導入方法だけを案内します（`shell-session` の推定は Guesslang がなくても行います）。

## 英語スペルチェック

:::{.section-lead}
`vs lint` は日本語校正と同時に、原稿中の英単語の綴り誤りも検出します。プログラミング言語・フレームワーク・略語など幅広い技術用語に対応した辞書を内蔵しています。
:::

原稿の Markdown に書いた英単語が対象です。コードブロック・数式・拡張記法（`:::{.class}`）・相互参照のラベルの中は対象外です。辞書は、一般英単語（SCOWL）、主要言語の技術用語、クラウドやツールの製品名など 50 以上を搭載し、`index_glossary_terms.yml` に登録した英字の語も既知語として扱います。

### 除外リストと --register

辞書に載っていない固有名詞や造語は「綴り誤り」として指摘されます。プロジェクト固有の語は、`--register` でまとめて許可語に加えられます。

```bash
# 未知語を除外リストへ一括登録
vs lint --register
```

`--register` は、スペルチェックで未知だった語をすべて `config/spellcheck_allowlist.yml` へ追記します。登録後、`config/spellcheck_allowlist.yml` を開いて「本当に正しい語」だけを残してください。消した誤記は、次回の `vs lint` で改めて指摘されます。手で書き足しても構いません。

```yaml
- "ajisai"
- "htmx"
- "vivliostyle"
```

- `--register` は**スペルチェック専用の操作**です。`--spellcheck-only` を併記しなくても、日本語校正は実行されません。
- 大文字小文字は区別せず、辞書順・重複なしで自動的に整えられます。ハイフンを含む語は、詰めた形（`vivliostarter`）でも既知語として扱われます。
- このプロジェクト固有のファイルです。別の本でも使いたい場合はコピーしてください。

### book.yml による設定

スペルチェックの動作は `config/book.yml` の `spellcheck` セクションで制御します。

```yaml
spellcheck:
  extra_dictionaries:      # 追加の辞書（初回実行時に取得）
    - ada
    - elixir
  check_code_blocks: false # コードブロック内をチェックするか（既定: false）
```

- **extra_dictionaries**: 標準搭載辞書に含まれない言語・分野の辞書を追加します。初回実行時にインターネットから取得し、`.cache/spellcheck-dictionaries/` にキャッシュされます。
- **check_code_blocks**: `true` にするとコードブロック内の英単語もチェックします。

## book.yml による調整（lint セクション）

:::{.section-lead}
日本語校正の細かな挙動は、`config/book.yml` の `lint` セクションで調整できます。書籍の文体に合わない規則を無効にしたり、許容する表記を指定したりするための設定です。
:::

```yaml
lint:
  # ルールごと丸ごと無効化したい textlint ルール ID（集約表示の [ ] 内の名前）
  disabled_rules:
    - arabic-kanji-numbers

  # 一文の最大文字数（0 で一文の長さを検査しない）。丸かっこの中は数えません
  sentence_length_max: 100

  # かっこ内の補足の最大文字数（0 で補足の長さを検査しない）
  parenthetical_length_max: 60

  # 「サーバ／パラメータ／フィルタ」等の末尾長音を省く文体なら true
  trim_long_vowel: true

  # インラインコードと和文の間のスペースを許容するなら true
  allow_space_around_code: true

  # 全角と半角（英数・記号）の間のスペースを許容するなら true
  allow_space_between_ja_en: true

  # 指摘の「行:」をクリックでエディタに開く（compact / path / off）
  line_links: compact
```

上の値は、どれも書かなかったときの既定値です。`book.yml` に置くのは**文体の選択**だけで、ルールそのものを足したり消したりするときは `config/.textlintrc.yml` を直接編集します。どの設定も検査そのものに効くので、`vs lint --fix` の振る舞いも同じように変わります。

### disabled_rules — ルール単位の無効化 @lint-disabled-rules

集約表示に出るルール ID（`[ ]` 内の名前）を指定すると、そのルール全体を無効にできます。たとえば `arabic-kanji-numbers`（`一つ => 1つ`）と `kansuji-counter-suffix`（`1つ => 一つ`）のように**逆を向いたルール**は、書籍の方針に合わない側を切ると衝突が解消します。既定では、数を漢数字で書く側に合わせて `arabic-kanji-numbers` を無効にしています。

切ったルールは表示に出ず、`vs lint --fix` でも修正が当たらず、問題件数にも数えません。`prh` と書くと、表記揺れの辞書がすべて止まります（辞書の項目を一つずつは切れません）。Vivlio Starter 独自の規則も、同じキーで無効にできます。

### sentence_length_max と parenthetical_length_max（文と補足の長さ）

`sentence_length_max` は一文の長さの上限で、既定は 100 文字です。**数えるのは和文だけ**で、インラインコード・丸かっこの中・欧文は字数に入れません。丸かっこの中の補足は `parenthetical_length_max`（既定 60 文字）で別に見ます。どちらも `0` を指定すると検査しません。

### trim_long_vowel（末尾長音の文体）

`true`（既定）では、「サーバ／パラメータ／フィルタ」のように**末尾の長音を省く技術文体**を選べます。同梱の辞書が出す `サーバ => サーバー` のような、末尾に長音を足すだけの指摘を切ります。著者が `config/textlint_rewrite.yml` に書いた規則（「この本では `ユーザー` と書く」など）は切らないので、この設定と両立します。

### `allow_space_around_code` と `allow_space_between_ja_en`（和欧間スペースの許容）

技術書では、`` `vs import` コマンド `` のようにインラインコードや英数字の前後にスペースを入れる書き方がよく使われます。`allow_space_around_code` はインラインコードと和文の間、`allow_space_between_ja_en` は全角と半角（英数・記号）の間のスペースを許容します（どちらも既定は `true`）。ルールそのものを無効にするので、`vs lint --fix` で意図的に入れたスペースが削除されることはありません。

### line_links（行番号をクリックで開く）

集約表示の行番号の見せ方を選びます。

| 値 | 表示 | 下線 |
|---|---|---|
| `compact` | `行: 223`（薄い青） | 端末によっては付く |
| `path` | `行: contents/11-intro.md:223` | 付かない |
| `off` | `行: 223` | — |

既定は `compact` です。下線が気になるなら `path`、クリックしても何も起きない端末なら `off` を選びます。出力先が端末でないとき（`vs lint > report.txt`）は、どの設定でも素の行番号です。

## 設定ファイルの場所

:::{.section-lead}
日本語校正の詳細なルールは、textlint の設定ファイルで管理します。書籍ごとの表記方針を設定として残しておけば、執筆が長期にわたっても同じ基準で原稿を見直せます。
:::

- `config/.textlintrc.yml`: textlint 本体の設定（フィルタ・ルール）
- `config/textlint_rewrite.yml`: 表記揺れ辞書（この本の表記）
- `config/textlint_allowlist.yml`: 除外リスト（書名・資格名称・この本の方針で通す語など）
- `config/textlint_dictionaries/`: 同梱の `prh` 辞書（固有名詞・技術用語・誤字・外来語の長音など。`vs upgrade` が更新するので編集しない）
- `config/spellcheck_dictionaries/`: 英語スペルチェック辞書
- `config/spellcheck_allowlist.yml`: スペルチェックのユーザー辞書（`--register` の追記先）

`vs lint` は必ず `config/.textlintrc.yml` を読みます。`🔴 textlint 設定ファイルが見つかりません` と出たら、プロジェクトのルートディレクトリで実行しているか、このファイルを消したり移したりしていないかを確かめてください。textlint などのツールが見つからないときは、`vs doctor --fix` で導入し直します（@chapref:ch-doctor）。

### 読点・半角カンマの上限を変える

一文に打てる読点「、」と半角カンマ「,」の上限は `config/.textlintrc.yml` に書いてあります。どちらも既定は 3 個です。

```yaml
rules:
  preset-ja-technical-writing:
    max-ten:
      max: 3    # 一文の読点「、」
    max-comma:
      max: 3    # 一文の半角カンマ「,」
```

読点が多い文は、句点で区切るか、語順を組み替えると読みやすくなることがあります。上限を変える前に、指摘された文を一度読み直してみてください。`max-comma` が数えるのは半角カンマだけなので、和文で当たるのは数字の桁区切り（`2,894`）か欧文の語の並びです。桁区切りの数字が多い本では、`disabled_rules` に `max-comma` と書いて規則全体を無効にするほうが意図に合います。

:::{.notice}
一文の長さ（`sentence-length`）だけは `.textlintrc.yml` ではなく `book.yml` の `lint.sentence_length_max` で変えます。`.textlintrc.yml` に書いても効きません。
:::

### 表記揺れ辞書の追加

`CSS 組版` と `CSS組版`、`ユーザー` と `ユーザ` のように、同じ語が違う表記で混ざることがあります。こうした揺れは `config/textlint_rewrite.yml` に登録すると検出できます。ここに書くのは**この本の表記**だけです。製品名・技術用語・誤字のように、どの本にも当てはまるものは同梱の辞書が受け持ちます。

```yaml
rules:
  - expected: CSS 組版      # そろえたい表記
    patterns:              # そこへ直したい表記
      - 'CSS組版'
      - 'CSS組み版'
  - expected: ユーザー
    patterns:
      - /ユーザ(?!ー)/     # スラッシュで囲むと正規表現
    specs:                 # 当たってほしい例・当たってほしくない例
      - from: ユーザが使う
        to:   ユーザーが使う
      - from: ユーザーが使う
        to:   ユーザーが使う
```

`expected` が正しい表記、`patterns` がそこへ寄せたい表記です。登録すると `vs lint` が指摘し、`vs lint --fix` で一括修正できます。`specs` を添えておくと、`vs lint` が辞書を読むたびに自己検査し、正規表現が期待と食い違えばその場で止まって知らせます。

:::{.tip}
表記の揺れは原稿が長くなるほど増え、後から直すほど影響範囲が広がります。一つ見つけた時点で辞書へ登録しておけば、以降は書いた端から指摘されるので揺れがたまりません。
:::

## まとめ

:::{.section-lead}
校正は、原稿を一度で完成させる作業ではありません。書き進めながら `vs lint` を繰り返し使うと、表記の方針を保ったまま、内容の推敲に集中しやすくなります。
:::

まず一章だけを指定して実行すると、どのような指摘が出るかを無理なく確かめられます。指摘を採用した理由も、採用しなかった理由も、allowlist・`disabled_rules`・表記揺れ辞書として少しずつ残していけます。そうして整えた校正の設定は、原稿が長くなるほど役に立ちます。
